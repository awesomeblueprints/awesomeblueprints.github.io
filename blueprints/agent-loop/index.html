The Agent Loop

Build an agent loop that plans, calls tools and stops: step budgets, termination conditions and error handling for LLM agents in Python.

medium3–5 daysVerified 2026-08-18
Agents
Read it on GitHub ↗ Back to the catalogue

A while loop that sends conversation state to a model, runs whatever tools it asks for, appends the results and repeats until it stops asking. Everything else you will bolt on later exists to buy back the predictability this trades away.

Complexity: medium · Typical build: 3–5 days · Verified: 2026-08-18 (re-check after ~90 days)

Examples in: Python. Only §4 is language-specific — the rules, failure modes and definition of done hold anywhere, and your agent translates the code.

Use when: the number of steps is unknown at design time, the next action depends on what the last one returned, and the task has an end state you can recognise — "find the bug in this repo", "get this ticket to done".

Not for: a sequence of steps that is fixed and known in advance. That is a chain of calls, and it is cheaper, faster and debuggable. Reaching for a loop because it feels more capable is the most common way to make a simple task expensive and non-deterministic.

⚙️ INSTRUCTIONS FOR THE AI — READ BEFORE WRITING ANY CODE

Do not start coding.

Step 1 — Refresh. Search the web and verify: the current message and tool-use shape for the provider being used — the block structure, the field names for a tool call and its result, and whether parallel tool calls are returned in one assistant message; the current model ids and their context limits; whether the provider's SDK now offers a built-in loop helper and what it does not cover. This is the fastest-moving surface in this whole subject. Report what you verified and where your assumptions were wrong.

Step 2 — Read the project, then audit what exists. Find any existing model client, tool registry, retry wrapper or message store — a project that has been calling an LLM at all usually has half of this already, under other names.

Then audit what exists. Walk §11 item by item, marking each already true, partly true or absent with the file that decides it. Report that before proposing anything.

Assume the project is right until it demonstrably is not. Code that satisfies an item stays, whatever its shape — §4 is illustrative, and its idioms translate into this project's language. Replacing something that works needs a one-line reason. Never delete a working path to make room for the version written here. If nothing relevant exists, say so and use §3.

The same applies to language. §4 is illustrative: translate its idioms into this project's language and libraries rather than importing its shape. §11 is what has to become true — not the syntax it happens to be written in.

Step 3 — Write a plan for the gap only, and get it approved. List: every tool the agent will have, the terminal condition, the three budgets, and what is out of scope.

In that plan, include a ## Proposed stack section. Do not ask an open question about frameworks. Propose whether to write the loop directly or adopt a framework — with a one-line reason, the versions verified in Step 1, and what would change the decision. Ask the user to confirm once.

Name what you are adding, leaving alone, and changing. Touch nothing else.

1. What a loop costs you, and what it buys

A fixed sequence of calls An agent loop
Who decides the next step Your code The model
Number of model calls Known Unknown until it ends
Cost per task Predictable A distribution with a long tail
Debugging a bad run Read the code Read the trace
Failure when it goes wrong Wrong answer Wrong answer, or never stopping
What you must add back Nothing Caps, truncation, loop detection, tracing

Control flow moves out of your code and into the model. That is the entire trade, and it is worth making only when the steps genuinely cannot be written down in advance.

The mistake that follows is subtler than choosing wrong: people write the loop, see it work on three examples, and ship it without the governors. A loop with no step cap is not a simpler loop — it is the same loop with an unbounded bill and no way to stop.

3. Project structure

agent/
├── loop.py           # the loop itself. Small, and it should stay small.
├── registry.py       # name -> (schema, handler). One place a tool is declared.
├── dispatch.py       # validate arguments, run, catch, serialise
├── budget.py         # steps, wall clock, cumulative tokens
├── truncate.py       # bound one tool result, with an explicit elision marker
└── tools/            # one file per tool. Each is a plain function.

The rule that keeps this maintainable: a tool is a plain function that knows nothing about the loop. It takes arguments, returns a string, and raises on failure. Tools that reach into conversation state cannot be tested, cannot be reused outside the agent, and cannot be reasoned about when the agent misbehaves.

4. Reference implementation

The loop. Provider details will differ — Step 1 is where you check them — but the shape does not:

def run_agent(task: str, tools: dict[str, Tool], cfg: AgentConfig, system: str) -> str:
    messages = [{"role": "user", "content": task}]
    schemas = [t.schema for t in tools.values()]
    deadline = time.monotonic() + cfg.max_wall_clock_s

    for _ in range(cfg.max_steps):
        # Out of budget: take the tools away and ask for an answer. Cutting the
        # loop dead instead returns nothing, and the work already paid for is lost.
        spent = time.monotonic() > deadline
        reply = client.create(
            system=system + ("\n\nBudget exhausted. Answer now with what you have."
                             if spent else ""),
            tools=[] if spent else schemas,
            messages=messages,
        )
        messages.append({"role": "assistant", "content": reply.content})

        calls = [b for b in reply.content if b.type == "tool_use"]
        if not calls:
            return "".join(b.text for b in reply.content if b.type == "text")

        # Every tool_use needs exactly one tool_result, in the same order, with
        # matching ids. Drop or reorder one and the next request is rejected.
        messages.append({"role": "user", "content": [execute(c, tools, cfg) for c in calls]})

    return "Step budget exhausted without a final answer."

Errors are messages, not exceptions. The model cannot recover from something it never sees:

def execute(block, tools, cfg):
    if block.name not in tools:
        return result(block, f"Unknown tool {block.name!r}. Available: {sorted(tools)}",
                      is_error=True)
    try:
        out = tools[block.name].run(**block.input)
        return result(block, truncate(str(out), cfg.max_tool_output_chars))
    except Exception as e:
        # Actionable text, never a stack trace: the trace tells the model about
        # your file layout and nothing about what to do differently.
        return result(block, f"{type(e).__name__}: {e}", is_error=True)

Truncation says that it happened. A silently cut result is worse than a short one, because the model treats a fragment as the whole:

def truncate(s: str, limit: int) -> str:
    if len(s) <= limit:
        return s
    keep = limit // 2
    return f"{s[:keep]}\n\n...[{len(s) - limit} chars elided]...\n\n{s[-keep:]}"

Loop detection. The most common runaway is not chaos, it is the same call repeating because the result never answered the question:

seen: set[tuple[str, str]] = set()
key = (block.name, json.dumps(block.input, sort_keys=True))
if key in seen:
    return result(block, "This identical call was already made and returned the "
                         "same thing. Try a different approach.", is_error=True)
seen.add(key)

5. Golden-standard rules

Rule Why
Three budgets, always: steps, wall clock, cumulative tokens Each bounds a different runaway; a step cap alone does not stop one expensive step
The system prompt names the terminal condition explicitly "Reply with text and no tool call when you have the answer" — models do not reliably infer this
Exceptions become tool results marked as errors An error the model cannot see is an error it retries blindly
Never return a stack trace to the model It describes your file layout and suggests nothing to do differently
Every tool result is truncated with a visible elision marker A silently cut result is read as the whole result
Every tool_use gets exactly one matching result, in order Reorder or drop one and the provider rejects the next request
Identical repeated calls are detected and reported back The commonest runaway is a call that repeats because its result did not answer the question
Tools return observable state, not "ok" A model that cannot see the effect of its action cannot tell success from silence
The system prefix is byte-stable across turns Rewriting it every turn defeats prompt caching, which is most of the bill
Mutable state goes in a tool result or the last user turn Same reason: the cached prefix must not change
Temperature stays low This is tool selection, not creative writing
Above roughly fifteen tools, split the agent rather than adding another Selection accuracy falls off a cliff, and no prompt wording recovers it
Every run emits a trace: per step, the tool, the arguments, tokens, latency A loop you cannot replay is a loop you cannot fix

6. Data contracts

class ToolResult(BaseModel):
    tool_call_id: str
    content: str          # always a string; serialise structured data yourself
    is_error: bool = False

class Tool(Protocol):
    name: str             # ^[a-z0-9_]{1,64}$
    description: str      # when to use it AND when not to
    input_schema: dict    # JSON Schema, additionalProperties: false
    def run(self, **kwargs) -> str: ...

class AgentConfig(BaseModel):
    max_steps: int = 20
    max_wall_clock_s: float = 300.0
    max_tokens_total: int = 200_000
    max_tool_output_chars: int = 8_000
    parallel_tools: bool = True     # false when tools mutate shared state

7. Build order

  1. The bare loop with two or three tools and a hard step cap. Nothing else.
  2. The dispatcher: argument validation, exceptions turned into error results.
  3. Truncation, with the elision marker visible in a real transcript.
  4. The terminal condition written into the system prompt, and a test that the agent stops on a task it can finish in one step.
  5. The remaining budgets — wall clock, then cumulative tokens.
  6. Tracing: one line per step with tool, arguments, tokens, latency. Do this before adding more tools, or you will be debugging blind.
  7. Loop detection on repeated identical calls.
  8. Parallel tool execution, only once you have confirmed the tools do not share mutable state.
  9. An eval set of at least thirty tasks with known outcomes, run in CI.

9. Metrics

Metric Target
Task success on a fixed eval set ≥ 85%, and never below the last release
Steps per task, p95 ≤ 0.6 × the cap. At the cap means the cap is doing the deciding
Tool error rate < 3%; above 10% the schemas or descriptions are wrong
Runs containing a repeated identical call < 1%
Cost per task, p95 vs p50 p95 < 3 × p50; a fatter tail means runaways
Cached input tokens as a share of input > 70%; below 40% the prefix is not stable
Runs with a complete trace 100%

10. Failure modes

Symptom Cause Fix
Same tool, same arguments, over and over The result never answered the model's question Detect the repeat and say so in the result
The loop never ends No terminal condition in the system prompt State it: text and no tool call means done
Context overflows mid-run Tool results unbounded Truncate every result; compact the history
Invented tool names or arguments Overlapping or vague descriptions Make descriptions mutually exclusive; additionalProperties: false
Right plan, wrong execution Tools return "ok" instead of what changed Return observable state
One request costs twenty times the median A retry storm inside a tool Budget on cumulative tokens, not only steps
A tool is never chosen Its description does not use the words users use Put real user vocabulary in the description
Provider rejects the next request A tool result missing, reordered or mis-ided One result per call, same order, matching ids
Cost doubled after a prompt tweak The system prefix changed every turn Keep the prefix byte-stable; move state into messages
Works in testing, wanders in production Real tasks are longer than test tasks Eval on the p95 task length, not the median

11. Definition of done

  • Step, wall-clock and cumulative-token budgets all exist and are all enforced.
  • Running out of budget produces an answer from what was gathered, not a dropped request.
  • The system prompt states the terminal condition in words.
  • Every tool has a JSON Schema with additionalProperties: false and required fields declared.
  • Every tool description says when not to use it.
  • Exceptions reach the model as actionable text marked as errors; no stack trace ever does.
  • Every tool result is truncated with a visible elision marker.
  • Every tool_use has exactly one matching result, in the same order.
  • A repeated identical call is detected and reported back to the model.
  • Every run emits a trace with per-step tool, arguments, tokens and latency.
  • The system prefix is byte-stable across turns, verified by the cache hit rate.
  • An eval set of at least thirty tasks runs in CI and blocks a regression.
