Streaming LLM Output over SSE

Streaming LLM output over SSE from FastAPI: event framing, backpressure, client disconnects, proxy buffering and cancelling the model call.

medium2–3 daysVerified 2026-08-19
Streaming
Read it on GitHub ↗ Back to the catalogue

A server-sent events endpoint that emits tokens as they are generated, reports failures that happen after the headers are already gone, and stops paying for generation the moment the client walks away.

Complexity: medium · Typical build: 2–3 days · Verified: 2026-08-19 (re-check after ~90 days)

Examples in: Python, with FastAPI. The architecture is language-agnostic: sections 5, 10 and 11 hold wherever you build this. Section 4 is illustrative — if your project is in another language, your agent translates the idioms rather than importing them, and nothing is lost. The equivalents are a ReadableStream response in Node, http.Flusher in Go, and Plug.Conn.chunk/2 in Elixir — and the proxy configuration in §5 is the same wherever the code runs.

Use when: a model call takes long enough that waiting for the whole answer feels broken — a chat reply, a generated document, a long summary — and the user should see it arrive.

Not for: a response the client cannot use until it is complete, such as structured output that has to parse before anything can be done with it. Streaming a JSON object token by token gives the user a progress bar made of syntax and costs you the ability to validate before sending. Also not for two-way traffic: if the client sends messages during generation, that is a WebSocket.

⚙️ INSTRUCTIONS FOR THE AI — READ BEFORE WRITING ANY CODE

Do not start coding.

Step 1 — Refresh. Verify the model SDK's streaming API and, specifically, how it surfaces a cancellation — that is what stops the meter when a client leaves. Verify how the framework detects a disconnected client mid-response. This is the single most valuable thing to check before writing code, because it is invisible in development. Report what you verified and what turned out wrong.

1. Why streaming works locally and batches in production

The endpoint is easy. Everything that makes it fail is somewhere else.

The obvious streaming endpoint This one
Works on localhost, arrives as one lump through the proxy Sends the header that disables buffering, and names the proxy settings it needs
A failure after the first token has no way to be reported Errors are in-band events, because the status code is already spent
A client that closes the tab leaves generation running to completion Disconnect cancels the call, and the meter stops
Token usage is recorded on completion, so cancelled runs are invisible Usage is recorded on every path, including cancellation

The first row is the one everybody hits, and the reason is worth stating exactly: a reverse proxy buffers responses by default. It reads the whole body before forwarding, which is right for ordinary responses and fatal here. Nothing errors — the user simply waits for the full answer and then sees it appear at once, which looks like a slow model rather than a configuration problem. Compression makes it worse, caching makes it worse again, and a default read timeout will cut a long generation off mid-sentence.

Two defences, and you want both: the proxy configured properly, and the X-Accel-Buffering: no response header, which works even where you do not control the proxy's configuration file.

The second row is the structural one. Once the first byte is sent, the status code is spent. A model that fails on token four hundred cannot produce a 500 — the client has had 200 OK for a second already. Every serious failure after that point has to be a message in the stream, and clients have to be built to expect one.

The rule the diagram encodes: there is exactly one point where a real HTTP status can still be returned, and it is before the generator starts. Everything after that arrow is in-band. Validation, authentication, rate limits and quota checks all belong on the left of it — moving any of them inside the generator turns a clean 429 into an error message the client has to parse.

3. Project structure

app/streaming/
├── events.py      the event envelope and the encoder — one place
├── endpoint.py    the route: validate, then hand off to the generator
├── generate.py    the async generator that talks to the model
└── usage.py       recording, called on every exit path

One rule: the generator never raises out of itself. An exception escaping a streaming generator closes the connection with no explanation, and the client sees a truncated answer indistinguishable from a network drop. Catch inside, emit an error event, return.

4. Reference implementation

# app/streaming/events.py
import json
from dataclasses import dataclass


def encode(event: str, data: dict) -> str:
    """One SSE frame.

    The blank line terminates the event and is not optional — without it the
    client buffers indefinitely waiting for the end of a frame that never comes.
    A single newline inside `data` would also split the frame, which is why the
    payload is always JSON rather than raw text.
    """
    return f"event: {event}\ndata: {json.dumps(data, ensure_ascii=False)}\n\n"


COMMENT_KEEPALIVE = ": keepalive\n\n"   # ignored by clients; resets idle timers

# app/streaming/endpoint.py
from fastapi import APIRouter, Request
from fastapi.responses import StreamingResponse

router = APIRouter()


@router.post("/chat/stream")
async def chat_stream(request: Request, payload: ChatRequest, user=Depends(current_user)):
    # Everything that could reject the request happens here, before the response
    # starts. This is the last moment a real status code exists: after the first
    # byte the client already has 200, and a 429 raised inside the generator can
    # only ever arrive as an error message in the body.
    await enforce_rate_limit(user)
    await enforce_quota(user)
    conversation = await load_conversation(payload.conversation_id, user)

    return StreamingResponse(
        generate(request, conversation, payload, user),
        media_type="text/event-stream",
        headers={
            # Belt and braces. proxy_buffering off in the nginx config is the
            # primary fix; this header works even where you do not control that
            # file — a managed gateway, a platform you deploy to, a CDN in front.
            "X-Accel-Buffering": "no",
            "Cache-Control": "no-cache, no-transform",   # no-transform also stops
                                                          # intermediaries compressing
            "Connection": "keep-alive",
        },
    )

# app/streaming/generate.py
import asyncio, time
from app.streaming.events import encode, COMMENT_KEEPALIVE


async def generate(request, conversation, payload, user):
    started = time.monotonic()
    text_so_far: list[str] = []
    finish = "error"
    seq = 0

    try:
        # Metadata first, before any token. The client needs the message id to
        # attach the text to, and it needs it before there is text — otherwise it
        # buffers the first tokens with nowhere to put them.
        yield encode("start", {"message_id": message_id, "model": payload.model})

        async with model.stream(conversation.messages) as stream:
            last_beat = time.monotonic()
            async for delta in stream:
                # The client has gone: a closed tab, a navigation, a lost network.
                # Without this check generation runs to completion and you are
                # billed in full for an answer nobody will ever read.
                if await request.is_disconnected():
                    finish = "cancelled"
                    return              # `finally` still records usage

                seq += 1
                text_so_far.append(delta)
                # The sequence number is what makes a resumed connection possible:
                # a client that dropped can ask for everything after its last seq
                # instead of paying for the answer twice.
                yield encode("delta", {"seq": seq, "text": delta})

                if time.monotonic() - last_beat > 15:
                    # A model that thinks for a long time before its first token
                    # leaves the connection idle, and an idle connection is closed
                    # by proxies on a timer. A comment frame resets that clock.
                    yield COMMENT_KEEPALIVE
                    last_beat = time.monotonic()

        finish = "stop"
        yield encode("done", {"seq": seq, "finish_reason": finish})

    except asyncio.CancelledError:
        finish = "cancelled"
        raise                            # never swallow cancellation
    except Exception as exc:
        # The status line is long gone, so this cannot be a 500. It has to be an
        # event the client is built to expect — and it must not carry the
        # exception text, which routinely contains the prompt and the API key.
        finish = "error"
        log.exception("stream failed")
        yield encode("error", {"code": "generation_failed", "retryable": True})
    finally:
        # Every exit path: success, error, cancellation. Recording only on success
        # makes cancelled generations invisible, and cancelled generations are the
        # ones that surprise you on the invoice.
        await record_usage(user, message_id, text_so_far, finish,
                           seconds=time.monotonic() - started)

# The proxy half. Without these the endpoint above still batches, and nothing
# in the application will tell you.
location /chat/stream {
    proxy_pass http://app;
    proxy_http_version 1.1;         # 1.0 has no chunked transfer encoding
    proxy_buffering off;            # the default reads the whole body first
    proxy_cache off;                # a cached stream is served stale to everyone after
    gzip off;                       # compression re-buffers what you just unbuffered
    proxy_read_timeout 3600s;       # the default cuts long generations off mid-sentence
    chunked_transfer_encoding on;
}

5. Golden-standard rules

Rule Why
Forbidden: deploying without confirming the proxy does not buffer It is the failure of this blueprint. Nothing errors — the stream simply arrives as one lump, and it looks like a slow model.
Forbidden: letting an exception escape the generator The connection closes with no explanation and the client cannot tell a failure from a finished answer.
Forbidden: an error message carrying exception text It routinely contains the prompt, the system message and sometimes the API key. Send a code the client can map.
Forbidden: validation, authentication or limits inside the generator The status code is already spent. Everything that can reject belongs before the first byte.
Forbidden: generating on after the client has gone You are billed for output nobody will read, and it is the cost nobody notices because there is no user to complain.
Usage is recorded on every exit path Recording only on success hides exactly the runs that were abandoned — the ones that surprise you on the invoice.
Every event is JSON with a type and a sequence number Raw text breaks the frame on the first newline, and without a sequence a dropped client must regenerate rather than resume.
Metadata is emitted before the first token The client needs somewhere to put the text before the text arrives.
Idle periods send a keepalive comment A model that thinks before answering leaves the connection silent, and proxies close silent connections on a timer.
Compression is off, and marked off no-transform tells intermediaries not to re-compress what you deliberately left uncompressed.
There is a total time budget for a stream Otherwise a stalled provider holds a connection and a worker slot until something else times out.
The client contract includes the error event A client that only handles deltas and completion treats a failure as a short answer.

6. Data contracts

event: start   data: {"message_id": "01J...", "model": "..."}
event: delta   data: {"seq": 1, "text": "Your "}
event: done    data: {"seq": 412, "finish_reason": "stop"}
event: error   data: {"code": "generation_failed", "retryable": true}

Exactly one terminal event — done or error — and clients rely on it. A stream that simply stops is indistinguishable from a dropped connection, and the client cannot tell whether to retry, resume or show what it has.

seq is what makes a resume cheaper than a retry: a client that reconnects sends its last sequence number and receives what came after, instead of paying for the whole answer again. Without it, every dropped mobile connection is a second invoice.

7. Build order

  1. A stream of fixed text, no model. Curl it and confirm tokens arrive over time. Then deploy it and curl it through the proxy — this is where the real problem lives, and finding it now costs nothing.
  2. The proxy configuration and the header, and repeat the deployed test until it streams.
  3. The model call, with metadata first, deltas, and one terminal event.
  4. Disconnect cancellation, with a test that closes the client mid-stream and asserts the provider call was cancelled.
  5. Errors as in-band events, with a test that forces a mid-stream failure and asserts the client receives a terminal error rather than a truncated stream.
  6. Usage recording on every path, with a test per path.
  7. Keepalives and the total time budget.

Step 1 deploys before there is anything to deploy on purpose. The buffering problem cannot be reproduced locally, and every hour spent building on top of it is an hour spent on something that does not work yet.

10. Failure modes

Symptom Cause Fix
The whole answer appears at once after a long wait, only in production A proxy, gateway or CDN buffers the response by default proxy_buffering off and the X-Accel-Buffering: no header; test through the proxy
Long generations are cut off mid-sentence at a consistent duration The proxy's read timeout is shorter than the generation Raise it for this route; send keepalives during silence
The stream dies while the model is still thinking, before any token The connection was idle past a timeout Keepalive comment frames during the wait
The client shows a truncated answer with no error An exception escaped the generator and closed the connection Catch inside; emit a terminal error event
A user's prompt or an API key appears in the browser The exception text was put into the error event Send a code, never the exception
The bill is larger than the visible traffic explains Generation continues after clients disconnect, and cancelled runs are not recorded Check for disconnect each iteration; record usage on every exit path
A rate-limited user gets a 200 with an error inside it The limit check runs inside the generator Move every rejection before the first byte
The client hangs after the last token The final frame was not terminated by a blank line, or there is no terminal event Always emit done; always end frames with a blank line
Every dropped mobile connection produces a duplicate charge The client can only retry from the beginning Emit sequence numbers and support resume
The stream works in one environment and batches in another Only the nginx config was fixed, and the other environment has a different proxy The response header covers what the config cannot reach
Text arrives with occasional replacement characters The response was compressed and re-chunked by an intermediary no-transform, and compression off for this route

11. Definition of done

  • Tokens arrive incrementally through the production proxy, verified with a client that timestamps each event, not only on localhost
  • The response carries X-Accel-Buffering: no and Cache-Control: no-transform, asserted by a test on the headers
  • Closing the client mid-stream cancels the provider call within one iteration, covered by a test that asserts the call was cancelled
  • Every stream ends with exactly one terminal event, done or error, asserted by a test for each path
  • A mid-stream failure produces a terminal error event, and the response contains no exception text — covered by a test asserting a recognisable secret is absent
  • Rate limit and quota rejections return a real HTTP status before any body is sent, covered by a test
  • Usage is recorded on success, on error and on cancellation, with one test per path
  • A generation that produces no token for longer than the keepalive interval still holds the connection, covered by a test
  • Every event carries a monotonically increasing sequence number, and a client can request everything after a given one
  • A stream exceeding the total time budget is terminated with an error event rather than left open
  • The proxy configuration this endpoint depends on is committed to the repository, not only applied to a server
