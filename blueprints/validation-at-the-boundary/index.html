Input Validation at the API Boundary

Input validation at the API boundary: parsing untrusted data once into types the rest of the code can trust, instead of checking everywhere.

low1–2 daysVerified 2026-08-18
API
Read it on GitHub ↗ Back to the catalogue

Parse, don't validate: one schema at each edge turns unknown input into a typed value, and everything inward can stop asking whether the data is real.

Complexity: low · Typical build: 1–2 days · Verified: 2026-08-18 (re-check after ~90 days)

Examples in: TypeScript, with Zod. Only §4 is language-specific — the rules, failure modes and definition of done hold anywhere, and your agent translates the code. Parse-don't-validate holds in any language; only the library changes — Pydantic in Python, Ecto changesets in Elixir, go-playground/validator or a hand-rolled constructor in Go.

Use when: data arrives from anywhere you do not control — HTTP bodies, query strings, webhooks, queue messages, environment variables, third-party responses, model output — and the rest of the code should be able to trust it.

Not for: validating your own database rows on the way out, or re-checking a value that has already been parsed once — that is duplicated logic that will drift.

⚙️ INSTRUCTIONS FOR THE AI — READ BEFORE WRITING ANY CODE

Do not start coding.

Step 1 — Refresh. Search the web and verify the current major of the validation library and its import path. This one has a live trap: Zod 4 is now the default export from "zod", with "zod/v3" kept for the old major and "zod/v4" as a legacy alias — and because v4 first shipped inside late 3.x releases under a subpath, a minor upgrade can change behaviour. Confirm which major the project resolves to before writing a single schema. Also verify the framework's current way to attach a parsed value to the request.

Step 2 — Read the project. Find where input is checked today: inline if statements, framework decorators, hand-written type guards, casts. Note which layers currently receive untyped objects — those are the ones that will stop needing defensive code.

Then audit what exists. Walk §11 item by item, marking each already true, partly true or absent with the file that decides it. Report that before proposing anything.

Assume the project is right until it demonstrably is not. Code that satisfies an item stays, whatever its shape — §4 is illustrative, and its idioms translate into this project's language. Replacing something that works needs a one-line reason. Never delete a working path to make room for the version written here. If nothing relevant exists, say so and use §3.

Step 3 — Write a plan for the gap only, and get it approved. List: every boundary you are covering, the schema for each, what happens to unknown fields, and the error shape a failure produces.

In that plan, include a ## Proposed stack section. Propose the validation library and where parsed values are attached — with a one-line reason, the major verified in Step 1, and what would change the decision.

Name what you are adding, leaving alone, and changing. Touch nothing else.

Step 4 — Build in the order in §7. Step 5 — §11 is the definition of done.

1. Why checking is weaker than parsing

Validate, then use Parse into a type
What the next function receives The original untyped object A value that cannot be malformed
Forgetting a check Compiles, ships, fails later Does not compile
Where the rules live Wherever somebody remembered One schema per boundary
Unknown extra fields Ride along, unnoticed Stripped or rejected, by policy
Coercion Ad hoc, per call site Declared once, in the schema
Second caller of the same logic Repeats the checks, slightly differently Inherits the guarantee

The distinction is not stylistic. Validating returns a boolean and leaves the data exactly as untrustworthy as it was; the knowledge lives in the programmer's head until it evaporates. Parsing returns a new value whose type encodes what was proven, so the compiler carries the knowledge instead.

The practical consequence: with parsing, a missing check is a type error at the call site. With validation, it is an incident.

The rule this diagram encodes: every arrow crossing into the interior passes through a schema, and no arrow inside it does. Third-party responses and queue messages are boundaries too — that is the pair people forget.

3. Project structure

src/
├── schemas/
│   ├── http/             # one file per route group; request and response
│   ├── messages/         # queue and event payloads
│   ├── vendors/          # third-party responses — yes, these too
│   └── env.ts            # parsed once at boot, exported as a frozen object
├── domain/               # takes typed values. No guards, no casts, no `any`.
└── routes/               # parse, then hand the result to the domain

The rule that keeps this maintainable: a schema is defined once and the type is derived from it, never written alongside it. Hand-written types drift from the runtime rules within weeks, and the compiler will not notice, because both are individually valid.

4. Reference implementation

The schema is the type. One declaration, both guarantees:

import * as z from 'zod';   // v4 — see Step 1 before trusting this import

export const CreateOrder = z.object({
  productId: z.string().uuid(),
  quantity:  z.number().int().positive().max(100),
  note:      z.string().max(500).optional(),
  // Amounts are integer minor units at the boundary, so no float ever
  // reaches the domain and gets rounded on the way through.
  tipMinor:  z.number().int().nonnegative().default(0),
}).strict();               // unknown keys are an error, not silent baggage

export type CreateOrder = z.infer<typeof CreateOrder>;   // derived, never written

.strict() is a decision worth making deliberately. Stripping unknown keys is forgiving and hides client bugs; rejecting them catches a misspelled field on the first request instead of the first support ticket. Reject on your own API; strip on third-party responses, which add fields without warning.

Parse once, at the edge. The handler is the last place that sees unknown:

export async function POST(req: Request) {
  const parsed = CreateOrder.safeParse(await req.json());
  if (!parsed.success) {
    // Field-level detail, so a form can highlight the input that failed.
    return jsonResponse(422, {
      error: 'validation_failed',
      fields: parsed.error.issues.map(i => ({
        path: i.path.join('.'), code: i.code, message: i.message,
      })),
    });
  }
  return createOrder(parsed.data);        // typed from here inward
}

Configuration is input too. Parse it at boot and fail loudly:

const Env = z.object({
  DATABASE_URL: z.string().url(),
  PORT: z.coerce.number().int().default(3000),   // env values are always strings
  LOG_LEVEL: z.enum(['debug', 'info', 'warn', 'error']).default('info'),
});

// Throwing here kills the process at startup. A missing variable discovered at
// boot is a failed deploy; discovered at 3am it is an outage.
export const settings = Object.freeze(Env.parse(process.env));

5. Golden-standard rules

Rule Why
The static type is derived from the schema, never written beside it Two hand-kept definitions drift, and neither side reports it
Every boundary parses: HTTP, queue, webhook, vendor response, environment The ones people skip are queue payloads and vendor responses
Nothing past the boundary receives unknown or any One cast reintroduces every problem this prevents
Environment is parsed at startup and the process dies on failure A missing variable must fail the deploy, not the first request that needs it
Your own API rejects unknown fields; vendor responses strip them Catch client typos; survive a vendor adding a field
Coercion is declared in the schema, not done at the call site Otherwise "3" becomes 3 in one place and stays a string in another
Every string has a maximum length An unbounded string is a memory and storage problem waiting for a bored user
Failures return field-level detail A single sentence cannot tell a form which input to highlight
Parsed values are immutable after the boundary Mutating one silently invalidates what was proven about it
Money is integer minor units at the boundary A float that gets this far will be rounded somewhere you cannot see
The same schema is reused by tests to build fixtures A fixture that cannot pass its own schema is testing a shape that cannot exist
Never parse the same input twice at different depths The second parse is the one that will be forgotten when the rules change

6. Data contracts

/** Uniform failure shape, so every boundary reports the same way. */
export type ParseFailure = {
  code: 'validation_failed';
  fields: Array<{ path: string; code: string; message: string }>;
};

/** Boundaries return a result rather than throwing: a malformed request is an
 *  expected outcome, not an exceptional one. */
export type Parsed<T> = { ok: true; value: T } | { ok: false; error: ParseFailure };

7. Build order

  1. Environment schema, parsed at boot. Smallest boundary, immediate payoff.
  2. One route, parsed end to end, with the failure shape settled.
  3. The failure mapper, shared by every boundary from here on.
  4. The remaining HTTP routes, one at a time.
  5. Queue and webhook payloads — the boundary that gets skipped.
  6. Third-party responses, stripping unknown keys rather than rejecting.
  7. Delete the defensive code the interior no longer needs: guards, casts, null checks that can no longer fire. This step is the actual reward.
  8. A lint rule banning any and non-null assertions in the domain layer.

10. Failure modes

Symptom Cause Fix
Type says one thing, runtime another Type hand-written next to the schema Derive it with infer
A field silently stopped arriving Client renamed it; schema strips unknowns .strict() on your own API
Crash at 3am on a missing env var Configuration read lazily where it is used Parse the whole environment at boot
"5" compared against 5 Coercion done at some call sites only Declare coercion in the schema
Poison message loops forever Queue payload never parsed Parse it; route failures to the dead letter queue
Vendor deploy broke your service Their response parsed strictly Strip unknown keys on inbound third-party data
500 on a malformed body Parse throwing instead of returning a result safeParse, mapped to 422
Behaviour changed after a minor dependency bump Zod's major moved under you Pin the major; verify the import path
Form cannot highlight the bad field Failure returned as one sentence Field-level details in the failure shape

11. Definition of done

  • Every boundary — HTTP, queue, webhook, vendor response, environment — parses through a schema.
  • No static type duplicates a schema by hand; all are derived.
  • The domain layer contains no any, no casts and no non-null assertions, enforced by lint.
  • Configuration is parsed at startup and the process exits on failure.
  • Your own API rejects unknown fields; third-party responses strip them.
  • Every string field has a maximum length.
  • A malformed request returns 4xx with field-level details, never 5xx.
  • Tests build fixtures from the same schemas the runtime uses.
  • The defensive checks the interior no longer needs have been deleted.
