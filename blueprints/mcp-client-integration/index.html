MCP Client Integration

MCP client integration: connecting an agent to Model Context Protocol servers, with tool discovery, result budgets, timeouts and failure isolation.

medium3–5 daysVerified 2026-08-19
MCPAgents
Read it on GitHub ↗ Back to the catalogue

Connecting external MCP servers as a source of tools for your agent: a connection lifecycle that survives a server going away, a tool list you control rather than inherit, and a hard limit on what a third party can put into your context.

Complexity: medium-high · Typical build: 3–5 days · Verified: 2026-08-19 (re-check after ~90 days)

Examples in: Python. The architecture is language-agnostic: sections 5, 10 and 11 hold wherever you build this. Section 4 is illustrative — if your project is in another language, your agent translates the idioms rather than importing them, and nothing is lost. The protocol details below are from the specification revision named on the Verified line; the isolation and budget concerns hold regardless of which revision you target.

Use when: an agent should use tools that somebody else maintains — a hosted service, a colleague's server, a vendor's integration — instead of you writing and keeping a wrapper for each.

Not for: tools you own and deploy alongside the agent. Routing your own function through a protocol and a transport adds a process boundary, a failure mode and a serialisation step to a function call. Also not a substitute for deciding which tools an agent should have: connecting a server with forty tools does not give your agent forty useful tools, it gives it a much harder choice.

⚙️ INSTRUCTIONS FOR THE AI — READ BEFORE WRITING ANY CODE

Do not start coding.

Step 1 — Refresh. Verify the protocol revision each server you intend to connect actually implements, because the transport changed substantially in the current one and older servers are still common. In the current revision there are no protocol-level sessions, there is no initialize handshake — every request carries its protocol version and client capabilities in _meta — there is no GET stream endpoint, and SSE streams are not resumable: a broken stream loses the in-flight request and it must be re-issued with a new id. Confirm whether the SDK you are using implements the revision you need. Verify the required request headers and that their values must match the request body. Report what you verified and what turned out wrong.

Step 2 — Read the project, then audit what already exists. Find the agent's existing tool surface, because everything connected here joins it and the model's choice gets harder with each addition. Find whether there is a per-turn context budget today, since an external tool result is the least controlled thing that will ever enter it. List the servers to connect and, for each, who operates it and what it can reach — a server that can write somewhere is a different risk from one that only reads. Find how secrets for those servers would be supplied. Then audit §11 item by item, each marked already true, partly true or absent, with the file that decides it, reported before anything is proposed.

Assume the project is right until it demonstrably is not; code satisfying an item stays even where its shape differs from §4; replacing something that works needs a one-line reason; never delete a working path to make room for the blueprint's version. The same holds for language — §4 is illustrative, its idioms get translated into the project's language, and §11 is what has to become true rather than the syntax.

Step 3 — Write a plan for the gap only, and get it approved, including a ## Proposed stack section, the allow-list of tools per server, and what the agent does when a server is unreachable. Do not ask open framework questions — propose, and ask for confirmation once. Say what you are adding, what you are leaving alone, and what you propose to change, and touch nothing else.

Step 4 — Build in the order in §7. Step 5 — §11 is the definition of done.

1. What you are actually connecting

An MCP server is code you did not write, whose tool descriptions go into your prompt and whose results go into your context. The protocol makes it easy to connect. The work is in the boundary.

Connecting a server and using its tools Treating it as an untrusted dependency
Every tool the server offers is exposed to the model An allow-list, so a server adding tools does not silently expand what your agent can do
A tool result goes into the context whole Results are capped, and the cap is enforced by you, not requested of them
A server that hangs hangs the turn Every call is bounded, and an unreachable server degrades to a missing tool
Tool descriptions are trusted text They are third-party text arriving in your prompt, and they are treated as such

The first row is the one that changes over time rather than on day one. You connect a server with four tools, review them, and ship. Three months later it has eleven, and your agent has been using them since the day they appeared — including whichever one deletes things. An allow-list turns that into a deliberate change instead of an automatic one.

The fourth row is the uncomfortable one. Tool names and descriptions are written by the server operator and placed directly into your model's prompt. A description saying "always call this before answering any question" is instruction text in your context that you did not write. This is not hypothetical for servers you do not control, and there is no clever parsing that fixes it — the mitigations are that you chose the server, you chose which tools, and the tool cannot do more than its own permissions allow.

One protocol detail shapes the code more than any other: the current revision has no sessions and no handshake. Every request stands alone and carries its own protocol version and client capabilities. That makes reconnection cheap — there is no state to re-establish — and it means a connection is not a thing you hold so much as a place you send requests.

3. Project structure

app/mcp/
├── servers.py     which servers, and which of their tools are allowed
├── connect.py     the connection: headers, deadlines, reconnection
├── translate.py   MCP tool definitions to your agent's tool format
├── dispatch.py    calling a tool, with the deadline and the result budget
└── health.py      which servers are currently usable

One rule: the allow-list is code, not configuration discovered at runtime. A list fetched from the server, or defaulting to "everything advertised", is not a list — it is the server deciding. Changing what your agent can do should be a commit someone reviews.

4. Reference implementation

# app/mcp/servers.py
from dataclasses import dataclass, field


@dataclass(frozen=True)
class ServerConfig:
    name: str
    url: str
    # Named, never a pattern and never empty-means-all. A server that adds a tool
    # next month must not gain that capability in your agent silently — and a
    # server that renames one should fail loudly rather than quietly lose it.
    allowed_tools: frozenset[str]
    timeout: float = 20.0
    max_result_chars: int = 8000
    required: bool = False        # if False, the agent runs without it


SERVERS = [
    ServerConfig(name="docs", url="https://docs.example.com/mcp",
                 allowed_tools=frozenset({"search_docs", "get_page"})),
    ServerConfig(name="tickets", url="https://tickets.example.com/mcp",
                 allowed_tools=frozenset({"search_tickets"}),   # deliberately not create_ticket
                 timeout=10.0),
]

# app/mcp/connect.py
import uuid

PROTOCOL_VERSION = "2026-07-28"


def _headers(method: str, name: str | None) -> dict[str, str]:
    # The current revision mirrors body fields into headers so that proxies and
    # gateways can route without parsing JSON. The server MUST reject a request
    # whose headers disagree with its body, so these are derived from the body
    # rather than written twice.
    headers = {
        "Content-Type": "application/json",
        # Both are required on every POST: the server may answer with a single
        # JSON object or with an SSE stream, and it chooses per request.
        "Accept": "application/json, text/event-stream",
        "MCP-Protocol-Version": PROTOCOL_VERSION,
        "Mcp-Method": method,
    }
    if name is not None:
        headers["Mcp-Name"] = _header_safe(name)
    return headers


async def request(server: ServerConfig, method: str, params: dict,
                 name: str | None = None) -> dict:
    body = {
        "jsonrpc": "2.0", "id": uuid.uuid4().hex, "method": method,
        "params": {**params, "_meta": {
            # There is no handshake in this revision: every request carries its
            # own protocol version and capabilities. That is why reconnection is
            # cheap — there is no session state to rebuild.
            "io.modelcontextprotocol/protocolVersion": PROTOCOL_VERSION,
            "io.modelcontextprotocol/clientInfo": {"name": CLIENT_NAME,
                                                   "version": CLIENT_VERSION},
            "io.modelcontextprotocol/clientCapabilities": {},
        }},
    }
    async with asyncio.timeout(server.timeout):
        response = await http.post(server.url, headers=_headers(method, name), json=body)

    if response.status_code == 400:
        # A modern server uses 400 for version mismatch, missing capability and
        # header/body disagreement. Read the JSON-RPC error before concluding the
        # server is old — the difference decides whether to correct the request or
        # to fall back to an older protocol.
        raise ProtocolError(response.json().get("error", {}))
    return response.json()

# app/mcp/translate.py
async def load_tools(server: ServerConfig) -> list[Tool]:
    listed = await request(server, "tools/list", {})
    tools = []

    for spec in listed["result"]["tools"]:
        if spec["name"] not in server.allowed_tools:
            # Logged, not silently dropped. A server growing new tools is
            # information: it may be a feature you want, and it may be a change
            # in what that server can do to you.
            log.info("mcp tool not allowed", extra={"server": server.name,
                                                    "tool": spec["name"]})
            continue

        tools.append(Tool(
            # Namespaced. Two servers will eventually both offer `search`, and
            # without a prefix one silently shadows the other in your registry.
            name=f"{server.name}__{spec['name']}",
            # The description is third-party text going straight into your
            # prompt. Delimit it so the model can tell where your instructions
            # end and a vendor's begin, and cap it so a long one cannot crowd
            # out your system prompt.
            description=fence(spec["description"][:DESCRIPTION_LIMIT]),
            schema=spec["inputSchema"],
        ))

    # The list result carries a freshness hint and a cache scope. Honour it:
    # calling tools/list on every turn is a network round trip per turn for a
    # list that rarely changes.
    return tools, listed["result"].get("ttlMs", DEFAULT_TTL_MS)

# app/mcp/dispatch.py
async def call(server: ServerConfig, tool: str, arguments: dict) -> ToolResult:
    if not health.is_up(server.name):
        # A server that is down becomes a missing tool, not a failed turn. The
        # agent is told, and can answer without it or say what it cannot do.
        return ToolResult(is_error=True,
                          content=f"{server.name} is unavailable right now.")
    try:
        result = await request(server, "tools/call",
                               {"name": tool, "arguments": arguments}, name=tool)
    except (TimeoutError, ProtocolError, ConnectionError) as exc:
        health.record_failure(server.name)
        # Never the raw error: it can contain the URL, and the URL can contain a
        # token. The model gets something it can act on instead.
        return ToolResult(is_error=True,
                          content=f"{tool} failed on {server.name}. Try another approach.")

    text = render(result)
    if len(text) > server.max_result_chars:
        # The cap you enforce, not the one they promise. This is the only control
        # you have over how much of your context a third party consumes, and an
        # unbounded result is a context-window failure with a delay on it.
        text = text[:server.max_result_chars] + "\n\n[truncated by the client]"
    health.record_success(server.name)
    return ToolResult(content=text)

5. Golden-standard rules

Rule Why
Forbidden: exposing every tool a server advertises The set changes without you. An allow-list makes new capability a reviewed commit instead of an automatic one.
Forbidden: an unbounded external result It is the least controlled thing entering your context, and a large one truncates the conversation from the front later.
Forbidden: an unbounded call to an external server One unreachable third party otherwise hangs the whole turn.
Forbidden: returning a transport error verbatim to the model It can contain the server URL, and the URL can contain a credential.
Forbidden: treating a tool description as your own text It is written by the server operator and lands in your prompt. Delimit it, cap it, and choose the servers deliberately.
Tool names are namespaced by server Two servers will both offer search, and without a prefix one shadows the other with no warning.
A server being down degrades to a missing tool The agent should be able to answer without it, or say what it cannot do.
Tool lists are cached, honouring the freshness hint Otherwise it is a round trip per turn for a list that changes monthly.
Header values are derived from the body, never written twice The server rejects a mismatch, and two sources of the same value drift.
A blank connection is assumed to be cheap, because it is There is no handshake and no session in the current revision, so reconnection is a new request rather than a re-established state.
Streams are not resumable — a broken one is re-issued as a new request Resumability was removed; a client that waits to resume waits forever.
Every server's operator and reach are written down "Which third parties can this agent's tools touch" is a question you will be asked, and it should not require reading code.

6. Data contracts

POST /mcp
Accept: application/json, text/event-stream
MCP-Protocol-Version: 2026-07-28
Mcp-Method: tools/call
Mcp-Name: search_docs

Headers mirror the body, and the server must reject any disagreement — so they are computed from the body rather than written alongside it. The reason is worth understanding: a load balancer may route on the header while the server executes on the body, and if those differ, the routing decision and the work happen on different values.

Two protocol properties shape everything above them:

no sessions      every request stands alone and carries its own version and
                 capabilities; reconnection has no state to rebuild
no resumption    a broken stream loses its request; re-issue with a new id

7. Build order

  1. One server, one tool, one call. Confirm the protocol revision it actually speaks before writing anything around it.
  2. The allow-list, before a second tool is exposed — it is trivial now and a retrofit once the agent depends on tools nobody chose.
  3. Deadlines and the result budget, with a test using a deliberately slow server and one returning far too much.
  4. Namespacing and translation, with a test that two servers offering the same tool name both remain reachable.
  5. Health tracking and degradation, with a test that an unreachable server leaves the agent able to answer.
  6. Tool-list caching, honouring the freshness hint.
  7. A second real server, which is where the assumptions from the first one show up.

Step 2 that early because the allow-list is the only control here that gets harder to add as the agent becomes useful. Everything else can be tightened later.

10. Failure modes

Symptom Cause Fix
The agent used a tool nobody knew it had The server added tools and everything advertised is exposed An allow-list in code
The agent forgets its instructions after using an external tool An unbounded result filled the context and the history was truncated Cap results client-side
A turn hangs and then times out at the outer layer The call to an external server had no deadline of its own Bound every call; degrade to a missing tool
A server URL with a token in it appears in the conversation A transport error was returned to the model verbatim Log the error; return a fixed message
Two servers' tools conflict and one stops being called Both advertise the same tool name and the registry has one key Namespace by server
The model starts behaving oddly after connecting a server A tool description contains instruction-like text now sitting in your prompt Delimit and cap descriptions; reconsider the server
Every turn is slower after connecting servers tools/list runs per turn Cache the list and honour its freshness hint
A request is rejected with a header-mismatch error Headers were written separately from the body and drifted Derive headers from the body
A client waits forever after a dropped stream It expected to resume; resumability was removed from the transport Re-issue as a new request
A server rejects everything with 400 The protocol version is not one it supports, or a required header is missing Read the JSON-RPC error body; it names the supported versions
An old server does not respond as expected to a modern request It predates the current revision, which removed sessions and the handshake Detect the era from the error body and fall back deliberately

11. Definition of done

  • Every exposed tool appears in an allow-list in code, and a test asserts a server advertising an unlisted tool does not expose it
  • Every external call has a deadline; a test with a slow server asserts a recoverable error rather than a hang
  • Every external result is capped client-side, with a test using an oversized result
  • No transport error text reaches the model, covered by a test that fails a call with a credential in the URL and asserts its absence
  • Tool names are namespaced by server, and a test connects two servers offering the same tool name and reaches both
  • An unreachable server leaves the agent able to complete a turn, covered by a test
  • Tool lists are cached and the server's freshness hint is honoured, verified by counting requests across turns
  • Request headers are derived from the request body, and a test asserts they match
  • Tool descriptions are delimited and length-capped before entering the prompt, covered by a test
  • The protocol revision each server speaks is recorded, and an unsupported one fails at start-up rather than at first use
  • For each server, its operator and what it can reach are written in the repository beside its configuration
