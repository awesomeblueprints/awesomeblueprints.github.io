One Error Envelope for an HTTP API

One error envelope for an HTTP API: stable error codes, machine-readable payloads and handlers that clients and agents can branch on.

low1–2 daysVerified 2026-08-18

One error shape for a whole API: machine-readable, safe to show a stranger, and honest about whether retrying will help. Written so that a client can branch on failures without reading prose.

Complexity: low · Typical build: 1–2 days · Verified: 2026-08-18 (re-check after ~90 days)

Examples in: TypeScript. Only §4 is language-specific — the rules, failure modes and definition of done hold anywhere, and your agent translates the code.

Use when: anything with clients — a web app, a mobile app, another service, or an AI agent — needs to react differently to different failures, and you want one shape rather than one per route.

Not for: a script or a single-consumer internal tool where a stack trace in the log is the whole requirement.

⚙️ INSTRUCTIONS FOR THE AI — READ BEFORE WRITING ANY CODE

Do not start coding.

Report what you verified.

Step 2 — Read the project. Find every place that currently returns an error: route handlers, middleware, the framework's default handler, and anything that catches and rethrows. Count the distinct shapes already in use — that number is the size of the problem.

Then audit what exists. Walk §11 item by item, marking each already true, partly true or absent with the file that decides it. Report that before proposing anything.

Assume the project is right until it demonstrably is not. Code that satisfies an item stays, whatever its shape — §4 is illustrative, and its idioms translate into this project's language. Replacing something that works needs a one-line reason. Never delete a working path to make room for the version written here. If nothing relevant exists, say so and use §3.

Step 3 — Write a plan for the gap only, and get it approved. List: the envelope fields, the initial error-code vocabulary, the mapping from internal exception types to codes and statuses, and what is deliberately out of scope.

In that plan, include a ## Proposed stack section. Propose whether to adopt RFC 9457 verbatim or a project-local shape — with a one-line reason and what would change the decision. Ask the user to confirm once.

Name what you are adding, leaving alone, and changing. Touch nothing else.

Step 4 — Build in the order in §7. Step 5 — §11 is the definition of done.

1. Why a message string is not an error

Ad-hoc errors An envelope
What the client branches on Substring matching on English prose A stable code
Effect of rewording a message Client breaks, silently Nothing
"Should I retry?" Guesswork from the status code An explicit field
Localisation Impossible — the server picked the language Client maps code to its own text
Support ticket "It said something went wrong" A trace id that finds the request
Leaking internals Stack traces reach users Never crosses the boundary

The failure this prevents is quiet. A client somewhere does if (msg.includes("not found")), someone improves the wording six months later, and the branch stops firing. Nothing throws. The behaviour just changes.

3. Project structure

src/
├── errors/
│   ├── envelope.ts       # the response type. One definition, exported.
│   ├── codes.ts          # the closed vocabulary of error codes
│   ├── domain.ts         # typed domain errors: NotFound, Conflict, RateLimited…
│   └── handler.ts        # the single exception handler, mounted once
├── domain/               # throws domain errors. Knows nothing about HTTP.
└── routes/               # throws or lets through. Never formats an error.

The rule that keeps this maintainable: exactly one place constructs the envelope. A second one appears the first time somebody is in a hurry, and from then on the shape has two versions and the client has to handle both.

4. Reference implementation

The envelope. Small on purpose — every field earns its place:

export type ErrorEnvelope = {
  error: ErrorCode;      // stable, machine-readable, from a closed set
  message: string;       // human-readable, safe to display, never parsed
  retryable: boolean;    // explicit: does trying again have any chance
  traceId: string;       // the one string support asks for
  details?: unknown;     // structured, per-code; field errors live here
};

retryable is a field rather than an inference from the status code because the status alone cannot say it. A 429 is retryable; a 400 is not; a 500 usually is but not when it is a permanent downstream misconfiguration. Only the code that raised it knows.

Domain errors carry their mapping. The domain layer never imports HTTP:

export abstract class DomainError extends Error {
  abstract readonly code: ErrorCode;
  abstract readonly status: number;
  readonly retryable: boolean = false;
  readonly details?: unknown;
}

export class NotFound extends DomainError {
  readonly code = 'not_found'; readonly status = 404;
  constructor(resource: string) { super(`${resource} not found`); }
}

export class RateLimited extends DomainError {
  readonly code = 'rate_limited'; readonly status = 429;
  readonly retryable = true;
  constructor(readonly retryAfterSeconds: number) { super('Rate limit exceeded'); }
}

One handler, two audiences. The only place an envelope is built:

export function toEnvelope(err: unknown, traceId: string) {
  if (err instanceof DomainError) {
    logger.warn({ traceId, code: err.code, err });        // expected: warn
    return { status: err.status, body: {
      error: err.code, message: err.message,
      retryable: err.retryable, traceId, details: err.details } };
  }

  // Unknown means a bug. Log everything; tell the client nothing.
  logger.error({ traceId, err });
  return { status: 500, body: {
    error: 'internal_error',
    message: 'Something went wrong on our side.',   // deliberately uninformative
    retryable: true, traceId } };
}

The generic message is not laziness. An unmapped exception's text can contain a connection string, a file path or a row from another tenant — and nobody auditing that message knows what it will say next month.

5. Golden-standard rules

Rule Why
One module builds every envelope Two builders means two shapes and a client that handles both
Error codes come from a closed set, checked at compile time A typo becomes a code nobody handles, and it ships
message is for humans and is never parsed by a client Rewording must never break a caller
retryable is set explicitly at the raise site The status code cannot express it, and the handler cannot infer it
Unmapped exceptions become one generic 500 Their text is unaudited and may contain anything
Every response carries a trace id, success or failure Without it a support ticket is unanswerable
The domain layer imports nothing HTTP It has to work from a job, a CLI and a test
Validation failures return field-level details, not a sentence A form needs to know which input to highlight
Auth failures are deliberately vague to the client, detailed in the log "No such user" is an account-enumeration oracle
4xx is logged at warn, 5xx at error Expected failures must not drown the real ones
Never 200 with { ok: false } Proxies, caches, retries and clients all read the status
Adding a code is a versioned change Clients switch on it; new codes must be additive

6. Data contracts

/** Closed vocabulary. Adding is additive; renaming is a breaking change. */
export const ERROR_CODES = [
  'validation_failed', 'not_found', 'conflict', 'unauthenticated',
  'forbidden', 'rate_limited', 'upstream_unavailable', 'internal_error',
] as const;
export type ErrorCode = typeof ERROR_CODES[number];

/** details for validation_failed — enough to point at the offending input. */
export type FieldError = { path: string; code: string; message: string };

7. Build order

  1. envelope.ts and codes.ts. Types only, no behaviour.
  2. The exception handler, mounted once, mapping unknown errors to 500.
  3. One domain error — NotFound — through a real route, end to end.
  4. Trace id threaded into every response, success included.
  5. The remaining domain errors, one at a time, each with a test asserting code, status and retryable.
  6. Validation details, shaped as field errors.
  7. Sweep the codebase for hand-built error responses and delete them.
  8. A test that asserts no 5xx body contains a stack trace or a file path.

10. Failure modes

Symptom Cause Fix
A client broke after a copy change It matched on message Codes are the contract; message is display only
Users see a connection string An unmapped exception was rendered Generic body for anything not a domain error
Everything is a 500 Domain errors thrown as plain Error Give each a class with code, status, retryable
Support cannot find the request No trace id in the response Return it on every response
Retry storms after a bad deploy Non-retryable failures marked retryable Set it at the raise site, deliberately
Log volume exploded Expected 4xx logged at error 4xx warn, 5xx error
Client shows "undefined" Two shapes in flight; one lacks message One builder, one shape
Account enumeration reported Auth error distinguished unknown user from wrong password One vague code for both; keep the detail in the log

11. Definition of done

  • Exactly one module constructs error responses; no route builds its own.
  • Every error response validates against the envelope type.
  • Error codes are a closed union, checked at compile time.
  • retryable is set at the raise site, never inferred by the handler.
  • Every response, success or failure, carries a trace id.
  • An unmapped exception yields a generic 500 — verified by a test that throws a raw Error.
  • No 5xx body contains a stack trace, a file path or an internal identifier.
  • Validation failures return field-level details a form can act on.
  • Authentication failures do not reveal whether the account exists.
  • The domain layer imports nothing from the HTTP framework.
