Redis Cache Layer

A Redis cache layer: key design, TTLs, stampede protection, invalidation on write, and knowing what should happen when Redis is down.

medium2–3 daysVerified 2026-08-19
Redis
Read it on GitHub ↗ Back to the catalogue

Caching that names its keys, expires everything, invalidates on write, survives the moment a thousand requests miss the same key at once — and degrades to a slower application rather than a broken one when Redis is gone.

Complexity: medium · Typical build: 2–3 days · Verified: 2026-08-19 (re-check after ~90 days)

Examples in: Python, with Redis and FastAPI. The architecture is language-agnostic: sections 5, 10 and 11 hold wherever you build this. Section 4 is illustrative — if your project is in another language, your agent translates the idioms rather than importing them, and nothing is lost. The key schema, invalidation and stampede concerns are identical with Memcached, and the degradation rule matters more, not less, with an in-process cache.

Use when: a read is expensive and repeated — an aggregate over many rows, a third-party response, a permission set computed per request — and the answer is allowed to be slightly old.

Not for: hiding a query that is slow because it is wrong. Caching an unindexed scan makes the first request slow and every later one fast, right up to the invalidation, and then the same scan runs under whatever load arrived meanwhile. Fix the query first; cache what is still expensive. Also not for data that must be exact on read — a balance, a stock level at checkout, a permission that has just been revoked.

⚙️ INSTRUCTIONS FOR THE AI — READ BEFORE WRITING ANY CODE

Step 1 — Refresh. Verify the Redis client and whether its operations accept a timeout — a cache that blocks on a slow Redis is slower than no cache, and this is the single most important setting here. Verify the server's maxmemory-policy, because a cache configured with noeviction returns write errors when it fills rather than evicting, which turns a full cache into an outage. Confirm the API for scripted atomic operations, since invalidation and stampede control both need one. Report what you verified and what turned out wrong.

Find every existing cache — Redis, an in-process dictionary, a memoisation decorator — and for each record its key shape, its TTL and what invalidates it. Measure the two or three reads this work is meant to speed up, so there is a number to improve. Find whether Redis is already a hard dependency of any request path. Then audit §11 item by item, each marked already true, partly true or absent, with the file that decides it, reported before anything is proposed.

1. Why a cache is a correctness decision

Adding a cache looks like a performance change. It is a decision about how wrong an answer may be, and four defaults get it wrong.

The cache that was added quickly This one
Keys are formatted strings scattered across the codebase, so nothing can find them again to invalidate them Keys come from one builder, so invalidation can enumerate what it must remove
Some entries have no TTL, and nobody can say what is in there Everything expires; the TTL is the maximum staleness, stated per entry
An entry is invalidated where someone remembered to Invalidation is attached to the write, so a new write path cannot forget
When Redis is down, requests fail When Redis is down, requests are slower

The fourth row is the one that turns an optimisation into an outage. A cache is supposed to make a working system faster; if its absence makes the system stop, it was never a cache — it was an undeclared dependency, and it took the application down for something it was only ever meant to accelerate.

There is a fifth failure that has no naive counterpart, because it only appears under load. A popular key expires; every request that arrives in the next few hundred milliseconds misses; all of them run the expensive query at once. The database, which was fine, is now serving a thousand copies of the same work — and because the load is caused by the expiry rather than by traffic, it repeats on a timer. The cache did not fail here; it worked exactly as designed.

3. Project structure

app/cache/
├── keys.py         every key shape in the system — one file, no exceptions
├── client.py       get, set, delete, with timeouts and failure containment
├── decorator.py    the read-through wrapper
└── invalidate.py   which keys a given write clears

One rule: no key is formatted anywhere except keys.py. An f-string in a handler is a key that invalidation cannot find, and the entry it writes will be served until its TTL regardless of what the database now says. Enforce it with a grep in CI, not with review.

4. Reference implementation

# app/cache/keys.py
NAMESPACE = "orders"
VERSION = "v3"      # bump to invalidate every entry of a shape at once, without
                    # scanning and without a deploy-time flush

def order(order_id: int) -> str:
    return f"{NAMESPACE}:{VERSION}:order:{order_id}"

def orders_for_customer(customer_id: int) -> str:
    return f"{NAMESPACE}:{VERSION}:customer:{customer_id}:orders"

def keys_invalidated_by_order_write(order) -> list[str]:
    # The write path asks this rather than deciding for itself. When a new cached
    # read is added, it is added here, and every existing write path clears it
    # without being touched — which is the only way this stays correct.
    return [order(order.id), orders_for_customer(order.customer_id)]

# app/cache/client.py
import asyncio, logging
from redis.asyncio import Redis

log = logging.getLogger(__name__)

# A cache read that takes longer than the query it replaces is worse than no cache.
# Bounded low and deliberately: this is a fast path or it is nothing.
TIMEOUT = 0.05


async def get(key: str) -> bytes | None:
    try:
        async with asyncio.timeout(TIMEOUT):
            return await redis.get(key)
    except (redis.RedisError, TimeoutError):
        # Unavailable and absent are one branch. This single decision is what makes
        # the cache optional at runtime instead of an undeclared dependency that
        # takes the application down with it.
        log.warning("cache unavailable", extra={"op": "get"})
        return None


async def set(key: str, value: bytes, ttl: int) -> None:
    try:
        async with asyncio.timeout(TIMEOUT):
            # Every write has a TTL. An entry without one is served until someone
            # notices, and nobody notices — the answer is merely wrong, not broken.
            await redis.set(key, value, ex=ttl)
    except (redis.RedisError, TimeoutError):
        log.warning("cache unavailable", extra={"op": "set"})

# app/cache/decorator.py
import math, random, time

BETA = 1.0


def cached(key_fn, ttl: int):
    def decorator(fn):
        async def wrapper(*args, **kwargs):
            key = key_fn(*args, **kwargs)
            raw = await client.get(key)

            if raw is not None:
                value, computed_at, delta = unpack(raw)
                # Probabilistic early expiration. As the TTL approaches, the chance
                # that any one request refreshes early rises; the log of a random
                # number desynchronises callers, so one recomputes while the rest
                # keep serving a nearly-fresh value.
                #
                # This is preferred to a lock for read-mostly data: a lock makes
                # every other caller wait, which converts a database spike into a
                # latency spike. Use a lock instead when serving a slightly stale
                # value is genuinely unacceptable.
                expiry = computed_at + ttl
                if time.time() - delta * BETA * math.log(random.random()) < expiry:
                    return value

            start = time.monotonic()
            value = await fn(*args, **kwargs)
            delta = time.monotonic() - start        # how long this costs to rebuild
            # Jitter the TTL. Entries written together — after a deploy, or a bulk
            # import — otherwise expire together, and the stampede returns on a timer.
            await client.set(key, pack(value, time.time(), delta),
                             ttl=ttl + random.randint(0, ttl // 10))
            return value
        return wrapper
    return decorator


@cached(keys.order, ttl=300)
async def get_order(order_id: int) -> Order: ...

# app/cache/invalidate.py
async def after_order_write(order) -> None:
    """Called from the write path, inside the same function that commits.

    Delete, never update. A cache write here would race with a concurrent request
    that read the old value a moment ago and is about to store it — leaving the
    stale value cached for a full TTL, with the database saying otherwise and
    nothing to indicate which is which.
    """
    for key in keys.keys_invalidated_by_order_write(order):
        await client.delete(key)

5. Golden-standard rules

Rule Why
Forbidden: an entry written without a TTL It is served until someone notices, and nobody notices — a wrong answer is not an error. The TTL is the maximum staleness, so it must exist.
Forbidden: a key formatted outside the key module Invalidation cannot find what it cannot enumerate, and that entry will be served regardless of the database.
Forbidden: a cache failure propagating to the caller Then it is not a cache, it is a dependency — and it takes down the application for something meant only to speed it up.
Forbidden: an unbounded cache operation A read that blocks longer than the query it replaces is worse than no cache at all.
Forbidden: updating a cache entry on write instead of deleting it It races with a concurrent read that is about to store the old value, and the loser is cached for a full TTL.
Invalidation lives in the write path, not beside it Somewhere else means a new write path can forget, and it will.
The key module owns which keys a write clears Adding a cached read then updates every write path at once, without touching any of them.
TTLs are jittered Entries written together expire together, and the stampede comes back on a schedule.
A popular key is refreshed before it expires, not after Otherwise every request that arrives during the recompute runs the same expensive work.
The key namespace carries a version A shape change is then one constant, rather than a scan or a flush.
maxmemory-policy evicts With noeviction a full cache returns errors on write, turning a capacity problem into an outage.
Hit rate and cache latency are measured per key shape An aggregate hit rate hides the one shape that never hits, which is the one costing you.

6. Data contracts

key       <namespace>:<version>:<entity>:<id>[:<qualifier>]
value     serialised, with the time it was computed and how long it took
ttl       always present; jittered; the stated maximum staleness for that read

Storing the computation cost alongside the value is what makes early refresh possible: a read that takes two seconds to rebuild should start refreshing earlier than one that takes twenty milliseconds, and the only way to know is to have measured it when it was last built.

The version segment is worth the ugliness. When a cached shape changes, every entry of the old shape becomes unreadable at once by changing one constant — no scan, no flush, no deploy-time migration, and no window in which a new deployment deserialises an old value into the wrong type.

7. Build order

  1. The key module and the client with timeouts and failure containment, before anything is cached. Then a test that Redis being unreachable makes the endpoint slower and not broken — that behaviour is the foundation, not a refinement.
  2. One cached read, with hit rate and latency measured before and after.
  3. Invalidation in the write path, with a test asserting a write makes the next read return the new value.
  4. TTL jitter.
  5. Early refresh, with a load test that misses one popular key concurrently and asserts the loader ran once.
  6. Serialisation with the version segment, and a test that an old-shape value is ignored rather than deserialised.
  7. Per-shape metrics, then extend to the remaining reads.

Step 1 first because degradation is the property that makes everything else safe to add. A cache built the other way around is a dependency by the time anyone thinks to test it.

9. Metrics

Metric Target
Hit rate, per key shape > 80% for anything worth caching; below that, reconsider
Cache operation latency, p99 < 5 ms, and always under the timeout
Requests served during a Redis outage 100%, at source latency
Concurrent loads of one key on expiry 1
Entries without a TTL 0
Stale reads after a write 0 beyond the invalidation path's own latency
Memory used against maxmemory < 80%, with an evicting policy configured

10. Failure modes

Symptom Cause Fix
The application goes down when Redis does Cache errors propagate to the caller Treat unavailable as a miss, in one place
Every request slows down when Redis is degraded No timeout on cache operations, so each request waits on it Bound every operation; treat the timeout as a miss
The database spikes on a schedule with no traffic change A popular key expires and every concurrent request recomputes it Early refresh, TTL jitter, or a lock for the few keys where staleness is unacceptable
The database spikes minutes after every deploy Entries were all written at start-up and expire together Jitter the TTL at write time
A user updates something and still sees the old value The write path does not invalidate, or clears a different key than the read wrote One key module; invalidation attached to the write
A stale value persists for a full TTL after a correct write The write updated the cache and raced with a concurrent read storing the old value Delete on write; let the next read repopulate
Some entries are years old They were written without a TTL Require a TTL in the API so it cannot be omitted
Writes to Redis start failing under memory pressure maxmemory-policy is noeviction Choose an evicting policy; a cache that cannot evict is not a cache
A deploy causes deserialisation errors on cached values The cached shape changed and old entries were still readable Bump the version segment in the key namespace
Hit rate looks healthy and the slow endpoint is still slow The aggregate hides one key shape that never hits Measure per shape
Caching a slow query made the p99 worse The query was slow because it was wrong; now it runs under accumulated load after each invalidation Fix the query; cache what remains expensive

11. Definition of done

  • With Redis stopped, every endpoint still answers correctly, covered by a test that asserts both the response and a source-latency timing
  • Every cache operation has a timeout, and exceeding it is treated as a miss, covered by a test
  • No key is constructed outside the key module, checked by grep in CI
  • Every write to the cache sets a TTL, enforced by the API rather than by review
  • A write followed immediately by a read returns the new value, covered by a test per cached read
  • Concurrent requests missing the same key result in exactly one load, covered by a concurrency test
  • TTLs are jittered, verified by writing many entries and asserting a spread of expiry times
  • Bumping the key version makes every old entry unreachable, covered by a test
  • maxmemory-policy is set to an evicting policy, verified by querying the running server
  • Hit rate and operation latency are exported per key shape, not only in aggregate
  • Every cached read has its maximum staleness written down next to its TTL
  • A cache write failing does not fail the request, covered by a test
