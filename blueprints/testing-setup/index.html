Test Harness and Unit Tests

A test harness and unit tests: project layout, fixtures, fakes over mocks, coverage that means something and tests that fail for one reason.

low1–2 daysVerified 2026-08-19
Testing
Read it on GitHub ↗ Back to the catalogue

Test infrastructure from nothing: a runner configured to fail on flakiness rather than tolerate it, fixtures scoped so tests cannot leak into each other, factories instead of shared sample data, and time and randomness pinned so a green suite means something.

Complexity: low · Typical build: 1–2 days · Verified: 2026-08-19 (re-check after ~90 days)

Examples in: Python, with pytest. The architecture is language-agnostic: sections 5, 10 and 11 hold wherever you build this. Section 4 is illustrative — if your project is in another language, your agent translates the idioms rather than importing them, and nothing is lost. The equivalents are Vitest or Jest with --sequence.shuffle in TypeScript, go test -shuffle=on in Go, and ExUnit with async: true in Elixir — where the ordering and determinism concerns are identical.

Use when: a project has no tests, or has tests that nobody trusts — they fail sometimes, they pass when the code is wrong, or they must be run in a particular order. Covers layout, fixtures, factories, mocking the outside world, and a coverage bar that is worth having.

Not for: tests that need a real database, a real queue or a real HTTP peer. Those are integration tests: different infrastructure, different isolation problem, different speed budget. Trying to serve both from one harness is how a unit suite becomes a four-minute one nobody runs before pushing.

⚙️ INSTRUCTIONS FOR THE AI — READ BEFORE WRITING ANY CODE

Do not start coding.

Step 1 — Refresh. Verify the test runner and its plugins. If the project is async, verify the async plugin's current major — its configuration has changed across versions, the event_loop fixture override that appears in most examples was removed, and loop scoping is now configured rather than monkey-patched. Confirm the current names for the ordering-shuffle plugin, the time-freezing library and the HTTP-mocking library. Report what you verified and what turned out wrong.

Step 2 — Read the project, then audit what already exists. Find every existing test and record: how long the suite takes, whether it passes with -p randomly or the equivalent shuffle enabled, and whether any test reaches the network or the clock. Run the suite twice in a row without cleaning — if the second run differs, something persists between runs and that is the first thing to fix. Find where sample data comes from today; a shared fixtures file that many tests mutate is the usual source of order dependence. Then audit §11 item by item, each marked already true, partly true or absent, with the file that decides it, reported before anything is proposed.

Assume the project is right until it demonstrably is not; code satisfying an item stays even where its shape differs from §4; replacing something that works needs a one-line reason; never delete a working path to make room for the blueprint's version. The same holds for language — §4 is illustrative, its idioms get translated into the project's language, and §11 is what has to become true rather than the syntax.

Step 3 — Write a plan for the gap only, and get it approved, including a ## Proposed stack section and the current suite runtime as the number to protect. Do not ask open framework questions — propose, and ask for confirmation once. Say what you are adding, what you are leaving alone, and what you propose to change, and touch nothing else.

Step 4 — Build in the order in §7. Step 5 — §11 is the definition of done.

1. Why a green suite can mean nothing

A test suite has one job: when it is green, the code is probably right. Four common defaults break that.

The usual setup This one
Tests run in file order, so one test's leftovers set up the next one Order is shuffled every run, so a dependency between tests fails immediately
datetime.now() and random() reach the real clock and the real generator Both are pinned, so a test that passes today passes in December and on a leap day
A shared fixtures module holds sample objects that tests mutate Each test builds what it needs from a factory, and nothing is shared
Coverage is a percentage on a dashboard Coverage is a floor in CI, and the number is chosen to be defensible

The first row is the expensive one because the failure appears far from its cause. A test suite with an ordering dependency is green on the developer's machine and red in CI, or green all week and red when someone adds a test in the middle of the file. Every hour spent on that is spent on the harness, not on the bug — and the usual outcome is that someone pins the order and the rot is preserved.

Shuffling is not a nicety; it is the only way this class of defect is visible at all. Turn it on before there are enough tests for it to hurt.

The fourth row deserves a warning of its own. Coverage measures which lines ran, not which behaviours are checked. A suite that executes every line and asserts nothing reports one hundred per cent. Use it as a floor that stops the number falling, never as evidence that the tests are good.

Everything a unit test touches is something the harness constructed, which is what makes the suite fast and what makes a failure mean something about the code rather than about the environment.

3. Project structure

tests/
├── conftest.py         root fixtures — small, and shared by everything
├── factories.py        one builder per domain object
├── unit/
│   ├── conftest.py     fixtures only these tests need
│   └── test_orders.py
pyproject.toml          runner configuration lives here, not in a separate ini

One rule: a fixture lives at the narrowest scope that can hold it. A fixture in the root conftest.py is constructed for tests that never asked for it and becomes a dependency nobody can remove. Push it down until exactly the tests that use it can see it.

4. Reference implementation

# pyproject.toml
[tool.pytest.ini_options]
testpaths = ["tests"]
addopts = [
    "--strict-markers",     # a typo in a marker name is an error, not a silently
                            # unmarked test that then runs in every selection
    "--strict-config",
    "-ra",                  # show why things were skipped; silent skips hide rot
    "--cov=app",
    "--cov-report=term-missing",
    "--cov-fail-under=75",  # a floor to stop the number falling, not a quality claim
]
# The default when tests do not say otherwise. Explicit beats implicit here:
# auto-detection makes a forgotten marker look like a passing synchronous test
# that in fact never ran its body.
asyncio_mode = "strict"
asyncio_default_fixture_loop_scope = "function"
markers = [
    "slow: takes more than a second — excluded from the default run",
]
filterwarnings = [
    "error",                # a deprecation warning is a future breakage with a date
    "ignore::DeprecationWarning:third_party_lib.*",
]

# tests/conftest.py
import random
import pytest
from time_machine import travel

# Chosen once, printed on failure. A test that depends on a particular random draw
# must be reproducible; without a fixed seed, "it failed once in CI" is unfixable.
SEED = 20260819


@pytest.fixture(autouse=True)
def deterministic(monkeypatch):
    # autouse because determinism is not opt-in: the test that forgets to ask for it
    # is exactly the one that fails on the last day of the month.
    random.seed(SEED)
    with travel("2026-08-19T12:00:00+00:00", tick=False):
        yield


@pytest.fixture(autouse=True)
def no_network(monkeypatch):
    # A unit test that reaches the network is an integration test wearing a
    # disguise: slow, flaky, and green when the service it calls is broken.
    # Blocking it at the socket makes that impossible rather than discouraged.
    import socket

    def deny(*args, **kwargs):
        raise RuntimeError("network access in a unit test — mock it or move it to tests/integration")

    monkeypatch.setattr(socket, "socket", deny)

# tests/factories.py
from dataclasses import dataclass
import itertools
from decimal import Decimal
from app.models.order import Order

_ids = itertools.count(1)


def an_order(**overrides) -> Order:
    """Build a valid Order. Every field has a working default; a test overrides
    only what it is about.

    This is the point of a factory over a shared sample object. A test that says
    `an_order(quantity=0)` states its own subject in one line — and it cannot
    affect any other test, because it built its own object.
    """
    defaults = dict(
        id=next(_ids),
        customer_id=next(_ids),
        quantity=1,
        total=Decimal("10.00"),
        status="pending",
    )
    return Order(**{**defaults, **overrides})

# tests/unit/test_orders.py
import pytest
from app.services.orders import price_order
from tests.factories import an_order


def test_bulk_discount_applies_from_ten_units():
    # The name says the behaviour, so a failure in CI is legible without opening
    # the file. "test_price_1" is a line number with extra steps.
    order = an_order(quantity=10, total=Decimal("100.00"))
    assert price_order(order) == Decimal("90.00")


@pytest.mark.parametrize("quantity", [0, -1])
def test_non_positive_quantity_is_rejected(quantity):
    with pytest.raises(ValueError, match="quantity"):
        price_order(an_order(quantity=quantity))
        # match= is not decoration: without it this passes when the code raises
        # ValueError for a completely unrelated reason, which is how a test keeps
        # passing after the behaviour it covered was deleted.

5. Golden-standard rules

Rule Why
Forbidden: tests that depend on execution order Shuffle every run. Without it the dependency is invisible until someone inserts a test, and then it is a day of work far from the cause.
Forbidden: a unit test touching the network, the filesystem outside a temp directory, or a real database It is an integration test in disguise: slow, flaky, and green when its dependency is broken. Block it at the socket rather than asking people not to.
Forbidden: reading the real clock or unseeded randomness Those tests pass today and fail on the last day of a month, across a daylight-saving boundary, or once in a hundred CI runs.
Forbidden: shared mutable sample objects One test's mutation becomes another's precondition, and the suite becomes order-dependent without anyone writing an ordering.
Forbidden: pytest.raises without matching the message It passes when the code raises the right type for the wrong reason, which outlives the behaviour it was meant to cover.
Coverage is a floor, never a goal It measures lines executed, not behaviours checked. A suite that asserts nothing can reach one hundred per cent.
Every fixture sits at the narrowest scope that works A root fixture is built for tests that never asked for it and becomes a dependency nobody can remove.
Markers are declared and strict An unknown marker should be an error; otherwise a typo silently unmarks a test and it runs in every selection.
Warnings are errors, with a short explicit ignore list A deprecation warning is a breakage with a date on it. Reading it in CI now is cheaper than debugging it after an upgrade.
The default run excludes slow tests, and CI runs everything If running tests before pushing is inconvenient, they stop being run before pushing.
Test names state the behaviour A CI failure should be legible from the name alone, without opening the file.
Assertions are about behaviour, not about how it was implemented A test asserting that a private method was called breaks on every refactor and catches no bug.

6. Data contracts

The contract is what a test may assume, and it is deliberately small:

time        frozen at a fixed instant; advancing it is explicit
randomness  seeded from one constant, printed on failure
network     unavailable; any attempt raises
order       arbitrary — nothing may depend on what ran before
state       nothing persists between tests

A test that needs any of these relaxed is telling you it belongs in another suite. That signal is worth more than the convenience of relaxing it, because it is the only automatic way a unit suite stays fast.

7. Build order

  1. Runner configuration, one trivial test, and shuffle enabled from the first commit. Turning it on later means fixing every accumulated dependency at once.
  2. Determinism — frozen clock, seeded randomness — as autouse fixtures, then a test that asserts the clock is frozen.
  3. Factories for the two or three objects tests need most.
  4. The network block, then run the existing tests and see what fails. Whatever does was never a unit test.
  5. Real unit tests for the highest-risk logic — pricing, permissions, state transitions.
  6. Coverage floor, set just under the current number so it can only go up.
  7. Slow marker and the split run.

Step 1 puts shuffle first because it is the only item on this list that gets harder every day it is postponed.

8. Blocks to pull in

Nothing here is a prerequisite. These are adjacent problems, by name only — resolve them separately if they apply.

  • Integration tests with real dependencies — the suite this one deliberately excludes
  • GitHub Actions CI — where this suite runs on every change
  • Docker Compose dev environment — where the dependencies the unit suite avoids actually live
  • Pydantic request and response schemas — the boundary these tests exercise most

10. Failure modes

Symptom Cause Fix
Tests pass locally and fail in CI, or fail only when a new test is added An ordering dependency: one test leaves state another relies on Enable shuffle, fix what it finds, keep it on
A test fails once a month and passes on retry It reads the real clock, or an unseeded random value Freeze time and seed randomness with autouse fixtures
A test fails when a third-party service is down It was never a unit test Block the network in the harness; move the test to the integration suite
Coverage is high and bugs still ship Coverage counts executed lines, not assertions Treat it as a floor; judge the suite by what it asserts
A test keeps passing after the behaviour it covered was deleted pytest.raises without a message match, or an assertion on a mock rather than on a result Match the message; assert on outcomes
Every refactor breaks dozens of tests that found no bug Tests assert on internal calls rather than on behaviour Assert on what the caller observes
Nobody runs the suite before pushing It takes minutes because slow tests are in the default run Mark them and exclude them by default; CI runs everything
A new test mysteriously affects an old one Both mutate a shared sample object built once at module or session scope Factories, function scope, one object per test
A test is skipped in CI for months and nobody notices Skips are silent by default Report skip reasons and review them
An upgrade breaks the suite in a way nobody saw coming Deprecation warnings were never surfaced Turn warnings into errors with a narrow ignore list

11. Definition of done

  • The suite passes with the order shuffled, run at least ten times in CI with different seeds
  • Running the suite twice in a row without cleaning produces identical results
  • A test asserts that the clock is frozen and that the seeded generator produces a known value
  • Attempting a network connection from a unit test raises, covered by a test that asserts the raise
  • Every domain object used by more than two tests has a factory, and no test mutates an object it did not build
  • The coverage floor is enforced in CI and is at or above the current level
  • Unknown markers cause an error, verified by adding a misspelled one and observing the failure
  • Warnings are errors, with an explicit ignore list containing only third-party entries and a reason for each
  • The default run excludes tests marked slow and finishes in under ten seconds
  • Every pytest.raises in the suite matches a message or an error attribute, checked by grep in CI
  • Test names describe behaviour, verified by reading the CI output of a deliberately failed run
