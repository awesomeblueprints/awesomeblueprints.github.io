Structured LLM Output with JSON Schema

Structured LLM output with JSON Schema: constrained decoding, validation, retries on malformed output and types that make constraints real.

low2–3 daysVerified 2026-08-19
Prompting
Read it on GitHub ↗ Back to the catalogue

Getting a model to emit data your code can parse every time — by constrained decoding, by a tool-call schema, or by prompt-parse-repair — and handling the case where the shape is right and the values are still wrong.

Complexity: low · Typical build: 2–3 days · Verified: 2026-08-19 (re-check after ~90 days)

Examples in: Python with Pydantic. Only §4 and §6 are language-specific — the rules, failure modes and definition of done hold anywhere, and your agent translates the code.

Use when: the model's output feeds code rather than a person — extraction, classification, filling a form, producing arguments for something downstream — and a parse failure is an incident rather than a nuisance.

Not for: prose a human will read. Forcing JSON onto a task that wants prose measurably degrades the prose, and you gain nothing your code can use.

⚙️ INSTRUCTIONS FOR THE AI — READ BEFORE WRITING ANY CODE

Do not start coding.

Step 1 — Refresh. Search the web and verify: whether the provider being used offers strict schema adherence or constrained decoding today, what subset of JSON Schema it enforces, and what it silently ignores — support for oneOf, $ref, pattern and nested optionals is the part that moves; the field name for the finish or stop reason and its value on truncation; whether forcing a specific tool is still supported and how it is spelled. Report what you verified and where your assumptions were wrong.

Step 2 — Read the project, then audit what exists. Find every place a model response is parsed. Look specifically for a bare json.loads, a find("{"), a try/except that swallows the raw response, and any schema written twice — once as a type and once as a string in a prompt.

Then audit what exists. Walk §11 item by item, marking each already true, partly true or absent with the file that decides it. Report that before proposing anything.

Assume the project is right until it demonstrably is not. Code that satisfies an item stays, whatever its shape — §4 is illustrative, and its idioms translate into this project's language. Replacing something that works needs a one-line reason. Never delete a working path to make room for the version written here. If nothing relevant exists, say so and use §3.

The same applies to language. §4 is illustrative: translate its idioms into this project's language and libraries rather than importing its shape. §11 is what has to become true — not the syntax it happens to be written in.

Step 3 — Write a plan for the gap only, and get it approved. List: which mechanism each call site moves to, which schemas need flattening, which fields need a stated null case, and which business rules belong in semantic validation rather than in the schema.

In that plan, include a ## Proposed stack section. Do not ask an open question. Propose the mechanism per call site and the validation library — with a one-line reason, the versions verified in Step 1, and what would change the decision. Ask the user to confirm once.

Name what you are adding, leaving alone, and changing. Touch nothing else.

1. Three mechanisms, and why the weakest one is the default

json.loads(response) fails in production in a small, boring set of ways: markdown fences, a preamble, a trailing comma, an unescaped quote, or an object cut in half because the token limit was reached. Prompting harder does not remove any of them; it lowers their rate.

Constrained decoding Tool-call schema Prompt, parse, repair
How it works The sampler cannot emit a violating token The provider validates the call You validate afterwards
Syntactic failure Impossible Rare The rate you measure
Cost of a failure — A rejected call An extra round trip
Availability Provider and model dependent Wherever tools exist Everywhere
Enforces meaning No No No

Use the strongest one the provider supports, per call site. The common mistake is choosing the third because it was the first one that worked in a notebook.

None of the three make the values correct. A schema-valid object can contain an order id that does not exist. Parsing and validation are two layers, and the second one is the one teams skip.

3. Project structure

extraction/
├── models.py       # the schema, defined once. JSON Schema is generated from it.
├── emit.py         # mechanism selection: constrained > tool-call > prompted
├── extract.py      # pull a JSON value out of mixed text, brace-aware
├── repair.py       # one retry loop, capped, error text passed verbatim
├── rules.py        # semantic validation: ranges, cross-field, referential
└── audit.py        # raw responses on every failure, with the schema version

The rule that keeps this maintainable: the schema exists in exactly one place, and the string sent to the model is generated from it. A schema pasted into a prompt and also declared as a type will diverge, and the failure looks like a model problem for as long as it takes someone to compare the two.

4. Reference implementation

Extraction that survives real responses. text.find("{") to text.rfind("}") breaks on nested objects and on prose containing braces:

FENCED = re.compile(r"```(?:json)?\s*(\{.*?\}|\[.*?\])\s*```", re.S)

def extract_json(text: str) -> str:
    if m := FENCED.search(text):
        return m.group(1)
    start = min((i for i in (text.find("{"), text.find("[")) if i != -1), default=-1)
    if start == -1:
        raise ValueError("no JSON value in the response")
    opener, closer = ("{", "}") if text[start] == "{" else ("[", "]")
    depth = 0; in_str = False; esc = False
    for i, ch in enumerate(text[start:], start):
        if in_str:
            esc = (ch == "\\") and not esc
            if ch == '"' and not esc: in_str = False
        elif ch == '"': in_str = True
        elif ch == opener: depth += 1
        elif ch == closer:
            depth -= 1
            if depth == 0: return text[start:i + 1]
    raise ValueError("unterminated JSON - the response was truncated")

The call, with the diagnosis in the right order:

def call_structured(system: str, user: str, model_cls, max_repairs: int = 2):
    messages = [{"role": "user", "content": user}]
    sys_prompt = system + "\n\nReturn JSON matching this schema and nothing else:\n" \
                 + json.dumps(model_cls.model_json_schema())

    for attempt in range(max_repairs + 1):
        resp = client.create(model=MODEL, max_tokens=4096, temperature=0,
                             system=sys_prompt, messages=messages)
        raw = resp.content[0].text

        # Before blaming the JSON: a cut-off response is a budget problem.
        if resp.stop_reason == "max_tokens":
            raise Truncated("raise max_tokens or shrink the schema; a retry will not help")

        try:
            return model_cls.model_validate_json(extract_json(raw))
        except (ValidationError, ValueError) as e:
            audit.record(attempt, e, raw)          # the raw text is the only debuggable artefact
            if attempt == max_repairs:
                raise
            messages += [
                {"role": "assistant", "content": raw},
                # The validation error IS the instruction. Do not paraphrase it.
                {"role": "user", "content": f"That output failed validation:\n{e}\n\n"
                                            "Return only the corrected JSON. No prose, no fences."},
            ]

Forcing a tool call is the strongest mechanism available almost everywhere:

resp = client.create(
    model=MODEL, max_tokens=2000,
    tools=[{"name": "record_extraction",
            "description": "Record the extracted fields.",
            "input_schema": TicketExtraction.model_json_schema()}],
    tool_choice={"type": "tool", "name": "record_extraction"},   # not optional
    messages=[{"role": "user", "content": ticket}])
data = TicketExtraction.model_validate(
    next(b.input for b in resp.content if b.type == "tool_use"))

5. Golden-standard rules

Rule Why
The schema is defined once in code; the model's copy is generated from it Two copies diverge, and the divergence reads as a model failure
Use the strongest mechanism the provider supports at that call site Prompting when strict mode exists is choosing a failure rate you did not need
Temperature 0 for extraction This is transcription, not writing
additionalProperties: false on every object Otherwise extra keys arrive and are silently dropped
Schema depth ≤ 3, fields ≤ 15 per object Adherence falls off sharply with nesting; split the call instead
Every optional field says when to return null, per field "Return null if not stated. Do not infer." is the difference between a null and a fabrication
Check the finish reason before diagnosing a parse error Truncation retried at the same limit fails identically forever
Extraction is brace-aware and fence-aware The naive scan breaks on the first nested object
Repairs are capped at two and pass the validation error verbatim Beyond two the model is not going to get there; a paraphrased error is not actionable
Semantic validation is a separate layer from parsing A schema-valid object can still contain a fabricated id
Every failure logs the raw response and the schema version It is the only artefact that explains what happened
Structure the envelope, leave prose fields free Forcing structure onto the prose degrades it and buys nothing

6. Data contracts

class TicketExtraction(BaseModel):
    model_config = {"extra": "forbid"}

    issue: str = Field(max_length=200, description="The primary problem, one sentence.")
    severity: Literal["critical", "high", "medium", "low"]
    severity_quote: str = Field(description="The exact phrase that drove severity.")
    product_area: str | None = Field(None, description="null if not stated. Do not infer.")
    affected_users: int | None = Field(None, ge=0, description="null if not stated.")

    @field_validator("severity_quote")
    @classmethod
    def must_be_a_quote(cls, v: str) -> str:
        # Semantic, not syntactic: 400 characters is a summary, not a quotation.
        if len(v) > 200:
            raise ValueError("severity_quote must be a short verbatim phrase")
        return v

Semantic rules that do not belong in the schema, and where they go instead:

Rule Belongs in
severity is one of four values The schema, as an enum
affected_users is not negative The schema, as a bound
severity_quote appears verbatim in the source text rules.py — needs the input
The referenced order_id exists rules.py — needs the database
critical requires an outage phrase rules.py — cross-field

7. Build order

  1. Define the schema once, and generate the model's copy from it. Delete any second copy living in a prompt string.
  2. Log the raw response on every failure, with the schema version. Do this first: everything after it is easier to diagnose.
  3. Check the finish reason before parsing, and raise a distinct error on truncation.
  4. Robust extraction — fences, preambles, nesting.
  5. Syntactic validation against the schema.
  6. The repair loop, capped at two, error text verbatim.
  7. Move to the strongest mechanism the provider supports: forced tool call, then constrained decoding if available.
  8. The semantic layer — ranges, cross-field rules, referential checks.
  9. A fixed set of at least fifty inputs with known correct output, run in CI, reporting first-attempt parse rate and semantic failure rate separately.

9. Metrics

Metric Target
First-attempt parse rate ≥ 99%; below 95% the mechanism is wrong, not the prompt
Repair success rate ≥ 80%; below 50% the error text is not reaching the model usefully
Truncation rate < 0.1%; above 1% the token budget is sized to the median, not the tail
Semantic validation failures < 2% — these are the ones that reach production as bad data
Correct nulls where the value is absent ≥ 95%; the rest are fabrications
Repair tokens as a share of total < 3%

10. Failure modes

Symptom Cause Fix
JSON cut off mid-object Token limit reached Check the finish reason; raise the limit or shrink the schema. Retrying is useless
Markdown fences around the JSON Default formatting Fence-aware extraction; say "no fences" in the prompt
A sentence before the JSON The model narrating Move to a forced tool call or constrained decoding
A plausible value where null belonged The null case was never described Per-field: "null if not stated. Do not infer."
A value outside the enum Not using strict mode Constrained decoding, or a Literal type with validation
Valid shape, wrong values No semantic layer Add one; the schema was never going to catch this
The repair loop never converges The error was paraphrased, or the schema is impossible to satisfy Pass the error verbatim; re-read the schema yourself
Reliability drops as the schema grows Depth and field count Flatten to three levels; split into two calls
Parses fine, fails on one customer's data Extraction is naive about nesting or quotes Brace-aware scan with string-state tracking
Nobody can reproduce yesterday's failure The raw response was discarded Log it on every failure

11. Definition of done

  • The schema is defined once in code and the model's copy is generated from it.
  • The strongest mechanism the provider supports is in use at every call site.
  • additionalProperties: false on every object, required fields declared.
  • Schema depth is ≤ 3 and no object has more than ~15 fields.
  • Every optional field's description states when to return null.
  • Temperature is 0 for every extraction call.
  • The finish reason is checked before any parse failure is diagnosed.
  • Extraction handles fences, preambles and nested objects.
  • Repairs are capped at two and pass the validation error verbatim.
  • A semantic validation layer checks ranges, cross-field rules and referential integrity.
  • Every failure logs the raw response and the schema version.
  • A fixed input set runs in CI and reports parse rate and semantic failure rate separately.
