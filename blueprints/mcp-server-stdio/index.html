MCP Server over stdio

An MCP server over stdio: exposing local tools, files and commands to a developer's own agent, with the process model and limits it implies.

low1–2 daysVerified 2026-08-19
MCPAgents
Read it on GitHub ↗ Back to the catalogue

A local MCP server that exposes your own tools to a coding agent: a skeleton that starts in one command, errors an agent can act on, results that respect the context they land in, and an installation entry someone else can copy.

Complexity: low · Typical build: 1–2 days · Verified: 2026-08-19 (re-check after ~90 days)

Examples in: Python. The architecture is language-agnostic: sections 5, 10 and 11 hold wherever you build this. Section 4 is illustrative — if your project is in another language, your agent translates the idioms rather than importing them, and nothing is lost. The protocol details below are from the specification revision named on the Verified line.

Use when: something on a developer's own machine should be available to their agent — a project's build system, an internal command-line tool, a local database, a scratch directory — and it runs as the same user with the same permissions they already have.

Not for: anything reached over a network or used by more than one person. That is a different product: it needs authorization, tenant isolation, rate limits and a deployment, and none of those exist here — a stdio server has exactly the permissions of the process that spawned it, and that is the whole of its security model.

⚙️ INSTRUCTIONS FOR THE AI — READ BEFORE WRITING ANY CODE

Do not start coding.

Step 1 — Refresh. Verify the SDK and the protocol revision it implements. Several things were removed in the current revision that older examples still show: the initialize handshake is gone — each request carries its protocol version and client capabilities in _meta — and ping, logging/setLevel and the roots-list-changed notification no longer exist. Roots, Sampling and Logging are deprecated, so do not build on them in new work; log to standard error instead of using the logging feature. Confirm that server/discover is required and what it must advertise. Confirm the client's configuration format for registering a local server, since that is what a user copies. Report what you verified and what turned out wrong.

Step 2 — Read the project, then audit what already exists. Find what the server will actually expose and, for each candidate, whether it is safe to run without a person watching — a stdio server inherits the user's permissions, so "delete a branch" runs with the same authority as the user typing it. Find whether any of the underlying commands write to standard output, because that is the transport and anything printed there corrupts the protocol. Establish how the server will be launched: an installed executable, a script in a repository, a package runner. Then audit §11 item by item, each marked already true, partly true or absent, with the file that decides it, reported before anything is proposed.

Assume the project is right until it demonstrably is not; code satisfying an item stays even where its shape differs from §4; replacing something that works needs a one-line reason; never delete a working path to make room for the blueprint's version. The same holds for language — §4 is illustrative, its idioms get translated into the project's language, and §11 is what has to become true rather than the syntax.

Step 3 — Write a plan for the gap only, and get it approved, including a ## Proposed stack section, the tool list with what each can reach, and the configuration snippet a user will copy. Do not ask open framework questions — propose, and ask for confirmation once. Say what you are adding, what you are leaving alone, and what you propose to change, and touch nothing else.

Step 4 — Build in the order in §7. Step 5 — §11 is the definition of done.

1. Why a working server is still a bad one

The skeleton takes an hour. What separates a server people keep from one they disable is entirely in what it sends back.

The server that works The server that stays installed
A failure is a stack trace, or nothing A failure is a sentence saying what to do instead
A tool returns everything it found It returns what fits, and says what it truncated
Descriptions describe the implementation They describe when to use the tool, because that is what the model is choosing on
Something prints a diagnostic to standard output Nothing does, because standard output is the wire

The last row is the failure unique to this transport and it is absolute. Standard output is the protocol. A stray print, a library that logs to stdout, a progress bar from a subprocess — any of it lands in the middle of a JSON-RPC message and the client sees a parse error, usually with no indication of where it came from. Everything diagnostic goes to standard error, and this has to be true of every library you call, not only of your own code.

The first row is what makes the difference in use. An agent cannot debug you. Told "error: 2", it retries the same call. Told "no repository at that path; pass an absolute path to a directory containing .git", it fixes the call and moves on. Error messages here are part of the interface, not diagnostics — they are read by something that will act on them immediately.

The second row is a cost you impose on your users. Everything you return occupies the agent's context, and a tool that returns a whole file for a question about one function has spent the user's budget on your behalf. Returning less, and saying what was left out, is a feature.

The rule the diagram encodes: there is exactly one arrow to standard output and it carries the protocol. Every other outbound arrow — logs, warnings, progress, a subprocess's chatter — goes to standard error. This is not a style preference; it is what makes the transport work.

3. Project structure

src/myserver/
├── __main__.py     the entry point, so `python -m myserver` starts it
├── server.py       the server, its identity and its version
├── tools/
│   └── repo.py     one module per group of tools
├── resources.py    read-only data the agent may fetch
└── limits.py       the result budget, in one place
README.md           the configuration snippet a user copies, and what it can reach

One rule: the README carries a working configuration entry. Not instructions for writing one — the JSON itself, with the command and arguments filled in. It is what someone pastes, and it is the difference between a server people install and one they mean to get around to.

4. Reference implementation

# src/myserver/server.py
import logging, sys
from mcp.server import Server

# stderr, always. Standard output is the transport: one line printed there lands
# in the middle of a JSON-RPC message and the client reports a parse error with
# no hint about where it came from. This applies to every library you call, not
# only to your own code.
logging.basicConfig(stream=sys.stderr, level=logging.INFO)

server = Server("myserver", version=__version__)

# src/myserver/tools/repo.py
MAX_RESULT_CHARS = 8000


@server.tool()
async def find_symbol(name: str, path: str = ".") -> str:
    """Find where a symbol is defined in this repository.

    Use this when you need the definition of a function, class or constant and do
    not know which file it is in. Returns the file, the line and the signature —
    not the body; read the file for that.

    The description is what the model chooses on, so it says *when to use this*
    and what comes back. Describing the implementation instead is the most common
    reason a good tool never gets called.
    """
    root = Path(path).resolve()
    if not (root / ".git").exists():
        # An agent cannot debug you. "error: 2" gets retried unchanged; this gets
        # corrected and the turn continues. Error text here is interface, not
        # diagnostics.
        raise ToolError(
            f"No repository at {root}. Pass an absolute path to a directory "
            f"containing a .git folder.")

    matches = await search(root, name)
    if not matches:
        # A dead end that says what to try next. "Not found" alone makes the
        # agent guess; naming the next move usually ends the loop.
        return (f"No definition of {name!r} found under {root}. "
                f"Check the spelling, or search for a partial name.")

    rendered = "\n".join(f"{m.file}:{m.line}  {m.signature}" for m in matches)
    if len(rendered) > MAX_RESULT_CHARS:
        # Everything returned occupies the user's context. Returning less, and
        # saying so, is a feature — an unbounded result spends a budget that is
        # not yours on data nobody asked for.
        kept = rendered[:MAX_RESULT_CHARS].rsplit("\n", 1)[0]
        return (f"{kept}\n\n[{len(matches)} matches; showing the first few. "
                f"Narrow the search with a more specific name.]")
    return rendered

# src/myserver/resources.py
@server.resource("repo://conventions")
async def conventions() -> str:
    """Content the agent may read, addressed by URI rather than called.

    Resources suit stable reference material — conventions, schemas, a changelog.
    The distinction that matters in practice: a tool is something the model
    decides to do, a resource is something it or the user can pull in. Modelling
    reference text as a tool makes the model choose whether to read it; modelling
    an action as a resource hides it from the decision.
    """
    return (Path.cwd() / "CONVENTIONS.md").read_text()

# src/myserver/__main__.py
def main() -> None:
    # A module entry point, so the configuration line is stable and does not
    # depend on where a script happens to be installed.
    asyncio.run(server.run_stdio())


if __name__ == "__main__":
    main()

## Install

Add this to your client's MCP configuration:

```json
{
  "mcpServers": {
    "myserver": {
      "command": "uvx",
      "args": ["--from", "myserver", "python", "-m", "myserver"],
      "env": {}
    }
  }
}
```

This server runs as you, with your permissions. It reads files under the
directory it is started in and runs no commands that write.

5. Golden-standard rules

Rule Why
Forbidden: writing anything but protocol messages to standard output It is the wire. One stray line corrupts a message and the client reports a parse error with no clue where it came from.
Forbidden: an unbounded tool result It spends the user's context budget, which is not yours to spend, on data nobody asked for.
Forbidden: an error message that does not say what to do next The agent cannot debug you. An unactionable error is retried unchanged until the turn is wasted.
Forbidden: building new work on deprecated features Roots, Sampling and Logging are deprecated in the current revision. Log to standard error and take paths as parameters.
Forbidden: a tool that acts destructively without saying so in its description This server has the user's own permissions; the description is the only warning anything gets.
Descriptions say when to use the tool, not how it works The model is choosing, and it chooses on the description. This is the most common reason a good tool is never called.
A dead end names the next thing to try "Not found" makes the agent guess; "not found, try a partial name" usually ends the loop.
Truncation is stated, never silent An agent that cannot tell a partial result from a complete one draws confident conclusions from half the data.
The README carries a paste-ready configuration entry It is the difference between a server people install and one they mean to.
The entry point is a module, not a path to a script Paths differ per machine; a module entry point is the same line for everyone.
Tools are tested by calling them directly, not only through a client Most of what can be wrong here — errors, truncation, descriptions — is testable without a transport.
What the server can reach is written in the README Someone installs this on a machine with their credentials on it, and they are entitled to know.

6. Data contracts

tool      a thing the model decides to do; chosen by its description
resource  content addressed by a URI, pulled in rather than invoked
prompt    a reusable template the user can select

The distinction between the first two decides how a capability appears. A tool enters the model's decision; a resource does not, and is fetched when something asks for it. Reference material modelled as a tool makes the model choose whether to read it, and it will sometimes choose wrong. An action modelled as a resource disappears from the decision entirely.

Every result is text going into a context window someone else is paying for. The budget is part of the contract: a bounded result with a note about what was left out is more useful than a complete one that pushes the conversation's earlier turns out of the window.

7. Build order

  1. The skeleton with one tool, launched from a real client. Confirm the transport works before anything depends on it.
  2. Standard-error logging, and a check that nothing writes to standard output — including anything a subprocess prints.
  3. Actionable errors, with a test asserting each failure path names a next step.
  4. The result budget, with a test on an input that produces far too much.
  5. Descriptions rewritten as selection criteria, then a real session to see whether the right tool gets chosen.
  6. Resources and prompts, only where the distinction in §6 actually applies.
  7. The README with a paste-ready entry, tested by installing on a second machine.

Step 2 second because a stdout leak breaks the protocol in a way that looks like an SDK bug, and it is much cheaper to prevent than to find later.

Metric Target
Bytes written to standard output that are not protocol messages 0
Tool results exceeding the stated budget 0

10. Failure modes

Symptom Cause Fix
The client reports a parse error and the server looks fine Something wrote to standard output — your code, a library, or a subprocess Route all diagnostics to standard error; capture subprocess output
The agent retries the same failing call until the turn ends The error text says what went wrong but not what to do Rewrite errors as instructions
The agent's earlier context disappears after using this server An unbounded result filled the window Cap results and say what was cut
The agent draws a confident wrong conclusion from a partial list Truncation was silent Always mark it
A useful tool is never chosen The description describes the implementation instead of the situation Rewrite it as when-to-use
The server works for you and not for a colleague The configuration entry points at a path that exists only on your machine A module entry point; a paste-ready README snippet
An example from the documentation does not work It predates the current revision, which removed the handshake and several methods Check the revision the SDK implements
A feature works now and warns about deprecation Roots, Sampling or Logging Use parameters and standard error instead
A tool did something destructive nobody expected It runs with the user's permissions and its description did not say what it does Say so in the description; consider not shipping it
Every turn is slower after installing this server Descriptions are long, and they are re-sent on every turn Shorten them; fewer, better tools
The server dies silently mid-session An unhandled exception reached the top level and the process exited Handle at the boundary; return an error result and stay alive

11. Definition of done

  • A test asserts that a full session produces no non-protocol bytes on standard output, including from any subprocess the tools run
  • Every tool has a result budget, and a test with an oversized input asserts truncation and its notice
  • Every error path returns a message naming a next action, covered by one test per path
  • Every tool description states when to use the tool and what it returns, reviewed by reading them as a group
  • The README contains a configuration entry that works when pasted, verified on a machine that has never run this server
  • The entry point is a module, so the configuration line contains no machine-specific path
  • Every tool is callable directly in tests, without a client or a transport
  • No deprecated protocol feature is used, checked against the revision the SDK implements
  • An unhandled exception in a tool returns an error result and leaves the server running, covered by a test
  • The README states what the server can read, what it can write, and with whose permissions it runs
  • Every tool has been chosen at least once in a real session, or removed
