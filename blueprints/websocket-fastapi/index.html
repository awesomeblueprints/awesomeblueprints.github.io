FastAPI WebSocket Endpoint

A FastAPI WebSocket endpoint: connection lifecycle, authentication, heartbeats, backpressure and cleaning up when a client vanishes.

medium3–5 daysVerified 2026-08-19
FastAPIStreamingPython
Read it on GitHub ↗ Back to the catalogue

A bidirectional channel with authentication at the handshake, rooms, a heartbeat that detects the half-open connections TCP will not, and a rule for the slow client — because in a broadcast someone is always slow, and waiting for them stalls everyone else.

Complexity: medium · Typical build: 3–5 days · Verified: 2026-08-19 (re-check after ~90 days)

Examples in: Python, with FastAPI and Starlette's WebSocket API. The architecture is language-agnostic: sections 5, 10 and 11 hold wherever you build this. Section 4 is illustrative — if your project is in another language, your agent translates the idioms rather than importing them, and nothing is lost. The equivalents are ws or Socket.IO in Node, Phoenix Channels in Elixir — which solve most of §10 for you — and gorilla/websocket in Go.

Use when: the server needs to push — live updates, a chat, a collaborative document, progress on a long job — and polling is either too slow or too expensive.

Not for: a stream that only flows from server to client, where server-sent events are simpler, survive proxies better and reconnect on their own. Also not for request-response dressed up as a socket: if every message expects exactly one reply, you have written HTTP with worse tooling and no caching. And not, on its own, for more than one replica — an in-process connection registry stops working at the second one.

1. Why the tutorial WebSocket falls over

The tutorial version accepts a connection, appends it to a list, and broadcasts by looping over the list. Four things go wrong, all of them in production only.

The tutorial endpoint This one
Anyone who can reach the URL is connected; authentication is added "later" The connection is rejected during the handshake if the token is bad
A disconnected client is removed when a send fails — so the list holds dead entries until the next broadcast Removal happens in a finally, so it happens even when the handler raises
Broadcast awaits each send, so one slow client stalls the room Sends are independent, and a client that cannot keep up is disconnected
A connection that died without a close frame stays in the list forever A heartbeat detects it, because TCP will not

The third row is the one that is invisible until it is an outage. Awaiting each send is backpressure, and backpressure is correct for one connection. Across a room it means the whole broadcast runs at the speed of the worst connection — which is usually a phone on a train that has already stopped receiving. Libraries built for this abandon backpressure during a broadcast on purpose: slowing every client to let the slowest catch up is the wrong trade, because the slowest is about to time out anyway.

The fourth row explains most "ghost user" reports. A laptop that closes its lid sends nothing. TCP will not notice for a long time, and the socket looks open. The only thing that finds it is a heartbeat with a deadline.

The rule the diagram encodes: every connection has exactly one writer. Two tasks sending on one socket interleave frames and corrupt the stream — in most implementations that is a runtime error, and in the rest it is worse. Fanning out through a per-connection queue is what makes the single-writer rule hold without anyone having to remember it.

3. Project structure

app/ws/
├── auth.py         handshake authentication — the only place a socket is rejected
├── registry.py     connections, rooms, the per-connection send queue
├── protocol.py     the message envelope both sides agree on
└── routes.py       the endpoint: accept, receive loop, finally-disconnect

One rule: the registry is the only thing holding a socket object. A handler that captures a socket and outlives the connection sends into a closed transport, and the resulting error surfaces somewhere unrelated. Everything else refers to a connection by id.

4. Reference implementation

# app/ws/auth.py
from fastapi import WebSocket, status

SUBPROTOCOL_PREFIX = "bearer."


async def authenticate(ws: WebSocket) -> User | None:
    """Authenticate during the handshake, before accept().

    A browser cannot set an Authorization header on a WebSocket, so the token has
    to travel another way. The subprotocol header is the least bad option: unlike a
    query string it is not written to access logs, not kept in browser history, and
    not leaked in a Referer. Cookies work too, and bring CSRF along with them.
    """
    offered = ws.headers.get("sec-websocket-protocol", "")
    token = next(
        (p.strip()[len(SUBPROTOCOL_PREFIX):] for p in offered.split(",")
         if p.strip().startswith(SUBPROTOCOL_PREFIX)),
        None,
    )
    if token is None:
        await ws.close(code=status.WS_1008_POLICY_VIOLATION)
        return None
    try:
        claims = decode_access_token(token)
    except Exception:
        # Reject before accept: an unauthenticated socket is never registered, so
        # there is no window in which it could be broadcast to.
        await ws.close(code=status.WS_1008_POLICY_VIOLATION)
        return None
    return await load_user(int(claims["sub"]))

# app/ws/registry.py
import asyncio
from dataclasses import dataclass, field

SEND_QUEUE_MAX = 64          # messages, not bytes — tune against your message size


@dataclass
class Connection:
    id: str
    user_id: int
    socket: WebSocket
    # One queue, one writer task. Two tasks calling send() on one socket interleave
    # frames; most implementations raise, and the ones that do not corrupt the stream.
    outbox: asyncio.Queue = field(default_factory=lambda: asyncio.Queue(SEND_QUEUE_MAX))
    rooms: set[str] = field(default_factory=set)


class Registry:
    def __init__(self) -> None:
        self._conns: dict[str, Connection] = {}
        self._rooms: dict[str, set[str]] = {}

    async def writer(self, conn: Connection) -> None:
        while True:
            message = await conn.outbox.get()
            if message is None:
                return
            await conn.socket.send_text(message)     # the only send() in the codebase

    def broadcast(self, room: str, message: str) -> None:
        """Not a coroutine, deliberately.

        Awaiting each send makes the broadcast run at the speed of the slowest
        client — usually one that has already stopped receiving. Instead each
        connection gets the message in its own bounded queue, and a client that
        cannot drain its queue is disconnected rather than allowed to slow the room.
        """
        for cid in list(self._rooms.get(room, ())):
            conn = self._conns.get(cid)
            if conn is None:
                continue
            try:
                conn.outbox.put_nowait(message)
            except asyncio.QueueFull:
                # A full queue means this client is not keeping up. Dropping the
                # message would leave it silently out of sync, which is worse than
                # a disconnect it can detect and recover from by reconnecting.
                asyncio.create_task(self.disconnect(cid, code=1013))   # try again later

    async def disconnect(self, cid: str, code: int = 1000) -> None:
        conn = self._conns.pop(cid, None)
        if conn is None:
            return                                   # already gone; idempotent on purpose
        for room in conn.rooms:
            self._rooms.get(room, set()).discard(cid)
        await conn.outbox.put(None)
        with contextlib.suppress(Exception):
            await conn.socket.close(code=code)

# app/ws/routes.py
@router.websocket("/ws")
async def websocket_endpoint(ws: WebSocket):
    user = await authenticate(ws)
    if user is None:
        return

    # Echo the subprotocol back, or the browser rejects the handshake it offered.
    await ws.accept(subprotocol=ws.headers.get("sec-websocket-protocol", "").split(",")[0].strip())
    conn = registry.add(user, ws)
    writer = asyncio.create_task(registry.writer(conn))
    beat = asyncio.create_task(heartbeat(conn))

    try:
        while True:
            raw = await ws.receive_text()
            await handle(conn, raw)
    except WebSocketDisconnect:
        pass
    finally:
        # finally, always. Cleaning up only on the WebSocketDisconnect path leaks a
        # registry entry every time a handler raises for any other reason — and the
        # leak is invisible until a broadcast sends into a dead socket.
        beat.cancel()
        writer.cancel()
        await registry.disconnect(conn.id)


async def heartbeat(conn: Connection) -> None:
    # TCP does not tell you the client is gone. A laptop that closed its lid sends
    # nothing and the socket stays open for as long as the network lets it. The
    # ping/pong deadline is the only thing that finds this.
    while True:
        await asyncio.sleep(HEARTBEAT_SECONDS)       # must be under the proxy's idle timeout
        conn.last_ping = time.monotonic()
        await conn.outbox.put(PING)
        if time.monotonic() - conn.last_pong > HEARTBEAT_SECONDS * 2.5:
            await registry.disconnect(conn.id, code=1001)
            return

5. Golden-standard rules

Rule Why
Forbidden: accepting the connection before authenticating it An accepted socket is a registered socket, and there is then a window in which it receives broadcasts it should never see.
Forbidden: the token in the query string It lands in access logs, browser history and referrer headers, all of which outlive the session. Use the subprotocol header or a cookie.
Forbidden: two tasks sending on one socket Frames interleave. Most implementations raise; the ones that do not corrupt the stream. One writer per connection, fed by a queue.
Forbidden: an unbounded send queue It converts a slow client into unbounded memory growth, and the process dies for a reason that looks nothing like its cause.
Forbidden: awaiting each send inside a broadcast The room then runs at the speed of its worst connection, which is usually one that has already stopped receiving.
Cleanup happens in a finally Removing the connection only on the disconnect exception leaks an entry every time a handler raises for another reason.
A client that cannot drain its queue is disconnected Dropping messages instead leaves it silently out of sync, which is harder to detect than a reconnect.
Heartbeat interval is below the proxy's idle timeout Otherwise the proxy closes connections that both ends believe are healthy, on a schedule nobody connects to the cause.
A missed heartbeat deadline closes the connection TCP will not report a client that vanished. This is the only detection you have.
Every message carries a type and a version A socket outlives a deploy. Both ends must be able to skip a message shape they do not understand.
Shutdown sends a close frame before exiting Otherwise every client reconnects on a timeout, and a rolling deploy becomes a reconnect storm.
Disconnect is idempotent It is called from the receive loop, the writer, the heartbeat and shutdown, sometimes at once.

6. Data contracts

{"v": 1, "type": "order.updated", "room": "orders:42", "id": "01J...", "data": {}}

v and type are what let a client survive a deploy: a message type it does not know is skipped rather than fatal. id is what makes reconnection recoverable — without a monotonic identifier, a client that reconnects cannot ask for what it missed, and "did I miss anything" has no answer.

The close code is part of the contract too. 1000 is a normal close and the client should not retry immediately; 1008 is a policy violation and retrying with the same token is pointless; 1013 means try again later. A client that treats every close identically reconnects in a tight loop against a server that just rejected it.

7. Build order

  1. Accept, echo, disconnect — with cleanup in a finally from the first version, because retrofitting it means auditing every exit path.
  2. Handshake authentication, with a test that a bad token is rejected before accept.
  3. Registry and rooms, with a test that a disconnect removes membership.
  4. The per-connection writer and queue, then a test asserting two concurrent broadcasts do not interleave on one socket.
  5. The slow-client policy: a test with a client that never reads, asserting it is disconnected and the others still receive.
  6. Heartbeat, with a test that a client which stops responding is closed within the deadline.
  7. Graceful shutdown sending close frames, and the message envelope with its version.

Step 5 before step 6 because the slow client is the failure that takes down the room, while the missed heartbeat only leaks one entry.

10. Failure modes

Symptom Cause Fix
Users appear online who left hours ago The client vanished without a close frame and TCP never reported it Heartbeat with a deadline that closes the connection
A whole room stops receiving updates whenever one user is on a bad network The broadcast awaits each send, so it runs at the slowest client's speed Per-connection queues; disconnect the client that cannot keep up
Memory grows steadily with connection count and never returns Unbounded send queues, or registry entries never removed Bound the queue; clean up in a finally
RuntimeError about concurrent sends, under load only Two tasks called send on the same socket One writer task per connection, fed by a queue
Connections drop at a suspiciously regular interval The proxy's idle timeout is shorter than the heartbeat Heartbeat more often than the proxy's timeout
It works locally and the upgrade fails in production The proxy was not configured to forward the upgrade headers Configure it; test through the proxy, not around it
Every deploy causes a reconnect storm that overloads the new instances Shutdown killed sockets without close frames, so every client retried on its own timeout Send close frames on shutdown; have clients back off with jitter
A client reconnects in a tight loop against a rejecting server It treats every close code the same Distinguish the codes: a policy violation must not be retried immediately
After a deploy, some clients disconnect on an unrecognised message The message shape changed without a version, and old clients treat the unknown as fatal Version the envelope; skip unknown types
A user in one room receives another room's messages Membership was not cleaned up on disconnect, and the id was reused Make disconnect idempotent and remove from every room it holds

11. Definition of done

  • A connection with a missing or invalid token is closed before accept(), covered by a test
  • The token never appears in a query string, verified by inspecting the client's connect call
  • Disconnecting removes the connection from the registry and from every room, covered by a test that inspects both
  • A handler raising an unexpected exception still removes the connection, covered by a test
  • Exactly one task sends on each socket, verified by a test that triggers two concurrent broadcasts and asserts no interleaving error
  • A client that never reads is disconnected once its queue fills, and other clients in the room still receive — covered by one test asserting both
  • A client that stops answering heartbeats is closed within the deadline, covered by a test
  • The heartbeat interval is shorter than the proxy's idle timeout, with that timeout named in a comment
  • Shutdown sends a close frame to every connection before the process exits, covered by a test
  • Every message carries a version and a type, and an unknown type is ignored rather than fatal, covered by a test
  • Calling disconnect twice for the same connection is harmless, covered by a test
  • Memory per connection is measured and recorded, with a figure for the intended maximum connection count
