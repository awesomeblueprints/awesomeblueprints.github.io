WebSocket Broadcast with Redis Pub/Sub

WebSocket broadcast with Redis pub/sub: delivering messages across replicas, subscriber-loop health, delivery lag and duplicate handling.

medium3–5 daysVerified 2026-08-19
RedisStreaming
Read it on GitHub ↗ Back to the catalogue

Fanning a message to every replica so that two users in one room see each other even when they landed on different processes — with an honest account of what Pub/Sub drops, and a separate path for the history a reconnecting client needs.

Complexity: medium-high · Typical build: 3–5 days · Verified: 2026-08-19 (re-check after ~90 days)

Examples in: Python, with Redis and FastAPI. The architecture is language-agnostic: sections 5, 10 and 11 hold wherever you build this. Section 4 is illustrative — if your project is in another language, your agent translates the idioms rather than importing them, and nothing is lost. The equivalents are the Socket.IO Redis adapter in Node, Phoenix PubSub in Elixir, and NATS or a Postgres LISTEN/NOTIFY bus where Redis is not already present.

Use when: a real-time feature already works on one process and now has to run on more than one — because it was scaled, or because a rolling deploy briefly runs two versions at once. That second case surprises people: you do not need to have chosen horizontal scaling to hit this.

Not for: a single-process deployment that will stay single-process, where an in-memory registry is correct and this is a service, a failure mode and a delivery guarantee you did not need. Also not a message queue: nothing here is durable, and using it for work that must not be lost is a category error §1 exists to prevent.

Confirm whether Streams are available, because §5 sends anything requiring delivery guarantees there rather than to Pub/Sub. Step 2 — Read the project, then audit what already exists. Find the existing connection registry and every place that broadcasts — each becomes a publish. Find whether any feature currently assumes one process: presence counts, "who is typing", per-room sequence numbers, in-memory rate limits. Those are the things that break silently at the second replica, and listing them is most of the value of this audit. Determine whether messages missed during a reconnect must be recoverable; the answer decides whether Pub/Sub alone is enough. Then audit §11 item by item, each marked already true, partly true or absent, with the file that decides it, reported before anything is proposed.

1. Why the in-process registry stops at replica two

A connection registry in a process's memory is correct and complete — for that process. The moment there are two, every user is connected to one of them and invisible to the other.

One process A bus between processes
A broadcast reaches everyone, because everyone is here A broadcast is published once and every instance delivers to its own connections
"Three people online" is a length of a list It is a count that has to be aggregated across instances, with a way to expire the dead ones
A message published while a client reconnects is simply not sent The gap is real and visible, and needs a history the client can ask for
Nothing to configure and nothing to fail A dependency that can be down, and a decision about what happens then

Pub/Sub is fire-and-forget, and this is the fact the whole design has to respect. A subscriber that is disconnected does not have messages queued for it; they are dropped and never replayed. During the gap between a subscriber dropping and re-subscribing, everything published is permanently lost — for that instance, and therefore for every client on it.

That is acceptable for "someone is typing" and unacceptable for "your order shipped". So the design is two paths, not one: Pub/Sub for the live fan-out, and a durable record for anything a client must eventually see. Trying to make Pub/Sub reliable is the mistake this section exists to prevent — the tool for at-least-once delivery with replay is Streams with consumer groups, and it is a different tool for a different guarantee.

The rule the diagram encodes: the durable write happens before the publish. Publishing first and persisting after leaves a window where a client saw a message that no history contains — so a reconnect appears to lose it, and the client's own view contradicts the server's.

3. Project structure

app/ws/
├── registry.py     unchanged: local connections and rooms
├── bus.py          publish, the subscriber loop, and the instance id
├── history.py      recent messages per room, bounded and expiring
└── presence.py     who is in a room, aggregated across instances

One rule: nothing outside bus.py publishes or subscribes. A second subscriber loop somewhere else means messages are delivered twice locally, and the duplicate looks like a client bug for a long time before anyone suspects the server.

4. Reference implementation

# app/ws/bus.py
import asyncio, json, uuid
import redis.asyncio as redis

INSTANCE_ID = uuid.uuid4().hex      # per process, not per host: two workers on one
                                    # machine are two instances for every purpose here


class Bus:
    def __init__(self, url: str, registry: Registry) -> None:
        # Two connections, deliberately. A connection in subscribe mode cannot run
        # ordinary commands in most clients, and sharing one produces errors that
        # read like a protocol bug rather than a usage mistake.
        self._pub = redis.from_url(url)
        self._sub = redis.from_url(url)
        self._registry = registry

    async def publish(self, room: str, message: dict) -> None:
        message["origin"] = INSTANCE_ID
        # Persist first. Publishing first leaves a window where a connected client
        # has seen something the history does not contain — so after a reconnect the
        # message vanishes, and the client's view contradicts the server's.
        await history.append(room, message)
        await self._pub.publish(f"room:{room}", json.dumps(message))

    async def run(self) -> None:
        """The subscriber loop. Reconnects forever, because it must."""
        while True:
            try:
                pubsub = self._sub.pubsub(ignore_subscribe_messages=True)
                await pubsub.psubscribe("room:*")
                async for raw in pubsub.listen():
                    message = json.loads(raw["data"])
                    room = raw["channel"].decode().removeprefix("room:")
                    # Delivered to this instance's connections only. The publisher's
                    # own instance receives its own message too, which is what keeps
                    # the delivery path identical everywhere — one code path, tested
                    # once, rather than a local shortcut that drifts.
                    self._registry.deliver_local(room, message)
            except redis.ConnectionError:
                # Messages published during this gap are gone: pub/sub queues nothing
                # for a disconnected subscriber. That is why anything a client must
                # eventually see is in history, and why clients ask for it on reconnect.
                await asyncio.sleep(RECONNECT_BACKOFF)

# app/ws/history.py
async def append(room: str, message: dict) -> None:
    key = f"history:{room}"
    async with redis_client.pipeline(transaction=True) as pipe:
        # A capped list: the last N messages, expiring if the room goes quiet.
        # Unbounded history in a cache is a memory leak with a long fuse.
        pipe.lpush(key, json.dumps(message))
        pipe.ltrim(key, 0, HISTORY_MAX - 1)
        pipe.expire(key, HISTORY_TTL)
        await pipe.execute()


async def since(room: str, last_id: str | None) -> list[dict]:
    """What a reconnecting client missed.

    Bounded on purpose: if the client was away longer than the history, it is told
    so and reloads from the API instead of silently receiving a partial view. A gap
    the client cannot detect is worse than one it can.
    """
    raw = await redis_client.lrange(f"history:{room}", 0, HISTORY_MAX - 1)
    messages = [json.loads(m) for m in reversed(raw)]
    if last_id is None:
        return messages
    for i, m in enumerate(messages):
        if m["id"] == last_id:
            return messages[i + 1:]
    raise HistoryGap(room)          # the client must do a full reload

# app/ws/presence.py
async def touch(room: str, user_id: int) -> None:
    # A key per user per room, with a TTL longer than the refresh interval. This is
    # what makes presence self-healing: an instance that is killed refreshes
    # nothing, and its users expire on their own. A set that is cleaned up on
    # disconnect leaks a member every time a process dies without warning — which
    # is what a deploy, an OOM kill and a crash all look like.
    await redis_client.set(f"presence:{room}:{user_id}", INSTANCE_ID, ex=PRESENCE_TTL)


async def members(room: str) -> set[int]:
    # SCAN, never KEYS: KEYS walks the entire keyspace and blocks the server, which
    # is single-threaded — so one presence query stalls every other client.
    return {int(k.decode().rsplit(":", 1)[1])
            async for k in redis_client.scan_iter(f"presence:{room}:*", count=100)}

5. Golden-standard rules

Rule Why
Forbidden: using Pub/Sub for anything that must not be lost A disconnected subscriber has nothing queued for it and messages published during the gap are gone permanently. Use a durable structure for delivery guarantees.
Forbidden: publishing before the durable write It leaves a window where a client saw a message no history contains, so a reconnect appears to lose it.
Forbidden: sharing one connection between subscribe mode and ordinary commands Most clients cannot, and the resulting errors read like a protocol bug rather than a usage mistake.
Forbidden: KEYS for presence or room enumeration The server is single-threaded; a full keyspace walk stalls every other client. Use incremental scanning.
Forbidden: unbounded history A cache with no cap is a memory leak with a long fuse, and it fails when the system is busiest.
Presence is expiring keys, not a maintained set A set cleaned up on disconnect leaks a member on every crash, OOM kill and deploy. Expiry heals without anyone doing anything.
The subscriber loop reconnects forever, with backoff Its death is silent — the instance keeps serving and simply stops delivering, which no health check notices.
An instance delivers its own published messages through the bus One delivery path, tested once. A local shortcut is a second path that drifts from the first.
Every message carries an origin instance and an id Without them, duplicates cannot be detected and a client cannot say what it already has.
Messages carry a room-scoped ordering identifier "What did I miss" has no answer otherwise, and the reconnect story falls apart.
A history gap is reported, not hidden A client silently missing messages is a bug users report as data loss. Tell it to reload.
Redis being down degrades cross-instance delivery only Local delivery should keep working. A real-time feature that takes the whole application down with its bus is a worse outcome than a temporarily narrower broadcast.

6. Data contracts

{"v": 1, "type": "chat.message", "room": "orders:42",
 "id": "01J8Z...", "origin": "9f3a...", "ts": 1755600000, "data": {}}

Three guarantees, and their limits, stated so nobody assumes more:

live fan-out    best effort. Published once, delivered to instances currently
                subscribed. Nothing is queued for one that is not.
history         last N messages per room, expiring. A client away longer than N
                is told there is a gap rather than given a partial view.
presence        eventually correct within one TTL. Never exact — a user who
                vanished is present until their key expires.

Presence being approximate is a property, not a defect. Making it exact requires either sticky sessions or a coordinated registry, and both cost more than the feature is worth for a number displayed next to a room name.

7. Build order

  1. Two instances, one bus, one room. Prove a message sent to instance A reaches a client on instance B. Everything else is refinement of this.
  2. The subscriber loop with reconnection, then kill Redis while a client is connected and confirm the instance recovers and resumes delivering.
  3. Publish through the bus everywhere, including for the publisher's own connections, and delete any local shortcut.
  4. Message ids and the origin field.
  5. History, capped and expiring, with the gap signal.
  6. Reconnect flow: client reconnects with its last id, receives what it missed, or is told to reload.
  7. Presence with expiring keys, and a test that killing an instance clears its users within one TTL.

Step 2 immediately after step 1 because the subscriber loop dying is the failure mode with no symptom: the instance keeps answering health checks and simply stops delivering.

10. Failure modes

Symptom Cause Fix
Two users in one room cannot see each other after scaling up The registry is per process and nothing crosses instances Publish to the bus; deliver locally on receipt
One instance stops delivering while its health check stays green The subscriber loop died and nothing restarted it Reconnect forever with backoff; monitor subscription state, not process health
Messages sent during a brief Redis outage are gone forever Pub/Sub queues nothing for a disconnected subscriber Expected — that is why history exists; anything that must not be lost goes to a durable structure
A client reconnects and silently misses messages History was shorter than the gap and the shortfall was not reported Detect the gap and tell the client to reload
Clients see every message twice A second subscriber loop exists, or the publisher also delivers locally One loop, one path; everything goes through the bus
Presence counts drift upwards over days Presence is a set cleaned up on disconnect, and processes sometimes die without one Expiring keys refreshed while connected
Redis CPU spikes and every client stalls Presence or rooms enumerated with KEYS Incremental scanning
Redis memory grows until it evicts things you needed History has no cap or no expiry Cap the list and set a TTL
A rolling deploy briefly splits a room in two Old and new instances are both running — the same problem as scaling, arriving unannounced This blueprint; it applies even to a deployment you consider single-instance
The whole API goes down when Redis does The bus is on the request path and its failure is not contained Degrade to local-only delivery; keep the application serving
A client receives its own message twice It applied the message optimistically and again on delivery Use the message id to reconcile on the client

11. Definition of done

  • With two instances running, a message from a client on one reaches a client on the other, covered by a test that runs both
  • Killing Redis and restarting it leaves both instances delivering again without a restart, covered by a test
  • The subscriber loop's subscription state is exported as a metric and alerted on, not inferred from process health
  • Every message carries an id, an origin instance and a version, asserted on a received message
  • A message is present in history before it is published, verified by a test that inspects both after a publish
  • History is capped and expires, verified by publishing beyond the cap and asserting the oldest is gone
  • A client reconnecting with its last id receives exactly what it missed, covered by a test
  • A client away longer than the history receives an explicit gap signal rather than a partial list
  • Presence for an instance that is killed clears within one TTL without any cleanup running, covered by a test
  • No code path uses KEYS, checked by grep in CI
  • With Redis unavailable, clients on the same instance still exchange messages and the API still serves, covered by a test
  • Only bus.py publishes or subscribes, checked by grep in CI
