Chunking and Embeddings for Retrieval

Chunking and embedding documents for retrieval: chunk size, overlap, metadata and re-embedding without rebuilding the whole index.

medium3–5 daysVerified 2026-08-19
Vector searchRetrievalEvals
Read it on GitHub ↗ Back to the catalogue

What happens to a document before it reaches any vector store: split so that a chunk still means something on its own, enriched so it can be found, embedded in batches with a cache, and updated when the document changes without paying to re-embed the corpus.

Complexity: medium · Typical build: 3–5 days · Verified: 2026-08-19 (re-check after ~90 days)

Examples in: Python. The architecture is language-agnostic: sections 5, 10 and 11 hold wherever you build this. Section 4 is illustrative — if your project is in another language, your agent translates the idioms rather than importing them, and nothing is lost. Nothing here is tied to a particular store: this is the step before the store, and the same pipeline feeds any of them.

Use when: retrieval quality is the problem and the search itself looks correct — the right index, the right query, and answers built from fragments that do not say enough to answer with.

Not for: documents that are already short and self-contained — a product record, a support macro, a FAQ entry. Splitting those makes them worse. Also not for parsing: extracting clean text from a scanned PDF, a spreadsheet or a slide deck is a separate problem, and this pipeline assumes text that is already correct. Garbage in is chunked faithfully.

1. Where retrieval quality is actually decided

A perfect index over bad chunks returns bad chunks perfectly. This is the step where most of the quality is won or lost, and it is the one most often treated as a utility function.

Splitting by a character count Splitting for what a chunk has to do
A chunk starts mid-sentence and ends mid-table; retrieval returns a fragment that answers nothing Boundaries follow the document's own structure
The chunk says "it costs €40" with no indication of what "it" is Each chunk carries the context that makes it interpretable alone
The whole corpus is re-embedded whenever anything changes Only changed chunks are embedded; the rest are cached by content
Chunk size was picked from a blog post Chunk size was measured on this corpus against real questions

The second row is the failure that survives every other fix. A chunk is retrieved alone and read alone, so a passage whose subject is three paragraphs above is useless the moment it is separated from them — the retriever finds it, the model reads it, and neither can tell what "it" refers to. Overlap helps a little and mostly wastes tokens. What works is making each chunk self-describing: the document title, the section heading, and where useful a sentence of context, added before embedding. That is a small, cheap change and it does more for retrieval quality than most index tuning.

The third row is what makes the whole thing affordable to iterate on. Embedding is charged per token and a full re-embed of a real corpus is not a decision you want to make casually — which is exactly why people stop tuning chunk size. Key the cache on a hash of the chunk text. Editing one paragraph then re-embeds a handful of chunks rather than all of them, and tuning becomes something you can afford to do more than once.

There is a related idea worth knowing about, because it addresses the same problem from the other end: index small chunks for precise matching, but return their larger parent section to the model. It is more machinery — two granularities to store and keep in step — and it is usually the next thing to try when self-describing chunks are not enough, rather than the first.

The rule the diagram encodes: the manifest is what makes an update an update. Without a record of which chunks a document produced last time, re-ingesting an edited document adds the new chunks and leaves the old ones behind — so the corpus grows, and retrieval starts returning text that is no longer in the document.

3. Project structure

app/ingest/
├── normalise.py   text in, clean text out; boilerplate removed
├── split.py       the splitting strategy, and only this file knows it
├── enrich.py      title, heading and context added before embedding
├── embed.py       cache, batching, provider limits, retries
├── manifest.py    what each document currently contributes
└── pipeline.py    the sequence, rerunnable end to end

One rule: chunk text is stored, not only its vector. The text that was embedded — after enrichment — is kept alongside the vector. Without it you cannot explain a retrieval, cannot re-embed with a new model without re-running the whole pipeline, and cannot tell whether a bad result came from bad chunking or bad search.

4. Reference implementation

# app/ingest/split.py
def split(text: str, target_tokens: int = 400, overlap_tokens: int = 50) -> list[Chunk]:
    """Split along the document's own structure, then only by size if forced.

    Character counts are a proxy for what the model actually sees. Measure in
    tokens: the same character budget holds very different amounts of English,
    Japanese and source code, and a limit set in characters is wrong for two of
    the three.
    """
    sections = split_on_headings(text)
    chunks: list[Chunk] = []

    for section in sections:
        if count_tokens(section.body) <= target_tokens:
            chunks.append(Chunk(text=section.body, heading=section.heading))
            continue
        # Only now fall back to splitting by size, and prefer paragraph
        # boundaries. A table or a code block split down the middle produces two
        # chunks that are each unreadable, and retrieval cannot repair that.
        for piece in split_on_paragraphs(section.body, target_tokens, overlap_tokens,
                                         keep_together=(TABLE, CODE_BLOCK)):
            chunks.append(Chunk(text=piece, heading=section.heading))
    return chunks

# app/ingest/enrich.py
def enrich(chunk: Chunk, doc: Document) -> str:
    """Make the chunk interpretable on its own, before it is embedded.

    This is the highest-value few lines in the pipeline. A chunk is retrieved
    alone and read alone: a passage saying "it costs €40" is useless when its
    subject was three paragraphs above. Prefixing the title and heading is cheap,
    improves both the embedding and what the model sees, and does more than most
    index tuning.
    """
    header = f"{doc.title}"
    if chunk.heading:
        header += f" — {chunk.heading}"
    return f"{header}\n\n{chunk.text}"

# app/ingest/embed.py
import hashlib

MAX_INPUTS_PER_REQUEST = 96          # verify both against the provider: they are
MAX_TOKENS_PER_REQUEST = 100_000     # separate limits and both are enforced


def content_hash(text: str, model: str) -> str:
    # The model is part of the key. Without it, changing model silently serves
    # vectors from the old one out of the cache, and every search is subtly wrong
    # with nothing to indicate it.
    return hashlib.sha256(f"{model}\x00{text}".encode()).hexdigest()


async def embed_all(texts: list[str], model: str) -> list[list[float]]:
    keys = [content_hash(t, model) for t in texts]
    cached = await cache.get_many(keys)
    todo = [(i, t) for i, (t, k) in enumerate(zip(texts, keys)) if k not in cached]

    for batch in _batches(todo):
        # Both limits, not just the count. A batch of ninety-six short strings is
        # fine and ninety-six long ones is rejected — and a provider that rejects
        # the whole request rather than part of it turns one oversized chunk into
        # a failed batch.
        vectors = await _with_retry(provider.embed, [t for _, t in batch], model=model)
        for (i, text), vector in zip(batch, vectors):
            cached[keys[i]] = vector
            await cache.set(keys[i], vector)

    return [cached[k] for k in keys]


async def _with_retry(fn, *args, **kwargs):
    # Rate limits are normal operation at this volume, not an exception. Respect
    # the provider's own retry hint when it gives one; back off with jitter when
    # it does not, because synchronised retries from several workers reproduce
    # exactly the load that caused the limit.
    for attempt in range(6):
        try:
            return await fn(*args, **kwargs)
        except RateLimited as exc:
            await asyncio.sleep(exc.retry_after or (2 ** attempt) + random.random())
    raise

# app/ingest/pipeline.py
async def ingest_document(doc: Document) -> IngestResult:
    chunks = split(normalise(doc.text))
    texts = [enrich(c, doc) for c in chunks]
    ids = [chunk_id(doc.id, i) for i in range(len(chunks))]
    vectors = await embed_all(texts, model=settings.embedding_model)

    await store.upsert(ids=ids, texts=texts, vectors=vectors,
                       metadata=[{"document_id": doc.id, "chunk_index": i,
                                  "heading": c.heading, "title": doc.title,
                                  "embedding_model": settings.embedding_model}
                                 for i, c in enumerate(chunks)])

    # Delete what this document used to produce and no longer does. Skipping this
    # is the most common ingestion bug: an edited document leaves its old chunks
    # in place, so the corpus grows and retrieval returns text that is no longer
    # in the document — with nothing anywhere reporting it.
    previous = await manifest.get(doc.id)
    for stale in set(previous) - set(ids):
        await store.delete(stale)
    await manifest.set(doc.id, ids)

    return IngestResult(chunks=len(chunks), embedded=len(chunks) - cache_hits())

5. Golden-standard rules

Rule Why
Forbidden: splitting without looking at real documents first The strategy is decided by what is in them. Skipping this is why pipelines split mid-table.
Forbidden: measuring chunk size in characters The same character budget holds very different amounts of English, Japanese and code. Measure in the model's tokens.
Forbidden: embedding a chunk that cannot be understood alone It is retrieved alone and read alone. Prefixing the title and heading is the cheapest large improvement available.
Forbidden: re-embedding unchanged text Embedding is charged per token, and the cost of a full re-embed is what stops people from ever tuning chunk size.
Forbidden: a cache key that omits the model A model change then serves old vectors from the cache and every search is subtly wrong.
Forbidden: re-ingesting without removing chunks the document no longer produces The corpus grows and retrieval returns text that is no longer in the document.
Structure is respected before size A table or code block split in half yields two unreadable chunks, and retrieval cannot repair that.
Batches respect both the input count and the token limit They are separate limits, both enforced, and a rejected batch usually fails whole.
Rate limits are handled as normal operation At corpus volume they are expected. Backoff needs jitter, or several workers retry in unison and recreate the load.
The enriched text is stored, not only the vector Without it you cannot explain a retrieval or re-embed with a new model without re-running everything.
Chunk size is chosen by measurement on this corpus Sizes from articles are properties of someone else's documents and someone else's questions.
Ingestion is rerunnable and idempotent It will be interrupted. A run that cannot be repeated safely turns a failure into a manual repair.

6. Data contracts

Chunk(
    id="<document_id>:<index>",     # derived, so re-ingestion replaces
    text="<title> — <heading>\n\n<body>",   # what was embedded, stored as such
    metadata={"document_id", "chunk_index", "heading", "title", "embedding_model"},
)
Manifest = {document_id: [chunk_id, ...]}   # what this document contributes now

The manifest is the piece most pipelines lack, and its absence is invisible until someone notices the corpus is larger than the documents. It answers one question — which chunks does this document currently own — and that question is the whole of correct updating.

Storing the enriched text rather than the raw body matters more than it looks: it is what was embedded, so it is the only text that explains a retrieval. Storing the raw body instead means the vector and the text you can show a developer come from different strings.

7. Build order

  1. Read twenty real documents and write down what is in them. Headings, tables, code, repeated boilerplate. Everything below follows from this and nothing substitutes for it.
  2. Split and print — no embedding. Read fifty chunks. If they do not stand alone as text, no amount of retrieval work will fix it, and this is the cheapest moment to discover that.
  3. Enrichment, then read the same fifty again.
  4. The content-hash cache, before any tuning. It is what makes step 5 affordable to run more than once.
  5. Measure chunk size against real questions — two or three sizes, the same question set, recall compared. Choose from the numbers.
  6. Batching with both provider limits and retries, then a full corpus run.
  7. The manifest and deletion, with a test that editing a document to have fewer chunks removes the extras.

Step 4 before step 5 is the point of the ordering. Without the cache, each tuning run costs a full re-embed, so the first choice becomes the permanent one — and the first choice is a guess.

10. Failure modes

Symptom Cause Fix
Retrieved passages are fragments that answer nothing Split by size with no regard for structure Split on headings and paragraphs first; fall back to size only when forced
A chunk is retrieved and the model cannot tell what it refers to The chunk is not interpretable alone Prefix the title and heading before embedding
Search returns text that is no longer in the document Re-ingestion added new chunks and left the old ones Keep a manifest per document and delete what disappeared
Nobody tunes chunk size because it is too expensive Every run re-embeds the corpus Cache by content hash and model
Search became subtly wrong after a model change The cache key omitted the model, so old vectors were served Include the model in the key
Batches fail for large documents and succeed for small ones The token limit was exceeded although the input count was fine Respect both limits
A corpus run dies partway through with rate-limit errors Retries without jitter, or none at all Respect the provider's hint; back off with jitter
Chunk sizes work for English documents and badly for others Size measured in characters Measure in the model's tokens
A retrieval cannot be explained after the fact Only the vector was stored, or the raw text rather than the enriched text Store what was embedded
An interrupted ingestion left the corpus in an unclear state Ingestion is not idempotent Derived ids and upsert; rerunning is the repair
Recall improved on the evaluation and users disagree The evaluation questions all match one document type present in the sample Draw the question set from real usage

11. Definition of done

  • Fifty chunks from real documents were read and none is uninterpretable on its own
  • No chunk splits a table or a code block, verified by a test over the sample corpus
  • Chunk size is measured in the model's tokens, not characters, verified in the splitter's tests
  • Every chunk is enriched with its document title and section heading before embedding, and the enriched text is what is stored
  • Re-ingesting an unchanged corpus performs zero embedding calls, covered by a test
  • The cache key includes the embedding model, and a test asserts a model change misses the cache
  • Editing one paragraph re-embeds only the affected chunks, covered by a test that counts calls
  • Editing a document so it produces fewer chunks removes the extras, covered by a test
  • Batching respects both the input-count and the token limits, covered by a test with deliberately long inputs
  • Rate limits are retried with jitter and the provider's hint is honoured, covered by a test
  • Chunk size was chosen by comparing recall across at least two sizes on a committed question set, and the numbers are recorded
  • Ingestion can be interrupted and rerun with no manual repair, demonstrated once
