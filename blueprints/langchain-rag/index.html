LangChain RAG Retrieval Chain

A LangChain RAG retrieval chain: retriever, prompt and parser wired for grounded answers, including the follow-up question most chains fail.

Read it on GitHub ↗ Back to the catalogue

A retrieval chain over a vector store you already have: the follow-up question rewritten before it is embedded, retrieved passages assembled with citations the answer can be checked against, and an explicit answer for "nothing relevant was found" instead of an invented one.

Complexity: medium · Typical build: 2–4 days · Verified: 2026-08-19 (re-check after ~90 days)

Examples in: Python, with LangChain. The architecture is language-agnostic: sections 5, 10 and 11 hold wherever you build this. Section 4 is illustrative — if your project is in another language, your agent translates the idioms rather than importing them, and nothing is lost. The rewrite, assembly, grounding and empty-result concerns are properties of retrieval, not of any framework — they apply equally to a chain you write by hand.

Use when: documents are already indexed and searchable, and what is missing is the path from a user's question to a grounded answer — including the second question, which is where most retrieval chains fall over.

Not for: building the index. Chunking, embedding and ingestion decide most of the answer quality and are a separate problem; a retrieval chain over a badly chunked corpus retrieves fragments correctly and answers wrongly. Also not for a corpus small enough to fit in the context window — retrieval there adds a failure mode and removes nothing.

1. Where retrieval chains actually fail

Composition is not the hard part here — the pieces fit together in an afternoon. The failures are all in the retriever and the prompt.

The tutorial retrieval chain This one
Embeds the user's message as typed Rewrites it into a standalone question first, because "and the second one?" retrieves nothing
Fetches a fixed number of chunks and pastes them in Assembles a bounded context with identifiers the answer can cite
Answers from whatever came back Says it does not know when nothing relevant came back
Returns prose Returns prose plus the sources it used, checkable

The first row is the one that separates a demo from a product. The demo is tested with one question at a time. In use, the second message is "and for the previous quarter?" — five words with no nouns. Embedded as typed it retrieves nothing useful, so the model answers from the first question's context and is confidently wrong about the second. The rewrite step is not an optimisation; it is what makes a conversation possible at all.

The third row is the one that produces the incident. A vector search always returns its top-k — similarity has no threshold and no concept of "nothing here". Ask about a topic the corpus does not cover and you get the k least dissimilar passages, which are irrelevant, and a model handed irrelevant context will generally use it. The absence of an answer must be a decision the chain makes, not one you hope the model reaches.

The rule the diagram encodes: there are two arrows into "does not know", and neither is the model's choice. One fires when nothing clears the relevance threshold; the other when the answer cites a passage that was never retrieved. Both are decisions the chain makes about the model's output rather than instructions given to it.

3. Project structure

app/rag/
├── rewrite.py      history plus question to a standalone question
├── retrieve.py     the retriever, its filters and the relevance gate
├── assemble.py     passages to a bounded, labelled context
├── chain.py        the composition
└── prompts/
    ├── rewrite.v2.md
    └── answer.v4.md

One rule: the retrieved passages are returned alongside the answer, always. Not only when a citation feature is switched on. It costs nothing, it is what makes an evaluation possible, and it is the only way to tell a grounded answer from a fluent one after the fact.

4. Reference implementation

# app/rag/rewrite.py
REWRITE = ChatPromptTemplate.from_messages([
    ("system", Path("app/rag/prompts/rewrite.v2.md").read_text()),
    ("human", "Conversation:\n{history}\n\nLatest message: {question}"),
])

# A small, fast model. This call happens on every turn and its output is one
# sentence; paying frontier prices for it doubles cost and latency for no gain.
rewrite_chain = REWRITE | fast_model | StrOutputParser()


async def standalone_question(question: str, history: list[Message]) -> str:
    if not history:
        return question           # nothing to resolve against; skip the call entirely
    # "And the second one?" embeds to nothing useful. This is the step that turns a
    # demo that answers single questions into something that holds a conversation.
    return await rewrite_chain.ainvoke({"history": render(history[-6:]),
                                        "question": question})

# app/rag/retrieve.py
RELEVANCE_FLOOR = 0.35        # calibrate against your own corpus; see §7 step 3


async def retrieve(question: str, tenant_id: str, k: int = 8) -> list[Passage]:
    # The tenant filter is not optional and does not belong in the prompt. A
    # retriever without it will happily return another customer's documents, and
    # the model will summarise them fluently.
    hits = await store.asimilarity_search_with_relevance_scores(
        question, k=k, filter={"tenant_id": tenant_id})

    # The relevance gate. Vector search has no concept of "nothing here" — it
    # returns the k least dissimilar passages whether or not any is relevant. Ask
    # about something the corpus does not cover and you get k irrelevant chunks,
    # and a model given irrelevant context will use it.
    kept = [Passage.from_hit(h, score) for h, score in hits if score >= RELEVANCE_FLOOR]
    return kept

# app/rag/assemble.py
CONTEXT_BUDGET_CHARS = 12_000


def assemble(passages: list[Passage]) -> tuple[str, dict[str, Passage]]:
    """Bounded, labelled context plus the map used to check the citations.

    Labels are short and stable so the model can cite them cheaply, and the map is
    what makes a citation verifiable rather than decorative.
    """
    blocks, by_label, used = [], {}, 0
    for i, p in enumerate(passages, start=1):
        label = f"S{i}"
        block = f"[{label}] {p.title} — {p.text}"
        # A budget, not a count. Ten chunks of very different sizes is not a
        # predictable amount of context, and the overflow is silently truncated by
        # the provider — from the end, where the instructions usually are.
        if used + len(block) > CONTEXT_BUDGET_CHARS:
            break
        blocks.append(block); by_label[label] = p; used += len(block)
    return "\n\n".join(blocks), by_label

# app/rag/chain.py
class Answer(BaseModel):
    text: str
    cited: list[str] = Field(default_factory=list)   # the labels the model used


async def answer_question(question: str, history, tenant_id: str) -> RagResult:
    standalone = await standalone_question(question, history)
    passages = await retrieve(standalone, tenant_id)

    if not passages:
        # Decided here, not asked of the model. An instruction to "say you do not
        # know if the context is insufficient" is followed unevenly; a branch is
        # followed every time.
        return RagResult(text=NO_ANSWER_TEXT, sources=[], grounded=True)

    context, by_label = assemble(passages)
    answer: Answer = await (ANSWER_PROMPT | model | parser).ainvoke(
        {"context": context, "question": standalone})

    # Citation check. A label the model invented means it answered from something
    # that was not retrieved — which is the definition of the failure this whole
    # pipeline exists to prevent, and it is cheap to detect.
    invented = [label for label in answer.cited if label not in by_label]
    if invented:
        log.warning("ungrounded citation", extra={"labels": invented})
        return RagResult(text=NO_ANSWER_TEXT, sources=[], grounded=False)

    return RagResult(text=answer.text,
                     sources=[by_label[label] for label in answer.cited],
                     grounded=True)

5. Golden-standard rules

Rule Why
Forbidden: embedding a follow-up message as typed "And the second one?" retrieves nothing useful, so the model answers the previous question's context and is confidently wrong.
Forbidden: answering from whatever the search returned Vector search always returns its top-k. With no threshold, an uncovered topic yields k irrelevant passages and a fluent wrong answer.
Forbidden: a tenant or permission filter expressed in the prompt A filter is a query parameter. Asked of the model, it is a suggestion, and the failure is another customer's data summarised convincingly.
Forbidden: relying on an instruction to say "I do not know" It is followed unevenly. A branch on an empty result is followed every time.
Forbidden: an unbounded assembled context Overflow is truncated silently by the provider, usually from the end, where the instructions are.
Citations are verified against what was retrieved An invented label is direct evidence the answer was not grounded, and checking costs one set membership.
The rewrite uses a small model It runs every turn and produces one sentence; frontier pricing there doubles cost and latency for nothing.
Retrieved passages are returned with every answer It is the only way to tell a grounded answer from a fluent one afterwards, and the only way to evaluate.
The context budget is characters, not chunks Chunks vary in size, so a chunk count is not a predictable amount of context.
The relevance floor is calibrated against this corpus Scores are not comparable across embedding models or corpora, and a borrowed threshold is arbitrary.
Both prompts are versioned files Retrieval quality is judged by evaluation, and an evaluation must be able to name which prompt it scored.
An empty result is a normal outcome, not an error Treating it as a failure teaches everyone to suppress it, which is how the wrong-answer path gets built.

6. Data contracts

Passage(id=..., text=..., title=..., score=0.71, metadata={...})
RagResult(text=..., sources=[Passage, ...], grounded=True)

grounded is the field worth arguing for. It is false when the model cited something that was not retrieved, and it separates two failures that look identical to a user: an answer the system could not support, and an answer it never had the material for. Without it, both arrive as prose and both get believed.

The relevance score is part of the contract too, and its meaning is local. A score is comparable only within one embedding model and one corpus, so the threshold is a measured property of this system — not a number to copy from anywhere, including from here.

7. Build order

  1. Retrieve and print, no model. Run twenty real questions and read what comes back. If the passages are wrong, nothing downstream can fix it, and the problem is ingestion rather than this chain.
  2. The answer prompt with labelled context and citations, and a test that the answer's labels exist in what was retrieved.
  3. Calibrate the relevance floor: score questions the corpus does answer and questions it does not, and choose the threshold that separates them. Copying a number here means guessing.
  4. The empty branch, with a test asking about something the corpus does not contain, asserting the refusal.
  5. The rewrite step, with a test on a two-turn conversation whose second question is meaningless alone.
  6. The tenant filter, with a test asserting one tenant cannot retrieve another's documents.
  7. The context budget and the citation check, then a small evaluation set to measure before tuning further.

Step 1 before anything else because retrieval quality bounds everything. Time spent on the prompt while the retriever returns the wrong passages is time spent making a wrong answer read better.

10. Failure modes

Symptom Cause Fix
The first question is answered well and the second is confidently wrong The follow-up was embedded as typed and retrieved nothing relevant Rewrite into a standalone question before retrieving
A question the corpus does not cover gets a detailed answer Top-k always returns something, and irrelevant context was used A relevance floor, and a branch on the empty result
One customer's data appears in another's answer The tenant filter was in the prompt, or absent Filter in the query
The answer cites a source that does not support it Citations were never checked against what was retrieved Verify the labels; treat an invented one as ungrounded
The model ignores its instructions on long documents The assembled context overflowed and was truncated from the end Budget in characters and stop at the limit
Retrieval quality is fine and answers are still poor The chunks are fragments — a chunking problem, not a chain problem Fix ingestion; nothing here can compensate
A threshold copied from an article rejects everything, or nothing Scores are not comparable across embedding models or corpora Calibrate against this corpus
Latency doubled after adding the rewrite A frontier model is producing one sentence Use a small model, and skip the call when there is no history
Nobody can tell whether a past answer was grounded Sources are not returned or not stored Return passages with every answer and keep them
Answers got worse after a prompt change and there is no way back Prompts are inline and unversioned Versioned prompt files, recorded per run
An evaluation shows improvement and users disagree The evaluation questions are all answerable; none tests the refusal path Include unanswerable questions in the set

11. Definition of done

  • A follow-up question that is meaningless in isolation retrieves the correct passages, covered by a two-turn test
  • A question about a topic absent from the corpus produces an explicit refusal and no sources, covered by a test
  • The relevance threshold was calibrated against this corpus, and the questions used are committed
  • Every answer returns the passages it used, and a test asserts sources are present whenever text is
  • An answer citing a label that was not retrieved is marked ungrounded and not returned as an answer, covered by a test
  • Tenant filtering happens in the query; a test asserts one tenant cannot retrieve another's documents
  • The assembled context never exceeds its budget, covered by a test with deliberately oversized passages
  • The rewrite step is skipped when there is no history, covered by a test asserting no model call
  • Both prompts live in versioned files and the versions appear in traces
  • An evaluation set exists containing both answerable and unanswerable questions, and it runs on demand
  • Retrieval can be run and inspected independently of the answer step, so a quality problem can be attributed to one or the other
