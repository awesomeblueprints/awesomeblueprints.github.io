JWT Refresh Tokens and Session Revocation

JWT refresh tokens and session revocation: rotation, reuse detection, logging out every device and disabling a compromised account.

medium3–5 daysVerified 2026-08-19
Auth
Read it on GitHub ↗ Back to the catalogue

Long sessions built from short access tokens, with rotation on every refresh, reuse detection that kills a stolen token's whole family, and a revocation path that makes "log out everywhere" and "disable this account now" actually work.

Complexity: medium-high · Typical build: 3–5 days · Verified: 2026-08-19 (re-check after ~90 days)

Examples in: Python, with FastAPI and PostgreSQL. The architecture is language-agnostic: sections 5, 10 and 11 hold wherever you build this. Section 4 is illustrative — if your project is in another language, your agent translates the idioms rather than importing them, and nothing is lost. The concurrency fix in §4 is a single SQL statement and translates directly; the mistake it prevents has been found in shipped authentication libraries in more than one language.

Use when: users must stay signed in for days or weeks, or you need to end a session on demand — a stolen device, a password change, an administrator disabling an account, a "sign out of all sessions" button.

Not for: a service whose clients are machines holding a long-lived key, or an API where a fifteen-minute token is simply reissued from stored credentials. This system exists to hold state about sessions, and if you have nothing to revoke it is cost with no benefit. Half of all projects genuinely do not need it; the other half need all of it.

1. Why this is a different system, not a longer token

The tempting version is to raise the access token's expiry to thirty days. It removes the login prompt and it removes every control you had.

A long-lived access token Rotating refresh tokens with server-side state
Cannot be revoked. A stolen token works until it expires, and nothing you do changes that Revocation is a row update; the next refresh fails
"Log out everywhere" is a button that does nothing Deleting the user's session rows ends every session
Theft is undetectable — the thief's requests are indistinguishable from the user's Rotation makes reuse of a spent token a detectable event
Disabling an account takes effect whenever the token happens to expire It takes effect at the next refresh, bounded by the access token's short life

The third row is the one that justifies the design. If a refresh token can be used exactly once, and the used one is replaced, then a token presented twice means two parties hold it — the legitimate client and someone else. You cannot tell which is which, and that is fine: the correct response is to invalidate the whole family and make both re-authenticate. The legitimate user logs in again; the attacker cannot.

This adds state, and that is the point. A stateless system cannot revoke. Every mechanism here is a consequence of deciding that revocation must work.

The rule the diagram encodes: every path to issuing a new refresh token goes through one atomic swap, and the losing branch is not an error — it is the detector. A design where validation and revocation are separate steps has a window between them, and that window is the vulnerability in §10's first row.

3. Project structure

app/auth/
├── sessions.py     the family model, rotate(), revoke_family(), revoke_all()
├── refresh.py      the refresh endpoint and reuse handling
├── cookies.py      how the refresh token is set and cleared
└── tokens.py       access tokens — unchanged from the access-token layer

One rule: the refresh token is a random opaque string, stored hashed, and it is never a JWT. A JWT refresh token is self-validating, which is exactly the property you are trying to remove — the whole point is that the server decides, per presentation, whether this token is still alive. Hashing it means a database leak does not hand over live sessions.

4. Reference implementation

-- One family per login. Rotation appends to a family; detection kills one.
CREATE TABLE refresh_tokens (
    id           BIGSERIAL PRIMARY KEY,
    family_id    UUID        NOT NULL,
    user_id      BIGINT      NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    -- The hash, never the token. A dump of this table must not yield live sessions.
    token_hash   BYTEA       NOT NULL UNIQUE,
    parent_id    BIGINT      REFERENCES refresh_tokens(id),
    revoked_at   TIMESTAMPTZ,
    expires_at   TIMESTAMPTZ NOT NULL,
    created_at   TIMESTAMPTZ NOT NULL DEFAULT now(),
    user_agent   TEXT,       -- so a user can recognise their own sessions in a list
    ip           INET
);
CREATE INDEX ix_refresh_family ON refresh_tokens (family_id);
CREATE INDEX ix_refresh_user_live ON refresh_tokens (user_id) WHERE revoked_at IS NULL;

# app/auth/sessions.py
import hashlib, secrets
from sqlalchemy import text

REFRESH_TTL = timedelta(days=30)


def new_token() -> tuple[str, bytes]:
    raw = secrets.token_urlsafe(32)          # CSPRNG, not uuid4 and not the clock
    # SHA-256 is right here and Argon2 is not: this is a 256-bit random value, not a
    # human-chosen password, so there is nothing to brute-force and the hash is on
    # the hot path of every refresh.
    return raw, hashlib.sha256(raw.encode()).digest()


async def rotate(session, presented: str) -> tuple[str, str] | None:
    """Spend one refresh token and issue its successor. Returns None if the token
    was already spent or revoked — which the caller must treat as reuse."""
    digest = hashlib.sha256(presented.encode()).digest()

    # THE load-bearing statement in this blueprint. Validation and revocation happen
    # in one update, so there is no window between them.
    #
    # Read-then-revoke as two steps looks correct and is not: two concurrent refreshes
    # both pass the check before either writes, and both mint successors. The family
    # forks, and each branch keeps full access — surviving any single revocation.
    # This exact bug has been disclosed in shipped authentication libraries.
    #
    # `revoked_at IS NULL` in the predicate is what makes it a compare-and-swap.
    # The rowcount is the answer: 1 means we won, 0 means someone else did.
    result = await session.execute(
        text("""
            UPDATE refresh_tokens
               SET revoked_at = now()
             WHERE token_hash = :digest
               AND revoked_at IS NULL
               AND expires_at > now()
         RETURNING id, family_id, user_id
        """),
        {"digest": digest},
    )
    row = result.first()
    if row is None:
        return None                          # spent, revoked or expired — the caller decides

    raw, new_digest = new_token()
    await session.execute(
        text("""
            INSERT INTO refresh_tokens
                (family_id, user_id, token_hash, parent_id, expires_at)
            VALUES (:family, :user, :hash, :parent, now() + :ttl)
        """),
        {"family": row.family_id, "user": row.user_id,
         "hash": new_digest, "parent": row.id, "ttl": REFRESH_TTL},
    )
    return raw, create_access_token(str(row.user_id), await scopes_for(session, row.user_id))


async def revoke_family(session, presented: str) -> None:
    # Reuse detected. We cannot tell the thief from the victim, so neither keeps
    # access: kill every token descended from this login. The user signs in again;
    # the attacker cannot.
    await session.execute(
        text("""
            UPDATE refresh_tokens SET revoked_at = now()
             WHERE family_id = (SELECT family_id FROM refresh_tokens WHERE token_hash = :d)
               AND revoked_at IS NULL
        """),
        {"d": hashlib.sha256(presented.encode()).digest()},
    )

# app/auth/refresh.py
@router.post("/refresh")
async def refresh(request: Request, response: Response, session=Depends(get_session)):
    presented = request.cookies.get("__Host-refresh")
    if not presented:
        raise UNAUTHORIZED

    rotated = await rotate(session, presented)
    if rotated is None:
        # The token existed once and is being presented again — or never existed.
        # Both are handled the same way, and deliberately: probing must not reveal
        # which. revoke_family is a no-op for a token that was never real.
        await revoke_family(session, presented)
        await session.commit()
        clear_refresh_cookie(response)
        await alert_reuse_detected(presented)   # a security event, not a log line
        raise UNAUTHORIZED

    raw, access = rotated
    set_refresh_cookie(response, raw)
    return {"access_token": access, "token_type": "bearer"}

# app/auth/cookies.py
def set_refresh_cookie(response: Response, raw: str) -> None:
    response.set_cookie(
        # The __Host- prefix is enforced by the browser: Secure, no Domain, Path=/.
        # It stops a subdomain — including one an attacker controls via a stale DNS
        # record — from writing a cookie the main site will send.
        key="__Host-refresh",
        value=raw,
        httponly=True,      # JavaScript cannot read it, so an XSS payload cannot steal it
        secure=True,
        samesite="strict",  # not sent on cross-site requests, which covers the CSRF
                            # case for this endpoint without a separate token
        max_age=int(REFRESH_TTL.total_seconds()),
        path="/auth",       # sent only to the endpoints that need it
    )

5. Golden-standard rules

Rule Why
Forbidden: validating and revoking a refresh token in two steps Two concurrent refreshes both pass validation before either writes, and the family forks into branches that each keep full access. One conditional update, and the rowcount is the answer.
Forbidden: a JWT as the refresh token Self-validating is the property you are removing. The server must decide per presentation, which requires state.
Forbidden: storing refresh tokens in plaintext A database dump then hands over live sessions for as long as they last. Store the hash; compare the hash.
Forbidden: treating reuse as a single-token problem The token was presented twice, so two parties hold it and you cannot tell which. Invalidate the family.
Forbidden: refresh tokens readable by JavaScript An XSS payload that can read the refresh token owns the account for a month. HttpOnly, and never in local storage.
Refresh tokens are CSPRNG output A token derived from a counter, a timestamp or a v4 UUID from a seeded generator is guessable at a rate you cannot observe.
Rotation happens on every refresh, without exception If a token can be used twice legitimately, reuse is no longer a signal and detection is impossible.
Password change and deactivation revoke every family Otherwise "I changed my password because I was compromised" leaves the attacker's session running.
Reuse detection raises an alert, not a log line It is the only high-signal indication of credential theft you will get, and it arrives once.
Sessions are listable and individually revocable by the user "Sign out of this device" is only possible if a session is a row someone can point at.
Expired and long-revoked rows are pruned on a schedule The table grows with every refresh — thousands of rows per active user per month — and the indexes degrade quietly.
The refresh endpoint is rate-limited per family An attacker holding a stolen token otherwise gets unlimited attempts to win the rotation race.

6. Data contracts

family      one login. Rotation appends; revocation applies to all of it.
token       opaque, 256 bits of CSPRNG output, stored only as a hash
lifetime    access ~15 min, refresh ~30 days sliding — the refresh lifetime is
            the maximum time a stolen token stays useful if reuse is never detected
states      live -> spent (rotated) -> revoked. Terminal, never reversible.

The rowcount of the compare-and-swap is part of the contract, not an implementation detail: 1 means this caller spent the token, 0 means somebody else already did. Every branch of the endpoint hangs off that number, and a driver or ORM that hides it makes the design unimplementable.

7. Build order

  1. The table and rotate() as one conditional update, with a test that calls it twice on the same token and asserts the second returns nothing.
  2. The concurrency test, immediately: fire N parallel refreshes with the same token and assert exactly one succeeds. This is the whole blueprint; write it before anything depends on rotation.
  3. Reuse detection and family invalidation, with a test that spends a token, rotates on, then replays the old one and asserts every descendant is dead.
  4. Cookie handling with the prefix and attributes, asserted on the response headers.
  5. Logout, and logout everywhere.
  6. Revocation on password change and deactivation, each with a test.
  7. Pruning, rate limiting, and the session list endpoint.

Step 2 before step 3 because the race is invisible in serial tests and every implementation passes those. If it is not tested concurrently, assume it is broken — that is how it reached shipped libraries.

Metric Target

10. Failure modes

Symptom Cause Fix
A revoked session keeps working, and revoking again does not help Concurrent refreshes forked the family; each branch is independent and revoking one leaves the others One atomic compare-and-swap; check the rowcount; add the concurrency test
Users are randomly signed out, more often on slow connections A page issued parallel requests, two refreshes raced, and the loser was treated as reuse — invalidating a legitimate family Have clients serialise refresh through one in-flight promise; consider a short grace window in which the immediate predecessor is accepted without alerting
A stolen token is used for weeks and nothing notices Tokens are not rotated, so reuse is indistinguishable from normal use Rotate on every refresh; detection depends on single use
A database leak results in account takeovers Refresh tokens were stored in plaintext and were still live Store only the hash
An XSS report is followed by long-term account compromise The refresh token was readable from JavaScript, in local storage or a non-HttpOnly cookie HttpOnly, Secure, SameSite, __Host- prefix
A user changes their password after a compromise and the attacker stays signed in Password change did not revoke existing families Revoke all families on password change and on deactivation
"Sign out of all devices" appears to work and the other device keeps working Only the current family was revoked Revoke by user, not by family, and test with two live sessions
Refresh latency degrades over months The token table grew unbounded and its indexes with it Prune expired and long-revoked rows on a schedule
An attacker with a stolen token keeps winning the race against the real client The refresh endpoint has no rate limit, so retries are free Rate-limit per family and per address
A cookie set on a subdomain overrides the session cookie No __Host- prefix, so a subdomain could write it Use the prefix; the browser then enforces the constraints
Reuse detection fires constantly in one environment A client retries refresh automatically on network failure, replaying the same token Make the client's retry reuse the in-flight request rather than re-presenting the token

11. Definition of done

  • Firing many parallel refreshes with the same token results in exactly one success and no forked family, asserted by a concurrency test that runs in CI
  • Presenting a token twice serially fails the second time and revokes every token in the family, covered by a test
  • Refresh tokens are stored hashed; a test asserts the presented value does not appear in the table
  • Refresh tokens come from a CSPRNG and are at least 256 bits
  • The refresh cookie carries HttpOnly, Secure, SameSite and the __Host- prefix, asserted on the response headers
  • Changing a password revokes every session for that user, covered by a test with two live sessions
  • Deactivating a user revokes every session, covered by a test
  • "Sign out of all devices" ends a session established on another client, covered by a test with two live sessions
  • A reuse-detection event reaches an alert channel, not only the log, verified once end to end
  • Expired and revoked rows are pruned on a schedule, and a test asserts the pruning removes them and nothing else
  • The refresh endpoint is rate-limited per family, covered by a test
  • A user can list their active sessions with enough detail to recognise them, and revoke one individually
