FastAPI Routers and API Versioning

FastAPI routers and API versioning: splitting a large main.py into modules, dependency wiring and versioned routes clients can migrate off.

low1–2 daysVerified 2026-08-19
FastAPIAPIPython
Read it on GitHub ↗ Back to the catalogue

Endpoints split across routers that each own one resource, mounted under a version prefix at one place in the application — so a breaking change ships as a new mount rather than as a change every client has to absorb at once.

Complexity: low · Typical build: 1–2 days · Verified: 2026-08-19 (re-check after ~90 days)

Examples in: Python, with FastAPI. The architecture is language-agnostic: sections 5, 10 and 11 hold wherever you build this. Section 4 is illustrative — if your project is in another language, your agent translates the idioms rather than importing them, and nothing is lost. The equivalents are express.Router() and Nest modules in TypeScript, Blueprint in Flask, scope/pipeline in Phoenix, and chi.Mount in Go.

Use when: endpoints are accumulating in one file, or a change to a response shape would break clients you cannot upgrade, or two routes have quietly claimed overlapping paths. Works on an empty application and on one with 800 lines in main.py — in the second case the job is to move existing endpoints into modules without changing what any of them does.

Not for: a service with a handful of endpoints and one consumer you deploy alongside it. Versioning has a real cost — two code paths, two test suites, a deprecation calendar — and paying it before anyone depends on the old shape buys nothing. Split the file when it hurts; add versions when a client you do not control exists.

⚙️ INSTRUCTIONS FOR THE AI — READ BEFORE WRITING ANY CODE

Do not start coding.

Step 1 — Refresh. Verify the installed FastAPI and Starlette versions. Confirm that APIRouter still takes prefix, tags, dependencies and responses; that include_router accepts the same; that generate_unique_id_function still exists on the application constructor; and that lifespan is the current startup mechanism rather than on_event, which has been deprecated. Check whether the reported bug producing duplicate operationId values for a route declaring several HTTP methods is fixed in your version — §5 forbids that declaration style because of it. Report what you verified and what turned out wrong.

Step 2 — Read the project, then audit what already exists. Produce the route table before proposing anything: every path, method, handler function and source file. From it, identify routes whose paths can shadow each other — a literal segment and a path parameter at the same position — and note the declaration order, because that is what decides which one answers. Find where the app is constructed, whether a reverse proxy or root_path is involved, whether any router-level dependency exists today, and how errors are currently handled. Then audit §11 item by item, each marked already true, partly true or absent, with the file that decides it, reported before anything is proposed.

Assume the project is right until it demonstrably is not; code satisfying an item stays even where its shape differs from §4; replacing something that works needs a one-line reason; never delete a working path to make room for the blueprint's version. The same holds for language — §4 is illustrative, its idioms get translated into the project's language, and §11 is what has to become true rather than the syntax.

On an existing application this is a move, not a rewrite. Handler bodies are relocated unchanged. If a handler needs editing to fit a router, that is a separate change with its own reason, proposed separately. The test that the move worked is that the route table before and after are identical.

Step 3 — Write a plan for the gap only, and get it approved, including a ## Proposed stack section and, on an existing app, the before-and-after route table. Do not ask open framework questions — propose, and ask for confirmation once. Say what you are adding, what you are leaving alone, and what you propose to change, and touch nothing else.

Step 4 — Build in the order in §7. Step 5 — §11 is the definition of done.

1. Why every endpoint in one file stops working

The obvious version is decorators on app in main.py. It is the right answer for the first twenty endpoints and then fails in four ways at once.

Everything on app in one file Routers mounted under a version
Two routes claim overlapping paths and the file order silently decides which answers Each resource owns its paths in one module, where a collision is visible
A breaking change to a response reaches every client on deploy The old shape keeps serving under its prefix while clients migrate
Authentication is repeated per endpoint, and the one that was missed looks exactly like the ones that were not One dependency on the router covers every route in it, including ones added later
Merges conflict in one file that every feature touches Conflicts are confined to the resource that changed

The third row is where the real incidents come from. A missing Depends on one endpoint out of sixty is invisible in review — it is an absence, and absences do not appear in a diff you are scanning for what changed. Moving the requirement to the router turns it into something a route cannot opt out of by accident.

The version prefix belongs at the mount, not in the handler. A handler that knows whether it is v1 or v2 will grow a branch on that, and the two versions become one function with a conditional — which is the thing versioning exists to avoid. Handlers stay ignorant; the router they live in decides.

The rule the diagram encodes: the service layer has no arrow from a version. Both ordersone and orderstwo reach the same service, and the difference between them lives entirely in their schemas. A version that reaches into business logic is a fork, and forks get maintained twice and diverge.

3. Project structure

app/
├── main.py                 builds the app, mounts routers, registers handlers — nothing else
├── api/
│   ├── v1/
│   │   ├── __init__.py     assembles the v1 router from the resource routers
│   │   ├── orders.py
│   │   └── products.py
│   └── v2/
│       ├── __init__.py
│       └── orders.py       only what changed; v2 re-exports the rest from v1
├── deps.py                 shared dependencies
└── errors.py               exception handlers

One rule: main.py contains no path operation. It builds the application, includes routers and registers handlers. The moment one endpoint is declared there "just for now", main.py becomes a module with behaviour, it starts importing from everywhere, and it is the file every branch touches.

A real disagreement, worth deciding rather than inheriting. FastAPI's own documentation lays projects out by layer — a routers/ directory, a models/ directory. A widely-read set of production conventions argues the opposite from experience: that layer-first stopped scaling on a monolith with many domains, and that each domain should hold its own router, schemas, models and service. Both work. Layer-first is easier to navigate under about ten resources; domain-first wins when resources outnumber the people working on them, because it confines a change to one directory. The layout above is layer-first at the top and domain-first inside a version, which is the common middle. Choose deliberately and write down which you chose — the expensive outcome is half of each.

4. Reference implementation

# app/api/v1/orders.py
from fastapi import APIRouter, Depends, HTTPException, status
from app.deps import require_authenticated_user
from app.schemas.order import OrderCreate, OrderRead

router = APIRouter(
    prefix="/orders",                                  # never a trailing slash
    tags=["orders"],                                   # required: operation ids are built from it
    dependencies=[Depends(require_authenticated_user)], # applies to every route below, including
                                                        # ones added next year by someone who
                                                        # never read this file
    responses={404: {"description": "Order not found"}},
)


# Literal segments before parameterised ones. Routing is first match wins, so with
# the reverse order "/orders/search" is matched by "/orders/{order_id}" and arrives
# as order_id="search" — a 422, or worse a lookup, never a search.
@router.get("/search", response_model=list[OrderRead])
async def search_orders(q: str) -> list[OrderRead]: ...


@router.get("/{order_id}", response_model=OrderRead)
async def get_order(order_id: int) -> OrderRead: ...


# One decorator per method. Declaring methods=["POST", "PUT"] on a single route
# generates duplicate operation ids and silently breaks client generation.
@router.post("", response_model=OrderRead, status_code=status.HTTP_201_CREATED)
async def create_order(payload: OrderCreate) -> OrderRead: ...

# app/api/v1/__init__.py
from fastapi import APIRouter
from app.api.v1 import orders, products

router = APIRouter()
router.include_router(orders.router)
router.include_router(products.router)

# app/api/v2/__init__.py
from fastapi import APIRouter
from app.api.v1 import products          # unchanged in v2 — mounted, not copied
from app.api.v2 import orders

router = APIRouter()
router.include_router(orders.router)
router.include_router(products.router)   # the same router object, a second mount

# app/main.py
from contextlib import asynccontextmanager
from fastapi import FastAPI
from fastapi.routing import APIRoute
from app.api import v1, v2
from app.errors import register_handlers


def unique_id(route: APIRoute) -> str:
    # Default ids concatenate function name, path and method, producing client methods
    # like createOrderApiV1OrdersPost. This yields orders-create_order, which survives
    # a path change — so a generated SDK does not rename half its methods when a
    # prefix moves.
    return f"{route.tags[0]}-{route.name}"


@asynccontextmanager
async def lifespan(app: FastAPI):
    yield


app = FastAPI(
    lifespan=lifespan,
    generate_unique_id_function=unique_id,
    # Off deliberately. The default 307 to the slashed variant is rewritten to http
    # by a TLS-terminating proxy, so the client follows a redirect out of https.
    # An exact-path 404 is a better failure than a silent downgrade.
    redirect_slashes=False,
    # Only when the app is mounted under a sub-path by the proxy. Wrong here and
    # every generated URL and doc link is wrong; verify against the proxy config.
    root_path="",
)

app.include_router(v1.router, prefix="/api/v1")
app.include_router(v2.router, prefix="/api/v2")
register_handlers(app)

# tests/test_routes.py
def test_no_shadowed_routes():
    # A literal segment declared after a path parameter at the same position is
    # unreachable. Nothing warns; the route simply never runs. This is the check
    # that would have caught it before the deploy.
    seen: dict[tuple[str, int], list[str]] = {}
    for route in app.routes:
        for method in getattr(route, "methods", ()):
            parts = route.path.strip("/").split("/")
            for i, part in enumerate(parts):
                key = (f"{method}:{'/'.join(parts[:i])}", i)
                seen.setdefault(key, []).append(part)
    for key, parts in seen.items():
        params = [p for p in parts if p.startswith("{")]
        literals = [p for p in parts if not p.startswith("{")]
        if params and literals:
            assert parts.index(literals[0]) < parts.index(params[0]), (
                f"literal segment declared after a path parameter at {key}")

5. Golden-standard rules

Rule Why
Forbidden: a path operation declared in main.py It is how main.py becomes the file every branch edits and every module imports. There is never a good "just this one".
Forbidden: a router prefix ending in / FastAPI rejects it, and the reason is that the joined path would carry a double slash that some proxies normalise and some do not.
Forbidden: one route declaring several HTTP methods It generates duplicate operation ids, which breaks client generation without an error. One decorator per method.
Forbidden: a handler that branches on its API version That is one function serving two contracts, and it is exactly what versioning exists to prevent. Give v2 its own handler or its own schema; share the service.
Literal path segments are declared before parameterised ones First match wins. /{id} declared first swallows /search, and nothing warns — the route is simply never reached.
Authentication is a router dependency, not a per-route one A route added later inherits it. A per-route requirement is one an author has to remember, and the one they forget looks identical to the ones they did not.
Every router carries a tag Operation ids are derived from it, documentation groups by it, and a tagless route breaks the id function on the day it is added.
Version lives in the mount prefix, nowhere else A version string inside a handler, a schema or a service is a second place to update and the one that will be missed.
A version that did not change is mounted, not copied The same router object under two prefixes. A copied file drifts, and the drift is silent because both still pass their tests.
Slash redirects are disabled behind a proxy The 307 loses https when a TLS-terminating proxy is in front. A clean 404 on the wrong path beats a redirect that downgrades the scheme.
Exception handlers are registered once, on the app Per-router error handling produces responses that differ by resource, and clients then need a branch per endpoint.
A deprecated version has a removal date written down before it is deprecated "Deprecated" with no date is permanent, and the second version becomes maintenance you never escape.

6. Data contracts

The contract this blueprint defines is not a body shape — it is the route table.

METHOD  PATH                        OPERATION ID          TAG       AUTH
GET     /api/v1/orders/search       orders-search_orders  orders    required
GET     /api/v1/orders/{order_id}   orders-get_order      orders    required
POST    /api/v1/orders              orders-create_order   orders    required
GET     /api/v2/orders/{order_id}   orders-get_order_v2   orders    required

Generate it from the running application rather than maintaining it by hand, and commit it. A diff of that file is the only review artefact that makes an accidentally shadowed route, a missing authentication requirement or a changed operation id visible as a change rather than as an absence.

7. Build order

  1. Produce the route table from the current application and commit it. On an empty project this is empty and takes a minute. On an existing one it is the baseline that proves the refactor changed nothing.
  2. Move one resource into its own router, mounted at the same paths it had before. Regenerate the table and confirm it is byte-identical.
  3. Move the rest, one resource per commit, checking the table each time.
  4. Add the router-level authentication dependency and remove the per-route duplicates. Confirm the table's auth column, and confirm an unauthenticated request to each route is rejected.
  5. Introduce the version prefix — mount the existing routers at /api/v1. Keep the old unversioned paths mounted alongside if clients exist, with a removal date recorded.
  6. Add the shadowing test and the operation id function.
  7. Only when a breaking change is actually needed: create v2 with the one changed resource, mounting the unchanged routers.

Step 1 before step 2 because the risk in this work is not writing a bad router, it is silently losing a route during the move. The table is what makes that impossible rather than unlikely.

8. Blocks to pull in

Nothing here is a prerequisite. These are adjacent problems, by name only — resolve them separately if they apply.

  • Pydantic request and response schemas — what the routes in each version actually exchange
  • Error envelope — the one response shape the handlers registered here produce
  • JWT authentication — what the router-level dependency verifies
  • Typed config and settings — where the version prefix and root path come from
  • GitHub Actions CI — where the committed route table gets checked

10. Failure modes

Symptom Cause Fix
/orders/search returns 422 complaining that search is not a valid integer /orders/{order_id} is declared before it; first match wins and the literal never gets a chance Declare literal segments first, and add the shadowing test
One endpoint out of sixty is reachable without a token, and nobody can say when that started Authentication is a per-route dependency and this route was added without it Move the dependency to the router; a new route then cannot opt out by omission
A client following a redirect ends up on http and the request is rejected or intercepted The trailing-slash 307 is generated without the forwarded scheme, so it downgrades behind a TLS-terminating proxy redirect_slashes=False, and configure the proxy to forward the scheme
Generated client methods are named createOrderApiV1OrdersPost, and renaming a prefix renames half the SDK Default operation ids concatenate function name, path and method Set generate_unique_id_function to build from tag and function name
Client generation fails or produces one method for two operations A single route declares multiple methods, producing duplicate operation ids One decorator per method
Documentation links and generated URLs are all missing a path segment The app is mounted under a sub-path by the proxy and root_path was not set to match Set root_path to the mount point; verify against the proxy config, not by guessing
v2 fixes a bug and v1 does not, though the code looks the same The unchanged router was copied into v2 rather than mounted, and the copies drifted Mount the same router object under both prefixes
A route in v1 behaves differently from v2 in a way no schema explains A handler or a service branches on the version Remove the branch; the difference belongs in the schema or in a separate handler
Every feature branch conflicts in the same file Path operations still live in main.py or in one shared router module Finish the split; the conflict rate is the symptom the structure exists to fix

11. Definition of done

  • main.py declares no path operation; a test asserts every route's handler is defined outside it
  • A committed route table lists every path, method, operation id, tag and whether authentication is required, and it is regenerated and diffed in CI
  • A test fails if any route is unreachable because a path parameter at the same position is declared before a literal segment
  • Every route carries at least one tag, asserted by a test
  • Operation ids are unique across the whole application, asserted against the generated schema
  • Authentication is declared once per router, and a test issues an unauthenticated request to every route in a protected router and expects rejection on each
  • Every route is reachable under its version prefix, and a request to a path without the prefix returns 404 rather than being served
  • A router shared between two versions is the same object, verified by identity rather than by reading
  • No handler, schema or service function contains a version string or a branch on version
  • Slash-redirect behaviour is set explicitly rather than left at the default, with a comment naming the proxy setup it assumes
  • Each deprecated version has a removal date recorded outside the code, and a test or CI check fails once that date has passed
