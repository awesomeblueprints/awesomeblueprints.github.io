Docker Compose for Local Development

Docker Compose for local development: databases, caches and queues, health checks, seed data and file watching behind one command.

low1 dayVerified 2026-08-19
Docker
Read it on GitHub ↗ Back to the catalogue

The whole stack up with one command on a machine that has never seen the project: services started in an order that waits for readiness rather than for containers, code reloading without a rebuild, and a documented way to throw it all away and start again.

Complexity: low · Typical build: 1 day · Verified: 2026-08-19 (re-check after ~90 days)

Examples in: Compose v2 with a Python service and PostgreSQL. The architecture is language-agnostic: sections 5, 10 and 11 hold wherever you build this. Section 4 is illustrative — if your project is in another language, your agent translates the idioms rather than importing them, and nothing is lost. The dependency ordering, seeding and reset concerns are identical under Tilt, Skaffold or a justfile wrapping plain docker run.

Use when: the project needs more than one process to run — an application plus a database, a cache, a queue, an object store — and onboarding currently involves a wiki page with steps that no longer work.

Not for: production orchestration. Compose has no rolling deploys, no health-based traffic shifting and no rescheduling; a stack that runs in it will run, right up until the first node failure. Also not for a single process with no dependencies, where a virtual environment and one command is the whole story.

⚙️ INSTRUCTIONS FOR THE AI — READ BEFORE WRITING ANY CODE

Do not start coding.

Step 1 — Refresh. Verify the installed Compose version. This blueprint uses depends_on with condition: service_healthy, and the develop.watch section, which needs a recent v2 — confirm both are supported. Confirm that the top-level version: key is obsolete and should be absent. Verify the readiness command for each dependency image you will use: it is image-specific and getting it wrong is the single most common defect in a compose file. Report what you verified and what turned out wrong.

Step 2 — Read the project, then audit what already exists. Find any existing compose file and record: whether depends_on uses conditions or bare names, which services declare healthchecks, whether data lives in a named volume or in the container, and how code currently reaches the container. Find how the application gets its configuration, and whether any secret is committed in the compose file today. Find out what a new developer currently has to do by hand — that list is the specification for this work. Then audit §11 item by item, each marked already true, partly true or absent, with the file that decides it, reported before anything is proposed.

Assume the project is right until it demonstrably is not; code satisfying an item stays even where its shape differs from §4; replacing something that works needs a one-line reason; never delete a working path to make room for the blueprint's version. The same holds for language — §4 is illustrative, its idioms get translated into the project's language, and §11 is what has to become true rather than the syntax.

Step 3 — Write a plan for the gap only, and get it approved, including a ## Proposed stack section listing every service with a one-line reason for its presence. Do not ask open framework questions — propose, and ask for confirmation once. Say what you are adding, what you are leaving alone, and what you propose to change, and touch nothing else.

Step 4 — Build in the order in §7. Step 5 — §11 is the definition of done.

1. Why "it works on the second up" is the defect

Every compose file starts correct and accumulates the same four problems.

The compose file that grew The one that is a specification
depends_on: [db] waits for the container to exist, not for the database to accept queries — so the first up fails and the second works Dependencies are gated on readiness commands, and the first up on a clean machine succeeds
Data lives inside the container, so down loses it and nobody knows which resets are destructive Data is in a named volume; there is one documented command that destroys it and it is the only one that does
Code reaches the container by rebuilding the image Code is synced into the running container; a rebuild happens only when dependencies change
Optional services start every time, so the machine runs eleven containers to work on one Optional services are behind profiles and start when asked for

The first row deserves the attention, because "run it again" is a workaround that survives for years and quietly costs every new hire an afternoon. Containers accept TCP connections well before the software inside them is ready — Postgres binds its port during initialisation, then runs setup, restarts internally, and only then accepts queries. A dependency expressed as "start db first" is not a dependency at all; it is a hint about ordering that the failure mode ignores.

A compose file is the executable version of the onboarding document. Judge it by one question: does a colleague who has never seen the repository get a working stack from one command? Anything that answer depends on belongs in the file.

The rule the diagram encodes: every arrow into the store passes through a readiness gate, and the application's arrow passes through the migration service as well. Ordering by declaration order is not ordering.

3. Project structure

compose.yaml            the stack — services, volumes, profiles, watch rules
compose.override.yaml   personal, git-ignored, applied automatically
.env.example            every variable the stack needs, with safe local values — committed
.env                    local values — git-ignored
Makefile                up, down, reset, seed, logs — the five commands anyone runs

One rule: the compose file contains no value that is a secret anywhere else. Local passwords are literals in the file so the stack works with no setup; anything that is also real elsewhere comes from .env, and .env is ignored. The moment a real credential appears here it is committed, and rotating it is a conversation rather than an edit.

4. Reference implementation

# compose.yaml
# No top-level `version:` — it is obsolete in Compose v2 and only produces a warning.

services:
  db:
    image: postgres:17-alpine
    environment:
      POSTGRES_PASSWORD: local          # deliberately a literal: the stack must work
      POSTGRES_DB: orders               # with no setup step at all
    ports: ["5432:5432"]                # published so a local client can attach
    volumes:
      - pgdata:/var/lib/postgresql/data
    healthcheck:
      # Image-specific and the most commonly wrong line in a compose file. A port
      # check passes during initialisation, when the server is up but not accepting
      # queries — which is exactly the window that makes the first `up` fail.
      test: ["CMD-SHELL", "pg_isready -U postgres -d orders"]
      interval: 2s
      timeout: 3s
      retries: 20
      start_period: 5s                  # failures here do not count toward retries

  cache:
    image: redis:7-alpine
    healthcheck:
      test: ["CMD", "redis-cli", "ping"]
      interval: 2s
      retries: 10

  migrate:
    build:
      context: .
      target: dev                       # the dev target from the same Dockerfile
    command: ["alembic", "upgrade", "head"]
    env_file: [.env]
    depends_on:
      db:
        condition: service_healthy
    restart: "no"                       # a one-shot task; restarting it on exit would loop

  api:
    build:
      context: .
      target: dev
    command: ["uvicorn", "app.main:app", "--host", "0.0.0.0", "--port", "8000", "--reload"]
    ports: ["8000:8000"]
    env_file: [.env]
    depends_on:
      db:
        condition: service_healthy
      cache:
        condition: service_healthy
      migrate:
        # Not service_started: the API must wait for migrations to finish, and to
        # have finished successfully. A failed migration should stop the stack,
        # not produce an app running against a half-applied schema.
        condition: service_completed_successfully
    develop:
      watch:
        # sync copies changed files into the running container — the reload watcher
        # picks them up. No rebuild, so the inner loop is a save, not a minute.
        - action: sync
          path: ./app
          target: /app/app
          ignore: ["__pycache__/", "*.pyc"]
        # A dependency change cannot be synced; it needs a new image.
        - action: rebuild
          path: ./uv.lock

  seed:
    build: {context: ., target: dev}
    command: ["python", "-m", "scripts.seed"]
    env_file: [.env]
    depends_on:
      migrate:
        condition: service_completed_successfully
    restart: "no"
    profiles: ["seed"]                  # never starts unless asked for by name

  mail:
    image: axllent/mailpit
    ports: ["8025:8025"]
    profiles: ["extras"]

volumes:
  pgdata:                               # named, so `down` keeps it and `down -v` does not

# Makefile — the five commands anyone needs. Their existence is the documentation.
up:            ## start the stack and follow logs
    docker compose up --watch

down:          ## stop everything, keep the data
    docker compose down

reset:         ## destroy the data and start clean — the ONLY destructive command
    docker compose down -v
    docker compose up -d
    docker compose --profile seed run --rm seed

seed:          ## load sample data into the current database
    docker compose --profile seed run --rm seed

logs:          ## follow one service: make logs S=api
    docker compose logs -f $(S)

5. Golden-standard rules

Rule Why
Forbidden: depends_on without a condition It waits for the container, not for the software. This is the whole of "it works on the second up".
Forbidden: a port check used as a healthcheck The port opens during initialisation, before the service accepts work — so the check passes exactly when it should not.
Forbidden: data written inside a container rather than a named volume down then destroys it, so no one can tell which commands are safe, and everyone hoards containers.
Forbidden: any credential in the compose file that is also real elsewhere It is committed the moment it is written. Local literals only; everything else from an ignored .env.
Forbidden: editing the compose file to work on your machine That is what compose.override.yaml is for. Personal edits to the shared file get committed by accident and break everyone.
Migrations are a service that must complete successfully before the app starts service_completed_successfully, not service_started. A failed migration must stop the stack rather than produce an app on a half-applied schema.
One-shot services set restart: "no" Otherwise the default restart policy loops them forever on their normal exit.
Code reaches the container by sync, not by rebuild A rebuild per edit is a minute; a sync is instant. Rebuild only when the lock file changes.
Optional services live behind profiles Otherwise every developer runs every service the project has ever needed, and the machine is the bottleneck.
start_period is set on slow dependencies Failures during it do not count toward the retry budget, so a slow first start does not mark a healthy service dead.
Exactly one command destroys data, and it is named for what it does If down sometimes destroys and sometimes does not, people stop trusting either.
.env.example lists every variable and is committed It is the only artefact that tells a new developer what the stack needs.

6. Data contracts

The contract is the set of commands, and it is small on purpose:

make up       clean machine to working stack, no manual step, first attempt
make down     stops everything, data survives
make reset    destroys data, recreates, reseeds — the only destructive command
make seed     loads sample data into the current database
make logs     follows one service

Five commands with stable meanings are worth more than a correct compose file nobody can drive. The test of the contract is not that the file is right — it is that a colleague with a clean machine gets a working stack from make up without asking a question.

7. Build order

  1. One service, up and reachable. No dependencies yet.
  2. Add the database with a real readiness check, and gate the app on it. Confirm docker compose down -v && docker compose up succeeds on the first attempt — that single check is most of this blueprint's value.
  3. Named volume, and confirm data survives down and up.
  4. Migrations as a service the app waits to complete successfully. Break a migration deliberately and confirm the app does not start.
  5. Watch rules — sync for source, rebuild for the lock file — and confirm an edit is live without a rebuild.
  6. Profiles for anything not needed on every run.
  7. The Makefile and .env.example, then test the whole thing the only way that counts: on a machine that has never run the project.

Step 2 is the load-bearing one. Everything after it is convenience; that step is the difference between a compose file and a working onboarding.

8. Blocks to pull in

Nothing here is a prerequisite. These are adjacent problems, by name only — resolve them separately if they apply.

  • Dockerfile for a production service — the multi-stage file whose dev target this builds
  • Alembic migrations — what the migration service runs
  • PostgreSQL connection pool and lifecycle — what the application does once the database is ready
  • Typed config and settings — what reads the variables this file supplies
  • Integration tests with real dependencies — the same services, started by the test run

9. Metrics

Metric Target
Manual steps between cloning and a working stack 0 beyond make up
First-attempt success rate of up from a clean machine 100%
Time from make up on a warm cache to a serving application < 30 s
Time from saving a source file to the change being live < 3 s
Containers started by default that the task does not need 0
Commands that destroy data Exactly 1

10. Failure modes

Symptom Cause Fix
The first up fails and the second works depends_on waited for the container; the database was still initialising Add a real readiness check and condition: service_healthy
The database is marked unhealthy on a cold start although it recovers The retry budget expired during first-time initialisation Set start_period so early failures do not count
The app starts against a schema that is missing the newest tables It depends on the migration service as service_started rather than service_completed_successfully Change the condition; a failed migration must stop the stack
The migration container restarts forever It exits when finished, and the default restart policy treats that as a crash restart: "no" on one-shot services
Data disappears and nobody agrees which command did it It was written inside the container, so any recreate lost it Named volume, and one documented destructive command
Every code change costs a rebuild Code reaches the container through the image Add develop.watch with a sync rule for source and a rebuild rule for the lock
A dependency change appears to have no effect The sync rule copied the lock file without rebuilding the image A separate rebuild action keyed on the lock file
The machine runs eleven containers to work on one service Everything starts by default Move optional services behind profiles
A colleague's compose changes break the stack for everyone Personal adjustments were made to the shared file Use compose.override.yaml, git-ignored
A real credential is in the repository history It was written as a literal in the compose file Rotate it; move it to .env; keep only local-only literals in the file
The stack works locally and the same images fail in CI CI runs without the .env that everyone has locally and nobody has committed Keep .env.example complete, and have CI build its environment from it

11. Definition of done

  • docker compose down -v && docker compose up succeeds on the first attempt, run in CI on a clean runner
  • Every service with dependents declares a healthcheck that exercises the service, not the port
  • The application service depends on migrations with service_completed_successfully, and a deliberately broken migration prevents it from starting — covered by a test
  • All persistent data is in named volumes; a test asserts data survives down and up
  • Exactly one documented command destroys data, and its name says so
  • Saving a source file changes behaviour in under three seconds with no rebuild
  • Changing the lock file triggers a rebuild, verified by observing the build
  • Starting with no profile brings up only the services needed to run the application
  • .env.example lists every variable the stack reads, verified by starting from a copy of it and nothing else
  • No credential in the compose file exists in any other environment, checked by a secret scanner in CI
  • A person who has never run the project reaches a working stack from make up without asking a question — tested with an actual person, once
