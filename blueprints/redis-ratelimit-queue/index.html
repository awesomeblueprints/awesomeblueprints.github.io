Redis Rate Limiting and Job Queues

Redis rate limiting and job queues: sliding windows, atomic Lua counters, reliable queues, retries, dead letters and clean worker shutdown.

medium3–5 daysVerified 2026-08-19
Redis
Read it on GitHub ↗ Back to the catalogue

Two subsystems on the same Redis with opposite guarantees: a limiter whose decisions must be atomic, and a queue whose jobs must survive the worker that was holding one when it died.

Complexity: medium-high · Typical build: 3–5 days · Verified: 2026-08-19 (re-check after ~90 days)

Examples in: Python, with Redis and FastAPI. The architecture is language-agnostic: sections 5, 10 and 11 hold wherever you build this. Section 4 is illustrative — if your project is in another language, your agent translates the idioms rather than importing them, and nothing is lost. The scripted-atomicity and visibility-timeout patterns transfer directly to any Redis client, and to SQS or a database-backed queue with only the primitives changing.

Use when: requests must be bounded per caller, or work must happen outside the request — sending mail, generating a document, calling a slow third party — and losing that work is not acceptable.

Not for: caching. It shares the server and nothing else: a cache may be lost entirely with no consequence, a queued job may not, and a design that treats them alike will lose jobs to an eviction policy. Also not for scheduled orchestration with dependencies between steps — that is a workflow engine, and building one on a queue is a project rather than a feature.

1. Two subsystems, one server, opposite guarantees

These share a dependency and nothing else, and the confusion between them is the most expensive mistake available here.

Cache Queue
Losing everything Costs a slow hour Costs work a user was told had happened
Eviction under memory pressure Correct behaviour Silent data loss
Duplicate processing Meaningless Sends the email twice, charges the card twice
The right maxmemory-policy An evicting one noeviction, or a separate instance

If a queue shares an instance with a cache under an evicting policy, jobs are deleted to make room for cache entries. Nothing errors. The job simply never runs, and the report is "sometimes the email does not arrive" — which is investigated as an email problem for a long time.

The limiter has its own trap, and it is a two-line one:

count = await redis.incr(key)      # request A: 1
if count == 1:
    await redis.expire(key, 60)    # request B ran INCR between these two lines

Two requests arriving together both increment before either sets the expiry. If the process dies in that window — or if the second request's branch never runs — the key has no TTL, the count never resets, and that caller is limited forever. Under low traffic the window is invisible; at the traffic that makes a limiter worth having, it is not. Redis executes a script atomically, so read-then-write becomes one operation.

The queue's version of the same problem is the worker that dies holding a job. If taking a job removes it from the list, the job is gone. If taking it moves it to a per-worker in-flight list, another worker can return it.

The rule the diagram encodes: a job is in exactly one of pending, in-flight or dead-letter at every instant, and every transition is atomic. A design where a job is briefly in neither is a design that loses jobs at exactly the rate its workers crash.

3. Project structure

app/
├── limits/
│   ├── scripts.py     the limiter script, loaded once
│   └── deps.py        the dependency that applies a limit to a route
└── jobs/
    ├── queue.py       enqueue, claim, acknowledge, requeue
    ├── worker.py      the loop, the reaper, signal handling
    └── handlers/      one module per job type

One rule: a job's payload is an identifier, never an object. Enqueue an order id, not the order. The payload is serialised at enqueue time and read minutes later; an embedded object is a snapshot that is already wrong, and it is why a job "sends the old email address" long after the user changed it.

4. Reference implementation

# app/limits/scripts.py
# One round trip, executed atomically. The two-command version — INCR then EXPIRE —
# has a window between them: two concurrent requests both increment before either
# sets the TTL, and if the process dies in that gap the key has no expiry and the
# caller is limited forever.
#
# A sliding window rather than a fixed one: with a fixed window, a caller gets the
# full allowance at 59.9s and again at 60.1s, so the real burst is twice the limit.
SLIDING_WINDOW = """
local key, now, window, limit = KEYS[1], tonumber(ARGV[1]), tonumber(ARGV[2]), tonumber(ARGV[3])
redis.call('ZREMRANGEBYSCORE', key, 0, now - window)
local used = redis.call('ZCARD', key)
if used >= limit then
  local oldest = redis.call('ZRANGE', key, 0, 0, 'WITHSCORES')
  return {0, math.ceil(oldest[2] + window - now)}    -- denied, and when to retry
end
redis.call('ZADD', key, now, ARGV[4])                -- unique member per request
redis.call('EXPIRE', key, math.ceil(window))         -- always, on every allow
return {1, 0}
"""


async def check(key: str, limit: int, window: int) -> tuple[bool, int]:
    try:
        allowed, retry_after = await _script(
            keys=[key], args=[time.time(), window, limit, uuid.uuid4().hex])
    except (redis.RedisError, TimeoutError):
        # Fail open, deliberately, and log it. A limiter that rejects everything
        # when Redis blinks has converted a dependency outage into a full outage —
        # and a limiter exists to protect against abuse, not to be the abuse.
        # Fail closed instead only where the limit protects money or a hard quota.
        log.warning("rate limiter unavailable, allowing")
        return True, 0
    return bool(allowed), retry_after

# app/limits/deps.py
def rate_limit(limit: int, window: int, scope: str):
    async def dep(request: Request, user=Depends(current_user_optional)):
        # Per identified caller when there is one; per address otherwise. Limiting
        # only by address puts an entire office behind one NAT into one bucket,
        # and limiting only by account leaves unauthenticated routes unprotected.
        who = f"user:{user.id}" if user else f"ip:{client_ip(request)}"
        allowed, retry_after = await check(f"rl:{scope}:{who}", limit, window)
        if not allowed:
            # 429 with Retry-After. Without it a client retries immediately and
            # its retries are themselves the load the limiter is trying to shed.
            raise HTTPException(429, "Too many requests",
                                headers={"Retry-After": str(retry_after)})
    return dep

# app/jobs/queue.py
CLAIM = """
local job = redis.call('RPOPLPUSH', KEYS[1], KEYS[2])   -- pending -> in-flight, atomic
if job then redis.call('HSET', KEYS[3], job, ARGV[1]) end  -- claim deadline
return job
"""


async def claim(worker_id: str) -> Job | None:
    """Move a job from pending to this worker's in-flight list, atomically.

    Popping without moving loses the job if the worker dies before it finishes —
    and a worker dies on every deploy, every OOM kill and every node replacement.
    The in-flight list is what lets the reaper return it.
    """
    raw = await _claim_script(
        keys=[PENDING, inflight_key(worker_id), CLAIMS],
        args=[time.time() + VISIBILITY_TIMEOUT])
    return Job.parse(raw) if raw else None


async def acknowledge(worker_id: str, job: Job) -> None:
    # Only after the handler returned. Acknowledging on receipt is at-most-once
    # delivery wearing the clothes of at-least-once.
    await redis.lrem(inflight_key(worker_id), 1, job.raw)
    await redis.hdel(CLAIMS, job.raw)


async def reap() -> int:
    """Return jobs whose claim deadline passed. Runs on a schedule, in one worker.

    This is the only thing that recovers work from a process that died between
    claiming and finishing. Without it the in-flight list grows quietly and the
    jobs in it never run again.
    """
    now = time.time()
    expired = [j for j, deadline in (await redis.hgetall(CLAIMS)).items()
               if float(deadline) < now]
    for job in expired:
        await redis.lpush(PENDING, job)
        await redis.hdel(CLAIMS, job)
    return len(expired)

# app/jobs/worker.py
async def run_worker(worker_id: str) -> None:
    stopping = asyncio.Event()
    # SIGTERM must finish the current job, not abandon it. A worker killed
    # mid-handler is recoverable through the reaper, but only after the visibility
    # timeout — so a clean stop is the difference between instant and delayed.
    loop.add_signal_handler(signal.SIGTERM, stopping.set)

    while not stopping.is_set():
        job = await claim(worker_id)
        if job is None:
            await asyncio.sleep(POLL_INTERVAL)
            continue
        try:
            # Bounded. An unbounded handler holds a claim past its deadline, the
            # reaper requeues the job, and it then runs twice concurrently.
            async with asyncio.timeout(JOB_TIMEOUT):
                await HANDLERS[job.type](job.payload)
            await acknowledge(worker_id, job)
        except Exception:
            if job.attempts + 1 >= MAX_ATTEMPTS:
                # A dead letter, not a silent drop and not an infinite retry. A job
                # retried forever is a permanent load and hides the bug behind it.
                await dead_letter(worker_id, job)
            else:
                await requeue(worker_id, job, delay=backoff(job.attempts))

5. Golden-standard rules

Rule Why
Forbidden: a queue on an instance with an evicting memory policy Jobs are deleted to make room for cache entries, silently. This is why "sometimes the email does not arrive".
Forbidden: read-then-write across two round trips in a limiter Concurrent callers race the gap; a key can end up with no expiry and limit someone forever. Use one atomic script.
Forbidden: popping a job without moving it to an in-flight list The job is lost if the worker dies, and workers die on every deploy.
Forbidden: acknowledging a job before the handler finished That is at-most-once delivery pretending to be at-least-once.
Forbidden: an unbounded job handler It holds its claim past the deadline, the reaper requeues, and the job runs twice at once.
Forbidden: a job payload containing an object rather than an identifier It is a snapshot that was already stale when the worker read it.
Every job is written to be safe to run twice The queue is at-least-once by design. Duplicates are normal operation, not an incident.
Failed jobs go to a dead letter after a bounded number of attempts Infinite retry is a permanent load that hides the bug causing it.
The reaper runs, and its output is monitored It is the only recovery path for a crashed worker, and its absence is invisible until work quietly stops.
The limiter fails open unless it guards money or a hard quota Otherwise a dependency blink becomes a full outage, caused by the thing meant to prevent one.
A 429 carries Retry-After Without it clients retry immediately, and the retries are the load being shed.
Limits key on the identified caller when there is one Address-only puts a whole office behind one NAT into a single bucket.
Workers finish the current job on SIGTERM Otherwise every deploy delays work by a visibility timeout.

6. Data contracts

job     {"id": "01J...", "type": "order.confirm", "payload": {"order_id": 42},
         "attempts": 0, "enqueued_at": 1755600000}
states  pending -> in-flight -> done, or -> pending (retry), or -> dead-letter
        exactly one at any instant; every transition atomic

The delivery guarantee is at least once, and saying so plainly is the point. Every handler must therefore be safe to run twice — not because something is broken, but because a worker dying between finishing the work and acknowledging it is normal, and no arrangement of these primitives removes that window.

The limiter's contract is the response: 429 with Retry-After, and a limit that is per caller and per scope so one endpoint's traffic cannot exhaust another's allowance.

7. Build order

  1. Confirm the memory policy, and separate the queue from the cache if they share an instance. This is one configuration check that prevents the worst failure in the document.
  2. The limiter as one atomic script, with a concurrency test: fire more parallel requests than the limit and assert exactly limit were allowed.
  3. 429 with Retry-After, and the failure-open path with a test that Redis being down allows traffic rather than blocking it.
  4. Enqueue, claim into in-flight, acknowledge — then kill a worker mid-job and assert the job is still in-flight rather than gone.
  5. The reaper, and a test that the killed worker's job runs again.
  6. Retries with backoff and the dead letter, with a test for a permanently failing job.
  7. Job timeouts and SIGTERM handling, then run the whole thing under a rolling restart and assert nothing was lost or duplicated beyond what is expected.

Steps 4 and 5 are the pair that matters. Testing them separately proves nothing: the guarantee is that a crash loses no work, and only killing a worker demonstrates it.

10. Failure modes

Symptom Cause Fix
Jobs vanish occasionally, with no error anywhere The queue shares an instance with a cache under an evicting policy Separate instances, or noeviction for the queue
One caller is rate-limited permanently and no window resets them The counter key was created without a TTL because the process died between INCR and EXPIRE One atomic script that always sets the expiry
A caller gets roughly twice the intended burst A fixed window: the full allowance at the end of one and again at the start of the next Sliding window
Work is lost on every deploy Jobs were popped rather than moved to an in-flight list, or workers are killed mid-handler Atomic claim into in-flight; finish the current job on SIGTERM
The in-flight list grows and those jobs never run No reaper, or the reaper stopped and nobody noticed Run it on a schedule; alert on in-flight age
A job runs twice concurrently The handler exceeded the visibility timeout and the reaper requeued it while it was still running Bound the handler below the visibility timeout
A broken job retries forever and saturates the workers No attempt limit Dead-letter after a bounded number of attempts
The whole API returns 429 during a Redis blip The limiter fails closed Fail open and log, except where the limit guards money
Clients hammer the endpoint harder after being limited The 429 carries no Retry-After Include it, computed from the window
An entire office is limited because of one user The key is the source address only Key on the identified caller where one exists
A job acts on stale data — an old email address, an old price The payload embedded an object instead of an identifier Enqueue an id; load the current state in the handler
Queue depth is fine and users still wait Depth is not the metric; the age of the oldest pending job is Monitor age, not only depth

11. Definition of done

  • The queue's Redis instance does not evict, verified by querying the running server's policy
  • Firing more concurrent requests than the limit allows exactly the limit, covered by a concurrency test
  • Every counter key has a TTL, verified by inspecting keys after a burst
  • A rejected request returns 429 with a Retry-After computed from the window, covered by a test
  • With Redis unavailable, requests are allowed and the event is logged, covered by a test
  • Killing a worker mid-job leaves the job recoverable, and the reaper runs it again — one test covering both
  • A job handler exceeding its timeout is cancelled before its claim expires, covered by a test
  • A permanently failing job reaches the dead letter after the configured attempts and stops retrying, covered by a test
  • SIGTERM lets the current job finish before the worker exits, covered by a test
  • Every job payload contains identifiers only, checked by review of the handler signatures and asserted for at least one job type
  • Every handler is safe to run twice, demonstrated by a test that runs one twice and asserts the effect happened once
  • Queue depth, oldest-pending age, in-flight age and dead-letter count are all exported as metrics
