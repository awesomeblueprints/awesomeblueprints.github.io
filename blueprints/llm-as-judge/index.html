LLM-as-a-Judge Evaluation

LLM-as-a-judge evaluation: rubrics, position and verbosity bias, self-preference, and calibration against human labels so a score means something.

medium3–4 daysVerified 2026-08-20
Evals
Read it on GitHub ↗ Back to the catalogue

Using an LLM to grade LLM output, built so the score means something: a rubric that produces the same verdict twice, a measured agreement with human labels, and the three biases that otherwise make the number confident and wrong.

Complexity: medium · Typical build: 3–4 days · Verified: 2026-08-20 (re-check after ~90 days)

Examples in: Python. The architecture is language-agnostic: sections 5, 10 and 11 hold wherever you build this. Section 4 is illustrative — if your project is in another language, your agent translates the idioms rather than importing them, and nothing is lost. Nothing here needs an evaluation framework; the frameworks that exist are conveniences over the same rubric, the same swap, and the same calibration table.

Use when: you change prompts or models often enough that hand-grading has become the bottleneck, and the quality you care about cannot be checked by an assertion.

Not for: anything a deterministic check can decide. If the answer is valid JSON or not, contains a required field or not, matches a known result or not — assert it. A judge costs money, latency and a calibration programme, and spending all three to check something == could have decided is the most common way this goes wrong. Also not for a first prompt with no version to compare against: with nothing to compare, a score is a number with no meaning attached.

1. Three biases, with numbers

A judge is not a measuring instrument until it has been checked against one. Three distortions are documented well enough to design around, and all three produce scores that look reasonable:

Position bias. In pairwise comparison, the order the two answers are shown in changes the verdict. Published swap-consistency rates for widely used models fall roughly between 70% and 78%, meaning something like a quarter of verdicts flip when the same two answers are presented in the opposite order; the flips are not random, they favour whichever answer came first. Design response: run every pairwise comparison twice with the positions reversed, and treat a disagreement as a tie rather than picking one. This doubles the cost of pairwise judging and it is not optional — a pairwise judge without a swap is measuring presentation order.

Verbosity bias. Judges prefer longer answers, at a rate reported around 17 percentage points above human preference for the same pairs. Design response: say so in the rubric ("a concise correct answer outranks a wordy partly-correct one"), which helps and does not fix it, and then measure the residue by regressing score on length. Length-controlled scoring — fitting the length effect and reporting the score with it removed — is the technique that actually works; published work applying it reports rank correlation with human preference rising from 0.94 to 0.98.

Self-preference. Models score text resembling their own output higher, independent of quality. Design response: never judge a model with a model from the same family. This is one line of configuration and it is the highest-value decision in this document.

The conclusion those three add up to: a judge's output is a measurement whose error you must estimate, not a verdict. Everything in §4 is machinery for estimating it.

The rule about what a judge is for

If a deterministic check can decide it, a judge must not.

Applied literally, this removes most of what people put in judge rubrics: valid JSON, required fields present, no forbidden strings, length within a limit, citations resolving to real documents, a numeric answer matching a known one. All assertions. What is left for the judge is genuinely and irreducibly a matter of degree — is this answer faithful to the source, is the tone appropriate, does it address what was asked — and that shorter list is also the list a judge is reasonably good at.

The edge that most implementations lack is audit -> report. Every reported score carries the judge's current agreement with human labels, because a score of 7.4 from a judge agreeing with people 62% of the time and the same 7.4 from a judge at 88% are different facts, and a report that renders them identically will be acted on identically.

evals/
├── cases/

│   └── labelled.jsonl        human verdicts — the scarce, valuable file
├── rubrics/
│   └── faithfulness.v2.md    one criterion per rubric, version in the filename
├── checks.py                 deterministic assertions, run before any judge call
├── judge.py                  the judge call, schema-constrained
├── swap.py                   the reversed-position pass and the tie rule
├── aggregate.py              length control and per-criterion aggregation
└── audit.py                  agreement, swap consistency, length correlation

One rule: one rubric file, one criterion. A rubric asking for helpfulness, accuracy and tone in one call returns one number that averages three incommensurable things, and when it moves you cannot say which one moved. Separate calls cost more and are the only version that answers a question.

4. Reference implementation

# evals/judge.py
from pydantic import BaseModel, Field


class Verdict(BaseModel):
    # Reasoning first, deliberately: the field order is the generation order, so
    # putting the score first makes the reasoning a justification written after
    # the fact. This ordering is free and it measurably changes the verdict.
    reasoning: str = Field(max_length=600)
    score: int = Field(ge=1, le=5)
    # A five-point scale, not a hundred-point one. Judges do not distinguish 73
    # from 76 — the extra resolution is noise that looks like signal, and it is
    # the first thing to remove when scores are unstable.


async def judge(case: dict, answer: str, rubric: str) -> Verdict:
    """One criterion, one call, schema-constrained.

    The judge model must not come from the same family as the model that produced
    `answer`: models score text resembling their own output higher regardless of
    quality, and this configuration line is the cheapest correction available.
    """
    assert settings.judge_family != settings.generator_family, "self-preference"
    return await judge_client.structured(
        model=settings.judge_model,
        schema=Verdict,
        temperature=0,          # A judge is a measurement; variance here is error
        seed=settings.eval_seed,
        messages=[
            {"role": "system", "content": rubric},
            {"role": "user", "content": render_case(case, answer)},
        ],
    )

# evals/rubrics/faithfulness.v2.md  (excerpt)
"""
Score 1 to 5 for faithfulness to the source text only. Ignore style, ignore
length, ignore whether the answer is interesting.

5 — every claim is supported by the source; nothing is added
4 — every claim is supported; one detail is imprecise but not wrong
3 — one unsupported claim that does not change the meaning
2 — an unsupported claim that changes the meaning
1 — contradicts the source

Do not prefer longer answers. A concise correct answer outranks a wordy
partly-correct one.

Each level is written so two people applying it to the same answer would agree.
If you cannot write the levels that way, the criterion is not ready to be judged
and the rubric is the thing to fix, not the model.
"""

# evals/swap.py
async def compare(case: dict, a: str, b: str, rubric: str) -> str:
    """Pairwise comparison, run in both orders.

    Roughly a quarter of verdicts flip when the order is reversed, and the flips
    favour whichever answer came first. A pairwise judge without this pass is
    partly measuring presentation order. Cost doubles; that is the price of the
    result meaning anything.
    """
    first = await judge_pair(case, a, b, rubric)
    second = await judge_pair(case, b, a, rubric)
    if first.winner != _mirror(second.winner):
        # Disagreement becomes a tie, not a coin flip. Recording it separately is
        # what makes swap consistency measurable at the aggregate level.
        return "tie:inconsistent"
    return first.winner

# evals/audit.py
import numpy as np


def audit(labelled: list[dict]) -> dict:
    """The measurement of the measurement. Run monthly and after every rubric
    change; providers update models without notice, so a judge validated once is
    a judge validated at one point in time.
    """
    agreement = np.mean([row["judge"] == row["human"] for row in labelled])
    swap_consistency = np.mean([row["order_a"] == row["order_b"] for row in labelled])
    # The slope of score against answer length. A strong positive slope means the
    # judge is partly measuring verbosity, and scores should be reported with the
    # length effect fitted out rather than raw.
    length_slope = np.polyfit(
        [len(r["answer"].split()) for r in labelled],
        [r["judge"] for r in labelled], 1)[0]
    return {
        "agreement": agreement,           # below ~0.75, the judge is not usable
        "swap_consistency": swap_consistency,  # below ~0.80, escalate to people
        "length_slope": length_slope,
        "n": len(labelled),
    }

# evals/runner.py  (excerpt)
async def evaluate(prompt_version: str) -> Report:
    for case in cases:
        answer = await generate(case, prompt_version)
        failures = deterministic_checks(answer, case)   # first, and free
        if failures:
            record(case, hard_fail=failures)
            continue          # no judge call: nothing to grade about broken output
        for rubric in RUBRICS:                # one call per criterion, never merged
            record(case, rubric, await judge(case, answer, rubric))
    # Every report carries the judge's current agreement. A score without it
    # invites a decision the number does not support.
    return Report(results=results, judge_audit=load_latest_audit(),
                  prompt_version=prompt_version)

5. Golden-standard rules

Rule Why
Forbidden: judging anything a deterministic check can decide It costs money and adds variance to answer a question == answers exactly.
Forbidden: a judge from the same model family as the model under test Self-preference inflates the score independently of quality; this is one configuration line.
Forbidden: pairwise comparison without a reversed-position pass Roughly a quarter of verdicts flip on order, favouring the first answer shown.
Forbidden: several criteria in one rubric or one call The result is one number averaging incommensurable things, and its movement is unattributable.
Forbidden: a judge in production without a measured agreement figure The score is then an opinion presented with the authority of a metric.
Forbidden: non-zero temperature in a judge call A measuring instrument with deliberate variance measures its own noise.
Forbidden: comparing scores across rubric versions The instrument changed; the difference is not a change in quality.
The score field comes after the reasoning field in the schema Field order is generation order; a score written first turns the reasoning into a rationalisation.
Scales are coarse — five points, not a hundred Judges do not distinguish fine gradations; the extra resolution is noise shaped like signal.
Every rubric level is written so two people would agree on it If you cannot write it that way, the criterion is not ready and the rubric is what to fix.
The rubric states that length is not a merit It reduces verbosity bias; it does not remove it, which is why the slope is measured too.
Scores are reported with the length effect fitted out Fitting it out is what raises correlation with human preference; raw scores carry the bias.
A human-labelled calibration set exists, 100–300 cases, and is re-audited monthly Providers update models silently; a judge validated once is validated at one moment.
Inconsistent swaps become ties, and are counted Counting them is what makes swap consistency an observable number rather than an assumption.
The prompt version, the judge model and the rubric version are recorded with every score Otherwise no result can be reproduced or attributed.

6. Data contracts

case         input, plus any deterministically checkable expectation
verdict      reasoning, then score on a coarse scale, schema-constrained
result row   case id, prompt version, judge model, rubric version, score, length
audit row    agreement, swap consistency, length slope, n, date

The calibration file is the asset. It is the only thing in this system that connects a number to a human judgement, it is slow to produce, and it decays as the product changes. Treat it accordingly: versioned in the repository, reviewed when the product's definition of a good answer moves, and grown from real disagreements rather than from cases someone invented.

Two thresholds, both from published practice, both worth writing into the audit rather than holding informally: agreement below about 75% means the judge is not usable for the decision it is being asked to inform, and swap consistency below about 80% means pairwise results on that criterion should go to a person.

7. Build order

  1. The deterministic checks, and the evaluation runner around them. No judge yet. This is where most of the value is and it is where the discipline of not judging what can be asserted gets established.
  2. The case file, versioned, built from real inputs including the ones that have failed before.
  3. The calibration set — a hundred cases, labelled by a person, before any judge is written. Building it afterwards means tuning a judge against itself, and the temptation to relabel the cases it got wrong is very strong once the judge exists.
  4. One rubric, one criterion, one schema-constrained call at temperature zero.
  5. The audit, immediately, against the calibration set. If agreement is under the floor, the rubric is what to fix, and this is the moment to find that out.
  6. The swap pass, if the design is pairwise.
  7. Length control in aggregation, once there is enough data to fit it.
  8. Reporting with the agreement figure attached, and the monthly re-audit as a scheduled job.

Step 3 before step 4 is the one people skip, and it is the one that determines whether anything downstream means anything.

9. Metrics

Metric Target
Judge agreement with human labels > 75%, measured monthly, reported with every score
Swap consistency on pairwise criteria > 80%; below that, escalate to a person
Correlation of score with answer length, after length control |slope| near zero
Criteria judged that a deterministic check could decide 0
Judge and generator from the same model family 0 criteria
Calibration set size 100–300 labelled cases, refreshed as the product changes
Scores reported without an accompanying agreement figure 0
Cost per evaluation run Known, and compared against the hand-grading it replaced
Time from a prompt change to a score < 15 minutes

10. Failure modes

Symptom Cause Fix
Scores are high and users are unhappy The judge was never calibrated against human labels Build the calibration set; measure agreement before trusting any score
Reversing the two answers changes the winner Position bias Run both orders; treat disagreement as a tie and count it
Longer answers consistently win Verbosity bias Say so in the rubric, then fit the length effect out of the reported score
A model scores its own family's output highest Self-preference Use a judge from a different provider family
Scores drift with no change on your side The provider updated the judge model silently Monthly re-audit; pin the judge version where the provider allows it
The same input scores differently on reruns Non-zero temperature, or a scale too fine to be stable Temperature zero and a seed; coarsen the scale
A score moved and nobody can say which aspect changed Several criteria merged into one rubric One criterion per rubric, one call each
The judge grades broken output on style Deterministic checks were not run first, or did not gate Assert first; skip the judge when hard checks fail
Reasoning reads as a justification for the score The score field precedes the reasoning field Reorder the schema
Evaluation costs more than the hand-grading it replaced Judging things assertions could decide, or judging every case on every criterion Prune the rubric list to what is irreducibly a matter of degree
Results cannot be reproduced Prompt version, judge model or rubric version not recorded Record all three on every row
Two releases are compared and the comparison is meaningless The rubric changed between them Version rubrics; never compare across versions

11. Definition of done

  • Deterministic checks run before any judge call and gate it, verified by reading the runner
  • No criterion is judged that an assertion could decide, verified by reviewing the rubric list one by one
  • The judge model is from a different family than the model under test, asserted in code
  • Judge calls run at temperature zero with a fixed seed where the provider supports one
  • Each rubric covers exactly one criterion and lives in a file with its version in the name
  • Every rubric level is written concretely enough that two people applying it would agree
  • The verdict schema places reasoning before the score, and the scale has five or fewer points
  • A human-labelled calibration set of at least 100 cases exists, versioned in the repository
  • An audit reports agreement, swap consistency and length slope, and it runs monthly as a scheduled job
  • Agreement is above 75%; if it is not, the rubric was revised rather than the threshold lowered
  • Pairwise comparisons run in both orders, and inconsistent pairs are recorded as ties and counted
  • Reported scores have the length effect fitted out, and the raw slope is tracked
  • Every score row records case id, prompt version, judge model and rubric version
  • Every report displays the judge's current agreement figure alongside the scores
  • Cost per run is measured and compared against the hand-grading it replaces
