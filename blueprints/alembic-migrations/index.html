Alembic Schema Migrations

Alembic migrations done properly: autogenerate review, safe rollbacks, zero-downtime column changes and one ordered history across environments.

medium2–3 daysVerified 2026-08-19
PostgreSQL
Read it on GitHub ↗ Back to the catalogue

Schema changes as reviewable, reversible, ordered files — with autogenerate treated as a first draft, because the changes it silently omits are the ones that cost you data, and the ones it gets wrong lock a production table.

Complexity: medium · Typical build: 2–3 days · Verified: 2026-08-19 (re-check after ~90 days)

Examples in: Python, with Alembic and SQLAlchemy 2.0 against PostgreSQL. The architecture is language-agnostic: sections 5, 10 and 11 hold wherever you build this. Section 4 is illustrative — if your project is in another language, your agent translates the idioms rather than importing them, and nothing is lost. The equivalents are Prisma Migrate or Drizzle Kit in TypeScript, Ecto migrations in Elixir, golang-migrate in Go, and ActiveRecord migrations in Rails — where autogenerate's blind spots are the same blind spots.

Use when: more than one person or more than one environment runs the same schema, and you need the change that worked on a laptop to arrive identically in production, in order, with a way back.

Not for: a database whose schema is owned by another team or another service. Running migrations against a schema you do not own turns a deploy into a cross-team incident. Also not for data backfills large enough to need batching and resumption — those are jobs with progress and restartability, and hiding one inside a migration means a failed deploy halfway through a rewrite.

⚙️ INSTRUCTIONS FOR THE AI — READ BEFORE WRITING ANY CODE

Do not start coding.

Step 1 — Refresh. Verify the installed Alembic version and confirm these defaults, because two of them changed and the wrong assumption produces migrations that omit real changes: compare_type (now on by default) and compare_server_default (off by default, and it must be turned on deliberately). Confirm the current async env.py recipe — running migrations against an async driver needs connection.run_sync, and examples written for the sync engine will not work. Confirm what autogenerate still does not detect: renames, unnamed constraints, sequences, and primary key or exclusion constraint changes. Report what you verified and what turned out wrong.

Step 2 — Read the project, then audit what already exists. Determine whether the database already has tables that no migration created — if so, the first migration must be a baseline that is stamped rather than run, and getting that wrong drops production tables. Find the metadata object the models share and whether it carries a naming convention. Check for more than one head in the existing revision history. Find how migrations run today: a container entrypoint, a deploy step, a human. Find whether any migration contains a data change. Then audit §11 item by item, each marked already true, partly true or absent, with the file that decides it, reported before anything is proposed.

Assume the project is right until it demonstrably is not; code satisfying an item stays even where its shape differs from §4; replacing something that works needs a one-line reason; never delete a working path to make room for the blueprint's version. The same holds for language — §4 is illustrative, its idioms get translated into the project's language, and §11 is what has to become true rather than the syntax.

Step 3 — Write a plan for the gap only, and get it approved, including a ## Proposed stack section and, explicitly, where migrations will run and what happens when one fails halfway. Do not ask open framework questions — propose, and ask for confirmation once. Say what you are adding, what you are leaving alone, and what you propose to change, and touch nothing else.

Step 4 — Build in the order in §7. Step 5 — §11 is the definition of done.

1. Why autogenerate is a draft, not an answer

Autogenerate diffs your models against the live schema and writes a migration. It is genuinely good at the common case, and the temptation is to treat its output as finished. The problem is not that it makes mistakes you can see. It is that its gaps are silent.

What it looks like it does What it actually does
Detects that you renamed a column Emits a drop of the old column and an add of the new one — the migration passes, and the data is gone
Detects constraint changes Cannot compare a constraint whose name the database invented, so the change is simply absent from the file
Detects type changes Compares types, but only the arguments the two types share
Detects default changes Ignores server defaults entirely unless you switch that on
Produces a migration you can run Produces a migration whose lock behaviour it has no opinion about

The rename row is the expensive one. Drop-and-add is a valid migration, it applies cleanly, the tests pass because the tests use the new name — and the column's contents are gone with no error anywhere. Nothing about the workflow will tell you; you find out when someone asks for the old values.

So the rule is not "check autogenerate's work". It is: autogenerate produces a draft, and a human reads every line before it is committed. The parts it cannot see are exactly the parts that are expensive.

The second theme is locks. A migration that is correct can still take a production table offline: on PostgreSQL, adding a non-nullable column, adding a unique or indexed column, or adding a constraint takes an ACCESS EXCLUSIVE lock, and a foreign key takes a share-row-exclusive lock on both tables. Under load the lock does not just block writers — it queues behind long readers and then blocks everything arriving after it.

The rule the diagram encodes: the migration step is not the application. There is one arrow from the pipeline into a job that runs alone, and the application instances start only after it succeeds. Running migrations from the application's own startup means every replica races to apply the same migration at the same moment.

3. Project structure

migrations/
├── env.py              async-aware; imports the metadata, sets the comparison flags
├── script.py.mako      the template every revision is generated from
└── versions/
    └── 20260819_1430_a1b2c3_add_orders_table.py
alembic.ini             file naming template and logging; the URL comes from settings

One rule: the database URL is read from application settings inside env.py, never written in alembic.ini. A URL in the ini file is a second source of truth that drifts from the application's, and it is the reason someone eventually runs a migration against staging while believing they are on a local database.

4. Reference implementation

# migrations/env.py
import asyncio
from alembic import context
from sqlalchemy.ext.asyncio import async_engine_from_config
from sqlalchemy import pool
from app.config import get_settings          # one source of truth for the URL
from app.db.base import Base
import app.models                            # imported for the side effect: a model
                                             # module that is never imported is invisible
                                             # to autogenerate, and its table is silently
                                             # proposed for deletion

target_metadata = Base.metadata
config = context.config
config.set_main_option("sqlalchemy.url", str(get_settings().database_url))


def do_run_migrations(connection) -> None:
    context.configure(
        connection=connection,
        target_metadata=target_metadata,
        # On by default in current versions, stated explicitly so an upgrade or a
        # downgrade of Alembic cannot change what your migrations detect.
        compare_type=True,
        # Off by default. Without it, changing a column's server default produces an
        # empty migration and the old default stays in the database forever.
        compare_server_default=True,
        # Each migration in its own transaction. A failure then leaves the earlier
        # migrations applied and recorded, so a retry resumes rather than restarting.
        transaction_per_migration=True,
        # Postgres-specific DDL that autogenerate would otherwise render generically.
        include_schemas=False,
    )
    with context.begin_transaction():
        # Never wait behind a long-running query for an ACCESS EXCLUSIVE lock. Failing
        # fast turns a potential outage into a failed deploy you can retry off-peak.
        connection.exec_driver_sql("SET lock_timeout = '5s'")
        connection.exec_driver_sql("SET statement_timeout = '300s'")
        context.run_migrations()


async def run_async_migrations() -> None:
    connectable = async_engine_from_config(
        config.get_section(config.config_ini_section, {}),
        poolclass=pool.NullPool,      # a migration run is one connection, once
    )
    async with connectable.connect() as connection:
        # The migration API is synchronous; run_sync drives it inside the greenlet
        # the async engine provides. This is the whole reason an async env.py differs.
        await connection.run_sync(do_run_migrations)
    await connectable.dispose()


asyncio.run(run_async_migrations())

# migrations/versions/20260819_1430_a1b2c3_add_order_status.py
"""add order status

Adding a NOT NULL column to a populated table rewrites it under an ACCESS EXCLUSIVE
lock. This is the three-step version: add nullable with a server default, backfill,
then enforce. Each step is safe to run while the application is serving.
"""
from alembic import op
import sqlalchemy as sa

revision = "a1b2c3"
down_revision = "9f8e7d"


def upgrade() -> None:
    # Step 1 — nullable, with a server default so new rows are already correct.
    op.add_column(
        "orders",
        sa.Column("status", sa.String(20), nullable=True, server_default="pending"),
    )
    # Step 2 — backfill. Small tables only. A table large enough to need batching
    # belongs in a separate job: a migration that fails halfway through a rewrite
    # leaves a deploy stuck with no progress to resume from.
    op.execute("UPDATE orders SET status = 'pending' WHERE status IS NULL")
    # Step 3 — enforce. Cheap here only because step 2 guaranteed no nulls remain.
    op.alter_column("orders", "status", nullable=False)


def downgrade() -> None:
    # Reversible on purpose. A downgrade that raises NotImplementedError is a
    # migration you cannot roll back, discovered during the incident that needs it.
    op.drop_column("orders", "status")

# migrations/versions/20260819_1500_b2c3d4_add_orders_customer_index.py
"""add index on orders.customer_id

CREATE INDEX takes a lock that blocks writes for its whole duration. CONCURRENTLY
does not, but it cannot run inside a transaction — so this revision opts out of the
per-migration transaction rather than being merged into a neighbouring one.
"""
from alembic import op

revision = "b2c3d4"
down_revision = "a1b2c3"


def upgrade() -> None:
    with op.get_context().autocommit_block():
        op.create_index(
            "ix_orders_customer_id", "orders", ["customer_id"], postgresql_concurrently=True
        )


def downgrade() -> None:
    with op.get_context().autocommit_block():
        op.drop_index("ix_orders_customer_id", postgresql_concurrently=True)

5. Golden-standard rules

Rule Why
Forbidden: committing an autogenerated migration unread Renames come out as drop-plus-add. The migration applies cleanly, the tests pass, and the data is gone with no error anywhere.
Forbidden: running migrations from application startup Every replica races to apply the same revision at the same moment, and the losers crash-loop. Migrations are a step that runs once, alone, before instances start.
Forbidden: a downgrade() that raises or is empty It is not reversible then, and you discover that during the incident that needs the rollback. If a step genuinely cannot be reversed, say so in the docstring and stop the release train there deliberately.
Forbidden: more than one head reaching the main branch Two migrations claiming the same parent means the schema depends on which merged first. Fail CI on it.
Forbidden: a large backfill inside a migration A failure halfway leaves a deploy blocked with no resumable progress. Batching and restartability make it a job, not a migration.
Add a NOT NULL column in three steps Nullable with a server default, backfill, enforce. One step takes an ACCESS EXCLUSIVE lock and rewrites the table while the application waits.
Indexes are created concurrently, in their own revision A plain CREATE INDEX blocks writes for its duration; the concurrent form cannot run inside a transaction, so it needs its own autocommit revision.
lock_timeout is set for every migration run Otherwise the migration queues for the lock behind a long reader — and everything arriving after it queues behind the migration. A failed deploy is cheaper than that.
compare_server_default is turned on explicitly It is off by default, and with it off a changed default produces an empty migration and the old default stays forever.
Every model module is imported by env.py A model that autogenerate cannot see is a table it proposes to drop.
The database URL comes from application settings An ini file with its own URL is a second source of truth, and it is why someone eventually migrates staging while believing they are local.
Constraint naming conventions exist before the first table Autogenerate cannot compare a constraint whose name the database invented, so those changes are silently absent.
An existing database gets a stamped baseline, not a first migration Running a generated "initial" migration against populated tables drops them.

6. Data contracts

The contract is the revision graph, and it has three invariants:

one head          every revision reachable from exactly one linear history
reversible        upgrade() and downgrade() are inverses, proven by running both
idempotent apply  running the same revision twice is impossible, enforced by the
                  version table, not by the migration's own logic

A migration is also a contract with the running application, and this is the one that gets missed. During a rolling deploy, the old code runs against the new schema. Dropping a column the previous version still selects breaks every instance that has not yet been replaced. That is why removals happen a release after the code stops using them, never in the same one.

7. Build order

  1. Initialise, wire env.py to the models' metadata and the settings URL, generate the first migration, apply it to an empty database. On a database that already has tables, stamp the baseline instead and confirm nothing runs.
  2. Set the comparison flags and prove them: change a column type and a server default, and confirm each appears in a generated migration.
  3. Prove reversibility as a habit: upgrade, downgrade, upgrade again on a throwaway database, and put that sequence in CI.
  4. Add the head check to CI, and confirm it fails on a deliberately branched history.
  5. Make migrations a deploy step that runs before instances start, with a failure stopping the rollout.
  6. Set lock_timeout and transaction_per_migration, and write the three-step NOT NULL pattern into the review checklist.
  7. Practise a failure: kill a migration halfway on a copy of production and confirm the retry resumes rather than restarting.

Step 3 before step 5 deliberately. A rollback you have never executed is not a rollback, and the first time you run one should not be during an incident.

8. Blocks to pull in

Nothing here is a prerequisite. These are adjacent problems, by name only — resolve them separately if they apply.

  • SQLAlchemy async ORM layer — the metadata these migrations are generated from
  • PostgreSQL connection pool and lifecycle — the database they apply to
  • GitHub Actions CD — where the migration step sits in a deploy
  • Integration tests with real dependencies — where migrations are applied to a test database
  • Background jobs and workers — where a large backfill belongs instead

9. Metrics

Metric Target
Heads in the revision history Exactly 1, checked in CI
Migrations whose downgrade() has been executed at least once 100%, in CI
Lock wait during a migration Bounded by lock_timeout, ≤ 5 s
Application instances starting before the migration step completes 0
Deploys rolled back because a migration broke the previous version still running 0
Autogenerated migrations committed without a human edit or an explicit "reviewed, no changes" note 0

10. Failure modes

Symptom Cause Fix
A column's data is gone after a deploy, and the migration applied cleanly A rename was autogenerated as drop-plus-add Hand-edit renames into alter_column(new_column_name=...); this is why the draft gets read
A generated migration is empty although the model changed The change was a server default, and compare_server_default is off by default Turn it on in env.py
A generated migration proposes dropping tables you still use The model module is not imported by env.py, so its tables are absent from the metadata Import every model module in env.py
The whole application stalls during a deploy, then recovers The migration queued for an ACCESS EXCLUSIVE lock behind a long reader, and every new query queued behind the migration Set lock_timeout; use the three-step pattern; create indexes concurrently
Several replicas crash-loop during a deploy, one succeeds Migrations run from application startup and every replica raced for them Move migrations to a step that runs once before instances start
Multiple head revisions are present Two branches each added a revision with the same parent alembic merge, and add the head check to CI so it cannot reach the main branch again
A migration fails halfway and the retry starts from the beginning Everything ran in one transaction, so nothing was recorded transaction_per_migration=True
A rollback is needed and downgrade() raises Reversibility was never tested, and the stub was never filled in Run upgrade-downgrade-upgrade in CI on every revision
A deploy breaks the previous version while it is still serving A column or table the old code still reads was dropped in the same release that stopped using it Split into two releases: stop using it, then remove it
The initial migration dropped a populated production database A generated "initial" migration was run against a database that already had tables Stamp the baseline instead; never run a generated initial against existing data
A concurrent index creation fails with "cannot run inside a transaction block" It was placed in an ordinary revision, which Alembic wraps in a transaction Put it in its own revision inside an autocommit block
Migrations succeed locally and fail in CI with a lock timeout CI runs against a database with concurrent activity that the laptop did not have Keep the timeout; it is telling you what production will do

11. Definition of done

  • alembic heads returns exactly one revision, checked in CI on every pull request
  • CI runs upgrade to head, downgrade to base, and upgrade to head again on a fresh database, and fails on any revision that cannot be reversed
  • compare_type and compare_server_default are both set explicitly in env.py, with a test proving a changed server default appears in a generated migration
  • Every model module is imported by env.py, verified by a test asserting that autogenerate against the current database produces an empty diff
  • lock_timeout and statement_timeout are set for the migration run, verified by reading the settings inside a migration
  • Migrations run as a step that completes before any application instance starts, and a failing migration stops the rollout — demonstrated once by deliberately failing one
  • transaction_per_migration is enabled, proven by failing the second of two migrations and confirming the first stayed applied and recorded
  • No migration file contains a data change that iterates more rows than a stated threshold, checked by review and recorded in the review checklist
  • Adding a non-nullable column is done in three revisions, with a test or a documented example of the pattern in the repository
  • Every index creation on an existing table uses the concurrent form in its own revision
  • The database URL appears in no committed file; env.py reads it from application settings
  • For an existing database, a baseline revision was stamped rather than run, and the version table shows it
