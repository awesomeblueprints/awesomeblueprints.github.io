GitHub Actions CI

GitHub Actions CI: pull-request workflows, dependency caching, service containers and required checks that genuinely block a merge.

low1–2 daysVerified 2026-08-19
CI/CD
Read it on GitHub ↗ Back to the catalogue

Every pull request checked the same way: lint, types, tests against real dependencies, and a build — with third-party actions pinned to immutable commits, the token scoped down, and superseded runs cancelled so the queue reflects reality.

Complexity: low · Typical build: 1–2 days · Verified: 2026-08-19 (re-check after ~90 days)

Examples in: GitHub Actions with a Python service. The architecture is language-agnostic: sections 5, 10 and 11 hold wherever you build this. Section 4 is illustrative — if your project is in another language, your agent translates the idioms rather than importing them, and nothing is lost. The concerns map directly onto GitLab CI, Buildkite and CircleCI; only the syntax and the name of the token change.

Use when: more than one person merges into a shared branch, or one person merges often enough to have broken it once. Covers the pull-request workflow, dependency caching, service containers, and making the checks actually block a merge.

Not for: deployment. That is a different trust boundary — it needs credentials, environments and approvals, and mixing it into the pull-request workflow is how a fork's pull request gets to run with production access. Also not a substitute for tests: a pipeline running a weak suite tells you the suite is weak, on a schedule.

⚙️ INSTRUCTIONS FOR THE AI — READ BEFORE WRITING ANY CODE

Do not start coding.

Step 1 — Refresh. Verify the current major of every action you will use, and resolve each to a full commit SHA — tags are mutable and have been moved maliciously in real incidents, so the tag is a label, not an identity. Verify the default permissions for GITHUB_TOKEN in this repository, since the organisation default may be permissive. Confirm the current syntax for service containers, dependency caching, and the concurrency group. Report what you verified and what turned out wrong.

Step 2 — Read the project, then audit what already exists. Find any existing workflow and record for each job: what triggers it, how long it takes, whether it is required for merge, and which actions it uses at which reference. List every action referenced by a mutable tag — that list is a work item. Find whether branch protection actually requires these checks, because a workflow that runs and does not block is decoration. Find the local commands for lint, types and tests, since CI must run the same ones. Then audit §11 item by item, each marked already true, partly true or absent, with the file that decides it, reported before anything is proposed.

Assume the project is right until it demonstrably is not; code satisfying an item stays even where its shape differs from §4; replacing something that works needs a one-line reason; never delete a working path to make room for the blueprint's version. The same holds for language — §4 is illustrative, its idioms get translated into the project's language, and §11 is what has to become true rather than the syntax.

Step 3 — Write a plan for the gap only, and get it approved, including a ## Proposed stack section and a target for total wall-clock time on a pull request. Do not ask open framework questions — propose, and ask for confirmation once. Say what you are adding, what you are leaving alone, and what you propose to change, and touch nothing else.

Step 4 — Build in the order in §7. Step 5 — §11 is the definition of done.

1. Why a pipeline that runs is not a pipeline that protects

A workflow file is easy. Four things decide whether it does anything.

The usual workflow This one
Checks run and report; merging is still possible while they are red The checks are required, so a red one blocks the button
Actions are referenced by tag — @v4 — and the tag can be moved Actions are pinned to a commit, which cannot be moved
GITHUB_TOKEN has whatever the organisation default grants Read-only by default, widened per job with a reason
Every push starts a run and the old ones keep going Superseded runs are cancelled, so the queue shows the current state

The second row is not theoretical. A widely used action was compromised and its tags were repointed at malicious code, which then ran inside every workflow that referenced it by tag — with whatever permissions that workflow's token held. A tag is a label someone else can move; a commit SHA is an identity. Pinning does not solve supply-chain risk on its own — a pinned action can still pull an unpinned Docker image or a dependency of its own — but it removes the cheapest attack, and combining it with a read-only default token bounds what a compromise can reach.

The first row is the one that quietly makes the rest pointless. A check that is not required is a suggestion, and the suggestion is ignored on the afternoon somebody needs to ship.

The rule the diagram encodes: the jobs fan out, and the gate is the only path to a merge. Nothing runs after the gate — this workflow produces no artefact anyone deploys and holds no credential that could deploy one.

3. Project structure

.github/workflows/
└── ci.yaml             one file, one purpose: decide whether this change may merge
Makefile                lint, typecheck, test — the same targets CI and humans run

One rule: CI runs the same commands a developer runs. If the workflow inlines its own flags, the two drift, and the failure that only reproduces in CI becomes a routine cost. Put the commands in the Makefile; let the workflow call the targets.

4. Reference implementation

# .github/workflows/ci.yaml
name: CI

on:
  pull_request:
  push:
    branches: [main]      # so main's status is known independently of any PR

# Read-only by default. Every job that needs more says so and says why. The
# organisation default may be write-all, and this line overrides it — which is the
# difference between a compromised action reading the repository and rewriting it.
permissions:
  contents: read

concurrency:
  # One run per branch. Pushing three times leaves one running instead of three,
  # so the queue reflects the current state and nobody merges on the result of a
  # commit that no longer exists.
  group: ci-${{ github.ref }}
  cancel-in-progress: true

jobs:
  static:
    runs-on: ubuntu-24.04
    steps:
      # Pinned to a commit, with the tag in a comment for readability. A tag can be
      # repointed by whoever controls the action's repository — that has happened,
      # and the malicious code then ran inside every workflow trusting the tag.
      - uses: actions/checkout@11bd71901bbe5b1630ceea73d27597364c9af683 # v4.2.2
      - uses: astral-sh/setup-uv@f0ec1fc3b38f5e7cd731bb6ce540c5af426746bb # v6.1.0
        with:
          enable-cache: true
          cache-dependency-glob: "uv.lock"   # the cache key is the lock, not the code
      - run: make lint
      - run: make typecheck

  unit:
    runs-on: ubuntu-24.04
    steps:
      - uses: actions/checkout@11bd71901bbe5b1630ceea73d27597364c9af683 # v4.2.2
      - uses: astral-sh/setup-uv@f0ec1fc3b38f5e7cd731bb6ce540c5af426746bb # v6.1.0
        with: {enable-cache: true, cache-dependency-glob: "uv.lock"}
      - run: make test-unit

  integration:
    runs-on: ubuntu-24.04
    services:
      postgres:
        image: postgres:17-alpine
        env: {POSTGRES_PASSWORD: ci, POSTGRES_DB: test}
        ports: ["5432:5432"]
        # Without this the job starts before the server accepts queries and the
        # first test fails — the CI form of "it works on the second up".
        options: >-
          --health-cmd "pg_isready -U postgres -d test"
          --health-interval 2s --health-timeout 3s --health-retries 20
    env:
      DATABASE_URL: postgresql+asyncpg://postgres:ci@localhost:5432/test
    steps:
      - uses: actions/checkout@11bd71901bbe5b1630ceea73d27597364c9af683 # v4.2.2
      - uses: astral-sh/setup-uv@f0ec1fc3b38f5e7cd731bb6ce540c5af426746bb # v6.1.0
        with: {enable-cache: true, cache-dependency-glob: "uv.lock"}
      - run: make test-integration

  build:
    runs-on: ubuntu-24.04
    steps:
      - uses: actions/checkout@11bd71901bbe5b1630ceea73d27597364c9af683 # v4.2.2
      - uses: docker/setup-buildx-action@b5ca514318bd6ebac0fb2aedd5d36ec1b5c232a2 # v3.10.0
      - uses: docker/build-push-action@471d1dc4e07e5cdedd4c2171150001c434f0b7a4 # v6.15.0
        with:
          push: false          # CI proves it builds; CD is what pushes and deploys
          cache-from: type=gha
          cache-to: type=gha,mode=max
          tags: app:${{ github.sha }}

# Makefile — one definition of each check, used by CI and by people
lint:            ; uv run ruff check . && uv run ruff format --check .
typecheck:       ; uv run mypy app
test-unit:       ; uv run pytest tests/unit -q
test-integration:; uv run pytest tests/integration -q

5. Golden-standard rules

Rule Why
Forbidden: third-party actions referenced by tag or branch A tag can be repointed by whoever controls that repository, and the replacement runs with your workflow's permissions. This has happened to a widely used action.
Forbidden: a default token with write permissions It is the blast radius of any compromise in any step. Read-only by default; widen per job with a stated reason.
Forbidden: secrets or deploy credentials in the pull-request workflow A pull request can change the workflow it runs under. Keep credentials in the deploy workflow, which runs from a trusted ref.
Forbidden: checks that run without being required for merge An advisory check is ignored on the afternoon somebody needs to ship. Enforce it in branch protection.
Forbidden: CI inlining commands that differ from the local ones They drift, and "only fails in CI" becomes routine. One definition, called from both.
Superseded runs are cancelled Otherwise the queue is full of results for commits that no longer exist, and someone merges on one.
The dependency cache is keyed on the lock file Keyed on anything that changes with the code, the cache misses every run and costs more than it saves.
Service containers declare health checks The job otherwise starts before the dependency accepts work and the first test fails for no reason anyone can reproduce.
Jobs are separate and run in parallel One long job hides which check failed and makes a lint error cost the full test time.
The runner image is pinned to a version, not latest latest moves under you, and the build that broke overnight changed nothing you can see in the diff.
CI builds the image but never pushes it Pushing needs credentials, and credentials do not belong in a workflow a pull request can influence.
Total wall-clock time has a target and is measured A pipeline slow enough to context-switch away from stops being read, and then stops being trusted.

6. Data contracts

The contract is the set of required checks, and it is what branch protection enforces:

lint          formatting and lint rules, same command as local
typecheck     the type checker, no new ignores
unit          the fast suite, shuffled
integration   the container-backed suite, within its time budget
build         the production image builds — not pushed

Adding a check to the workflow does not add it to this contract. The names above have to be listed in branch protection, and a renamed job silently drops out of the required set — which is why §11 asks for a test of the gate, not a reading of the file.

7. Build order

  1. One job that checks out and runs lint, required in branch protection from the first day. A pipeline that does not block is a habit that has to be broken later.
  2. Pin every action to a SHA and set permissions: contents: read.
  3. Split into parallel jobs for types and unit tests, and add caching keyed on the lock file.
  4. Add the integration job with service containers and their health checks.
  5. Add the build job, without pushing.
  6. Concurrency cancellation, then measure total time and set the target.
  7. Prove the gate: open a pull request that fails one check and confirm the merge button is blocked.

Step 7 is not ceremony. Required checks are configured outside the repository, by job name, and a renamed job leaves the gate silently open.

8. Blocks to pull in

Nothing here is a prerequisite. These are adjacent problems, by name only — resolve them separately if they apply.

  • GitHub Actions CD — the deploy workflow this one deliberately excludes
  • Test harness and unit tests — the fast suite this pipeline runs
  • Integration tests with real dependencies — what the service containers are for
  • Dockerfile for a production service — the image the build job proves still builds

9. Metrics

Metric Target
Wall-clock time on a pull request < 5 minutes
Cache hit rate on unchanged dependencies > 90%
Third-party actions referenced by a mutable tag 0
Jobs with write permissions 0, unless justified in a comment
Required checks that are not in branch protection 0
Flaky CI failures per week 0 — a retry button is a workaround, not a fix
Concurrent runs per branch 1

10. Failure modes

Symptom Cause Fix
Red main, discovered by the next person to pull The checks ran but were not required for merge Add them to branch protection and verify by trying to merge a failing pull request
A workflow started behaving differently with no change in the diff A tag-referenced action was updated or repointed Pin every action to a full commit SHA
A compromised step could have rewritten the repository The default token had write permissions permissions: contents: read at the top, widened per job
The integration job fails on its first database query The service container was not health-checked, so the job started before the server was ready Add --health-cmd options to the service
Every run reinstalls dependencies although nothing changed The cache key includes files that change with every commit Key the cache on the lock file only
Three runs of the same branch execute at once and the wrong one is merged on No concurrency group Group by ref with cancel-in-progress
A test fails only in CI and nobody can reproduce it CI runs different commands or flags from the local ones One definition in the Makefile, called from both
The pipeline broke overnight with no commits The runner label is latest and the image moved Pin the runner to a version
A check was renamed and merges stopped being blocked Branch protection lists checks by name, and the old name no longer reports Verify the gate after any rename
A pull request from a fork exfiltrated a secret The pull-request workflow had access to credentials Keep credentials out of this workflow entirely
Lint failures cost the same as a full test run Everything is in one job Split into parallel jobs

11. Definition of done

  • Every third-party action is referenced by a full commit SHA, checked automatically in CI
  • The workflow declares permissions at the top with read-only defaults, and any widening carries a comment saying why
  • A pull request with a failing check cannot be merged — verified by opening one, not by reading the settings
  • Renaming a job causes the gate to fail closed, or a check detects that a required check name is missing
  • Lint, type check, unit tests, integration tests and the image build each run as separate jobs
  • CI runs the same commands as a developer, defined in one place
  • The dependency cache is keyed on the lock file, and a run with unchanged dependencies shows a cache hit
  • Every service container declares a health check that exercises the service
  • Pushing twice to a branch leaves exactly one run in progress
  • The runner image and every container image are pinned to a version, not latest
  • No secret is referenced by this workflow, checked by grep in CI
  • Total pull-request wall-clock time is measured and reported, and a regression beyond the target is visible
