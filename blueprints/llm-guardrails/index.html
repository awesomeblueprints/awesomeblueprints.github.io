LLM Input Guardrails and Prompt-Injection Detection

LLM input guardrails and prompt-injection detection: trust boundaries, provenance marking, classifiers and measured false-positive rates.

medium2–3 daysVerified 2026-08-20
Safety
Read it on GitHub ↗ Back to the catalogue

Everything that happens to text between arriving at your system and reaching the model: what is rejected outright, what is marked as untrusted, and what is allowed through with its provenance still attached.

Complexity: medium · Typical build: 2–3 days · Verified: 2026-08-20 (re-check after ~90 days)

Examples in: Python, with FastAPI. The architecture is language-agnostic: sections 5, 10 and 11 hold wherever you build this. Section 4 is illustrative — if your project is in another language, your agent translates the idioms rather than importing them, and nothing is lost. Every element here is plain text handling and one classifier call; no library is required, and the ones that exist are conveniences over the same three checks.

Use when: model input can contain anything a user typed, or any text fetched from a page, a document, an email or a tool result.

Not for: input the system generated itself from data it already trusts — a templated prompt over your own database rows adds latency and a false-positive rate for an attack surface that is not there. Also not for output-side safety: what the model produces is a different check at a different point, and doing both in one function means neither can be tuned.

⚙️ INSTRUCTIONS FOR THE AI — READ BEFORE WRITING ANY CODE

Do not start coding.

Step 1 — Refresh. Injection remains the top-ranked risk in the current OWASP list for LLM applications, and the published defence evaluations move faster than the libraries. Verify: whether your model provider now exposes a first-party injection classifier or a content-safety endpoint, what its documented latency and pricing are, and whether the provider documents any structural separation between system and untrusted content beyond message roles. Do not adopt a library without reading what it actually checks — several present themselves as injection defences and are keyword lists. Report what you verified and what turned out wrong.

Step 2 — Read the project, then audit what already exists. Enumerate every path by which text reaches a model, and this is the step people do badly: it is not only the chat box. It is uploaded documents, fetched web pages, tool results, retrieved chunks, email bodies, filenames, webhook payloads and error strings that get summarised. For each one record where the text originates and whether anything currently inspects it. Find any existing validation — a moderation call, a length cap, a regex — and where it sits. Find what the model can do, because that is what an injection is worth. Then audit §11 item by item, each marked already true, partly true or absent, with the file that decides it, reported before anything is proposed.

Assume the project is right until it demonstrably is not; code satisfying an item stays even where its shape differs from §4; replacing something that works needs a one-line reason; never delete a working path to make room for the blueprint's version. The same holds for language — §4 is illustrative, its idioms get translated into the project's language, and §11 is what has to become true rather than the syntax.

Step 3 — Write a plan for the gap only, and get it approved, including a ## Proposed stack section and the inventory from step 2 as a table of source → trust level → checks applied. Do not ask open questions — propose, and ask for confirmation once. Say what you are adding, what you are leaving alone, and what you propose to change, and touch nothing else.

Step 4 — Build in the order in §7. Step 5 — §11 is the definition of done.

1. The premise, stated honestly

There is no input check that stops prompt injection. Published evaluations of the strongest available technique — marking untrusted content so the model can tell where it came from — report attack success falling from above 50% to below 2% with little loss of task quality. That is an excellent result and it is not zero, and the gap is not closing: the same evaluations show every prompting-based defence degrading against attacks written after it.

So the design premise is not prevention. It is this:

Assume an injection will eventually succeed, and make the cost of that success small. Input guardrails reduce how often it happens; what the model is allowed to do decides what it costs when it does.

That framing changes what belongs in this document. The three checks below are worth building because they are cheap and they remove the large volume of unsophisticated attempts. They are not worth trusting.

The trust rule, and the test that applies it

Every piece of text reaching a model is either trusted — authored by your system from data your system controls — or untrusted. The test:

Could a person outside your team have influenced these bytes?

If yes, untrusted. Apply it literally, because the interesting cases are the ones that feel internal: a retrieved document chunk (someone wrote the document), a tool result from a third-party API (someone controls that API's fields), a filename (the uploader chose it), an error message quoting user input, a previous assistant turn that summarised untrusted text. All untrusted. The classic failure is a system that carefully checks the chat box and then feeds it an unchecked web page.

The consequence of the rule is the one architectural decision here: untrusted text never enters the system prompt, and never arrives concatenated to trusted text without a marker saying where the boundary is.

Two properties the diagram encodes. There is exactly one entry point: both the user arrow and the fetched-content arrow reach the same normalise node. A second path that skips the gate is the failure this whole structure exists to prevent, and it is normally added six months later by someone adding a feature. And every decision reaches the log, including the ones that passed — a guardrail with no record of what it allowed cannot be tuned, only guessed at.

3. Project structure

app/guardrails/
├── gate.py         the single entry point: check(text, source) -> Checked
├── normalise.py    decoding, whitespace and invisible characters, length cap
├── structural.py   the checks that cost nothing: no model call
├── classifier.py   the model-based check, with its threshold and its timeout
├── marking.py      wrapping untrusted text with a provenance marker
└── decisions.py    the log record: source, checks, scores, outcome

One rule: nothing outside this package builds a prompt from untrusted text. The gate returns a wrapped object rather than a string, so a caller that skips marking has a type error rather than a silent vulnerability. That is the single design choice that makes the rule enforceable instead of aspirational.

4. Reference implementation

# app/guardrails/marking.py
import re
import unicodedata
from dataclasses import dataclass


@dataclass(frozen=True)
class Untrusted:
    """Untrusted text, wrapped so it cannot be used by accident.

    There is deliberately no `__str__` shortcut to the raw text. A caller that
    wants the content must call `render()` and therefore gets the marking. This
    is why the gate returns an object instead of a string: it converts "remember
    to mark untrusted content" from a rule people follow into one the type
    checker follows.
    """
    text: str
    source: str

    def render(self) -> str:
        # Datamarking: interleave a token the model is told marks untrusted
        # content. Published evaluation of this family of techniques reports
        # attack success dropping from above 50% to below 2%, with little loss of
        # task quality. It is the strongest cheap defence available and it is not
        # a guarantee.
        marked = self.text.replace(" ", "░")
        return (
            f"<untrusted source={self.source!r}>\n{marked}\n</untrusted>"
        )


def strip_invisibles(text: str) -> str:
    """Remove characters that are invisible to a reviewer and visible to a model.

    Zero-width joiners, bidirectional overrides and tag characters let an
    instruction be present in the bytes and absent from anything a human reads,
    including your own logs. Normalising to NFKC first collapses the lookalike
    encodings that otherwise reintroduce them.
    """
    text = unicodedata.normalize("NFKC", text)
    return "".join(c for c in text if unicodedata.category(c) not in {"Cf", "Co"})

# app/guardrails/structural.py
DELIMITER_PATTERN = re.compile(r"</?(system|instructions?|untrusted)\b", re.I)

# These are not an injection detector. They catch a specific, common, mechanical
# class: text that tries to close your framing and open its own. Treating a
# keyword list as the defence is the mistake this file is written to avoid —
# hence the name of the module and the comment you are reading.
def structural_findings(text: str) -> list[str]:
    findings = []
    if DELIMITER_PATTERN.search(text):
        findings.append("delimiter_forgery")
    if len(text) > LIMITS.max_chars:
        findings.append("over_length")
    if _ratio_of_non_language_bytes(text) > 0.3:
        # High-entropy blobs are the usual carrier for encoded instructions and
        # are almost never legitimate prose. Flag, do not reject: base64 in a
        # support ticket is real.
        findings.append("high_entropy")
    return findings

# app/guardrails/gate.py
async def check(text: str, source: str) -> Untrusted:
    """The single entry point. Every untrusted string in the system passes here.

    Order is deliberate: free checks before paid ones, so an obvious rejection
    never costs a classifier call.
    """
    text = strip_invisibles(text)[: LIMITS.max_chars]
    findings = structural_findings(text)
    if "delimiter_forgery" in findings:
        await decisions.record(source, findings, outcome="rejected")
        raise InputRejected("delimiter_forgery")

    try:
        score = await classifier.score(text, timeout=LIMITS.classifier_timeout_s)
    except TimeoutError:
        # Fail closed or fail open is a decision, not a default. Written here,
        # once, with its reason: this path serves user-facing chat, where
        # rejecting on a classifier outage would take the product down for
        # everyone, so it fails open and flags. A path that can move money makes
        # the opposite choice, and says so in its own configuration.
        score, findings = 0.0, findings + ["classifier_unavailable"]

    outcome = "rejected" if score >= LIMITS.reject_at else "allowed"
    await decisions.record(source, findings, score=score, outcome=outcome)
    if outcome == "rejected":
        raise InputRejected("classifier")
    return Untrusted(text=text, source=source)

# tests/test_gate.py
@pytest.mark.parametrize("payload", KNOWN_ATTEMPTS)   # a file, versioned, in-repo
async def test_known_attempts_are_caught_or_marked(payload):
    # The suite is a regression net, not a proof. Its value is that a change to a
    # threshold shows up as a diff instead of as an incident.
    try:
        wrapped = await check(payload, source="test")
    except InputRejected:
        return
    assert "<untrusted" in wrapped.render()


async def test_benign_input_is_not_rejected(benign_corpus):
    # The check that stops the guardrail from being tightened into uselessness.
    # Without a false-positive test, every incident ends with a lower threshold
    # and nobody measures what that costs.
    rejected = [t for t in benign_corpus if await _is_rejected(t)]
    assert len(rejected) / len(benign_corpus) < 0.01

5. Golden-standard rules

Rule Why
Forbidden: untrusted text in the system prompt, in any form It inherits the authority of everything around it, and no downstream check recovers from that.
Forbidden: concatenating untrusted text to trusted text without a provenance marker The model cannot distinguish what it was not told to distinguish; marking is what makes the distinction available.
Forbidden: a second path to the model that bypasses the gate One entry point is the entire control; a bypass added for a feature is the vulnerability.
Forbidden: returning untrusted text as a plain string from the gate A string can be interpolated by accident. An object with no implicit rendering cannot.
Forbidden: a keyword or regex list presented as injection defence It catches the attempts that were not trying; it produces false confidence in exchange.
Forbidden: treating input checks as sufficient, with unrestricted model capability behind them The best published defences leave a residual success rate; what the model may do decides what that residual costs.
Trust is decided by whether anyone outside the team could influence the bytes It is the only test that catches document chunks, tool results and filenames, which are where real incidents come from.
Input is normalised and stripped of invisible characters before any check Otherwise the check reads different bytes from the model, and from your logs.
A length cap is applied before the classifier It bounds both cost and the amount of material an attack can hide in.
Cheap structural checks run before any model call An obvious rejection should not cost a classifier invocation.
The classifier has a timeout and a written fail-open-or-closed decision per path The default is whichever the library chose, applied uniformly to paths with opposite risk profiles.
Every decision is logged, including allows, with the score A guardrail with no record of what it allowed can be tuned only by guessing.
A false-positive rate is measured against a benign corpus Every incident otherwise ends in a lower threshold that nobody prices.
Known attempts live in a versioned file with a test over them Threshold changes then appear as diffs rather than as incidents.

6. Data contracts

in     text plus its source identifier
out    a wrapped untrusted value, or a rejection carrying the reason code
log    source, findings, score, outcome, prompt version, timestamp

The source identifier is not decoration. It is what lets the log answer which channel is under attack, and it is what appears in the provenance marker so the model can weigh a support ticket differently from a fetched web page. Make it an enumeration, not a free string.

The rejection reason is an internal code. What the user sees is a fixed generic message: a reason that names the check tells an attacker which one fired and lets them tune against it in a handful of attempts.

7. Build order

  1. The inventory of paths from step 2, written down. Everything else is scoped by it, and the paths people forget — tool results, retrieved chunks — are found here or not at all.
  2. The gate as a single function returning a wrapped type, with normalisation and the length cap and nothing else. The type is what makes the rest enforceable, so it comes before any check.
  3. Marking, and the change at every prompt assembly site to use it. Do this before the classifier: it is the defence with the strongest published effect, and it costs nothing per request.
  4. The structural checks, with the benign corpus test alongside them from the first one.
  5. The decision log, before the classifier, so the classifier's threshold is set from data rather than from intuition.
  6. The classifier, with its timeout, and its fail-mode decision written per path.
  7. The known-attempts suite, run in CI.

Marking before classification is the sequencing that matters. Teams do it in the opposite order, spend a week on thresholds, and ship the cheaper and more effective control last.

8. Blocks to pull in

Nothing here is a prerequisite. These are adjacent problems, by name only — resolve them separately if they apply.

  • Guardrails and prompt-injection defence in depth — capability restriction, dual-model isolation, taint tracking and blast-radius design
  • Output validation — checking what the model produced before it is used
  • LLM tool registry and dispatcher — declaring what the model may call, which is what an injection is worth
  • Human-in-the-loop approval — the pause before an irreversible step
  • Rate limiting — bounding how many attempts one caller gets
  • Audit logging — where decision records are kept and for how long

Metric Target

10. Failure modes

Symptom Cause Fix
An injection arrives through a document or a tool result Only the chat box was treated as untrusted Apply the influence test to every source; route all of them through the gate
The model follows instructions found inside a fetched page Untrusted text was concatenated without a marker Mark it, and tell the model in the system prompt what the marker means
A check passes text the model then reads differently Invisible or lookalike characters were not normalised before checking Normalise and strip before every check
An attacker learns exactly which check fired The rejection reason was returned to the user Generic message out; the reason code stays in the log
A guardrail change causes a wave of complaints No benign corpus, so the false-positive cost was never measured Measure it before shipping any threshold change
A classifier outage takes the product down Fail-closed applied to a path where availability matters Decide the fail mode per path and write down the reason
A classifier outage silently disables the defence Fail-open applied to a path where safety matters Same, in the other direction; flag and alert either way
Nobody can tune the threshold Only rejections were logged Log allows with their scores too
A new feature reintroduces a vulnerability that was fixed It built a prompt from a raw string Have the gate return a type, so bypassing it fails to compile or type-check
The defence works in tests and not in the wild The known-attempts file is stale Add every real attempt seen in the log to the file
Guardrails were added and the incident still cost a lot Input checks were treated as the whole defence Restrict capability behind them; assume residual success

11. Definition of done

  • An inventory exists of every path by which text reaches a model, with a trust level for each, and it is checked against the code
  • Every one of those paths calls the gate, verified by grep against the inventory
  • The gate returns a wrapped type; no path constructs a prompt from a raw untrusted string, checked by type checker or CI grep
  • Untrusted text never appears in the system prompt, verified by reading every prompt assembly site
  • All untrusted text is rendered with a provenance marker, and the system prompt states what the marker means
  • Input is NFKC-normalised and stripped of format and private-use characters before any check, covered by a test with an invisible-character payload
  • A length cap is applied before the classifier call
  • Structural checks run before any model call, verified by reading the gate
  • The classifier has an explicit timeout, and the fail-open-or-closed choice is written per path with its reason
  • Every decision is logged with source, findings, score and outcome — allows included
  • Users receive a generic rejection message; no reason code is exposed, covered by a test
  • A versioned file of known attempts exists and a CI test runs the gate over all of them
  • A benign corpus test asserts a false-positive rate under 1%
  • Added p95 latency from the gate is measured and recorded
  • The set of actions available to the model behind the gate is written down, on the assumption that a check will eventually be passed
