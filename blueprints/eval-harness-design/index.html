LLM Eval Harness

An LLM eval harness: fixed test sets, deterministic checks, regression gates in CI and scores you can compare between prompt versions.

Read it on GitHub ↗ Back to the catalogue

The dataset, the scorers and the runner that turn "this feels better" into a number you can compare across changes — and the CI gate that stops a regression from shipping while the aggregate still looks fine.

Complexity: medium · Typical build: 3–5 days · Verified: 2026-08-19 (re-check after ~90 days)

Examples in: Python. Only §4 and §6 are language-specific — the rules, failure modes and definition of done hold anywhere, and your agent translates the code.

Use when: you are about to make the second change to any system built on a model. The first change you can eyeball; from the second onwards you are trading one set of failures for another and cannot see it.

Not for: a prototype nobody depends on yet, and not as a substitute for production monitoring. An offline harness measures a fixed set of inputs; it says nothing about the inputs you have not thought of.

1. Why spot-checking fails, and what a harness replaces it with

Systems built on models fail non-deterministically and improve non-monotonically. A prompt edit that fixes three cases breaks five others, and manual checking finds the three — because those are the cases you were thinking about when you made the edit.

Spot-checking A harness
What is measured The cases you remembered A fixed set, every time
A regression shows up When a user reports it Before merge
"Quality dropped" resolves to An argument A category and a list of failing case ids
Cost of checking a change An afternoon Minutes and cents
What you can debug afterwards A memory The stored output of every failing case

The attribution point is the one people underrate. "Quality dropped" is not actionable. "Refund questions fell from 0.91 to 0.62 while everything else held" is a fix rather than a rewrite.

And the most common failure is not a bad harness — it is a dataset that does not resemble production. Everything below depends on the cases being real. A set written by the same person who wrote the prompt, from imagination, measures how well the prompt handles what its author was already thinking about.

The rule this diagram encodes: deterministic scorers run before the judge, and the judge only sees what code could not decide. Reversing that order is how an eval suite becomes too expensive to run on every commit, which is the same as not having one.

3. Project structure

evals/
├── cases/
│   ├── extraction.jsonl     # one file per category. Versioned with the code.
│   └── refunds.jsonl
├── scorers/
│   ├── deterministic.py     # exact match, schema, coverage, code execution
│   └── judge.py             # rubric-based, temperature 0, one criterion at a time
├── runner.py                # execute, aggregate, diff, report
├── baselines/
│   └── <config-hash>.json   # updated only by a reviewed commit
└── artifacts/               # raw outputs, kept per run. Gitignored.

The rule that keeps this maintainable: the dataset lives in the repository next to the code it measures, and moves with it. A dataset in someone's cloud account drifts out of step with the prompt within a month, and nobody notices until a comparison silently stops meaning anything.

4. Reference implementation

The runner. An exception is a failing case, not a crashed run:

async def run_eval(cases, system, scorers, cfg, concurrency=8) -> EvalReport:
    sem = asyncio.Semaphore(concurrency)

    async def one(case):
        async with sem:
            start = time.monotonic()
            try:
                out = await system.run(**case.input)
                scores = {}
                for scorer in scorers:            # deterministic ones first
                    scores |= scorer(case, out)
                return CaseResult(case_id=case.id, output=out, scores=scores,
                                  passed=all(v >= 0.5 for v in scores.values()),
                                  latency_ms=(time.monotonic() - start) * 1000)
            except Exception as e:
                # One broken case must not cost you the other hundred and forty-nine.
                return CaseResult(case_id=case.id, output=None, scores={}, passed=False,
                                  error=f"{type(e).__name__}: {e}")

    results = await asyncio.gather(*[one(c) for c in cases])
    return aggregate(cases, results, config_hash(cfg))

The config hash is what makes two numbers comparable. Anything that changes behaviour goes into it:

def config_hash(cfg: dict) -> str:
    # prompt text, model id, temperature, retrieval k, chunk size - all of it.
    return hashlib.sha256(json.dumps(cfg, sort_keys=True).encode()).hexdigest()[:12]

Deterministic scorers — free, exact, reproducible, and they should cover most of the suite:

def exact_match(case, out):
    return {"exact_match": float(str(out).strip() == str(case.expected).strip())}

def schema_valid(model_cls):
    def scorer(case, out):
        try:
            model_cls.model_validate(out); return {"schema_valid": 1.0}
        except Exception:
            return {"schema_valid": 0.0}
    return scorer

def coverage(case, out):
    required = case.expected.get("must_contain", [])
    if not required:
        return {}
    hit = sum(1 for s in required if s.lower() in str(out).lower())
    return {"coverage": hit / len(required)}

The gate. A per-category regression is the one that matters, because the aggregate hides it:

def check_regression(report, baseline, tol=0.02):
    if baseline.config_hash != report.config_hash:
        print("config changed - this comparison is informational only")
    problems = [f"{m}: {baseline.overall[m]:.3f} -> {v:.3f}"
                for m, v in report.overall.items()
                if m in baseline.overall and v < baseline.overall[m] - tol]
    for cat, metrics in report.by_category.items():
        for m, v in metrics.items():
            before = baseline.by_category.get(cat, {}).get(m)
            if before is not None and v < before - tol * 2:
                problems.append(f"[{cat}] {m}: {before:.3f} -> {v:.3f}")
    if problems:
        raise SystemExit("REGRESSION:\n  " + "\n  ".join(problems))

5. Golden-standard rules

Rule Why
Cases come from real usage, not from imagination A set written by the prompt's author measures what its author already thought of
The person who wrote the prompt does not write the eval set alone The blind spot is the same blind spot in both
The dataset lives in the repository and is versioned with the code A dataset elsewhere drifts out of step, and comparisons quietly stop meaning anything
Every case has a category; every category has at least eight cases Below that, a slice metric is noise
The set contains adversarial, unanswerable and should-fail cases The failures that matter most are otherwise invisible
Deterministic scorers run first and cover everything code can decide They are exact, free and reproducible; a judge is none of the three
A judge is used only where code cannot decide, at temperature 0, one criterion at a time Multi-criterion judging collapses into a single vague impression
The judge model is never weaker than the system under test It becomes the ceiling on what you can measure
Raw output is stored for every case, passing or failing A score with no artefact cannot be debugged
Every report carries a config hash Two numbers from different configurations are not a comparison
The baseline is updated by a reviewed commit, never automatically An auto-updating baseline absorbs every regression silently
CI gates on per-category regression, not only the overall number One collapsed slice inside a flat aggregate is the normal case
An exception is recorded as a failure and the run continues One broken case must not cost you the rest
Every production bug becomes a permanent case Otherwise the same bug ships twice
Temperature 0 everywhere, in the system and in the judge Variance you did not remove is variance you will read as signal

6. Data contracts

class EvalCase(BaseModel):
    id: str
    input: dict[str, Any]
    expected: Any                 # reference output, or the criteria a judge applies
    category: str                 # every case has one; slices are the point
    difficulty: Literal["easy", "medium", "hard"] = "medium"
    source: Literal["production", "synthetic", "bug-report"] = "production"

class CaseResult(BaseModel):
    case_id: str
    output: Any                   # ALWAYS stored - a score alone is not debuggable
    scores: dict[str, float]
    passed: bool
    latency_ms: float
    error: str | None = None

class EvalReport(BaseModel):
    config_hash: str              # results compare ONLY within one hash
    n_cases: int
    overall: dict[str, float]
    by_category: dict[str, dict[str, float]]
    failures: list[CaseResult]
    cost_usd: float

7. Build order

  1. Collect fifty real cases. From logs, support tickets, whatever exists. Synthetic cases are allowed only where reality is unavailable, and a human reviews each one.
  2. Categorise them, and note which categories have fewer than eight cases. Those are the gaps to fill first.
  3. The runner, with bounded concurrency, exceptions recorded as failures, and every raw output stored.
  4. Deterministic scorers for everything code can decide: schema, exact match, required substrings, executed code.
  5. The config hash, recorded in every report.
  6. A stored baseline, committed deliberately.
  7. The CI gate — overall first, then per category with a wider tolerance.
  8. A judge, only for what remains: rubric, temperature 0, one criterion per call, calibrated against fifty human labels before you trust it.
  9. Adversarial and unanswerable cases, once the happy path is measured.
  10. A standing rule that every production bug is added as a case before its fix merges.

9. Metrics

Metric Target
Dataset size ≥ 150 cases; below 50, a five-point difference is indistinguishable from noise
Categories with at least eight cases 100% — a thinner slice reports noise as a number
Score variance across identical runs < 1 point; above 3 you are reading noise as improvement
Share of scores computed without a model ≥ 60%; below 30% the suite is too expensive to run often
Full-suite runtime < 10 minutes, or it stops being run
Cost per full run < $5
Production bugs represented as permanent cases 100%

10. Failure modes

Symptom Cause Fix
Eval scores high, users unhappy The dataset does not resemble production Source cases from real logs; compare the input distributions
Scores move between identical runs Non-determinism left in Temperature 0 everywhere; report variance across three runs
Aggregate flat, one slice collapsed No per-category reporting Report and gate per category
A failure cannot be investigated Only scores were kept Store the raw output of every case
The baseline creeps upward on its own It is updated automatically Make it a reviewed commit
Two runs disagree for no reason The configuration changed between them Compare only within one config hash; re-baseline on change
Eval passes, production breaks Only happy paths in the set Add adversarial, unanswerable and should-fail cases
Judge cost dominates the run A model is checking what code could check Deterministic scorers first, always
The judge prefers longer answers Uncalibrated rubric Calibrate against human labels; score one criterion at a time
Nobody runs it any more It takes half an hour Split: deterministic scorers on every commit, full suite nightly

11. Definition of done

  • The dataset lives in the repository and is versioned with the code.
  • Cases are sourced from real usage where possible; synthetic ones are human-reviewed.
  • Every case has a category, and every category has at least eight cases.
  • Adversarial, unanswerable and should-fail cases are present.
  • Deterministic scorers run first and cover everything code can decide.
  • A judge is used only where code cannot decide, at temperature 0, one criterion at a time.
  • The judge is calibrated against human labels before its scores are trusted.
  • Raw outputs are stored for every case, passing or failing.
  • Every report carries a config hash, and comparisons happen only within one hash.
  • The baseline is a reviewed commit and is never updated automatically.
  • CI gates on overall and per-category regression.
  • Exceptions are recorded as failures and the run completes.
  • Every production bug is added as a permanent case before its fix merges.
