Streaming LLM Output in the Browser

Streaming LLM output in the browser: consuming SSE, incremental rendering, cancellation, reconnects and partial UTF-8 decoding done right.

medium2–4 daysVerified 2026-08-19
Streaming
Read it on GitHub ↗ Back to the catalogue

Receiving and rendering a token stream: decoding that survives a character split across two chunks, state that survives a second request arriving before the first finished, scrolling that respects the user, and a stop button that actually stops the meter.

Complexity: medium · Typical build: 2–4 days · Verified: 2026-08-19 (re-check after ~90 days)

Examples in: TypeScript, with React and the fetch streams API. The architecture is language-agnostic: sections 5, 10 and 11 hold wherever you build this. Section 4 is illustrative — if your project is in another framework, your agent translates the idioms rather than importing them, and nothing is lost. The decoding, cancellation and identity concerns are identical in Vue, Svelte, SwiftUI and Kotlin; only the state primitive changes.

Use when: a backend already streams and the interface has to show it — a chat, a generated document, anything where the user watches text arrive.

Not for: a page that renders a completed response. Adding streaming to a client whose server does not stream produces a typewriter animation over an answer that was already whole, which costs complexity and buys the appearance of speed rather than speed. Also not for a client that only needs to know when the work is done — poll a status endpoint.

1. Half the streaming failures are on this side

The naive client reads chunks, converts them to text, and appends. Four things break, and none of them break in English on a fast connection.

The obvious client This one
Decodes each chunk independently Decodes incrementally, so a character split across two chunks survives
Appends to whichever message the callback closed over Every stream carries an id, and a callback that is no longer current is discarded
Scrolls to the bottom on every token Follows only while the user is at the bottom
Stopping hides the response Stopping aborts the request, so the server stops generating and the meter stops

The first row is invisible until it is not. A UTF-8 character is one to four bytes, chunk boundaries fall wherever the network puts them, and decoding a chunk that ends mid-character produces a replacement character. In English this almost never happens; in Russian, Greek, Japanese or with an emoji it happens constantly. The fix is one argument — decode in incremental mode so the decoder holds the partial bytes until the rest arrives — and it is the single highest-value line in this document.

The second row is the one that produces bug reports nobody can reproduce. A user sends a message, then sends another before the first finishes. Two streams are now running, both holding a reference to the message they were started for, and their updates interleave. Tokens from one answer land in the other, or a completed answer is overwritten by a stale write. Aborting the first request is not enough — abort stops the transport, and a callback already scheduled still runs. The state update itself has to check whether it is still the current stream.

The rule the diagram encodes: the identity guard sits between parsing and state, and nothing bypasses it. Every path that writes a message — a delta, a completion, an error, a resume — goes through the same check. A single write that skips it reintroduces the interleaving bug, and it will be found by a user rather than by a test.

├── render.tsx     incremental markdown rendering
└── scroll.ts      the follow-while-at-the-bottom behaviour

One rule: nothing outside useStream writes streamed text into state. A component that appends a token directly has bypassed the identity guard, and the bug it creates only appears when a user is fast enough to send twice.

4. Reference implementation

// src/streaming/decode.ts
export async function* readEvents(
  body: ReadableStream<Uint8Array>,
  signal: AbortSignal,
): AsyncGenerator<StreamEvent> {
  const reader = body.getReader();
  // stream: true is the whole point. Without it, a chunk ending mid-character is
  // decoded on its own and the trailing bytes become U+FFFD. With it, the decoder
  // keeps the partial sequence until the next chunk completes it. In English this
  // is rare; in Cyrillic, Greek, CJK or anything with an emoji it is constant.
  const decoder = new TextDecoder("utf-8");
  let buffer = "";

  try {
    while (true) {
      const { done, value } = await reader.read();
      if (done) break;
      buffer += decoder.decode(value, { stream: true });

      // Frames are separated by a blank line, and a frame can span chunks. Keep
      // the tail: it is a partial frame, not a complete one that happens to be short.
      const frames = buffer.split("\n\n");
      buffer = frames.pop() ?? "";

      for (const frame of frames) {
        const event = parseFrame(frame);
        if (event) yield event;
      }
    }
    buffer += decoder.decode();      // flush anything the decoder still holds
  } finally {
    // Releasing the lock matters on the abort path: without it the stream stays
    // locked and the connection is not released to the browser's pool.
    reader.releaseLock();
  }
}

function parseFrame(frame: string): StreamEvent | null {
  let name = "message", data = "";
  for (const line of frame.split("\n")) {
    if (line.startsWith(":")) continue;              // keepalive comment
    if (line.startsWith("event:")) name = line.slice(6).trim();
    if (line.startsWith("data:")) data += line.slice(5).trim();
  }
  return data ? { name, data: JSON.parse(data) } : null;
}

// src/streaming/useStream.ts
export function useStream() {
  const currentId = useRef<string | null>(null);
  const controller = useRef<AbortController | null>(null);

  const send = useCallback(async (text: string) => {
    // A second send while the first is running: abort the transport, then take a
    // new identity. Abort alone is not enough — a callback already scheduled will
    // still run and write into the wrong message.
    controller.current?.abort();
    const streamId = crypto.randomUUID();
    currentId.current = streamId;
    const ctrl = new AbortController();
    controller.current = ctrl;

    let lastSeq = 0;

    try {
      // fetch, not EventSource: EventSource is GET-only and cannot set an
      // Authorization header, which rules it out for an authenticated endpoint
      // with a request body.
      const response = await fetch("/chat/stream", {
        method: "POST",
        headers: { "Content-Type": "application/json", Authorization: `Bearer ${token}` },
        body: JSON.stringify({ text, after_seq: lastSeq || undefined }),
        signal: ctrl.signal,
      });

      // The status is only meaningful before the body starts. A rejection here is
      // a real code; anything after this point arrives as an error event.
      if (!response.ok) { showError(await response.json()); return; }

      let sawTerminal = false;

      for await (const event of readEvents(response.body!, ctrl.signal)) {
        // The guard. Every write goes through it, so a stale stream that has not
        // noticed its abort yet cannot touch state that now belongs to another.
        if (currentId.current !== streamId) return;

        if (event.name === "delta") {
          lastSeq = event.data.seq;
          appendToMessage(streamId, event.data.text);
        } else if (event.name === "done") {
          sawTerminal = true;
          finishMessage(streamId, event.data.finish_reason);
        } else if (event.name === "error") {
          sawTerminal = true;
          // Mid-answer failure: keep the text already shown. Discarding it throws
          // away work the user already read and was already billed for.
          failMessage(streamId, event.data.code, { keepPartial: true });
        }
      }

      if (!sawTerminal && currentId.current === streamId) {
        // The stream ended without saying so — a dropped connection, or a mobile
        // OS suspending the tab. Resume from the last sequence rather than
        // regenerating: the server already produced those tokens and you paid.
        await resumeFrom(streamId, lastSeq);
      }
    } catch (err) {
      if ((err as Error).name === "AbortError") return;   // deliberate, not a failure
      if (currentId.current === streamId) failMessage(streamId, "network", { keepPartial: true });
    }
  }, []);

  const stop = useCallback(() => {
    // Abort the request, not just the rendering. Hiding the output leaves the
    // server generating to completion and you are billed for all of it.
    controller.current?.abort();
    currentId.current = null;
  }, []);

  return { send, stop };
}

// src/streaming/scroll.ts
export function useFollowOutput(ref: RefObject<HTMLElement>, deps: unknown[]) {
  const following = useRef(true);

  useEffect(() => {
    const el = ref.current;
    if (!el) return;
    const onScroll = () => {
      // A threshold, not equality: sub-pixel layout and zoom mean scrollTop rarely
      // lands exactly at the bottom, and an exact check makes the view stop
      // following for reasons the user cannot see.
      following.current = el.scrollHeight - el.scrollTop - el.clientHeight < 40;
    };
    el.addEventListener("scroll", onScroll, { passive: true });
    return () => el.removeEventListener("scroll", onScroll);
  }, [ref]);

  useEffect(() => {
    // Follow only while the user has not scrolled up. Forcing the scroll on every
    // token makes it impossible to read what has already arrived — the single most
    // common complaint about streaming interfaces.
    if (following.current) ref.current?.scrollTo({ top: ref.current.scrollHeight });
  }, deps);
}

5. Golden-standard rules

Rule Why
Forbidden: decoding chunks without incremental mode A character split across a chunk boundary becomes a replacement character. Invisible in English, constant in most other scripts.
Forbidden: writing streamed text to state without checking the stream is current Aborting stops the transport, not a callback already scheduled. Two answers then interleave, and nobody can reproduce it.
Forbidden: treating a stopped stream as a rendering concern Hiding output leaves the server generating and billing. Stop means abort the request.
Forbidden: assuming a frame arrives whole in one chunk Frame boundaries and chunk boundaries are unrelated. Buffer the tail.
Forbidden: discarding partial text when a stream fails The user read it and you paid for it. Keep it and mark the failure.
Scrolling follows only while the user is at the bottom Forcing it on every token makes reading what already arrived impossible.
A stream that ends without a terminal event is a drop, not a completion Otherwise a truncated answer is presented as finished, which is worse than an error.
Resume by sequence rather than regenerating The tokens were produced and billed once already; regenerating pays twice and gives a different answer.
Markdown is parsed from accumulated text, not per chunk Parsing each chunk alone produces flicker as unclosed syntax opens and closes.
An aborted request is not an error Showing a failure for something the user asked for reads as a bug.
The identity guard is the only path into message state One write that skips it is enough to reintroduce interleaving.
The reader's lock is released on every path Otherwise an aborted stream leaves the connection held.

6. Data contracts

What the client requires of the server, and why each item exists:

event names     start, delta, done, error — a fixed, closed set
sequence        monotonic per stream; the client sends it back to resume
terminal        exactly one done or error; its absence means the stream dropped
errors          a code, never prose — the client maps it to a message it controls

If the server does not provide a sequence number, resume is impossible and every dropped mobile connection costs a second generation. That is a server change, not something the client can work around — worth saying plainly during Step 2 rather than building an expensive approximation.

7. Build order

  1. Read and render a stream of fixed text from the server — with incremental decoding from the first version, and a test using a multi-byte string split across chunk boundaries. It is one argument, and retrofitting it means debugging replacement characters first.
  2. Frame buffering, with a test that splits a frame across two chunks.
  3. The identity guard and abort, then a test that sends twice in quick succession and asserts the two answers never interleave.
  4. The stop button, with a test asserting the request was aborted rather than the output hidden.
  5. Terminal events and the drop case, with a test that ends a stream without one.
  6. Resume from the last sequence.
  7. Scroll following and incremental markdown.

Step 3 before the interface work because it is the only bug here that a user finds before a developer does, and it needs a test that deliberately races.

10. Failure modes

Symptom Cause Fix
Replacement characters appear in Cyrillic, CJK or emoji output Chunks decoded independently, splitting a multi-byte character Decode in incremental mode
Two answers mix together, and only for fast users A second stream started while the first was still writing state An identity per stream, checked at every write
A finished answer is overwritten by an older one Same cause; abort stopped the transport but not a scheduled callback The identity guard, not abort alone
The stop button hides the text and the bill is unchanged Stop was implemented as a rendering change Abort the request
An answer ends early and looks complete The stream dropped and the client had no terminal event to require Require a terminal event; treat its absence as a drop
Every dropped connection produces a full second generation The client retries from the start Resume from the last sequence
The view jumps to the bottom while the user is reading Scroll forced on every token Follow only while the user is at the bottom, with a threshold
The view stops following for no visible reason Bottom detected by exact equality, defeated by sub-pixel layout Use a threshold
Text flickers and reflows as it arrives Markdown re-parsed per chunk, so unclosed syntax opens and closes Parse from accumulated text
A failed stream discards everything already shown The error handler resets the message Keep the partial text; mark it failed
Pressing stop shows an error The abort was treated as a failure Detect the abort and return quietly
Streaming works on desktop and truncates on mobile The OS suspended the tab and killed the connection Resume on foreground from the last sequence

11. Definition of done

  • A response containing multi-byte characters renders correctly when the byte stream is split at every possible position, covered by a test that iterates the split points
  • An event frame split across two chunks is parsed once and correctly, covered by a test
  • Sending a second message before the first completes never mixes their text, covered by a test that starts both deliberately
  • Pressing stop aborts the HTTP request, asserted by observing the request state rather than the rendered output
  • An aborted stream produces no error in the interface, covered by a test
  • A stream ending without a terminal event is presented as interrupted, not as complete, covered by a test
  • After a drop, the client resumes from its last sequence and the recovered text matches an uninterrupted run, covered by a test
  • A mid-stream error keeps the text already received and marks the message failed, covered by a test
  • The view follows new output only while the user is at the bottom, and stops following after the user scrolls up — both covered
  • Markdown is rendered from accumulated text with no re-parse per chunk, verified by a render-count assertion
  • No component outside the streaming hook writes streamed text into state, checked by a lint rule or a grep in CI
  • The stream reader's lock is released on the success, error and abort paths, covered by a test
