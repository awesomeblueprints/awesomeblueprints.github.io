LLM Observability and Tracing

LLM observability and tracing: spans for model calls, prompt versions, token and cost attribution, and finding the run behind a bad answer.

medium4–6 daysVerified 2026-08-19
Observability
Read it on GitHub ↗ Back to the catalogue

A structured trace of every model call and every agent step — inputs, outputs, tokens, cost, latency and outcome — so that a complaint about yesterday can be reconstructed and replayed instead of guessed at.

Complexity: medium · Typical build: 4–6 days · Verified: 2026-08-19 (re-check after ~90 days)

Examples in: Python with OpenTelemetry. Only §4 and §6 are language-specific — the rules, failure modes and definition of done hold anywhere, and your agent translates the code.

Use when: a system that calls a model runs somewhere you cannot watch it, and someone will eventually say "it gave me a strange answer on Tuesday". Also when nobody can say which feature is responsible for the model bill.

Not for: replacing your existing application observability. This is a layer on top of it — the same trace, with the model-specific fields that ordinary logging has no place for.

1. Why ordinary observability misses all of it

Conventional monitoring answers one question: was there an error? Systems built on models fail without one. The call returns 200, the JSON parses, the latency is normal, and the answer is wrong. Every dashboard stays green while users read nonsense.

Question Ordinary logs Model traces
Did it error? Yes Yes
What exactly went into the model? The template, if you are lucky The assembled prompt
Which tools ran, with what arguments? Scattered across lines One tree per request
What did this request cost? Nothing A number, attributable to a feature
Can I re-run it unchanged? No Yes, from the stored payload
Did the user think it was good? Unknowable Feedback attached by trace id

The economic half is the part that surprises teams. Token cost is invisible without per-request attribution, and a tenfold regression is routinely discovered several weeks later, by finance, on an invoice.

The other trap is the one that looks like prudence: storing only errors, or sampling uniformly to control cost. Both throw away exactly the traces you will need, because the interesting failure returned 200 and looked like healthy traffic on the way past.

The rule this diagram encodes: spans hold references, payloads hold content. Inline the prompts and the trace store becomes too large to query, which ends with tracing switched off in the release that needed it.

3. Project structure

telemetry/
├── context.py     # trace id creation and propagation across async boundaries
├── spans.py       # llm_span and tool_span. Every field, every time.
├── payloads.py    # put/get by reference. The assembled prompt, not the template.
├── cost.py        # versioned price table; historical cost recomputable
├── sampling.py    # tail decision: what is always kept, and the rest
├── redact.py      # runs before any write, no exceptions
└── replay.py      # rebuild the exact input for one step of one trace

The rule that keeps this maintainable: what gets stored is the assembled prompt, not the template plus the variables. Reassembling it later requires the prompt-building code to be deterministic and unchanged since, and neither is true by the time you need it.

4. Reference implementation

One span per model call, with every field filled in — a span missing token counts is a span that cannot answer the cost question later:

@asynccontextmanager
async def llm_span(model: str, step: int):
    with tracer.start_as_current_span("llm.call") as span:
        span.set_attribute("gen_ai.request.model", model)
        span.set_attribute("llm.step_index", step)
        t0 = time.monotonic()
        holder = {}
        try:
            yield holder
            usage = holder["usage"]
            span.set_attributes({
                "gen_ai.usage.input_tokens": usage.input_tokens,
                "gen_ai.usage.output_tokens": usage.output_tokens,
                "llm.usage.cached_tokens": getattr(usage, "cache_read_input_tokens", 0),
                "llm.cost_usd": cost_of(model, usage),
                "llm.stop_reason": holder["stop_reason"],
                # References. Never the text itself.
                "llm.prompt_ref": await payloads.put(redact(holder["prompt"])),
                "llm.response_ref": await payloads.put(redact(holder["response"])),
            })
        except Exception as e:
            span.record_exception(e)
            span.set_status(trace.StatusCode.ERROR)
            raise
        finally:
            span.set_attribute("llm.latency_ms", (time.monotonic() - t0) * 1000)

Sampling decides at the end of the request, not the start. A head decision cannot know the request was going to fail:

def should_keep(t: Trace) -> bool:
    if t.outcome != "success":      return True    # every failure
    if t.total_latency_ms > 10_000: return True    # every slow request
    if t.total_cost_usd > 0.50:     return True    # every expensive request
    if t.feedback:                  return True    # anything a user reacted to
    return random.random() < 0.05                  # and a slice of the healthy traffic

Replay is the payoff. It works only because the assembled prompt was stored:

async def replay(trace_id: str, step: int, *, model: str | None = None):
    span = await spans.get_llm_span(trace_id, step)
    prompt = await payloads.get(span.prompt_ref)
    return await client.create(model=model or span.model,
                               temperature=span.temperature, **prompt)

The same function is how you evaluate a model upgrade: replay a thousand real traces against the new model and diff the outputs, instead of arguing from a benchmark.

5. Golden-standard rules

Rule Why
One trace id created at entry and propagated across every async boundary Orphaned spans are the commonest reason a trace cannot be read
Every model call emits a span with model, all token counts, cost, latency and stop reason Any missing field is a question you will not be able to answer later
Cached tokens are recorded separately Otherwise a caching regression is invisible and simply looks like higher cost
Prompts and responses go to a payload store; spans hold references Inlined payloads make the trace store unqueryable, and then unused
What is stored is the assembled prompt, not the template Reassembling later requires code that has not changed, which it has
Tool calls get spans with arguments, result size and an error flag The tool layer is where most agent failures actually happen
Sampling is tail-based, and always keeps failures, slow, expensive and user-flagged traces Uniform sampling keeps the boring traffic and loses the incident
Redaction runs before any write Traces live for months; anything sensitive in them is a standing liability
Payload retention and metadata retention are set separately Metadata is cheap and worth a year; payloads are neither
Telemetry is emitted asynchronously Otherwise observability becomes the latency problem it was meant to diagnose
The trace id is returned to the client Without it, user feedback cannot be attached to anything
Metrics are derived from spans, never emitted alongside them Two independent paths drift, and then neither is trusted
The cost table is versioned, and historical cost can be recomputed Prices change; a silent recalculation destroys every past comparison

7. Build order

  1. A trace id at the entry point, propagated everywhere. Nothing else works without this.
  2. One span per model call with model, tokens, latency and stop reason.
  3. The payload store, holding the assembled prompt and the response by reference.
  4. Redaction, before anything is written. Not a later hardening pass — a month of unredacted traces cannot be un-stored.
  5. Cost, from a versioned price table, on every span.
  6. Tool spans with arguments, result size and error flag.
  7. Tail sampling, with the always-keep list explicit in code.
  8. The trace id returned to the client, and a feedback endpoint that attaches to it.
  9. Metrics derived from spans, and the old separately-emitted ones deleted.
  10. Replay, and then use it to reproduce one real reported issue. Until that has happened once, you do not know it works.

Metric Target
Requests with a complete trace > 99%
Failed requests with a trace 100%. Not "most"
Traces that replay to a byte-identical prompt > 95%; below 80% prompt assembly is not deterministic
Added latency at p95 from tracing < 5 ms
Trace storage cost as a share of inference cost < 5%
Spend attributable to a trace 100%
User feedback linked to a trace > 95%

10. Failure modes

Symptom Cause Fix
A user's complaint cannot be reproduced Only the template was stored Store the assembled prompt
Traces cost more than inference Payloads inlined and nothing sampled Reference payloads; tail-sample successes
A tenfold cost regression found on the invoice No per-request cost Cost on every span, aggregated daily by route
Spans appear with no parent Context dropped at an async boundary Propagate explicitly; test the async path
Feedback cannot be attached to anything The trace id never reached the client Return it in the response body
Traces contain personal data Redaction added later, or never Redact before write; audit a sample monthly
The bug is not in the traces Uniform sampling Tail-based, with failures always kept
Metrics and traces disagree Emitted independently Derive metrics from spans
Replay produces a different prompt Prompt assembly is not deterministic Store the final assembled prompt, and stop reconstructing
Cost numbers changed retroactively The price table was edited in place Version it; recompute deliberately, and say so

11. Definition of done

  • A trace id is created at entry and propagated across every async boundary.
  • Every model call emits a span with model, all token counts including cached, cost, latency and stop reason.
  • Prompts and responses are stored by reference, never inlined in a span.
  • The stored prompt is the assembled prompt, and replay has reproduced it byte for byte.
  • Tool calls emit spans with arguments, result size and an error flag.
  • Sampling is tail-based and always keeps failures, slow, expensive and user-flagged traces.
  • Redaction runs before every write, and a sample is audited.
  • Payload retention and metadata retention are defined separately.
  • Telemetry emission is asynchronous and adds under 5 ms at p95.
  • The trace id is returned to the client and feedback attaches to it.
  • Metrics are derived from spans, with no separate emission path left.
  • The cost table is versioned and historical cost can be recomputed.
  • Replay has been used at least once to reproduce a real reported issue.
