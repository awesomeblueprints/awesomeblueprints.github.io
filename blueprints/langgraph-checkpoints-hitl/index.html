LangGraph Checkpoints and Human Approval

LangGraph checkpoints and human approval: durable runs that survive a restart, interrupt-based pauses and idempotent resume semantics.

high4–5 daysVerified 2026-08-20
LangGraphAgents
Read it on GitHub ↗ Back to the catalogue

A running graph that survives a restart, and a pause in the middle of it where a person answers before it goes on — built so that resuming produces the same run rather than a second one.

Complexity: high · Typical build: 4–5 days · Verified: 2026-08-20 (re-check after ~90 days)

Examples in: Python, with LangGraph. The architecture is language-agnostic: sections 5, 10 and 11 hold wherever you build this. Section 4 is illustrative — if your project is in another language, your agent translates the idioms rather than importing them, and nothing is lost. The same shape exists as LangGraph.js in TypeScript, and as a hand-written state machine that persists after every step in any language; what matters is the resume semantics in §1 and the idempotence rules in §5, which are properties of any pause-and-resume design, not of one library.

Use when: a run can take longer than the process that started it, or a step in it must not happen until a person says so.

Not for: a run that finishes inside one request and does nothing irreversible. Persistence there buys storage cost and a resume path nobody exercises, and an unexercised resume path is worse than none. Also not for approval of everything — an approval on every step is an approval on nothing, because it will be clicked through.

1. The one behaviour that decides the design

A checkpointer writes the state after every node boundary, keyed by a thread id. That much is unremarkable. The part that determines how you must write your nodes is what happens when you resume:

Resuming re-executes the node from its first line. The pause is not a coroutine suspension that picks up where it stopped. The node function runs again from the top; everything before the pause call happens a second time; the pause call itself, this time, returns the value the person supplied instead of pausing.

Two consequences follow, and between them they account for most of the bugs in systems built this way:

Everything before the pause must be idempotent. A node that charges a card and then asks for approval charges the card twice — once on the way in, once on the way back. The rule: a node that pauses does nothing with an outside effect before the pause. Read, compute, format the question, pause. Act afterwards.

Several pauses in one node are matched by position, not by identity. The runtime pairs resumed values to pause calls by the order they occur. If the number or order of pause calls can change between the first execution and the re-execution — because one of them is inside an if whose condition now reads differently, or inside a loop whose length depends on state — the answers land on the wrong questions, silently. The rule: one pause per node, at a fixed position, never inside a conditional or a loop. If you need two questions, use two nodes.

The rest of this document is the machinery that makes those two rules enforceable.

Which steps pause

Pausing everything trains people to click approve without reading, which is worse than not pausing, because it manufactures a record of consent that means nothing. The test to apply, per action:

Can the agent undo this itself, within the same run?

Reading a record, running a query, calling a read-only API, writing to a scratch table the run owns — yes, it can be undone; no pause. Sending a message, moving money, deleting data, writing to a third-party system, publishing anything a person will see — no, it cannot; pause. That is the whole test, and it is worth applying literally rather than by feel: "important" is not the criterion, and neither is "expensive". Reversibility is.

Two refinements that keep the list short enough to be read:

  • Thresholds, not categories. A refund of €2 and a refund of €20 000 are the same category and not the same decision. Pause above a stated amount, and state it in configuration rather than in code.
  • Batching. Ten identical actions in one run are one approval with the list attached, not ten. This is the single most effective defence against approvals being clicked through.

The arrow that carries the weight is engine -> act labelled node re-runs from its first line. Everything in §5 about idempotence exists because that arrow is not a resumption, it is a re-entry. Note also that the pending-approvals view is derived from the checkpoint store rather than being a second table someone writes to: a separate approvals table drifts from the graph's real state the first time a run fails between writing the row and pausing.

3. Project structure

app/agent/
├── checkpointer.py    the store, its connection, and its retention job
├── nodes/
│   ├── prepare.py     read-only work; nothing with an effect
│   ├── ask.py         exactly one pause call, at a fixed position
│   └── act.py         the irreversible step, guarded by an idempotency key
├── approvals.py       the pending-approvals view, derived from paused threads
└── runner.py          start(thread_id) and resume(thread_id, decision)

One rule: a node whose file contains a pause call contains no outbound call of any kind. It is greppable, which is the point — this is the invariant most likely to be broken by a well-meaning later edit that adds "just a quick lookup" above the pause.

4. Reference implementation

# app/agent/nodes/ask.py
from langgraph.types import interrupt


def ask_approval(state: AgentState) -> dict:
    """Exactly one pause, at a fixed position, with no effect before it.

    On the first execution `interrupt` stops the graph and the payload is stored
    with the checkpoint. On resume this whole function runs again from line one,
    and `interrupt` returns the value supplied by the reviewer instead of
    pausing. Nothing above this line may have an outside effect, because
    everything above this line happens twice.
    """
    decision = interrupt({
        "kind": "refund",
        "amount_eur": state["refund"]["amount_eur"],
        "customer": state["refund"]["customer_id"],
        # The question carries what the reviewer needs to decide with. A payload
        # of ids forces them into another system to find out what they are
        # approving, which is how approvals become reflexive.
        "reason": state["refund"]["reason"],
    })
    return {
        "approved": decision["approved"],
        "approved_by": decision["actor"],
        "approval_note": decision.get("note", ""),
    }

# app/agent/nodes/act.py
import hashlib


def _idempotency_key(state: AgentState) -> str:
    # Derived from the run and the action, not from a clock or a random value —
    # a key that changes between attempts is not an idempotency key.
    raw = f"{state['thread_id']}:refund:{state['refund']['id']}"
    return hashlib.sha256(raw.encode()).hexdigest()


async def act(state: AgentState) -> dict:
    """The irreversible step. Runs only after approval, and only once.

    The guard is not paranoia: a crash between the external call succeeding and
    the checkpoint being written leaves a run that will retry this node. The
    checkpoint boundary is after the node, so at-least-once execution is the
    contract you get, and idempotency is how you turn it into exactly-once
    effects.
    """
    if not state.get("approved"):
        return {"result": "declined", "messages": [DECLINED]}
    receipt = await payments.refund(
        amount=state["refund"]["amount_eur"],
        idempotency_key=_idempotency_key(state),
    )
    return {"result": "refunded", "receipt_id": receipt.id}

# app/agent/graph.py
from langgraph.checkpoint.postgres.aio import AsyncPostgresSaver

# The checkpointer is durable. An in-memory one is for tests only: it makes every
# resume path pass locally and none of them work after a deploy, which is the
# worst possible split because the failure appears only in production.
checkpointer = AsyncPostgresSaver.from_conn_string(settings.checkpoint_dsn)
graph = builder.compile(checkpointer=checkpointer)

# app/agent/runner.py
from langgraph.types import Command

CONFIG = lambda tid: {"configurable": {"thread_id": tid}}


async def start(thread_id: str, payload: dict) -> dict:
    result = await graph.ainvoke(payload, config=CONFIG(thread_id))
    # A paused run returns with the pause payload rather than a final answer.
    # Callers must handle both, so the shape is explicit here rather than being
    # discovered by whoever writes the second caller.
    return {"paused": "__interrupt__" in result, "state": result}


async def resume(thread_id: str, decision: dict, actor: str) -> dict:
    """Resume is authenticated and audited here, at the boundary.

    The graph cannot tell who supplied a decision; it only sees a value. Identity
    has to be established before the value is handed over, and recorded next to
    it — an approval with no actor is not an approval.
    """
    await audit.record(thread_id=thread_id, actor=actor, decision=decision)
    return await graph.ainvoke(
        Command(resume={**decision, "actor": actor}), config=CONFIG(thread_id)
    )

# tests/test_resume.py
async def test_the_node_reruns_from_the_top_on_resume(counter):
    # The test that documents the semantics. It should surprise a reader once,
    # and then never again — which is why it is worth writing even though it
    # asserts library behaviour rather than yours.
    first = await start("t1", PAYLOAD)
    assert first["paused"]
    assert counter.prepare_calls == 1
    await resume("t1", {"approved": True}, actor="alice")
    assert counter.ask_entries == 2   # the pausing node ran a second time


async def test_a_second_resume_does_not_act_twice(payments_spy):
    await start("t2", PAYLOAD)
    await resume("t2", {"approved": True}, actor="alice")
    await resume("t2", {"approved": True}, actor="alice")   # a double-clicked button
    assert payments_spy.calls_with_distinct_keys == 1

5. Golden-standard rules

Rule Why
Forbidden: any outbound call, write or side effect before a pause in the same node Resuming re-executes the node from its first line, so everything above the pause happens twice.
Forbidden: more than one pause call in a node Resumed values are matched to pause calls by position; two makes the pairing depend on execution order.
Forbidden: a pause inside a conditional or a loop The number of pause calls must be identical on re-execution, or answers land on the wrong questions with no error.
Forbidden: an in-memory checkpointer outside tests Every resume path passes locally and none survives a deploy — the failure appears only in production.
Forbidden: an irreversible action without an idempotency key derived from the run The checkpoint boundary is after the node, so the contract is at-least-once execution.
Forbidden: resuming without establishing who is resuming The graph sees a value, not an actor; an approval with no actor is not an approval.
Forbidden: a separate approvals table written alongside the pause It drifts from real graph state the first time a run dies between the write and the pause. Derive the view from paused threads.
An action pauses when the agent cannot undo it within the same run Reversibility is the criterion. Not importance, not cost.
Amount-like decisions pause above a configured threshold Category-wide approval on a category containing trivial cases is approval nobody reads.
Repeated identical actions in one run are one approval with the list attached It is the most effective defence against reflexive approval.
The pause payload contains what is needed to decide A payload of ids sends the reviewer to another system, and they stop looking.
A paused thread has a deadline and a default A run paused forever is a leaked resource and an unanswered customer; state what happens when nobody answers.
Checkpoints have a stated retention period and a job that enforces it The store grows per node boundary per run; unbounded, it is the first thing to fall over.
Node names and state fields are treated as a stored interface Checkpoints written by the old shape are resumed by the new code after a deploy.

6. Data contracts

thread id       the identity of a run; stable, and the key to everything stored
pause payload   the question: kind, the facts to decide with, and options
resume value    the answer: decision, actor, optional note — recorded before use
checkpoint      full state at a node boundary, keyed by thread id

Two properties of the resume value are worth stating because they are easy to get wrong. It is untrusted input — it arrives from an HTTP request like any other and needs the same validation, even though it feels internal. And it is an audit record — decision, actor and time are written before the graph is resumed, not after, because writing after means a crash during the resume erases the evidence that anyone approved anything.

The state schema itself is a stored format, versioned by consequence: a checkpoint written yesterday is deserialised by today's code. Adding a field with a default is safe; renaming or removing one breaks every paused run in the store. Treat a field removal as a migration, with a pass over pending threads.

7. Build order

  1. A durable checkpointer, with a linear graph and no pause at all. Prove that a run survives a process restart before adding anything that depends on it.
  2. Retention, written now, while the store is empty and the job is trivial to verify.
  3. One pausing node, containing nothing but the pause call, plus the test that asserts the node re-runs from the top on resume.
  4. The resume boundary, with identity established and the audit record written before the graph is resumed.
  5. The act node with an idempotency key, and the double-resume test.
  6. The pending-approvals view, derived from paused threads rather than stored separately.
  7. Deadlines and defaults for unanswered pauses, with a job that applies them.
  8. Notification, last, because it is the only part that can be a manual check in the meantime without anything being unsafe.

Step 1 before step 3 is the sequencing that matters: a pause on a non-durable checkpointer looks like it works, and that impression survives until the first deploy.

10. Failure modes

Symptom Cause Fix
A side effect happens twice around an approval Something with an effect runs before the pause in the same node Move it after the pause, or into an earlier node
An answer is applied to the wrong question Two pause calls in a node, or one inside a conditional or loop One pause per node, at a fixed position; split into two nodes
Resuming raises that no checkpoint exists No thread id on the original run, or a different one on resume The thread id is the identity; pass the same one
Everything resumes locally and nothing resumes in production An in-memory checkpointer Durable store everywhere but tests
A crash after an external call causes it to repeat on retry The checkpoint boundary is after the node; execution is at-least-once Idempotency key derived from the run and the action
A double-clicked approve button acts twice Resume is not guarded Same idempotency key; make a second resume a no-op
Paused runs accumulate and nothing chases them No deadline and no default A job that applies the stated default and records that it did
The database fills with checkpoints No retention policy State one and enforce it with a job
Paused runs break after a deploy A state field was renamed or removed, or node names changed Treat the state schema as a stored format; add with defaults, migrate on removal
Approvals are always granted, instantly Too many pauses, or payloads too thin to read Apply the reversibility test; batch repeats; put the facts in the payload
Nobody can say who approved something The actor came from the graph rather than from authentication at the boundary Establish identity outside the graph and record it before resuming
The pending list disagrees with what is actually paused An approvals table written next to the pause Derive the list from paused threads

11. Definition of done

  • A durable checkpointer is configured everywhere except tests, verified by reading the configuration for each environment
  • A run started before a process restart completes after it, covered by a test that actually restarts the process
  • No node contains both a pause call and an outbound call, checked by grep in CI
  • No node contains more than one pause call, and no pause appears inside a conditional or a loop, checked by grep in CI
  • A test asserts that the pausing node re-executes from its first line on resume
  • Every irreversible action uses an idempotency key derived from the thread id and the action, verified by reading each call site
  • Resuming twice with the same decision produces one external effect, covered by a test
  • The resume boundary authenticates the actor and writes the audit record before resuming the graph
  • The resume value is validated as untrusted input, covered by a test with a malformed decision
  • The list of pausing actions is written down, and every entry passes the "cannot be undone within the run" test
  • Repeated identical actions in one run raise one approval carrying the full list, covered by a test
  • Every pause payload contains the facts needed to decide, verified by reviewing each payload against what a reviewer would otherwise have to look up
  • Paused runs have a deadline and a stated default, applied by a job and recorded when applied
  • Checkpoint retention is stated and enforced by a job, verified by running it against seeded old rows
  • The pending-approvals view is derived from paused threads, not from a separate table
