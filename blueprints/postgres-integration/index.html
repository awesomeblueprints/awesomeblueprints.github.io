PostgreSQL Connection Pool and Lifecycle

A PostgreSQL connection layer: pool sizing, startup and shutdown, health checks and running behind a connection pooler in production.

low1–2 daysVerified 2026-08-19
PostgreSQL
Read it on GitHub ↗ Back to the catalogue

A connection pool owned by the application's lifespan, a health check that actually reaches the database, and a shutdown that finishes in-flight work — the layer an ORM or hand-written SQL sits on, without choosing either.

Complexity: low · Typical build: 1–2 days · Verified: 2026-08-19 (re-check after ~90 days)

Examples in: Python, with asyncpg and FastAPI. The architecture is language-agnostic: sections 5, 10 and 11 hold wherever you build this. Section 4 is illustrative — if your project is in another language, your agent translates the idioms rather than importing them, and nothing is lost. The equivalents are pg.Pool in Node, pgx.Pool in Go, Ecto.Repo in Elixir, and HikariCP in the JVM.

Use when: a service needs Postgres and you want the connection lifecycle right before anything is built on top — pool sizing, startup, shutdown, health, and the pooler in front of it in production.

Not for: a short-lived script or a one-off job. A single connection opened and closed around the work is correct there, and a pool in a process that runs for four seconds is machinery with nothing to amortise. Also not the place to choose an ORM: this layer deliberately ends before that decision.

1. Why a connection where you need one fails

The obvious version is a module-level connection, or a new connection per request. Both work on a laptop and fail differently under load.

A connection made where it is needed A pool owned by the lifespan
Each request pays the TCP handshake, TLS negotiation and authentication round trip before its first query The connection is already open; the request pays an acquire
Nothing bounds concurrency, so a traffic spike opens connections until the server refuses them — and the error surfaces as a failing health check, not as load The pool is the bound, and requests queue instead of overwhelming the server
A pool created at import time is inherited by every forked worker, and several processes read and write the same sockets The pool is created after the fork, inside the lifespan, so each worker owns its own
Shutdown drops whatever was in flight Shutdown stops accepting, drains, then closes

The third row produces the strangest incident in this list. Symptoms are corrupted responses, protocol errors, and queries answering with another request's rows — because two processes really are interleaving bytes on one socket. It is not a race in your code and reading your code will not find it. The pool must be created after the fork, which means inside the lifespan, not at module import.

The rule the diagram encodes: the pool has exactly one owner, and it is the lifespan. Nothing else creates a connection, and nothing outlives the process that made it.

3. Project structure

app/
├── db.py               the pool: creation, shutdown, the acquire helper
├── main.py             lifespan wires the pool up and down
├── health.py           the readiness endpoint that reaches the database
└── queries/
    └── orders.py       query functions taking a connection, returning rows
compose.yaml            Postgres for local development, with a healthcheck

One rule: only db.py holds a reference to the pool. Everything else receives a connection. A module that reaches for the global pool cannot be tested without one, and cannot be run inside someone else's transaction — which is what every integration test needs and what a background job will eventually need too.

4. Reference implementation

# app/db.py
from contextlib import asynccontextmanager
import asyncpg

_pool: asyncpg.Pool | None = None


async def create_pool(settings) -> asyncpg.Pool:
    return await asyncpg.create_pool(
        dsn=str(settings.database_url),
        # Sizing is arithmetic, not taste: max_size * worker_count must stay under
        # the server's max_connections with room for migrations, psql and the
        # replica. Ten workers at 20 is 200 connections against a default of 100.
        min_size=2,
        max_size=10,
        # A query that hangs holds a pool slot forever; once every slot is held the
        # service is down while the database looks idle. This is the single most
        # valuable line in the file.
        command_timeout=30,
        server_settings={
            "statement_timeout": "30000",          # the server's own backstop
            "application_name": "orders-api",      # so pg_stat_activity names the culprit
        },
        # Only when a pooler in transaction mode is in front. asyncpg caches
        # prepared statements per backend; the pooler moves you between backends
        # between transactions, so cached names refer to statements that are not
        # there. See §10 — it only fails under production concurrency.
        statement_cache_size=0 if settings.database_pooler_transaction_mode else 100,
    )


@asynccontextmanager
async def lifespan_pool(settings):
    global _pool
    # Created here, not at import: a pool built before the fork is inherited by
    # every worker, and they share sockets.
    _pool = await create_pool(settings)
    try:
        yield _pool
    finally:
        # close() waits for checked-out connections to be returned. terminate()
        # does not — it severs them mid-query, which rolls back work the client was
        # told had succeeded.
        await _pool.close()
        _pool = None


@asynccontextmanager
async def connection():
    if _pool is None:
        raise RuntimeError("pool not initialised — acquire outside the lifespan")
    async with _pool.acquire() as conn:
        yield conn

# app/main.py
from contextlib import asynccontextmanager
from fastapi import FastAPI
from app.config import get_settings
from app.db import lifespan_pool


@asynccontextmanager
async def lifespan(app: FastAPI):
    async with lifespan_pool(get_settings()):
        yield          # the app serves only while the pool is up


app = FastAPI(lifespan=lifespan)

# app/health.py
import asyncio
from fastapi import APIRouter, Response, status
from app.db import connection

router = APIRouter(tags=["health"])


@router.get("/health/live")
async def live() -> dict:
    # Liveness answers "is this process wedged". It must not touch the database:
    # if it did, a database blip would restart every healthy worker at once and
    # turn a recoverable outage into a thundering herd against a struggling server.
    return {"status": "ok"}


@router.get("/health/ready")
async def ready(response: Response) -> dict:
    # Readiness answers "can this process serve traffic", which requires a real
    # query. `SELECT 1` on an already-open connection proves the socket works;
    # acquiring from the pool first is what proves a slot is available.
    try:
        async with asyncio.timeout(2):
            async with connection() as conn:
                await conn.fetchval("SELECT 1")
    except Exception:
        # Never include the exception text: a connection error carries the DSN,
        # and the DSN carries the password.
        response.status_code = status.HTTP_503_SERVICE_UNAVAILABLE
        return {"status": "database unavailable"}
    return {"status": "ok"}

5. Golden-standard rules

Rule Why
Forbidden: creating the pool at module import It is inherited across a fork and several workers then share sockets. The symptoms look like data corruption and reading the code will not find them.
Forbidden: opening a connection outside the pool It escapes every bound you set — timeouts, sizing, metrics — and it is the connection that leaks.
Forbidden: returning a driver error message to a client or a probe Connection errors embed the DSN, and the DSN embeds the password.
Forbidden: terminate() in the normal shutdown path It severs in-flight queries, rolling back work a client was already told succeeded. Drain with close(); keep terminate for a timed-out drain.
Every query has a timeout, and so does every acquire A hung query holds a slot for as long as it hangs. Once all slots are held the service is down while the database sits idle — the least obvious outage in this document.
Pool size is derived, not chosen max_size × workers must fit under max_connections with headroom for migrations, a replica and a human with psql. Write the arithmetic in a comment.
Liveness never touches the database Otherwise one database blip restarts every worker simultaneously and a recoverable outage becomes a stampede.
Readiness always touches the database A readiness probe that only proves the process is running will happily route traffic to a worker whose pool is exhausted.
The application name is set on every connection It is what turns pg_stat_activity from a list of anonymous queries into an answer during an incident.
One module owns the pool; everything else is handed a connection A function that reaches for a global cannot be run inside a test's transaction, and integration tests need exactly that.
Local Postgres is gated on a real readiness check pg_isready, not an open port. The container accepts TCP long before it accepts queries.
The pooler's mode is written down where the pool is configured Transaction mode changes the driver configuration, not just the tuning, and the failures it causes appear only under production concurrency.

6. Data contracts

The contract this layer exposes is the connection, and two properties of it:

@asynccontextmanager
async def connection() -> AsyncIterator[Connection]:
    """Checked out for the duration of the block and returned on exit, including
    on exception. Carries a command timeout. Not safe to store, not safe to use
    after the block, not safe to share between tasks."""

Everything above this layer takes a connection as an argument rather than importing one. That single choice is what makes a query function usable inside a request, inside a background job, and inside a test that rolls back — without a branch for each.

7. Build order

  1. Pool created in the lifespan, one query, proven. Start the app, run a trivial query through the pool, shut it down cleanly. This is the whole risk of the layer, and everything after is addition.
  2. Compose with a pg_isready healthcheck, and confirm the app starts on the first up from a cold volume.
  3. Timeouts — command, statement, and a bounded acquire — and prove each by forcing it with pg_sleep.
  4. Readiness and liveness, split, with a test that stops the database and asserts readiness fails while liveness still passes.
  5. Drain on shutdown: send SIGTERM during an in-flight slow query and assert it completed rather than being severed.
  6. Pool sizing and application_name, with the arithmetic recorded.
  7. If a pooler is in front: set the driver's statement caching accordingly and run a concurrency test against it, because nothing below that level of load reproduces the failure.

Step 5 is placed before sizing deliberately. Losing in-flight work on every deploy is a correctness bug that ships silently; a pool that is slightly the wrong size is a performance problem you can see.

8. Blocks to pull in

Nothing here is a prerequisite. These are adjacent problems, by name only — resolve them separately if they apply.

  • Typed config and settings — where the DSN and the pool sizes are validated

  • Alembic migrations — schema changes against the same database
  • Docker Compose dev environment — the fuller local stack this compose file grows into

9. Metrics

Metric Target
Connection acquire wait, p99 < 10 ms under expected load
Pool slots in use at steady state < 70% of max_size
Connections opened per minute at steady state ~0 — a rising number means the pool is churning
max_size × workers against server max_connections ≤ 70%, leaving room for migrations and operators
Requests lost to a rolling restart 0
Time from database becoming unreachable to readiness failing < 5 s

10. Failure modes

Symptom Cause Fix
Protocol errors, garbled results, or a query returning another request's rows The pool was created at import and inherited across the worker fork; processes share sockets Create the pool inside the lifespan, after the fork
The service stops responding while the database shows almost no activity Every pool slot is held by a query that will never return, because no command timeout is set Set command_timeout and a server-side statement_timeout
InvalidSQLStatementNameError or DuplicatePreparedStatementError, only in production, only under load asyncpg caches prepared statements per backend; a pooler in transaction mode moves you between backends between transactions Disable the driver's statement cache, or use session mode, or a pooler version that tracks prepared statements — and measure the throughput cost, because disabling the cache is not free
FATAL: sorry, too many clients already after adding workers max_size × workers exceeded max_connections, and nobody did the multiplication Recompute; add a pooler rather than raising max_connections past what the server can schedule
Every deploy loses a handful of requests that returned 200 Shutdown terminates connections instead of draining them Drain with close(), bounded by a timeout, before the process exits
A database restart restarts every application worker at once Liveness probes the database, so a shared dependency failing marks every process dead Liveness checks the process; readiness checks the database
Health is green while requests fail Readiness returns 200 without touching the database, so an exhausted pool looks healthy Acquire from the pool and run a statement in the readiness path
The app fails on the first docker compose up and works on the second depends_on waited for the container, not for the server; Postgres accepts TCP before it accepts queries Gate on a pg_isready healthcheck with condition: service_healthy
A password appears in the logs A connection error was formatted into a log line or a probe response, and it contains the DSN Never render driver exceptions outward; log a fixed string and the error class
pg_stat_activity shows dozens of identical queries with no way to tell which service they belong to application_name was never set Set it in server_settings

11. Definition of done

  • The pool is created inside the lifespan and a test asserts no pool exists at import time
  • Starting the application with the database unreachable fails startup rather than serving traffic
  • Every connection carries a command timeout, proven by a test that runs pg_sleep beyond it and expects a timeout rather than a hang
  • A server-side statement_timeout is set, verified by querying the setting on a pooled connection
  • application_name is set, verified by reading pg_stat_activity in a test
  • /health/live returns 200 with the database stopped; /health/ready returns 503 within five seconds of the same, both covered by tests
  • SIGTERM during an in-flight query lets it finish and the process exits within the drain timeout, covered by a test
  • The pool sizing arithmetic is written in the code next to the numbers, and max_size × workers is under 70% of the server's max_connections
  • No module other than the pool module holds a reference to the pool, checked by grep in CI
  • Every query function accepts a connection rather than acquiring one, so a test can pass a connection inside a rolled-back transaction
  • No driver exception text reaches a log, a response or a probe body, covered by a test that fails connection with a bad password and asserts the password is absent from the output
  • docker compose up from an empty volume starts the application successfully on the first attempt
  • If a pooler is deployed in front, its mode is recorded next to the pool configuration and a concurrency test runs against it
