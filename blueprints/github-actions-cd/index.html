GitHub Actions CD

GitHub Actions CD: build once and promote the same image, environment approvals, smoke checks after deploy and a rollback you have run.

medium2–4 daysVerified 2026-08-19
CI/CD
Read it on GitHub ↗ Back to the catalogue

Deployment that starts where CI ended: one image built once and identified by its commit, cloud credentials issued per run instead of stored, production behind an approval, migrations before instances, and a health check that rolls back rather than reports.

Complexity: medium · Typical build: 2–4 days · Verified: 2026-08-19 (re-check after ~90 days)

Examples in: GitHub Actions deploying a container. The architecture is language-agnostic: sections 5, 10 and 11 hold wherever you build this. Section 4 is illustrative — if your project is in another language or on another platform, your agent translates the idioms rather than importing them, and nothing is lost. The identity, approval, migration-ordering and rollback concerns are the same on GitLab, Buildkite or Argo; only the syntax changes.

Use when: a service is deployed often enough that doing it by hand is a risk, and CI already runs and blocks merges. This builds on that: it does not repeat the checks, it requires them.

Not for: a project with no CI. Automating a deploy that nothing verified means shipping breakage faster and more reliably. Also not for a system where a bad release cannot be undone — a database rewrite, an irreversible external effect — where the correct answer is a manual gate with a human who understands the blast radius.

⚙️ INSTRUCTIONS FOR THE AI — READ BEFORE WRITING ANY CODE

Do not start coding.

Step 1 — Refresh. Verify whether the target platform supports federated identity from the CI provider, and the current configuration for it — issuing a short-lived credential per run removes the stored long-lived key, which is the single biggest improvement available here. Verify the current syntax for environments, required reviewers and deployment protection rules. Resolve every action to a commit SHA. Confirm how the platform reports a rollout's health and whether it can roll back on its own, because that decides whether §4's rollback step is a command you issue or a policy you configure. Report what you verified and what turned out wrong.

Step 2 — Read the project, then audit what already exists. Find how deploys happen today, including the manual steps, and write them down — that list is the specification. Find every long-lived credential stored as a secret and what it can reach; each is a work item. Find whether migrations currently run as part of the deploy and in what order relative to new instances starting. Find whether anything verifies the deploy afterwards. Determine whether the platform can roll back and how long it takes. Then audit §11 item by item, each marked already true, partly true or absent, with the file that decides it, reported before anything is proposed.

Assume the project is right until it demonstrably is not; code satisfying an item stays even where its shape differs from §4; replacing something that works needs a one-line reason; never delete a working path to make room for the blueprint's version. The same holds for language — §4 is illustrative, its idioms get translated into the project's language, and §11 is what has to become true rather than the syntax.

Step 3 — Write a plan for the gap only, and get it approved, including a ## Proposed stack section, the rollback procedure, and what happens if a migration succeeds and the deploy then fails. Do not ask open framework questions — propose, and ask for confirmation once. Say what you are adding, what you are leaving alone, and what you propose to change, and touch nothing else.

Step 4 — Build in the order in §7. Step 5 — §11 is the definition of done.

1. Why a deploy job is not continuous delivery

The obvious version adds a deploy step to the end of the existing pipeline. It works, and it collects four problems.

A deploy step bolted onto CI A separate delivery workflow
A long-lived cloud key sits in repository secrets, valid until someone rotates it A short-lived credential is issued per run, scoped to this repository and branch
The image is rebuilt for deploy, so what ships was never the thing that was tested One image, built once, identified by the commit, promoted through environments
Production deploys automatically because staging did Production is an environment with a required reviewer
Success means the workflow exited zero Success means the new version answered a health check, and failure rolls back

The second row is the one that produces the unexplainable incident. Rebuilding from the same commit is not reproducible unless every input is pinned, and most are not: a base image tag moved, a transitive dependency published a patch, a build argument differed. Tag the image with the commit SHA, build it once, and deploy that digest. Then "which code is in production" has an answer you can check rather than infer.

The fourth row is where teams discover their rollback does not exist. A workflow that exits zero after issuing a deploy command has told you the command was accepted. Whether the new version can serve traffic is a separate question, and it is the only one that matters.

The rule the diagram encodes: one arrow leaves the build, and every environment downstream consumes that same digest. No environment rebuilds. If any did, the thing verified in staging and the thing running in production would be different artefacts that merely share a commit message.

3. Project structure

.github/workflows/
├── ci.yaml         checks on pull requests — required, and unchanged by this work
└── cd.yaml         build, push, promote — runs only on main and only after CI

One rule: CD is triggered by a merge to a protected branch, never by a pull request event. A pull request can modify the workflow that runs it. Anything holding credentials must run from a ref that review has already gated, or a contributor can propose a change whose only purpose is to print your secrets.

4. Reference implementation

# .github/workflows/cd.yaml
name: CD

on:
  push:
    branches: [main]      # merge only; never pull_request, and never pull_request_target

permissions:
  contents: read
  id-token: write         # mint the short-lived identity token — this is what
                          # replaces a stored cloud key
  packages: write         # push the image

concurrency:
  # Never two deploys at once, and do NOT cancel: a half-applied deploy is worse
  # than a queued one. This is the opposite of the CI setting, deliberately.
  group: cd-production
  cancel-in-progress: false

jobs:
  build:
    runs-on: ubuntu-24.04
    outputs:
      digest: ${{ steps.push.outputs.digest }}
    steps:
      - uses: actions/checkout@11bd71901bbe5b1630ceea73d27597364c9af683 # v4.2.2
      - uses: docker/login-action@74a5d142397b4f367a81961eba4e8cd7edddf772 # v3.4.0
        with:
          registry: ghcr.io
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}
      - id: push
        uses: docker/build-push-action@471d1dc4e07e5cdedd4c2171150001c434f0b7a4 # v6.15.0
        with:
          push: true
          # The commit SHA, not `latest`. `latest` cannot answer "what is running
          # in production" and cannot be rolled back to a known point.
          tags: ghcr.io/${{ github.repository }}:${{ github.sha }}
          cache-from: type=gha

  staging:
    needs: build
    runs-on: ubuntu-24.04
    environment: staging
    steps:
      - uses: aws-actions/configure-aws-credentials@ececac1a45f3b08a01d2dd070d28d111c5fe6722 # v4.1.0
        with:
          # No stored access key. The workflow presents a signed identity token and
          # receives a credential valid for minutes, scoped to this repository and
          # this branch. A leaked log line is then worth nothing an hour later.
          role-to-assume: ${{ vars.STAGING_ROLE_ARN }}
          aws-region: eu-central-1
      - run: ./deploy.sh staging "${{ needs.build.outputs.digest }}"
      - name: Smoke check
        # The deploy command returning zero means the platform accepted it. This is
        # what proves the new version can actually serve.
        run: ./smoke.sh "$STAGING_URL"

  production:
    needs: [build, staging]
    runs-on: ubuntu-24.04
    # The environment carries the protection rules: required reviewers, and which
    # branches may deploy to it. The gate lives in the environment, not in this
    # file — a workflow edit cannot remove it.
    environment:
      name: production
      url: https://api.example.com
    steps:
      - uses: aws-actions/configure-aws-credentials@ececac1a45f3b08a01d2dd070d28d111c5fe6722 # v4.1.0
        with:
          role-to-assume: ${{ vars.PRODUCTION_ROLE_ARN }}
          aws-region: eu-central-1

      - name: Migrate
        # Before new instances start, and backward compatible by rule: during a
        # rolling deploy the previous version is still serving against this schema.
        # A migration that the old code cannot tolerate breaks production before
        # the new version has replaced it.
        run: ./migrate.sh "${{ needs.build.outputs.digest }}"

      - name: Deploy
        run: ./deploy.sh production "${{ needs.build.outputs.digest }}"

      - name: Verify
        id: verify
        # Poll until the new version reports ready, or give up. Without a timeout
        # a stuck rollout hangs the job until the runner limit, and nobody rolls back.
        run: ./verify.sh "https://api.example.com" --timeout 180

      - name: Roll back
        if: failure() && steps.verify.outcome == 'failure'
        # Deploying the previous digest, not reverting the commit: it is faster, it
        # needs no build, and it restores an artefact that was known to work.
        # Note the schema is NOT rolled back — that is why migrations must be
        # backward compatible.
        run: ./deploy.sh production "${{ vars.PREVIOUS_DIGEST }}"

# verify.sh — success means serving, not "command accepted"
#!/usr/bin/env bash
set -euo pipefail
url=$1; deadline=$(( $(date +%s) + ${3:-180} ))
until curl -fsS "$url/health/ready" >/dev/null; do
  [ "$(date +%s)" -lt "$deadline" ] || { echo "did not become ready"; exit 1; }
  sleep 5
done
# Readiness alone can be true on old instances that have not been replaced yet.
# Assert the version too, or the check passes while the deploy did nothing.
test "$(curl -fsS "$url/version" | jq -r .commit)" = "$GITHUB_SHA"

5. Golden-standard rules

Rule Why
Forbidden: a long-lived cloud key in repository secrets It is valid until someone remembers to rotate it, and it is reachable by every workflow. Federated identity issues a credential per run that expires in minutes.
Forbidden: CD triggered by a pull-request event A pull request can change the workflow that runs it. Anything holding credentials runs from a reviewed ref only.
Forbidden: rebuilding the image per environment Then what was tested and what ships are different artefacts. Build once; promote the digest.
Forbidden: deploying a mutable tag such as latest It cannot answer what is running, and it cannot be rolled back to a known point.
Forbidden: a migration the currently running version cannot tolerate During a rolling deploy the old code runs against the new schema. A dropped column breaks production before the new version has replaced it.
Forbidden: cancelling an in-flight deploy A half-applied deploy is worse than a queued one. Serialise; do not cancel.
Success means the new version served a request A deploy command exiting zero means it was accepted, which is a different claim.
The verification asserts the version, not just health Readiness can be answered by old instances that were never replaced, so the check passes while nothing was deployed.
Rollback deploys the previous digest, not a reverted commit It is faster, needs no build, and restores an artefact known to have worked.
Production is an environment with a required reviewer The gate then lives outside the workflow file, where editing the file cannot remove it.
Every deploy is traceable to a commit from the artefact alone Someone will need to answer "what is running" during an incident, without access to the pipeline.
Rollback is exercised on a schedule An untested rollback is a plan, and the first execution should not be during an outage.

6. Data contracts

artefact      one image, tagged with the commit SHA, referenced by digest
promotion     staging and production consume the same digest; neither rebuilds
credential    short-lived, per run, scoped to this repository and branch
gate          production requires an approval recorded outside the workflow file
success       the new version answered a health check and reported its own commit
rollback      redeploy the previous digest; the schema is not rolled back

The last line is the contract that constrains everything upstream. Because the schema does not roll back, every migration must be safe for the version being rolled back to. That single sentence is why a column is removed a release after the code stops using it, and it belongs in the deployment contract rather than in a migration checklist nobody reads.

7. Build order

  1. Build and push one image tagged with the commit, on merge to main. Nothing deploys yet. Confirm the digest is reproducible as a reference.
  2. Deploy that digest to staging with a stored credential if that is what exists. Getting the promotion shape right first is worth more than getting the credential right first.
  3. Replace the stored credential with federated identity, and delete the stored one. Deleting it is the step that matters; an unused key is still a key.
  4. Smoke check against staging, asserting the deployed version's commit.
  5. Production as a gated environment with a required reviewer.
  6. Migrations as a step before instances start, with the backward-compatibility rule written into the review checklist.
  7. Verification with a timeout, then rollback — and execute a rollback deliberately, on purpose, before you need one.

Step 7 last and non-optional. Everything before it makes deploys faster; only this step makes a bad deploy survivable, and it is the one that gets postponed.

8. Blocks to pull in

Nothing here is a prerequisite. These are adjacent problems, by name only — resolve them separately if they apply.

  • GitHub Actions CI — the checks this workflow requires rather than repeats
  • Alembic migrations — the backward-compatible schema changes this deploys
  • Dockerfile for a production service — the image built once and promoted
  • PostgreSQL connection pool and lifecycle — the readiness endpoint verification polls
  • Observability and tracing — where the deploy marker and the post-deploy signal land

9. Metrics

Metric Target
Time from merge to production < 20 minutes, excluding the approval wait
Long-lived cloud credentials stored as secrets 0
Images rebuilt between staging and production 0
Deploys that cannot be traced to a commit from the artefact 0
Time to roll back < 5 minutes
Rollbacks executed as a drill ≥ 1 per quarter
Failed deploys that left production in a mixed state 0

10. Failure modes

Symptom Cause Fix
Production behaves differently from staging with the same commit The image was rebuilt per environment and an unpinned input changed Build once, promote the digest
Nobody can say which code is in production The deployed tag is latest or a branch name Tag with the commit SHA and expose it on a version endpoint
A cloud key leaked and the exposure window was months A long-lived key was stored as a repository secret Federated identity, and delete the stored key
A contributor's pull request printed a production secret CD was triggered by a pull-request event Trigger on push to a protected branch only
Production broke during a deploy, before the new version was live A migration removed something the running version still used Backward-compatible migrations; remove a release later
The deploy reported success and users saw errors Success was defined as the deploy command exiting zero Poll a health endpoint and assert the version
Verification passes but nothing was deployed Old instances answered the readiness check Assert the reported commit matches the deployed one
A rollback was attempted and failed It reverted the commit and rebuilt, which takes as long as a deploy and can fail the same way Redeploy the previous digest
Two deploys ran at once and production ended in a mixed state The concurrency group cancelled in progress, or was absent Serialise deploys and do not cancel
The job hung until the runner limit and nobody rolled back Verification had no timeout Bound it, and treat the timeout as a failure that triggers rollback
The rollback ran and the application still failed The schema had moved forward and the old code could not read it This is the backward-compatibility rule; there is no fix at rollback time

11. Definition of done

  • No long-lived cloud credential exists as a repository or organisation secret, verified by listing them
  • The workflow triggers only on push to a protected branch, never on a pull-request event
  • The image is built once and staging and production deploy the same digest, asserted by comparing the deployed digests
  • Every running instance exposes the commit it was built from, and a deploy asserts it matches
  • Production deploys require an approval recorded in the environment, verified by attempting a deploy
  • Migrations run to completion before any new instance starts, and a failing migration stops the deploy — demonstrated once
  • Verification polls a health endpoint with a timeout, and a timeout is treated as a failure
  • A failed verification automatically redeploys the previous digest, demonstrated by deliberately deploying a broken image
  • A rollback has been executed on purpose within the last quarter, and the time it took is recorded
  • Two deploys triggered close together run one after the other, and neither is cancelled
  • Every action is pinned to a full commit SHA
  • The deployment contract, including that the schema is not rolled back, is written down where migration authors will read it
