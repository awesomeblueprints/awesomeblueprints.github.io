JWT Access Token Authentication

JWT authentication for an API: registration, login, token signing and verification, a current_user dependency, roles and scopes.

medium2–3 daysVerified 2026-08-19
Auth
Read it on GitHub ↗ Back to the catalogue

Registration, login and protected endpoints with a short-lived access token — stopping deliberately at the access token, because that is enough for most systems and the verification step is where the exploitable mistakes are.

Complexity: medium · Typical build: 2–3 days · Verified: 2026-08-19 (re-check after ~90 days)

Examples in: Python, with PyJWT, Argon2 and FastAPI. The architecture is language-agnostic: sections 5, 10 and 11 hold wherever you build this. Section 4 is illustrative — if your project is in another language, your agent translates the idioms rather than importing them, and nothing is lost. The equivalents are jose or jsonwebtoken with an explicit algorithms option in Node, golang-jwt with WithValidMethods in Go, and Guardian in Elixir — where the algorithm-allowlist requirement is exactly the same.

Use when: an API needs to know who is calling, the callers are your own clients, and you control both sides. Covers registration, login, a current_user dependency, roles and scopes.

Not for: long-lived sessions you must be able to revoke, "log out from all devices", or immediately disabling a compromised account. A signed token is valid until it expires and nothing can withdraw it — that needs a server-side session and refresh rotation, which is a separate system with its own threat model. Also not for delegating access to third-party clients: that is OAuth 2, and rolling your own is a bad trade.

1. Why the naive version is exploitable rather than merely weak

Most authentication bugs are not subtle. They are one missing argument.

The obvious implementation This one
jwt.decode(token, key) — the library reads the algorithm from the token's own header The algorithm is passed in as an allowlist; the token does not get a vote
The password is hashed with whatever the tutorial used Argon2id at current OWASP parameters, with the work factor stored in the hash so it can be raised later
A wrong password and an unknown user return different errors Both return the same response in the same time
Expiry is a number someone picked Short, because nothing can revoke the token before it expires

The first row is the one that ends in a breach report. If the verifier trusts the token's alg header, three attacks follow immediately: alg: none with the signature removed; an RS256 system fed an HS256 token signed with the public key — which is public, so the attacker has the "secret"; and kid pointed at a file or a SQL injection that yields a key the attacker chose. All three are prevented by the same thing: tell the library which algorithms you accept, rather than asking it to detect one.

The third row is quieter but real. If "no such user" returns faster than "wrong password", the endpoint is a user-enumeration oracle, and the attacker's next step is a credential-stuffing list narrowed to real accounts.

The rule the diagram encodes: there are two distinct rejection paths, and they mean different things. The decoder rejects with 401 — the credential is missing, malformed or expired, and retrying with a fresh token might work. The scope check rejects with 403 — the credential is fine and the answer will not change. Clients build their refresh logic on that distinction, so collapsing both into one status produces infinite refresh loops.

3. Project structure

app/
├── auth/
│   ├── passwords.py    hashing and verification, one algorithm, one place
│   ├── tokens.py       encode and decode — the only module that calls the JWT library
│   ├── deps.py         current_user, require_scopes
│   └── routes.py       register, login, me
└── models/user.py      the user, the hash, the active flag

One rule: tokens.py is the only module that imports the JWT library. Verification has one correct call shape and several dangerous ones; keeping it to one function means the allowlist is written once and reviewed once, instead of being an argument someone might omit at a second call site.

4. Reference implementation

# app/auth/passwords.py
from argon2 import PasswordHasher
from argon2.exceptions import VerifyMismatchError, VerificationError, InvalidHashError

# OWASP's stated minimum at the time of writing: 19 MiB, 2 iterations, 1 lane.
# Re-check the cheat sheet at the Verified date above — these numbers move upward
# with hardware, and a fixed number in a blueprint is a floor, never a ceiling.
_hasher = PasswordHasher(memory_cost=19456, time_cost=2, parallelism=1)

# A dummy hash of a random value, computed once at import. Verifying against it
# when the user does not exist makes the "no such user" path cost the same as the
# "wrong password" path — otherwise the endpoint tells an attacker which emails
# are registered, by timing alone.
_DUMMY = _hasher.hash("not-a-real-password-only-for-timing")


def hash_password(password: str) -> str:
    # Argon2 has no short input limit. bcrypt truncates at 72 bytes, which means
    # two different long passwords sharing a prefix both authenticate — if you must
    # use bcrypt, enforce a maximum length explicitly.
    return _hasher.hash(password)


def verify_password(password: str, stored_hash: str | None) -> bool:
    try:
        _hasher.verify(stored_hash or _DUMMY, password)
    except (VerifyMismatchError, VerificationError, InvalidHashError):
        return False
    return stored_hash is not None


def needs_rehash(stored_hash: str) -> bool:
    # The parameters are encoded in the hash string, so raising the work factor
    # later is a rehash on next successful login rather than a password reset for
    # everyone. This is the only migration path that does not annoy every user.
    return _hasher.check_needs_rehash(stored_hash)

# app/auth/tokens.py
from datetime import datetime, timedelta, timezone
import jwt                                   # PyJWT — maintained; python-jose is not
from app.config import get_settings

settings = get_settings()
ALGORITHM = "HS256"                          # one algorithm, named here, nowhere else


def create_access_token(subject: str, scopes: list[str]) -> str:
    now = datetime.now(timezone.utc)
    return jwt.encode(
        {
            "sub": subject,
            "scopes": scopes,
            "iat": now,
            # Short, because nothing can revoke this token before it expires. If a
            # long session is needed, that is refresh rotation — a different system.
            "exp": now + timedelta(minutes=15),
            "iss": settings.jwt_issuer,
            "aud": settings.jwt_audience,
        },
        settings.jwt_secret.get_secret_value(),
        algorithm=ALGORITHM,
    )


def decode_access_token(token: str) -> dict:
    return jwt.decode(
        token,
        settings.jwt_secret.get_secret_value(),
        # The load-bearing argument in this file. Without it the library reads the
        # algorithm out of the token's own header, which allows alg:none, and allows
        # an RS256 deployment to be fed an HS256 token signed with the public key.
        # The token does not get to choose how it is verified.
        algorithms=[ALGORITHM],
        # Checked explicitly rather than trusted to a default: a token minted by
        # another service of yours, or for a different audience, must not be
        # accepted here just because it verifies.
        audience=settings.jwt_audience,
        issuer=settings.jwt_issuer,
        options={"require": ["exp", "iat", "sub", "aud", "iss"]},
        leeway=10,                           # seconds, for clock skew between hosts
    )

# app/auth/deps.py
from typing import Annotated
from fastapi import Depends, HTTPException, status
from fastapi.security import OAuth2PasswordBearer
import jwt
from app.auth.tokens import decode_access_token

oauth2 = OAuth2PasswordBearer(tokenUrl="/auth/login")

# 401 says "your credential is missing, malformed or expired — try again with a
# new one". WWW-Authenticate is what tells a compliant client to do that.
UNAUTHORIZED = HTTPException(
    status.HTTP_401_UNAUTHORIZED,
    detail="Not authenticated",
    headers={"WWW-Authenticate": "Bearer"},
)


async def current_user(token: Annotated[str, Depends(oauth2)], session=Depends(get_session)):
    try:
        claims = decode_access_token(token)
    except jwt.PyJWTError:
        # One message for every decode failure. Distinguishing "expired" from
        # "bad signature" in the response tells an attacker which half of their
        # forgery worked.
        raise UNAUTHORIZED

    user = await session.get(User, int(claims["sub"]))
    # The database check is what makes deactivation take effect within the token's
    # lifetime rather than at its expiry. It costs one indexed read per request and
    # it is the difference between "disabled" and "disabled in fifteen minutes".
    if user is None or not user.is_active:
        raise UNAUTHORIZED
    user.scopes = claims.get("scopes", [])
    return user


def require_scopes(*required: str):
    async def guard(user=Depends(current_user)):
        if not set(required) <= set(user.scopes):
            # 403, not 401: the credential is valid and refreshing will not help.
            # Returning 401 here makes clients loop on refresh forever.
            raise HTTPException(status.HTTP_403_FORBIDDEN, "Insufficient scope")
        return user
    return guard

# app/auth/routes.py
@router.post("/login")
async def login(form: Annotated[OAuth2PasswordRequestForm, Depends()], session=...):
    user = await get_user_by_email(session, form.username)
    # verify_password runs against a dummy hash when the user is absent, so both
    # branches take the same time. Returning early here would undo that.
    if not verify_password(form.password, user.password_hash if user else None):
        raise HTTPException(status.HTTP_401_UNAUTHORIZED, "Incorrect email or password")
    if needs_rehash(user.password_hash):
        user.password_hash = hash_password(form.password)   # only place the plaintext exists
    return {
        "access_token": create_access_token(str(user.id), user.scopes),
        "token_type": "bearer",
    }

5. Golden-standard rules

Rule Why
Forbidden: decoding without an explicit algorithm allowlist The library otherwise reads the algorithm from the attacker-controlled header. This single argument prevents alg:none, RS256-to-HS256 confusion, and every variant of them.
Forbidden: an unmaintained JWT or hashing library Cryptographic code that nobody is patching is a liability with a countdown. Check maintenance status, not just popularity.
Forbidden: distinguishing "unknown user" from "wrong password", in the response or in the timing Either one turns login into an account-enumeration oracle. Verify against a dummy hash when the user is absent.
Forbidden: the signing key in the repository, or a default value for it A default key is the key everyone has. It must come from configuration and fail startup when missing.
Forbidden: putting anything secret or authoritative in the payload A JWT is signed, not encrypted; anyone can read it. Permissions in the token are a snapshot, and they are stale the moment they are minted.
401 and 403 mean different things and must not be interchanged 401 says retry with a new credential; 403 says the answer will not change. Collapsing them produces clients that refresh in an infinite loop.
Access tokens are short-lived — minutes, not days Nothing can revoke a signed token before it expires. The expiry is the revocation mechanism, so its length is your worst-case exposure.
aud and iss are validated, not just present Otherwise a token minted by another of your services, for another audience, verifies here and is accepted.
The user is loaded and checked on every request A token stays valid after the account is disabled. One indexed read is what makes deactivation immediate.
Password hashing parameters live in the hash It makes raising the work factor a rehash-on-login instead of a password reset for every user.
One module calls the JWT library Verification has one correct shape and several dangerous ones; a second call site is a second chance to omit the allowlist.
Failed logins are rate-limited per account and per address Without it, correct hashing only means the attacker's guesses are slower, not fewer.

6. Data contracts

{
  "sub": "1042",          # the user id as a string — the spec requires a string
  "scopes": ["orders:read"],
  "iat": 1755600000,
  "exp": 1755600900,      # 15 minutes — the worst-case window after a compromise
  "iss": "orders-api",    # who minted it; validated on the way in
  "aud": "orders-web",    # who it is for; validated on the way in
}

Everything in here is readable by anyone holding the token — base64 is not encryption. Include what is needed to route the request and nothing else: no email address, no name, no internal flags. Permissions in the payload are a snapshot at minting time, which is why the account's active state is re-read from the database rather than trusted from the token.

7. Build order

  1. Hashing first, with a test that the same password produces different hashes and that verification succeeds — proving the salt is per-password.
  2. Register and login, returning a token. No protected routes yet.
  3. Decode with the allowlist, and immediately write the attack tests: a token with alg changed to none, and one re-signed with a different algorithm. They must fail before anything depends on this.
  4. current_user, including the active check, with a test that disabling an account makes an already-issued token stop working.
  5. Scopes, with tests asserting 401 for a missing token and 403 for an insufficient one.
  6. Timing equalisation on login, with a test comparing the two paths.
  7. Rate limiting, and rehash-on-login.

Step 3 before step 4 deliberately: the attack tests are the point of this blueprint, and writing them before anything depends on the decoder means the guard is proven rather than assumed.

8. Blocks to pull in

Nothing here is a prerequisite. These are adjacent problems, by name only — resolve them separately if they apply.

  • JWT refresh tokens and session revocation — long sessions and logging out everywhere
  • Typed config and settings — where the signing key and lifetimes are validated at startup
  • FastAPI routing — where the authentication dependency is attached to a whole router
  • Error envelope — the shape these 401 and 403 responses take
  • Redis rate limiting — bounding failed login attempts

9. Metrics

Metric Target
Access token lifetime ≤ 15 minutes
Password verification time 50–500 ms — slow enough to matter, fast enough to serve
Timing difference between unknown-user and wrong-password Below measurement noise
Routes that should be protected and are not 0, asserted by a test over the route table
Failed login attempts allowed per account per minute ≤ 10
Time from disabling an account to its tokens failing < 1 request

10. Failure modes

Symptom Cause Fix
A forged token is accepted; its header says alg: none and it has no signature Decode was called without an algorithm allowlist, so the token chose its own verification Pass algorithms=[...] and add the forged-token test
A forged token is accepted on an RS256 system, signed with HS256 Same missing allowlist; the public key was used as an HMAC secret, and it is public Restrict the allowlist to the asymmetric algorithm
Attackers know which email addresses are registered Login returns a different error, or answers faster, when the user does not exist Verify against a dummy hash and return one message
A client refreshes in a loop and never succeeds An authorisation failure returned 401, so the client kept fetching new tokens for a problem no token solves 403 when the credential is valid but insufficient
A disabled account keeps working for a quarter of an hour The token is trusted without loading the user Load the user and check the active flag on every request
Two long passwords that share a prefix both authenticate bcrypt silently truncates input at 72 bytes Use Argon2id, or enforce a maximum password length
Every token in production becomes invalid after a deploy The signing key had a default value and was generated per process Require it from configuration and fail startup when absent
Tokens issued by a different internal service are accepted aud and iss are present but never validated Validate both explicitly
Authentication fails intermittently across hosts, near expiry Clock skew between machines A small leeway, and time synchronisation
Raising the hashing work factor would require resetting every password The parameters were not stored with the hash Use a hash format that encodes its parameters, and rehash on successful login
A user's revoked permissions still work Scopes were read from the token, which was minted before the change Keep the lifetime short, and read authoritative permissions from the database for anything sensitive

11. Definition of done

  • A token with its header altered to alg: none and its signature stripped is rejected, covered by a test
  • A token re-signed with a different algorithm from the allowlist is rejected, covered by a test
  • The same password hashed twice produces two different hashes, and both verify
  • Logging in with an unknown email and with a wrong password produce identical responses, and their timings are within noise, measured by a test
  • Every protected route returns 401 with no token and with an expired token, asserted by a test that walks the route table rather than a hand-written list
  • A valid token without the required scope returns 403, not 401
  • Disabling a user makes an already-issued token stop working on the next request
  • The signing key comes from configuration, has no default, and the application refuses to start without it
  • A token minted with a different aud or iss is rejected
  • The token payload contains no email, name or other personal data, asserted by decoding one in a test
  • Raising the hashing work factor causes a rehash on next login without invalidating existing passwords, covered by a test
  • Failed logins are rate-limited per account and per source address, covered by a test
  • No module outside tokens.py imports the JWT library, checked in CI
