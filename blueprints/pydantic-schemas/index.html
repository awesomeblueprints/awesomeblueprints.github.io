Pydantic Request and Response Schemas

Pydantic request and response schemas for FastAPI: separating what you accept from what you expose, with validation and safe response models.

low1–2 daysVerified 2026-08-19
APIPython
Read it on GitHub ↗ Back to the catalogue

Separate typed models for what a client may send and what it may see, so the shape of a database row can never become the shape of a public response — and a rejected request comes back naming the field rather than as a wall of generated noise.

Complexity: low · Typical build: 1–2 days · Verified: 2026-08-19 (re-check after ~90 days)

Examples in: Python, with Pydantic and FastAPI. The architecture is language-agnostic: sections 5, 10 and 11 hold wherever you build this. Section 4 is illustrative — if your project is in another language, your agent translates the idioms rather than importing them, and nothing is lost. The equivalents are Zod schemas with .parse() in TypeScript, Ecto.Changeset with separate cast sets in Elixir, struct tags plus a validator in Go, and ActiveModel::Serializer with strong parameters in Rails.

Use when: an HTTP API accepts JSON bodies or returns objects built from database rows, and you want the accepted shape and the exposed shape to be two decisions rather than one accident.

Not for: an internal function boundary inside one process — types and a dataclass are enough there, and a validation layer between your own modules is cost with no attacker on the other side. Also not for the configuration your app reads at startup: that is validated once at boot, not per request, and the two get conflated constantly.

⚙️ INSTRUCTIONS FOR THE AI — READ BEFORE WRITING ANY CODE

Do not start coding.

Step 1 — Refresh. Verify the installed Pydantic major version. This blueprint is written for v2: model_config = ConfigDict(...) rather than an inner class Config, model_validate rather than parse_obj, field_validator and model_validator rather than validator and root_validator, and from_attributes rather than orm_mode. Pydantic v3 was announced as a cleanup release that removes the v1 compatibility shims — check whether it has shipped and whether anything used here was on the removal list. Verify the FastAPI version and whether separate_input_output_schemas still defaults to true, because it changes the generated client SDK. Report what you verified and what turned out wrong.

Step 2 — Read the project, then audit what already exists. Find every route handler and record three things per route: whether it declares a response model, what its return type annotation is, and whether the object it returns is a database model. Find any existing schema module and note which models are used on both the request and the response side — those are the leak candidates. Find where validation errors are currently rendered. Then audit §11 item by item, each marked already true, partly true or absent, with the file that decides it, reported before anything is proposed.

Assume the project is right until it demonstrably is not; code satisfying an item stays even where its shape differs from §4; replacing something that works needs a one-line reason; never delete a working path to make room for the blueprint's version. The same holds for language — §4 is illustrative, its idioms get translated into the project's language, and §11 is what has to become true rather than the syntax.

Step 3 — Write a plan for the gap only, and get it approved, including a ## Proposed stack section naming the validation library and the version verified in Step 1, with a one-line reason. Do not ask open framework questions — propose, and ask for confirmation once. Say what you are adding, what you are leaving alone, and what you propose to change, and touch nothing else. If schemas already exist, the plan is to split the ones used on both sides, not to rewrite the layer.

Step 4 — Build in the order in §7. Step 5 — §11 is the definition of done.

1. Why one model per entity leaks

The obvious version is one Order model, used for the request body, the response and the database row. It is less code and it is wrong in four independent ways.

One model per entity A model per direction
A column added to the table appears in the public response the moment it is added to the model — nobody reviews a migration for disclosure Adding a column changes nothing a client can see until someone edits the read model
The client can send id, created_at, total_cents — anything the model has a field for The create model has only the fields a client is allowed to decide
Required on write and always-present on read are the same declaration, so one of them is a lie Each direction states its own truth
The generated OpenAPI schema describes a shape that is neither the request nor the response Two schemas that each match what actually crosses the wire

The second row is the expensive one, and it does not look like a security bug. It looks like a field that happens to be settable. Assigning total_cents in a request body is not an exploit against a parser — it is the API doing exactly what it was told, because nobody wrote down that the total is computed rather than supplied.

FastAPI's own documentation makes the disclosure case explicitly, with a Danger callout, and it is worth stating why the framework cannot simply solve it: the response model filters by validating into the declared shape, so the protection is only as good as the declared shape. Point it at the database model and there is nothing left to filter.

The rule the diagram encodes: there is no arrow from the store to the client. Every path out passes through a read model, and that is the only reason adding a column is not a disclosure decision.

3. Project structure

app/
├── schemas/
│   ├── order.py        OrderCreate, OrderUpdate, OrderRead — one file per resource
│   └── common.py       shared base classes and reusable field types
├── models/
│   └── order.py        the database model — imported by schemas/, never the reverse
├── routers/
│   └── orders.py       declares a response model on every route
└── errors.py           the validation error handler

One rule: schemas/ may import from models/, and models/ may never import from schemas/. The direction is what keeps the database free to change. The moment a model imports a schema, a column rename becomes an API change and the two layers are one layer with extra files.

4. Reference implementation

# app/schemas/order.py
from datetime import datetime
from decimal import Decimal
from typing import Annotated, Literal
from pydantic import BaseModel, ConfigDict, Field, field_serializer, model_validator

OrderStatus = Literal["pending", "paid", "shipped", "cancelled"]


class OrderCreate(BaseModel):
    # extra="forbid" turns a misspelled or over-eager field into a 422 instead of a
    # silent no-op. A client sending "total_cents" deserves to be told it is ignored;
    # the default behaviour tells them nothing and they ship believing it worked.
    model_config = ConfigDict(extra="forbid")

    product_id: int
    quantity: Annotated[int, Field(gt=0, le=1000)]
    note: Annotated[str, Field(max_length=500)] | None = None
    # No id, no status, no total, no created_at. Not because they are secret, but
    # because the client does not get to decide them.


class OrderUpdate(BaseModel):
    model_config = ConfigDict(extra="forbid")

    quantity: Annotated[int, Field(gt=0, le=1000)] | None = None
    note: Annotated[str, Field(max_length=500)] | None = None

    def changes(self) -> dict:
        # The whole point of PATCH: "field absent" and "field set to null" are
        # different instructions. `None` alone cannot tell them apart — model_fields_set
        # can, because it records what the client actually sent. Using exclude_unset
        # here is equivalent; using `if value is not None` is the bug.
        return {k: getattr(self, k) for k in self.model_fields_set}

    @model_validator(mode="after")
    def not_empty(self) -> "OrderUpdate":
        if not self.model_fields_set:
            raise ValueError("no fields to update")
        return self


class OrderRead(BaseModel):
    # from_attributes lets this be built straight from an ORM row object rather than
    # a dict. It reads attributes off whatever it is given — so it cannot pick up a
    # column this class does not declare.
    model_config = ConfigDict(from_attributes=True)

    id: int
    product_id: int
    quantity: int
    status: OrderStatus
    total: Decimal
    created_at: datetime

    @field_serializer("total")
    def money_as_string(self, value: Decimal) -> str:
        # Decimal to float loses cents at the edges and JSON has no decimal type.
        # A string is the only representation every client parses without surprise.
        return f"{value:.2f}"

# app/routers/orders.py
from fastapi import APIRouter, HTTPException, status
from app.schemas.order import OrderCreate, OrderRead, OrderUpdate

router = APIRouter(prefix="/orders", tags=["orders"])


# Both the decorator argument and the return annotation are declared. FastAPI will
# infer the response model from the annotation if the argument is omitted — so
# annotating `-> Order` with the database model quietly reinstates the leak, and
# `-> Any` disables filtering altogether. Say it twice and neither can drift.
@router.post("", response_model=OrderRead, status_code=status.HTTP_201_CREATED)
async def create_order(payload: OrderCreate) -> OrderRead:
    row = await service.create_order(payload)      # a typed object goes in
    return OrderRead.model_validate(row)           # a declared shape comes out


@router.patch("/{order_id}", response_model=OrderRead)
async def update_order(order_id: int, payload: OrderUpdate) -> OrderRead:
    row = await service.update_order(order_id, payload.changes())
    if row is None:
        raise HTTPException(status.HTTP_404_NOT_FOUND, "order not found")
    return OrderRead.model_validate(row)

# app/errors.py
from fastapi import Request, status
from fastapi.exceptions import RequestValidationError
from fastapi.responses import JSONResponse


async def validation_error_handler(request: Request, exc: RequestValidationError):
    # The default 422 body nests the location as an array and includes the raw input,
    # which echoes whatever the client sent back at them — including, on a login route,
    # the password they just posted. Flatten it and drop the input.
    return JSONResponse(
        status_code=status.HTTP_422_UNPROCESSABLE_ENTITY,
        content={
            "error": "validation_failed",
            "fields": [
                {
                    "field": ".".join(str(p) for p in err["loc"][1:]) or "body",
                    "message": err["msg"],
                }
                for err in exc.errors()
            ],
        },
    )

5. Golden-standard rules

Rule Why
Forbidden: using one model for both a request body and a response It is the entire failure this blueprint exists for. Every column added later becomes public without anyone deciding it should be.
Forbidden: returning a database row or ORM object from a handler Filtering only happens if the declared response shape is narrower than the row. Return the read model explicitly.
Forbidden: annotating a handler -> Any or -> <database model> FastAPI infers the response model from the return annotation. Both of these silently disable the protection while looking deliberate.
Declare the response model in the decorator and the return annotation Two statements of the same fact that the type checker keeps in agreement. One alone drifts on the next refactor.
extra="forbid" on every request model A field the client thought mattered and the server ignored is a bug report six weeks later. Reject it now, at the boundary, where the message can name it.
A create model contains only fields the client decides Ids, timestamps, totals, statuses and ownership are computed. A field present on the model is a field a client may set, whatever the documentation says.
PATCH uses what was sent, not what is non-null None cannot distinguish "leave it alone" from "clear it". model_fields_set or exclude_unset can. Treating them as the same makes it impossible to clear a nullable field.
Money is a decimal in, a string out Binary floats cannot represent cents exactly and JSON has no decimal type. Serialising through float loses money at the boundaries and nothing raises.
Validation errors never echo the submitted value The default handler includes the input. On an authentication route that is the password, on a payments route the card details — travelling to whatever collects your logs.
Enumerations are a closed type, not str A status field typed str accepts "shiped" and stores it. The set is known; write it down.
One schema file per resource, importing models, never imported by them The import direction is what lets the table change without changing the API.

6. Data contracts

class OrderCreate(BaseModel):
    quantity: Annotated[int, Field(gt=0, le=1000)]
    # not int — 0 and -5 are valid ints and neither is a valid order

class OrderRead(BaseModel):
    status: Literal["pending", "paid", "shipped", "cancelled"]
    # not str — the set is closed, and a typo must fail rather than persist
    total: Decimal
    # not float — cents do not survive binary floating point

Pydantic coerces by default: the string "123" arriving in an int field becomes 123, and "2000-01-01" becomes a date. That is usually what you want from a query string, where everything is a string anyway. It is usually not what you want from a JSON body, where the client had a real integer available and sent a string instead — which means their serialiser is doing something you should know about. Turn on strict mode per field where the distinction matters rather than globally, because global strictness breaks path and query parameters first.

7. Build order

  1. Split the most exposed resource into three models — create, update, read — and prove the split with a test asserting a known internal field is absent from the serialised response. One resource, end to end, before touching the rest.
  2. Declare the response model on every route in the decorator and the return annotation, and add the check from §11 that fails if a route has neither.
  3. Add extra="forbid" to request models and confirm an unknown field is a 422 rather than silence.
  4. Fix PATCH to apply only what was sent, with a test that clears a nullable field to null and another that omits it and leaves it unchanged.
  5. Replace the validation error handler and assert the submitted value is absent from the response body.
  6. Tighten the types — closed enumerations, bounded numbers, decimals for money, serialisers where the wire format differs from the internal one.
  7. Roll the split across the remaining resources.

Step 1 first because the leak is the risk. Everything after it is refinement of a boundary that already exists, and refinements are cheap to postpone.

8. Blocks to pull in

Nothing here is a prerequisite. These are adjacent problems, by name only — resolve them separately if they apply.

  • Input validation at the API boundary — the general principle, for inputs that are not HTTP bodies
  • Error envelope — one response shape for every failure, not only validation
  • Typed config and settings — validation at startup rather than per request
  • FastAPI routing — where these schemas get attached to versioned routes
  • SQLAlchemy ORM layer — the models these read schemas are built from

10. Failure modes

Symptom Cause Fix
A field nobody meant to publish appears in an API response after a migration One model shared between the table and the response; the column joined the public shape when it joined the model Split into a read model that lists exposed fields explicitly
A client sets a field that should be computed — a price, a status, an owner — and the server accepts it The create model has a field for it. Documentation saying it is read-only is not enforcement Remove the field from the create model; assign it in the service
The response model is declared and a private field still comes through The handler is annotated -> Any or -> <database model>, and the annotation wins Annotate the read model, and add the §11 check so it cannot regress
Clearing an optional field to null is impossible through PATCH The handler applies if value is not None, which cannot see the difference between absent and null Apply model_fields_set or model_dump(exclude_unset=True)
A PATCH with an empty body succeeds and updates nothing, returning 200 No model validator rejecting an update with no fields set Reject it — a no-op that reports success hides a client bug for months
A generated client SDK disagrees with the server about which response fields are optional Input and output schemas are generated separately, and a defaulted field is optional on input but always present on output — sharing one model makes the two contradict Separate the models; if SDK stability forces one schema, set the framework flag deliberately and write down why
Money is off by a cent, occasionally, on large orders Decimal serialised through float on the way out Serialise money as a string, and keep it decimal everywhere inside
A password or card number appears in the log aggregator, attached to a 422 The default validation error body echoes the submitted input Replace the handler and drop the input field
A status column contains a typo like "shiped" for one row The field is typed str, so the value validated Close the type with Literal or an enum

11. Definition of done

  • No model class is used both as a request body type and as a response model, verified by a test or a static check that names any that are
  • Every route declares a response model in the decorator and a matching return annotation; a route with neither fails a test that walks the app's routes
  • For each resource, a test asserts that a named internal field present on the database model is absent from the serialised response
  • Posting an unknown field to a create endpoint returns 422 and names the field
  • Posting a field the client must not decide — an id, a total, a status — returns 422 rather than being accepted or silently dropped
  • A PATCH that omits a nullable field leaves it unchanged, and a PATCH that sends it as null clears it; both covered by tests
  • A PATCH with an empty body is rejected rather than returning success
  • A validation error response contains the field path and the rule, and does not contain the submitted value, asserted by a test that posts a recognisable secret
  • Every enumerated field is a closed type, and a value outside the set is rejected at the boundary
  • Monetary values are decimal internally and strings on the wire, with a test covering a value that is not exactly representable as a float
  • models/ contains no import from schemas/, checked in CI
