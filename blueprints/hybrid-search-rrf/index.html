Hybrid Search: Keyword + Vector with RRF

Hybrid search combining keyword and vector retrieval with Reciprocal Rank Fusion: two branches, one ranked list, measurable recall gains.

medium3–5 daysVerified 2026-08-19
Vector searchRetrieval
Read it on GitHub ↗ Back to the catalogue

Running lexical and dense retrieval side by side and merging the two ranked lists by rank position rather than by score — the cheapest large recall gain available to a retrieval system.

Complexity: medium · Typical build: 3–5 days · Verified: 2026-08-19 (re-check after ~90 days)

Examples in: Python and SQL. Only §4 and §6 are language-specific — the rules, failure modes and definition of done hold anywhere, and your agent translates the code.

Use when: queries contain identifiers, error codes, SKUs, function names, proper nouns or exact phrases; or recall is short of target with embeddings alone.

Not for: a corpus of purely conceptual prose where you have measured that lexical search adds nothing. That case is rarer than teams assume — measure the two branches separately before deciding you do not need one.

1. Two retrieval methods with mirror-image blind spots

Dense embeddings encode meaning and are systematically bad at rare literal tokens. ERR_4021, pnpm-lock.yaml and Regulation 2016/679 are close to noise in embedding space — the model never saw them often enough to place them anywhere meaningful — so a query for ERR_4021 returns passages about errors in general.

Lexical scoring has the mirror weakness. "How do I stop the app crashing on start?" shares no terms at all with "Resolving boot-time segmentation faults".

Query Lexical Dense
ERR_4021 Exactly right Passages about errors
getUserById Exactly right Passages about users
"app crashes on start" Misses the paraphrase Exactly right
"cancel my subscription" Partial Exactly right
"Regulation 2016/679" Exactly right Something about data protection, maybe

Neither is fixable by tuning the other, and real query logs contain both kinds. So run both.

Why fuse by rank rather than by score. Lexical scores are unbounded and corpus-dependent; cosine similarities live in a narrow band. Making them comparable requires a calibration that drifts as the corpus and the query mix change, so a weighted blend that was tuned in March is quietly wrong by June. Rank position is scale-free. Reciprocal rank fusion needs no calibration at all, which is why a fifteen-line function beats a tuned blend in practice.

The rule this diagram encodes: the metadata filter is applied identically to both branches, before fusion. A filter on one branch only is a correctness bug — in a multi-tenant system it is a data-leak bug — and fusing before filtering leaves you with fewer results than you asked for.

3. Project structure

retrieval/
├── lexical.py     # analyzer config lives here, and it is corpus-specific
├── dense.py       # embedding of the query; no stemming, ever
├── fuse.py        # ~15 lines. Ranks in, fused list out. No score normalisation.
├── search.py      # both branches concurrently, one shared filter
└── evals/
    └── slices/    # one slice per query type; identifiers get their own

The rule that keeps this maintainable: per-branch recall is measured separately, and the per-branch ranks are kept on every fused result. When hybrid search underperforms, the answer is almost always visible in those two numbers, and invisible without them.

4. Reference implementation

Fusion itself. Scores are discarded; only positions matter:

def rrf_fuse(lists: dict[str, list[SearchHit]], cfg: FusionConfig) -> list[FusedHit]:
    scores, ranks = defaultdict(float), defaultdict(dict)
    for source, hits in lists.items():
        w = cfg.weights.get(source, 1.0)
        for hit in hits:                     # sorted best-first; rank is 1-based
            scores[hit.chunk_id] += w / (cfg.k + hit.rank)
            ranks[hit.chunk_id][source] = hit.rank
    fused = [FusedHit(chunk_id=cid, rrf_score=s, ranks=ranks[cid])
             for cid, s in scores.items()]
    fused.sort(key=lambda h: h.rrf_score, reverse=True)
    return fused[:cfg.n_output]

A document found by only one branch still scores — just lower. That is the behaviour you want: a rare identifier found only lexically should surface, and usually near the top, because it will be at rank 1 there.

Both branches, concurrently, with one filter:

async def hybrid_search(query, tenant_id, cfg, lexical, vectors, embedder):
    flt = {"tenant_id": tenant_id}                 # built once, passed to both
    lex_hits, dense_hits = await asyncio.gather(
        lexical.search(query, top_k=cfg.n_candidates, filter=flt),
        vectors.search(embedder.embed_query(query), top_k=cfg.n_candidates, filter=flt))
    return rrf_fuse({"lexical": _ranked(lex_hits, "lexical"),
                     "dense": _ranked(dense_hits, "dense")}, cfg)

One store, if you already run Postgres — no second system to operate, and the fusion is a join:

WITH lex AS (
  SELECT id, ROW_NUMBER() OVER (
           ORDER BY ts_rank_cd(tsv, plainto_tsquery('english', $1)) DESC) AS rank
  FROM chunks
  WHERE tenant_id = $2 AND tsv @@ plainto_tsquery('english', $1)
  LIMIT 50
),
dense AS (
  SELECT id, ROW_NUMBER() OVER (ORDER BY embedding <=> $3) AS rank
  FROM chunks
  WHERE tenant_id = $2
  ORDER BY embedding <=> $3
  LIMIT 50
)
SELECT COALESCE(l.id, d.id) AS id,
       COALESCE(1.0 / (60 + l.rank), 0) + COALESCE(1.0 / (60 + d.rank), 0) AS rrf
FROM lex l FULL OUTER JOIN dense d USING (id)
ORDER BY rrf DESC
LIMIT 20;

The analyzer is where identifier queries are won or lost. A default analyzer splits ERR_4021 into err and 4021, and the exact-match property you added the lexical branch for is gone. Configure it against your corpus, and keep a keyword sub-field for identifiers.

5. Golden-standard rules

Rule Why
Fuse by rank, never by normalised score Score calibration drifts with corpus and query mix; rank position does not
The fusion constant is 60 unless measurement says otherwise It is the published default and it works; tuning it is almost never where the gain is
Both branches receive an identical metadata filter A filter on one branch is a correctness bug, and in multi-tenant systems a leak
Filter before fusing, never after Fusing then filtering returns fewer results than requested
Both branches run concurrently They are independent; running them serially doubles latency for nothing
Candidate depth is well above the final k — about 50 for a k of 5 to 10 Fusion needs headroom; retrieving k per branch defeats it
Deduplication is keyed strictly on chunk id Anything else lets the same passage occupy several slots
The lexical analyzer preserves identifiers Splitting ERR_4021 removes the exact property the branch exists for
The analyzer matches the corpus: never stem a code corpus Stemming getUserById is actively harmful
The dense query is never stemmed or analyzed The embedding model expects natural text
Per-branch recall is measured separately, not only fused recall Otherwise a broken branch hides behind a healthy one
Weights are only changed after measuring per-branch recall on your own set You cannot tune what you have not measured
A weak branch is weighted down, not disabled It still contributes the cases the other one systematically misses
Per-branch ranks are retained on every result It is the entire debugging story in one field
The evaluation set has an identifier slice built from real query logs The whole point is a query type the aggregate metric hides

6. Data contracts

class SearchHit(BaseModel):
    chunk_id: str
    score: float          # branch-native. Debugging only - fusion never reads it.
    rank: int = Field(ge=1)
    source: str           # "lexical" | "dense"

class FusionConfig(BaseModel):
    k: int = 60           # lower lets top ranks dominate; higher flattens
    weights: dict[str, float] = {"lexical": 1.0, "dense": 1.0}
    n_candidates: int = 50    # per branch, before fusion
    n_output: int = 20        # after fusion; hand to the reranker

class FusedHit(BaseModel):
    chunk_id: str
    rrf_score: float
    ranks: dict[str, int]     # {"lexical": 3, "dense": 17} - keep this
Knob Default Change it when
Fusion constant k 60 Rarely. Lower to 20 to let the top of each list dominate
Candidates per branch 50 Raise to 100 if recall at 50 is under 0.9; it costs latency
Branch weights 1.0 and 1.0 Only after per-branch recall is measured on your own eval set
Lexical length normalisation Default Lower it when document lengths vary wildly
Stemming On for prose, off for code Match the corpus, not the default

7. Build order

  1. Measure the baseline: dense-only recall, and specifically on an identifier slice taken from real query logs. Without both numbers there is nothing to compare against.
  2. The lexical index, with an analyzer configured for the corpus and a keyword sub-field for identifiers.
  3. Verify the analyzer directly — query the lexical index for ERR_4021 and confirm it is not being split. This is the step people skip and then spend a week on.
  4. Both branches concurrently, sharing one filter object.
  5. Rank fusion at k=60, equal weights, deduplicated by chunk id.
  6. Measure again: fused recall, per-branch recall, and the identifier slice.
  7. A reranker over the fused head, once recall is good and precision is the remaining problem.
  8. Only then consider weights, and only where per-branch measurement supports the change.

9. Metrics

Metric Target
Fused recall at 50 ≥ 0.95
Per-branch recall at 50 Each ≥ 0.60; below 0.40 that branch is broken, not weak
Fusion lift over the better single branch ≥ +5 points; +1 or less means something is misconfigured
Overlap between the two lists 20–50%; above 80% the branches are redundant and one is wasted
Latency at p95 for both branches plus fusion < 250 ms
Recall on the identifier slice ≥ 0.95. This is the number the whole exercise is for

10. Failure modes

Symptom Cause Fix
Identifiers still not found The analyzer splits ERR_4021 into two terms Preserve alphanumerics; add a keyword sub-field
Hybrid is worse than dense alone The lexical branch returns noise that outranks good dense hits Fix the analyzer; weight it down only if its recall is genuinely low
Duplicates fill the top of the list Deduplication keyed on the object, not the chunk id Key on chunk id
One tenant sees another's documents The filter was applied to one branch only Build the filter once and pass it to both; test with two tenants
Latency doubled The branches run serially Run them concurrently; they are independent
Fewer results than requested Filtering happens after fusion Filter inside each branch, before fusing
It helps offline but not in production The eval queries are not like real ones Build the set from production query logs
Recall is poor in one language A single default analyzer for a multilingual corpus Per-language analyzer, or per-language index
Fusion barely moves the number Candidate depth equals the final k Retrieve about 50 per branch, fuse, then cut
Nobody can explain a bad result The per-branch ranks were discarded Keep them on the fused hit

11. Definition of done

  • Both branches receive an identical metadata pre-filter, applied before fusion.
  • Both branches run concurrently.
  • Fusion is over ranks with k=60, never over normalised scores.
  • Deduplication is keyed strictly on chunk id.
  • The lexical analyzer preserves identifiers, verified by querying the index directly.
  • The analyzer matches the corpus language, and code corpora are not stemmed.
  • The dense query is passed unstemmed and unanalyzed.
  • Candidate depth per branch is well above the final k.
  • Per-branch recall is measured separately, not only the fused number.
  • The eval set contains an identifier slice built from real query logs.
  • Per-branch ranks are retained on every fused result for debugging.
  • Branch weights, if changed at all, were changed on the basis of measured per-branch recall.
