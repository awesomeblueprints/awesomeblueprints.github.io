Cursor Pagination

Cursor pagination for REST APIs: stable ordering, opaque cursors, and paging that does not skip or repeat rows while the list changes.

Paginating a list that is being written to while it is read. OFFSET passes review, passes the test fixture, and then quietly duplicates and skips rows in production — this is the alternative that does not.

Complexity: low · Typical build: 1–2 days · Verified: 2026-08-18 (re-check after ~90 days)

Examples in: Postgres and TypeScript. Only §4 is language-specific — the rules, failure modes and definition of done hold anywhere, and your agent translates the code.

Use when: paging through a list that changes while a user reads it — feeds, inboxes, activity logs, search results, any admin table — or through a large result set from a script or an export.

Not for: a short fixed list you can return whole, or a UI that genuinely needs numbered pages and a total count and can accept a snapshot that drifts.

1. Why OFFSET is wrong on a live list

Take a feed sorted newest first, 20 per page. A reader loads page 1. While they read, three new rows arrive. They ask for page 2 — OFFSET 20.

Those three new rows now occupy positions 1 to 3. Everything shifted down by three. Rows 18, 19 and 20 — already shown on page 1 — are now at positions 21, 22, 23, and get served again. Meanwhile nothing was skipped in this direction, but delete three rows instead and the same arithmetic silently skips three the reader never sees.

LIMIT / OFFSET Keyset (cursor)
Rows inserted during paging Duplicates Unaffected
Rows deleted during paging Skips, silently Unaffected
Cost of page N Database walks and discards N×size rows Indexed seek, constant
Page 5000 Slow enough to time out Same speed as page 2
Jump to an arbitrary page Supported Not supported — by design
Total count Available, and expensive Not included
How you find out it is broken You do not —

The last row is why this is worth a blueprint. Nothing errors. The reader sees a post twice, assumes they scrolled wrong, and moves on.

3. Project structure

src/
├── pagination/
│   ├── cursor.ts         # encode / decode. One implementation, all endpoints.
│   ├── page.ts           # the response type: items + nextCursor
│   └── keyset.ts         # builds the WHERE clause from a decoded cursor
├── repositories/         # each list query takes a decoded cursor, never a page number
└── routes/               # never build a cursor by hand

The rule that keeps this maintainable: one encoder for the whole codebase. The second one shows up when someone needs "just a small change", and from then on a cursor from one endpoint silently fails to decode in another.

4. Reference implementation

The index comes first. Without it, keyset pagination is a table scan with extra steps — the index must match the sort exactly, including direction:

-- Sort key first, tie-breaker second, in the same order the query uses.
create index posts_feed_idx on posts (created_at desc, id desc);

The query. Row-value comparison expresses "everything after this row" in one predicate the planner can push straight into the index:

select id, created_at, title
  from posts
 where author_id = $1
   and (created_at, id) < ($2, $3)   -- strictly after the last row seen
 order by created_at desc, id desc
 limit $4;                            -- pageSize + 1, see below

The tie-breaker is not optional. created_at alone is not unique — two rows written in the same millisecond make the order non-deterministic, and the cursor lands in the middle of the tie, dropping one of them at random. Any column that is unique and monotonic with the sort works; the primary key is the usual choice.

Fetch one more than you need. It answers "is there another page" without a second query or a count:

export async function listPosts(authorId: string, cursor: Cursor | null, size: number) {
  const limit = Math.min(size, MAX_PAGE_SIZE);
  const rows = await repo.page(authorId, cursor, limit + 1);

  const hasMore = rows.length > limit;
  const items = hasMore ? rows.slice(0, limit) : rows;    // discard the probe row

  return {
    items,
    // No more rows means no cursor. A cursor that returns an empty page is a
    // client bug waiting to happen - it will poll forever.
    nextCursor: hasMore ? encodeCursor(items[items.length - 1]) : null,
  };
}

The cursor is opaque, and should be unforgeable if it can reach a user:

// Base64url of the sort tuple, signed. Opaque so clients cannot construct one
// and pin themselves to a shape you later need to change; signed so a crafted
// cursor cannot be used to probe rows the caller may not read.
export function encodeCursor(row: { createdAt: Date; id: string }): string {
  const payload = `${row.createdAt.toISOString()}|${row.id}`;
  return b64url(`${payload}.${hmac(payload)}`);
}

5. Golden-standard rules

Rule Why
The sort key always carries a unique tie-breaker A non-unique sort makes the order non-deterministic and the cursor lands mid-tie
An index exists matching the exact sort, direction included Otherwise this is a scan, and slower than the OFFSET it replaced
The cursor encodes the last row's key, never a row number A number is a position, and positions move
Cursors are opaque to the client A readable cursor becomes a contract you cannot change
Cursors that reach a user are signed An unsigned cursor is an injectable query fragment
Page size is clamped server-side ?limit=1000000 is otherwise a denial of service
Fetch size + 1 to detect the next page A COUNT(*) on every page costs more than the page
The final page returns a null cursor A cursor that yields nothing makes clients poll forever
The sort column and the cursor's column are the same one "Sort by title, cursor by id" quietly returns a random subset
Changing the sort invalidates outstanding cursors Detect the mismatch and restart rather than serving nonsense
No total count unless someone paid for it Exact counts on large tables are slow; offer an estimate instead
The same code paginates internal jobs and exports Batch scripts hit OFFSET pathology hardest, at page 5000

6. Data contracts

/** Opaque to the client; a signed tuple internally. */
export type Cursor = string & { readonly __brand: 'Cursor' };

export type Page<T> = {
  items: T[];
  /** null means this was the last page. Never an empty-but-present cursor. */
  nextCursor: Cursor | null;
};

/** Decoded form. `sort` is carried so a changed sort can be detected. */
export type DecodedCursor = { sort: string; key: [string, string] };

export const MAX_PAGE_SIZE = 100;
export const DEFAULT_PAGE_SIZE = 20;

7. Build order

  1. The composite index, as a migration, before any query change.
  2. cursor.ts — encode and decode, with a round-trip test.
  3. One endpoint converted, returning items and nextCursor.
  4. The drift test, which is the whole point: read page 1, insert five rows, read page 2, assert no item appears twice and none is missing.
  5. Signing, once the shape has settled.
  6. Page size clamping, with a test at the boundary and past it.
  7. The remaining endpoints, one at a time.
  8. Batch and export paths — these gain the most and are usually forgotten.
  9. Sort-change detection, returning a "restart pagination" error.

10. Failure modes

Symptom Cause Fix
A user reports seeing the same post twice OFFSET with concurrent inserts Keyset pagination
Items missing from a feed nobody deleted OFFSET with concurrent deletes Same
Page 500 times out, page 1 is instant OFFSET scanning and discarding Keyset — cost stops depending on depth
Rows occasionally dropped at page edges Non-unique sort key, no tie-breaker Add the primary key to sort and cursor
Pagination slower after the change Index missing or direction mismatched Index must match the ORDER BY exactly
Clients loop forever on the last page Final page returned a non-null cursor Return null when there is no next page
A crafted cursor returned another tenant's rows Cursor unsigned and trusted Sign it; re-apply the tenant filter regardless
Results went wrong after a sort change Old cursors decoded against a new sort Encode the sort; detect mismatch and restart
Memory blew up on one request Unclamped page size Clamp server-side

11. Definition of done

  • Every paginated query has an index matching its exact sort, direction included.
  • Every sort key includes a unique tie-breaker.
  • A test reads page 1, writes rows, reads page 2, and asserts no duplicates and no gaps.
  • The same test passes for concurrent deletes.
  • Cursors are opaque, and signed wherever a client can see them.
  • Page size is clamped server-side and covered by a test past the limit.
  • The last page returns a null cursor.
  • EXPLAIN shows an index scan examining about one page of rows, not a sequential scan.
  • Latency at a deep page is within 20% of the first page.
  • No endpoint uses OFFSET except where a reason is written down.
