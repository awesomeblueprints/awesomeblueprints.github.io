pgvector: Vector Search in Postgres

pgvector in PostgreSQL: index choice, HNSW tuning, filtered search and the post-filtering trap, without adding a second datastore to operate.

medium2–4 daysVerified 2026-08-19
PostgreSQLVector search
Read it on GitHub ↗ Back to the catalogue

Vector search in the database you already run: the index chosen and sized for the data, filters that do not quietly destroy recall, and a way to tell whether the search is still finding what it should as the table grows.

Complexity: medium · Typical build: 2–4 days · Verified: 2026-08-19 (re-check after ~90 days)

Examples in: SQL and Python, with Postgres and pgvector. The architecture is language-agnostic: sections 5, 10 and 11 hold wherever you build this. Section 4 is illustrative — if your project is in another language, your agent translates the idioms rather than importing them, and nothing is lost. The index-sizing and filtered-recall concerns are properties of approximate nearest-neighbour search and apply to any store; the specific behaviour described here is pgvector's.

Use when: the data is already in Postgres, the corpus is large enough that a full scan is too slow, and you would rather have transactions, backups and joins than a second datastore to operate.

Not for: a corpus small enough to scan exhaustively — a few thousand vectors compare faster than an approximate index can be tuned, and an exact scan has perfect recall for free. Also not for search where the query is a product code, an error identifier or an exact phrase: embeddings are near-blind to those, and no amount of index tuning fixes it.

1. The failure that returns ten rows and no error

An approximate index trades exactness for speed. That trade is invisible: the query returns the number of rows you asked for, quickly, and nothing indicates that better matches existed and were missed.

Adding the index and moving on Sizing it and measuring it
Parameters are left at their defaults, which are tuned for nothing in particular Parameters follow from the row count and are recorded with the arithmetic
A WHERE clause is added and recall silently collapses Filtering is designed for, and its cost is measured
Quality is judged by reading a few results Recall is measured against exact search on a fixed question set
Growth is noticed when someone complains Recall is re-measured as the table grows

The second row is the one that catches people who did everything else right. pgvector applies the filter after the index scan, not before. The graph search returns a fixed number of candidates — forty by default — ranked purely by similarity, and only then is the WHERE clause applied. Ask for ten results with a tenant filter and you may get three: the other thirty-seven candidates belonged to other tenants. The rows you wanted exist, are indexed, and were never considered.

This is the single most important thing to understand about this extension, because it is not a bug and it does not announce itself. There are three ways to live with it, and they suit different situations: raise the candidate count so more survive filtering, enable iterative scanning so the search re-runs until it has enough, or build a partial index per known filter value so the filter is implicit in which index is used. The last is the only one that is genuinely pre-filtering, and it only works when the filter values are known in advance.

One rule: the embedding model is a column, not an assumption. Every row records which model produced its vector. Two models' output in one column is a search that returns confident nonsense, no error is raised, and the only remedy is re-embedding everything — which you cannot even scope without that column.

4. Reference implementation

-- The table. The dimension is fixed at column creation and changing it later
-- means rewriting the table, so it is worth being sure about the model first.
CREATE TABLE document_chunks (
    id            BIGSERIAL PRIMARY KEY,
    tenant_id     BIGINT      NOT NULL,
    document_id   BIGINT      NOT NULL,
    content       TEXT        NOT NULL,
    embedding     vector(1536) NOT NULL,
    -- Which model produced this vector. Without it, a model upgrade silently
    -- mixes two vector spaces in one column and every search is subtly wrong
    -- with nothing to indicate it.
    embedding_model TEXT      NOT NULL,
    created_at    TIMESTAMPTZ NOT NULL DEFAULT now()
);

-- A payload index on anything filtered alongside the vector. Without it the
-- filter is evaluated by reading rows the vector index already returned, which
-- is the slow half of an otherwise fast query.
CREATE INDEX ix_chunks_tenant ON document_chunks (tenant_id);

-- The vector index, in its own migration and built concurrently: a plain build
-- holds a lock for its whole duration, and on a large table that is measured in
-- minutes of blocked writes.
--
-- m and ef_construction are build-time and cannot be changed without rebuilding.
-- Higher values mean better recall and a slower, larger build. The defaults are
-- reasonable; raising m helps most when the data has many near-duplicates.
--
-- Raise maintenance_work_mem first: the build is dramatically faster when the
-- graph fits in memory, and Postgres emits a notice when it does not.
SET maintenance_work_mem = '2GB';
CREATE INDEX CONCURRENTLY ix_chunks_embedding
    ON document_chunks USING hnsw (embedding vector_cosine_ops)
    WITH (m = 16, ef_construction = 64);

-- The operator class must match the distance operator used at query time.
-- Cosine here means queries use <=>; using <-> against this index falls back to
-- a sequential scan, which is fast on a laptop and catastrophic in production.

# app/search/query.py
SEARCH = text("""
    SELECT id, content, 1 - (embedding <=> :q) AS similarity
      FROM document_chunks
     WHERE tenant_id = :tenant
       AND embedding_model = :model
     ORDER BY embedding <=> :q
     LIMIT :k
""")


async def search(session, query_vector, tenant_id: int, k: int = 10):
    # ef_search is per session, not per index, and it is the main quality dial at
    # query time. The default candidate list is small; with a filter applied
    # afterwards, most of those candidates can be discarded and the query returns
    # fewer rows than asked for — with no error and no warning.
    await session.execute(text("SET LOCAL hnsw.ef_search = :ef"), {"ef": max(40, k * 8)})

    # Iterative scan re-runs the index search when post-filtering leaves too few
    # rows, instead of returning a short list. It costs latency on selective
    # filters and it is off by default. Turn it on deliberately, and measure —
    # on an unselective filter it changes nothing and costs nothing.
    await session.execute(text("SET LOCAL hnsw.iterative_scan = 'relaxed_order'"))

    return (await session.execute(SEARCH, {
        "q": str(query_vector), "tenant": tenant_id,
        "model": settings.embedding_model, "k": k,
    })).all()

-- A partial index per known filter value. This is the only option here that is
-- genuinely pre-filtering: the filter is implicit in which index is chosen, so
-- every candidate the graph returns already satisfies it.
--
-- It only works for values known in advance and few in number. One index per
-- tenant is right for five large tenants and absurd for fifty thousand.
CREATE INDEX CONCURRENTLY ix_chunks_embedding_docs
    ON document_chunks USING hnsw (embedding vector_cosine_ops)
    WHERE tenant_id = 1;

# app/search/recall.py
async def measure_recall(session, questions: list[Vector], k: int = 10) -> float:
    """Approximate results compared with exact ones, on a fixed question set.

    The only way to know whether the index is working. An approximate search
    always returns k rows quickly; whether they are the right k is invisible
    without this comparison, and it drifts as the table grows.
    """
    hits = 0
    for q in questions:
        # Exact search: disable the index for this statement only. Slow on
        # purpose — this is ground truth, not a query path.
        await session.execute(text("SET LOCAL enable_indexscan = off"))
        exact = {r.id for r in await session.execute(SEARCH_EXACT, {"q": str(q), "k": k})}
        await session.execute(text("SET LOCAL enable_indexscan = on"))
        approx = {r.id for r in await session.execute(SEARCH, {"q": str(q), "k": k})}
        hits += len(exact & approx) / k
    return hits / len(questions)

5. Golden-standard rules

Rule Why
Forbidden: shipping an approximate index without measuring recall against exact search It always returns k rows quickly. Whether they are the right rows is invisible, and it is the only thing that matters.
Forbidden: two embedding models sharing one column The vector spaces are unrelated, so the search returns confident nonsense with no error. Record the model per row.
Forbidden: a distance operator that does not match the index's operator class The index is ignored and the query becomes a sequential scan — fast on a laptop, catastrophic on real data.
Forbidden: building the vector index without CONCURRENTLY on a populated table It holds a lock for the whole build, which on a large table is minutes of blocked writes.
Forbidden: assuming a WHERE clause narrows the search It filters after the index returned its candidates, so a selective filter can leave almost nothing.
Every field filtered alongside the vector has its own index Otherwise the filter is evaluated by reading rows, which is the slow half of a fast query.
The candidate list size is set per request, from k It is a session parameter and the default is small. With filtering it is the difference between ten results and three.
Index parameters are derived from the row count, with the arithmetic recorded They are build-time and cannot be changed without a rebuild, so the reasoning has to outlive the person.
Build memory is raised before creating the index The build is dramatically faster when the graph fits in memory, and Postgres tells you when it does not.
Partial indexes are used only for few, known filter values They are the only real pre-filtering available here — and one index per tenant is right for five tenants and absurd for fifty thousand.
Recall is re-measured as the table grows An index tuned at a hundred thousand rows is not tuned at ten million, and nothing announces the change.
Iterative scanning is enabled deliberately and measured It fixes short result sets on selective filters and costs latency; on unselective ones it changes nothing.

6. Data contracts

embedding        vector(1536)   -- the dimension is fixed at column creation
embedding_model  TEXT NOT NULL  -- which model produced it; not optional

The model column is the contract that makes an upgrade survivable. Changing embedding model means every stored vector is in a different space from every new one, and a search across both is meaningless — but nothing raises. With the column, the migration is a filter on old rows and a backfill you can run in batches. Without it, the only honest option is to re-embed everything and hope nothing was served wrongly in the meantime.

Similarity scores are not comparable across models or corpora. A threshold tuned here is a measured property of this system, not a number to carry anywhere else — including from this document.

7. Build order

  1. Extension, column and exact search — no index. Prove the query and the distance operator are right while recall is trivially perfect.
  2. The golden question set and the recall measurement, built now, against exact results. Every later step is judged by it.
  3. The index, built concurrently with recorded parameters. Measure recall and latency. If recall is unacceptable, the parameters are wrong and this is the moment to find out.
  4. Filters, with recall measured with the filter applied — a separate number, and usually a much worse one.
  5. Iterative scanning or partial indexes, chosen from what step 4 showed, then measured again.
  6. Payload indexes and the session parameter derived from k.
  7. A recall check that runs on a schedule against production-sized data.

Step 2 before step 3 is the whole discipline. An index added before there is a way to measure it is an index nobody can tune, and the first measurement will be taken after someone complains.

10. Failure modes

Symptom Cause Fix
A filtered search returns far fewer rows than requested Filtering is applied after the index returned its candidates, and most were discarded Raise the candidate list size, enable iterative scanning, or use a partial index
Results look plausible and the right document is never found Recall is poor and nothing reports it Measure against exact search on a fixed question set
The query is suddenly slow after a model change The distance operator no longer matches the index's operator class, so the index is skipped Match the operator to the operator class; check with the planner
Search returns unrelated results after an embedding upgrade Two models' vectors share one column Record the model per row; filter and backfill
Creating the index blocked writes for minutes It was built without CONCURRENTLY Build concurrently, in its own migration
The index build takes hours The graph does not fit in build memory, and Postgres said so in a notice nobody read Raise maintenance_work_mem for the build
Recall was fine at launch and is poor a year later Parameters were sized for the original row count Re-measure on a schedule; rebuild with new parameters when it drops
Latency is fine and the filter is slow The filtered column has no index of its own Add one
A query for a product code or error identifier returns nothing useful Embeddings are near-blind to exact tokens This is not an index problem; add a lexical branch
A similarity threshold copied from a benchmark rejects everything Scores are not comparable across models or corpora Calibrate against this corpus
One tenant's search is slow and others are fast A partial index exists for some tenants and not that one Either partial indexes for all known values or none

11. Definition of done

  • Recall at 10 against exact search is measured on a committed question set, and the number is recorded
  • Recall is measured a second time with the most selective production filter applied, and both numbers are recorded
  • Every row records the embedding model that produced its vector, enforced as NOT NULL
  • A test asserts that querying with the wrong distance operator does not use the index, so the mismatch is caught rather than discovered by latency
  • The query planner is checked in a test to confirm the vector index is used, not a sequential scan
  • The vector index was created concurrently, verified in the migration
  • Index parameters appear in the migration with the arithmetic that produced them in a comment
  • Every field filtered alongside the vector has its own index, verified against the catalogue
  • The candidate list size is set per request and derived from k, covered by a test
  • A scheduled job re-measures recall and fails or alerts when it drops below the target
  • maintenance_work_mem is raised for index builds, and no build notice appears in the log
  • The similarity threshold in use was calibrated against this corpus, and the calibration questions are committed
