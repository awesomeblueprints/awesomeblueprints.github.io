LangGraph: Agent as a State Graph

LangGraph agents as state graphs: typed state, reducers, conditional edges, step ceilings and nodes you can test without running the graph.

medium3–4 daysVerified 2026-08-20
LangGraphAgents
Read it on GitHub ↗ Back to the catalogue

A run whose next step is decided at runtime, expressed as explicit nodes and edges over one typed state — so that the path a request took can be read after the fact instead of reconstructed from logs.

Complexity: medium · Typical build: 3–4 days · Verified: 2026-08-20 (re-check after ~90 days)

Examples in: Python, with LangGraph. The architecture is language-agnostic: sections 5, 10 and 11 hold wherever you build this. Section 4 is illustrative — if your project is in another language, your agent translates the idioms rather than importing them, and nothing is lost. The same shape exists as LangGraph.js in TypeScript and as a hand-written dispatch loop over a state object in any language; what matters is the state contract in §6 and the edge rules in §5, which do not depend on the library.

Use when: the next step depends on what the previous step produced — a tool result, a classification, a validation failure — and a fixed sequence of calls cannot express it.

Not for: a pipeline whose steps are known before the run starts. That is a composed chain, and a graph adds a state object, a compile step and a checkpoint story for no branching you actually have. Also not for a single model call with one tool, where the provider's own tool loop is smaller than a graph and fails in more obvious ways.

Do not start coding.

Step 2 — Read the project, then audit what already exists. Find every place that already loops over model calls — a while with a tool dispatch, a provider tool loop, a task queue re-invoking a prompt — and record how each one terminates and what it does when it does not. 1. Why a graph rather than a loop

The hand-written agent is a while loop: call the model, look at what came back, call a tool, append the result, call again. It is twenty lines and it works. What it does not give you is any of the following, and each one is the reason teams rewrite it:

The loop The graph
The path a request took is reconstructed from log lines The path is a sequence of node names, recorded
Stopping mid-run means losing everything before it State is checkpointed at every node boundary
Two independent steps run one after the other because the loop is a loop Two edges from one node run concurrently
A runaway run is caught by whatever timeout wraps it The graph has a step ceiling of its own
Adding a branch means another if in a function that already has six A branch is an edge with a named condition
Testing a step means running the loop A node is a function from state to state, tested alone

The cost is real and worth naming: you now have a state schema to maintain, a compile step, and a class of bug that does not exist in a loop — two branches writing the same field. §6 and §5 exist to make that class of bug impossible rather than rare.

The single idea underneath all of it: a node is a pure function from state to a partial state update. It does not mutate what it was given and it does not return the whole object. Everything else in this document follows from holding that line — the concurrency rules, the testability, the checkpointing. Nodes that reach outside the state to a global, a request object or a mutable default are the one thing that reliably destroys a graph, because they make the recorded path a lie.

Two things the diagram encodes. Every node writes to the checkpoint store, not just the interesting ones — a partially checkpointed graph resumes into a state that never existed. And branch A and branch B both reach merge, which is the exact place where two updates to the same field collide; that edge pair is why §6 requires a reducer on every field a branch can touch.

3. Project structure

app/agent/
├── state.py          the state schema and its reducers — read this first
├── nodes/
│   ├── plan.py       one file per node, each a plain function
│   ├── tools.py
│   └── finish.py
├── edges.py          the conditional-edge functions, returning node names
├── graph.py          assembly and compile — the only file that knows the shape
└── runner.py         the boundary: plain arguments in, plain result out

One rule: the compiled graph is built once, at import, and never inside a request handler. Compiling per request costs milliseconds you will not notice and hides a much worse bug — a graph rebuilt with different node objects has different closures, so a checkpoint written by one run resumes into another shape.

4. Reference implementation

# app/agent/state.py
import operator
from typing import Annotated, TypedDict
from langchain_core.messages import BaseMessage


def last_wins(current: str | None, incoming: str | None) -> str | None:
    """An explicit reducer for a field only one branch should write.

    Writing this out rather than leaving the field bare is the point: a bare
    field raises at runtime the first time two concurrent branches both set it,
    and that first time is usually in production, because tests rarely exercise
    both branches of a fan-out at once.
    """
    return incoming if incoming is not None else current


class AgentState(TypedDict):
    # `operator.add` is the reducer: concurrent branches appending messages
    # concatenate instead of overwriting. Without an annotation here, two
    # parallel nodes both returning `messages` is an error, not a merge.
    messages: Annotated[list[BaseMessage], operator.add]
    findings: Annotated[list[dict], operator.add]
    decision: Annotated[str | None, last_wins]
    steps_taken: Annotated[int, operator.add]

# app/agent/nodes/plan.py
from app.agent.state import AgentState


async def plan(state: AgentState) -> dict:
    """A node returns a PARTIAL update, never the whole state.

    Returning the whole object works right up until a reducer is added, at which
    point every field silently double-applies. Return only what this node
    decided.
    """
    reply = await model.ainvoke(state["messages"])
    return {"messages": [reply], "steps_taken": 1}

# app/agent/edges.py
from app.agent.state import AgentState

MAX_TOOL_STEPS = 12


def route_after_plan(state: AgentState) -> str:
    """Conditional edges return a node NAME, and they must be total.

    The step ceiling lives here, in the routing decision, not in the graph's
    recursion limit. The recursion limit is a crash guard: it raises, it does not
    let you write a message to the user, and it cannot tell a legitimate long run
    from a loop. A ceiling in the edge produces a controlled ending.
    """
    if state["steps_taken"] >= MAX_TOOL_STEPS:
        return "finish"
    last = state["messages"][-1]
    if getattr(last, "tool_calls", None):
        return "tools"
    return "finish"

# app/agent/graph.py
from langgraph.graph import END, START, StateGraph
from app.agent.state import AgentState
from app.agent.nodes import plan, tools, finish
from app.agent.edges import route_after_plan

builder = StateGraph(AgentState)
builder.add_node("plan", plan.plan)
builder.add_node("tools", tools.run_tools)
builder.add_node("finish", finish.finish)

builder.add_edge(START, "plan")
builder.add_conditional_edges("plan", route_after_plan, ["tools", "finish"])
builder.add_edge("tools", "plan")
builder.add_edge("finish", END)

# Compiled once, at import. `recursion_limit` is passed per invocation as a
# safety net well above the ceiling in `route_after_plan`, so that hitting it
# means a routing bug rather than a long-but-valid run.
graph = builder.compile()

# app/agent/runner.py
from app.agent.graph import graph


async def run(question: str, thread_id: str) -> str:
    """The boundary. Library types stay inside; callers pass and receive plain
    types, so replacing the graph library is a change in one directory.
    """
    result = await graph.ainvoke(
        {"messages": [("human", question)], "steps_taken": 0},
        config={"configurable": {"thread_id": thread_id}, "recursion_limit": 40},
    )
    return result["messages"][-1].content

# tests/test_nodes.py
async def test_plan_returns_a_partial_update():
    # A node is a function from state to a dict. Testing it needs no graph, no
    # compile and no checkpointer — which is the main practical payoff of the
    # shape and the reason nodes stay small.
    out = await plan({"messages": [HUMAN], "findings": [], "decision": None,
                      "steps_taken": 0})
    assert set(out) <= {"messages", "steps_taken"}


def test_routing_is_total():
    # Every conditional edge is enumerated in `add_conditional_edges`. A router
    # returning a name outside that list fails at runtime, not at compile, so
    # cover the branches.
    assert route_after_plan({**BASE, "steps_taken": 99}) == "finish"

5. Golden-standard rules

Rule Why
Forbidden: a node returning the whole state instead of a partial update Every field then double-applies through its reducer the moment one is added, and the corruption is silent.
Forbidden: a state field that two concurrent branches can write, without a reducer It raises at runtime on the first real fan-out, which is typically in production because tests rarely run both branches.
Forbidden: a node mutating the state object it was handed Checkpoints then record a state that the recorded path does not produce, and replay diverges from the original run.
Forbidden: compiling the graph inside a request handler Different node objects mean different closures; a checkpoint from one build resumes into another shape.
Forbidden: relying on the recursion limit to stop a loop It raises rather than returning; it cannot distinguish a long valid run from a cycle, and the user gets an exception instead of an answer.
Forbidden: reading configuration or request context from outside the state inside a node It makes the node untestable alone and makes the recorded path an incomplete account of the run.
Every run passes a thread id Without one there is no checkpoint identity, so nothing can be resumed or inspected afterwards.
Conditional edges enumerate their possible destinations An unenumerated name fails at runtime; enumerating turns it into a visible list you can test against.
A step ceiling lives in a routing function It produces a controlled ending with a message, which a limit exception cannot.
One node, one responsibility, one file Nodes are the unit of retry and of checkpointing; a node doing three things retries all three.
The library's types stop at the runner The graph library is young and moving; the boundary makes a major version a day in one directory.
Node names are stable strings, treated as an interface They appear in checkpoints and traces; renaming one invalidates stored runs.

6. Data contracts

state      one typed object, every field annotated with how it merges
node in    the full state, read-only
node out   a partial update — only the fields this node decided
edge out   a node name, from the enumerated set

The contract that matters is the reducer. A field with no reducer has an implicit one — last write wins — and that implicit rule is fine for a linear path and an error the first time two branches run at once. Decide it per field, in writing:

Field shape Reducer Because
An append-only log (messages, findings, tool results) concatenate Branches contribute; none owns the list
A single decision one branch makes an explicit last-wins function Writing it out documents that concurrency here is intentional
A counter add Two branches each taking a step took two steps
Something two branches genuinely disagree about a merge function that names the winner If you cannot write it, the field belongs to one node and the fan-out is wrong

The last row is the useful test: if you cannot write the reducer, the graph shape is wrong, not the state.

7. Build order

  1. The state schema, with a reducer on every field. Before any node. It is the contract the rest is written against, and retrofitting reducers means re-reading every node.
  2. One node and one test, run as a plain function with no graph at all.
  3. A two-node linear graph, compiled, so that the assembly and the runner boundary exist while there is almost nothing in them.
  4. The routing function and its step ceiling, with tests for the branches including the ceiling.
  5. The tool node, with a failing tool covered by a test — a tool error must become state, not an exception that escapes the graph.
  6. The fan-out, only now, and only if you have two genuinely independent steps. This is where the reducers earn their existence.
  7. Tracing with node names, so a slow run is attributable to a node.

Step 1 first is not a style preference. The reducers are the part that cannot be added later without re-reading everything already written.

10. Failure modes

Symptom Cause Fix
An error about conflicting updates to a state key Two concurrent branches write a field with no reducer Annotate the field with how it merges
State fields quietly double after adding a reducer A node returns the whole state rather than a partial update Return only the fields the node decided
A resumed run behaves differently from the original A node mutated the state it was given, so the checkpoint does not match the path Treat node input as read-only; build a new dict
The run stops with a recursion-limit exception A cycle with no exit condition, or a ceiling that lives only in the limit Put the ceiling in the routing function; keep the limit above it as a crash guard
A checkpoint cannot be resumed after a deploy Node names changed, or the graph is compiled per request with different closures Treat node names as an interface; compile once at import
A tool failure kills the whole run The tool node raises instead of recording Catch inside the node and return the failure as state the router can see
Two branches run sequentially although they are independent They are chained by an edge rather than both edged from the same node Fan out from one node and merge at another
Nothing can be resumed and no run can be inspected No thread id passed Pass one per run; it is the checkpoint identity
A node cannot be tested without standing up the app It reads configuration or request context from outside the state Pass everything through state or through the node's constructor
The graph works and nobody can say what it did Tracing is absent or does not record node names Attach tracing at compile; node names are the trace
Latency doubled after adding a subgraph Subgraph state is isolated, so shared data is being recomputed Pass what the subgraph needs explicitly; keep subgraphs for genuinely separable work

11. Definition of done

  • Every field in the state schema carries an explicit reducer, verified by reading the schema
  • No node returns the full state; each returns a partial update, verified by inspecting every node's return
  • A test asserts that a node's returned keys are a subset of the fields it owns
  • Every node is tested as a plain function, with no graph compiled and no checkpointer
  • Conditional edges enumerate their destinations, and every destination is covered by a test
  • A step ceiling exists in a routing function and produces a normal answer, covered by a test
  • The recursion limit is set above that ceiling and hitting it is treated as a bug, not as flow control
  • A failing tool produces a state update the router can act on, not an exception leaving the graph — covered by a test
  • Every run passes a thread id, verified at the runner boundary
  • The graph is compiled once at import; no compile call appears inside a request handler, checked by grep
  • The graph library is imported only under the agent directory, checked by grep in CI
  • Traces record node names and per-node duration, verified on a real run
  • If a fan-out exists, a test runs both branches concurrently and asserts the merged state
