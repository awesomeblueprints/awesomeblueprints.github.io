Dockerfile for a Production Service

A production Dockerfile: multi-stage builds, non-root users, small images, correct PID 1 signal handling and reproducible dependency layers.

low1 dayVerified 2026-08-19
Docker
Read it on GitHub ↗ Back to the catalogue

A multi-stage build where the dependency layer is cached separately from the code, the runtime image carries no compiler, the process runs unprivileged, and the container stops when it is asked to instead of being killed ten seconds later.

Complexity: low · Typical build: 1 day · Verified: 2026-08-19 (re-check after ~90 days)

Examples in: Python, with uv and a Debian slim base. The architecture is language-agnostic: sections 5, 10 and 11 hold wherever you build this. Section 4 is illustrative — if your project is in another language, your agent translates the idioms rather than importing them, and nothing is lost. The equivalents are npm ci --omit=dev from a package-lock.json in Node, a static binary from CGO_ENABLED=0 go build in Go, and a release build copied out of a mix release stage in Elixir.

Use when: a service needs an image that ships to a registry and runs somewhere you do not control — a rolling deploy, a scheduler, a colleague's machine — and you want the same bytes to run in all three.

Not for: the local development container, which wants the opposite trade-offs: source mounted rather than copied, a reload watcher, dev dependencies present. Building one image that tries to be both produces an image with a compiler in it and a slow inner loop.

⚙️ INSTRUCTIONS FOR THE AI — READ BEFORE WRITING ANY CODE

Do not start coding.

Step 1 — Refresh. Verify the current stable tag of the base image and whether the project's language runtime version is pinned by a file in the repository (.python-version, .nvmrc, go.mod). Verify the dependency tool and its lock file format, and the flags that install from the lock without resolving. Confirm the current syntax for BuildKit cache mounts. Find out where this image will run — Kubernetes, ECS, Compose, a bare daemon — because the stop grace period and whether an init process is available differ, and §10 has failures that only appear under one of them. Report what you verified and what turned out wrong.

Step 2 — Read the project, then audit what already exists. Find any existing Dockerfile and record: base image and tag, whether it is multi-stage, which user the process runs as, whether CMD is exec form or shell form, and what the build context currently contains. Measure the current image size and the time of an incremental build after a one-line code change — those two numbers are the baseline this work is judged against. Find whether a .dockerignore exists. Determine whether the application handles SIGTERM at all. Then audit §11 item by item, each marked already true, partly true or absent, with the file that decides it, reported before anything is proposed.

Assume the project is right until it demonstrably is not; code satisfying an item stays even where its shape differs from §4; replacing something that works needs a one-line reason; never delete a working path to make room for the blueprint's version. The same holds for language — §4 is illustrative, its idioms get translated into the project's language, and §11 is what has to become true rather than the syntax.

Step 3 — Write a plan for the gap only, and get it approved, including a ## Proposed stack section naming the base image and tag with a one-line reason, and the before-and-after numbers for image size and incremental build time. Do not ask open framework questions — propose, and ask for confirmation once. Say what you are adding, what you are leaving alone, and what you propose to change, and touch nothing else.

Step 4 — Build in the order in §7. Step 5 — §11 is the definition of done.

1. Why the obvious Dockerfile is expensive twice

The obvious version copies everything, installs, and runs. It produces a correct image, and it costs you on every build and every deploy.

Copy, install, run Multi-stage, ordered by change rate
One character of code invalidates the dependency layer and reinstalls everything Dependencies are their own layer, keyed by the lock file; code changes rebuild seconds, not minutes
The compiler and headers used to build wheels ship to production The runtime stage never sees them; the attack surface and the image both shrink
The process runs as root because nothing said otherwise An unprivileged user, so a container escape starts from a worse position
CMD python app.py starts a shell that never forwards signals The process is PID 1 and receives SIGTERM directly

The last row is the one that produces user-visible damage and is never investigated, because it does not look like an error. Shell-form CMD runs your process as a child of /bin/sh. SIGTERM goes to the shell, the shell does not forward it, and the daemon waits out its grace period — ten seconds by default on Linux — before SIGKILL. Every deploy therefore severs whatever was in flight, and the only trace is a small, steady rate of client-side errors during rollouts that everyone assumes is normal.

There is a second half to it: a process that is PID 1 gets no default signal handlers from the kernel. Exec form is necessary but not sufficient — the application must also install a handler, or run under an init that does.

The rule the diagram encodes: only the built dependency tree crosses the stage boundary. Nothing that was needed to produce it — compiler, headers, caches, source archives — has an arrow into the runtime stage. If something does, the split has bought you nothing.

3. Project structure

Dockerfile              both stages, and both targets
.dockerignore           what never enters the build context
pyproject.toml          the dependency declaration
uv.lock                 the resolved versions — committed, and the cache key

One rule: .dockerignore is written before the first build, not after. Everything in the build context is sent to the daemon and can silently land in a layer — .git, .env, node_modules, test fixtures, a local database file. A secret that reaches a layer stays in the image even if a later layer deletes it, and the image is what you push to a registry.

4. Reference implementation

# syntax=docker/dockerfile:1

# ---------- build stage ----------
# Pinned by digest as well as tag: a tag is a moving pointer, so "the same
# Dockerfile" can produce different images next month and you cannot reproduce the
# one that is currently in production.
FROM python:3.13-slim-bookworm@sha256:REPLACE_WITH_REAL_DIGEST AS build

COPY --from=ghcr.io/astral-sh/uv:latest /uv /usr/local/bin/uv

ENV UV_COMPILE_BYTECODE=1 \
    UV_LINK_MODE=copy \
    UV_PYTHON_DOWNLOADS=never

WORKDIR /app

# Dependencies first, code second. This ordering is the entire caching strategy:
# the lock file changes weekly, the code changes hourly, and Docker invalidates
# every layer after the first one that changed.
COPY pyproject.toml uv.lock ./
# --frozen fails if the lock is out of date with pyproject, so a build cannot
# quietly resolve to versions nobody reviewed.
# --no-install-project installs only dependencies; the project itself is not
# copied yet, so this layer survives every code change.
RUN --mount=type=cache,target=/root/.cache/uv \
    uv sync --frozen --no-dev --no-install-project

# Now the code, and the project itself into the same environment.
COPY . .
RUN --mount=type=cache,target=/root/.cache/uv \
    uv sync --frozen --no-dev

# ---------- runtime stage ----------
FROM python:3.13-slim-bookworm@sha256:REPLACE_WITH_REAL_DIGEST AS runtime

# Created before anything is copied, so ownership is right without a recursive
# chown — which would otherwise duplicate the whole tree into another layer.
RUN groupadd --system --gid 1001 app \
 && useradd --system --uid 1001 --gid app --no-create-home app

WORKDIR /app

COPY --from=build --chown=app:app /app/.venv /app/.venv
COPY --from=build --chown=app:app /app/app /app/app

ENV PATH="/app/.venv/bin:$PATH" \
    PYTHONUNBUFFERED=1 \
    PYTHONDONTWRITEBYTECODE=1

USER app

EXPOSE 8000

# Exec form. Shell form would start /bin/sh as PID 1, and the shell does not
# forward SIGTERM — so the daemon waits out its grace period and SIGKILLs the
# container, severing in-flight requests on every deploy.
# --init gives a real init as PID 1: it forwards signals and reaps zombies, which
# a language runtime as PID 1 does not do. Compose sets it per service; Kubernetes
# has no equivalent flag, so there you either install tini or handle SIGTERM in
# the application. Do one of them; do not assume.
CMD ["uvicorn", "app.main:app", "--host", "0.0.0.0", "--port", "8000"]

# Deliberately absent: HEALTHCHECK. Under an orchestrator the platform's own probes
# decide readiness, and a second definition here is one more thing to keep in sync
# that nothing reads. Add it only when the target is a bare daemon or Compose.

# .dockerignore
.git
.gitignore
.venv
__pycache__/
*.pyc
.env
.env.*
tests/
docs/
compose*.yaml
Dockerfile
.dockerignore
*.md
.pytest_cache/
.ruff_cache/

# app/main.py — the other half of stopping cleanly
import signal
from contextlib import asynccontextmanager
from fastapi import FastAPI


@asynccontextmanager
async def lifespan(app: FastAPI):
    yield
    # Runs on SIGTERM because the server installs a handler. Exec form gets the
    # signal to the process; this is what makes the process do something with it.
    # Without both halves the container is killed at the end of the grace period.
    await drain_background_work()

5. Golden-standard rules

Rule Why
Forbidden: shell-form CMD or ENTRYPOINT The shell becomes PID 1 and does not forward SIGTERM, so every stop is a kill after the grace period and every deploy severs in-flight work.
Forbidden: running as root It is the default only because nothing said otherwise, and it turns a container escape from difficult into routine.
Forbidden: a build that resolves dependencies instead of installing a lock Two builds of the same commit then produce different images, and the one in production is not the one you tested.
Forbidden: copying the whole context before installing dependencies It invalidates the dependency layer on every code change, which is the difference between a five-second build and a five-minute one.
Forbidden: secrets as build arguments or ENV Both are recorded in the image metadata and survive any later deletion. Use a build secret mount, or inject at runtime.
The base image is pinned by digest, not only by tag A tag moves. Pinned by tag alone, the same Dockerfile produces a different image next month and the one in production cannot be reproduced.
The runtime stage contains no compiler or headers If it does, the multi-stage split bought nothing but complexity.
.dockerignore exists before the first build Anything in the context can land in a layer, and a secret in a layer stays in the image after it is deleted.
The user is created before files are copied, and copies set ownership A recursive chown afterwards rewrites every file into a new layer, often doubling the image.
Signals are handled by the application or by an init process, decided explicitly Exec form delivers the signal; something still has to act on it. PID 1 gets no default handlers.
HEALTHCHECK only when nothing else probes the container Under an orchestrator it duplicates the platform's probes and drifts from them.
Dev and prod are separate targets in one file Shared base layers, different final stages. One image trying to be both ships a compiler and still has a slow inner loop.

6. Data contracts

The contract is the image, and it has four observable properties:

starts as an unprivileged user      id -u inside the container is not 0
stops on SIGTERM                    exits before the grace period, with code 0
same input, same output             the same commit and lock produce the same digest
carries no build toolchain          no compiler, no headers, no package caches

These are testable from outside the image without knowing what is in it, which is the point — they are the things a platform, a scanner and a colleague rely on, and none of them can read your Dockerfile.

7. Build order

  1. Single-stage build that runs, with exec-form CMD. Record the image size and the incremental build time — these are the numbers to beat.
  2. .dockerignore, then rebuild and confirm the context shrank.
  3. Split into build and runtime stages, copying only the dependency tree. Confirm no compiler in the final image.
  4. Reorder so dependencies install before code is copied, and confirm a one-line code change rebuilds without reinstalling.
  5. Non-root user, with ownership set during the copies rather than after.
  6. Prove the stop path: send SIGTERM to a container with an in-flight request and confirm it exits cleanly, before the grace period, with the request completed.
  7. Pin the base by digest and add the dev target.

Step 6 late but never last: it is the item most likely to be skipped, and the only one whose absence is invisible until it is costing you requests on every deploy.

9. Metrics

Metric Target
Final image size < 250 MB for a Python service; measure and record yours
Incremental build after a one-line code change < 15 s
Rebuild after a dependency change < 90 s with a warm cache mount
Time from SIGTERM to exit < 5 s, and always under the platform's grace period
Requests failed during a rolling restart 0
Processes running as UID 0 in the container 0
Critical vulnerabilities in the runtime image 0 at build time, scanned in CI

10. Failure modes

Symptom Cause Fix
A small, steady rate of client errors during every deploy, and nobody can reproduce it Shell-form CMD: the shell is PID 1 and swallows SIGTERM, so the container is SIGKILLed at the end of the grace period with requests in flight Exec form, and handle the signal in the application
The container exits immediately on SIGTERM with work unfinished Exec form is right, but nothing installed a handler — PID 1 gets no defaults Handle the signal in the application, or run under an init process
Every build takes minutes even for a one-word change The code is copied before dependencies are installed, invalidating that layer every time Copy the lock file and install first; copy code last
The image is far larger than the application The runtime stage inherits the build toolchain, or a recursive chown duplicated the file tree Copy only the dependency tree across; set ownership in the COPY
Two builds of the same commit produce different behaviour Dependencies were resolved at build time rather than installed from a lock, or the base tag moved --frozen from a committed lock; pin the base by digest
A scanner reports a secret in the image, and it is not in the current filesystem It was added in an earlier layer and deleted in a later one; layers are additive Rebuild without it; rotate the secret — it is in the registry history
The build sends gigabytes to the daemon before starting No .dockerignore, so .git and local artefacts are part of the context Add one, then confirm the context size dropped
The application cannot write its temp files or bind its port It runs unprivileged now; the paths it writes are root-owned, or the port is below 1024 Set ownership on those paths; bind above 1024 and map at the platform
The container is reported unhealthy under an orchestrator while the platform probe passes A HEALTHCHECK in the image disagrees with the platform's probe Remove the image-level check where a platform probes it
Zombie processes accumulate in a long-running container The runtime as PID 1 does not reap children, and something in the process spawns subprocesses Run under an init that reaps

11. Definition of done

  • docker run --rm <image> id -u returns a non-zero UID
  • CMD and ENTRYPOINT are exec form, verified by inspecting the image config rather than by reading the Dockerfile
  • Sending SIGTERM to a container with an in-flight request results in exit code 0 before the platform's grace period, with the request completed — covered by a test in CI
  • Changing one line of application code and rebuilding does not reinstall dependencies, verified by the build log
  • The runtime image contains no compiler and no package-manager cache, verified by running the build tool inside it and expecting failure
  • Building the same commit twice produces the same image digest
  • The base image is pinned by digest, and a scheduled job checks whether a newer digest exists for that tag
  • .dockerignore excludes .git, .env* and test directories, verified by listing the image's filesystem
  • No secret appears in docker history or in the image config
  • Image size and incremental build time are recorded, and CI fails if either exceeds an agreed ceiling
  • A dev target exists in the same file and shares the dependency layers with the production target
