Idempotency Keys and Safe Retries

Idempotency keys and safe retries: making webhooks, payments, queued jobs and client POSTs safe to deliver twice without double effects.

low1–3 daysVerified 2026-08-18
Reliability
Read it on GitHub ↗ Back to the catalogue

How to make an operation safe to run twice, so that a retry — from a client, a queue, a webhook sender or a human hitting the button again — changes nothing the second time.

Complexity: low-medium · Typical build: 1–3 days · Verified: 2026-08-18 (re-check after ~90 days)

Examples in: TypeScript and Postgres. Only §4 is language-specific — the rules, failure modes and definition of done hold anywhere, and your agent translates the code.

Use when: an operation can be delivered or invoked more than once — webhooks, queued jobs, payments, outbound email, any POST a client may retry — and running it twice would double-charge, double-send or double-write.

Not for: naturally idempotent reads, or operations where doing the work twice is genuinely harmless — adding retry machinery to those is cost without benefit.

1. Why "it worked" is not the same as "it ran once"

An ordinary write A retry-safe write
Delivery assumption Exactly once At least once — plan for the duplicate
Who retries Nobody, in the happy path Client timeouts, queue redelivery, sender retries, the user
Effect of running twice Usually nothing visible Two charges, two emails, two rows
When you find out — From the customer
Where the guarantee lives Nowhere A unique constraint in the schema

The trap is that a duplicate is not an error state. The first call succeeded; the response was simply lost on the way back. The sender does the correct thing and retries. Any design that treats the second delivery as anomalous will get this wrong, because it is the normal case.

So the question is never "how do I stop retries" — you cannot, and you do not want to. It is "what does the second attempt do instead of the work".

The rule this diagram encodes: the claim and the effect commit together, in one transaction, in one database. Split them across two systems and there is a window where the key says "done" and the work never happened.

3. Project structure

src/
├── idempotency/
│   ├── key.ts            # derive a key: header, or a stable hash of the request
│   ├── claim.ts          # claim(key, tx) -> Won | Replay(storedResponse)
│   └── schema.sql        # the table and its unique index
├── domain/               # the actual effects. Knows nothing about retries.
└── handlers/             # claim, then call domain, then store the response

The rule that keeps this maintainable: the domain layer stays unaware of idempotency. It exposes an operation that is called once; the wrapper decides whether to call it. The moment "have we done this already" leaks into business logic, every future operation has to remember to ask.

4. Reference implementation

Claiming the key. The entire guarantee is a unique index plus a conflict clause — one round trip, no read-then-write race:

create table idempotency_records (
  key            text primary key,          -- the unique index IS the lock
  operation      text        not null,       -- 'charge', 'send_invite' — see §5
  request_hash   text        not null,       -- guards against key reuse
  status         text        not null,       -- 'in_progress' | 'completed'
  response       jsonb,                      -- replayed verbatim
  created_at     timestamptz not null default now(),
  completed_at   timestamptz
);

export async function claim(tx: Tx, key: string, operation: string, requestHash: string) {
  // ON CONFLICT DO NOTHING makes this a single atomic "did I win?" - two
  // concurrent requests cannot both see an empty table and both proceed.
  const inserted = await tx.query(
    `insert into idempotency_records (key, operation, request_hash, status)
     values ($1, $2, $3, 'in_progress')
     on conflict (key) do nothing
     returning key`,
    [key, operation, requestHash],
  );
  if (inserted.rowCount === 1) return { won: true } as const;

  const existing = await tx.one(
    `select operation, request_hash, status, response
       from idempotency_records where key = $1`, [key]);

  // Same key, different request body: the client reused a key for new content.
  // Replaying the old response here would silently answer the wrong question.
  if (existing.request_hash !== requestHash || existing.operation !== operation) {
    throw new IdempotencyKeyReused(key);
  }
  if (existing.status === 'in_progress') throw new RequestInFlight(key);
  return { won: false, response: existing.response } as const;
}

Doing the work. The effect and the completion record commit together. If the process dies mid-way, both roll back and the next delivery starts clean:

export async function runOnce<T>(key: string, operation: string, req: unknown,
                                 effect: (tx: Tx) => Promise<T>): Promise<T> {
  const hash = stableHash(req);
  return db.transaction(async (tx) => {
    const claimed = await claim(tx, key, operation, hash);
    if (!claimed.won) return claimed.response as T;

    const result = await effect(tx);          // domain write, same transaction

    await tx.query(
      `update idempotency_records
          set status = 'completed', response = $2, completed_at = now()
        where key = $1`, [key, result]);
    return result;                             // commit publishes both, or neither
  });
}

The one thing a transaction cannot protect. An outbound call to a third party is not rolled back by your database. Do it after commit, keyed, and let the provider deduplicate:

// Inside the transaction: record the intent. After commit: perform it.
// The provider's own idempotency key makes the post-commit retry safe.
await stripe.charges.create(payload, { idempotencyKey: key });

5. Golden-standard rules

Rule Why
The uniqueness lives in a database constraint, never in application code An if (await exists(key)) check has a race between the check and the write
The claim and the effect commit in one transaction, in one database Two systems means a window where one says done and the other never ran
The key is scoped by operation The same client key reused across two endpoints must not collide
A key arriving with a different request body is an error, not a replay Otherwise a reused key silently answers the wrong question
The stored response is replayed verbatim A recomputed response can differ from what the caller already acted on
A replay returns the original status code too A 201 that becomes a 200 on retry breaks clients that branch on it
Third-party calls happen after commit, with the provider's own idempotency key Your transaction cannot roll back their charge
Keys are expired on a schedule, not never The table grows forever; pick a window longer than the longest sender retry
Expiry is longer than every upstream retry window Expire at 24h while the sender retries for 72h and you re-run the work
An in-flight duplicate is refused, not queued Blocking invites deadlock; a 409 tells the caller to retry later
Client-supplied keys are validated for shape and length The key is a primary key; unbounded input becomes an index problem
Where no client key exists, hash the semantic content, not the raw bytes Whitespace or key order must not produce a new key

/** Derived once, at the boundary. Never re-derived deeper in the stack. */
export type IdempotencyKey = string & { readonly __brand: 'IdempotencyKey' };

export type ClaimResult<T> =
  | { won: true }                    // you are the first; do the work
  | { won: false; response: T };     // someone already did; return this

/** Stable across formatting: sort keys, drop undefined, normalise numbers. */
export function stableHash(request: unknown): string;

7. Build order

  1. The table and its unique index, as a migration. Nothing else yet.
  2. claim(), with a test that runs two concurrent claims of the same key and asserts exactly one wins. Do this before any real operation uses it.
  3. runOnce() wrapping one real operation end to end.
  4. The replay path — assert the second call writes nothing and returns the identical body and status.
  5. Key reuse detection — same key, different body, expect a hard error.
  6. The in-flight case — a second delivery while the first is still running.
  7. Third-party calls, moved after commit and given the provider's key.
  8. Expiry, as a scheduled delete, with the window written down and justified.

10. Failure modes

Symptom Cause Fix
Charged twice, one order row Third-party call inside the transaction, retried after rollback Move it after commit; pass the provider an idempotency key
Two rows for one request under load Check-then-insert instead of a unique constraint on conflict do nothing, and let the index decide
Retry returns a different response than the first call Response recomputed instead of stored Store it at completion; replay verbatim
Duplicates reappear after a quiet period Keys expired sooner than the sender's retry window Expiry longer than the longest upstream retry
Second call hangs In-flight duplicate waiting on the first Refuse with 409; do not block
Everything duplicates after a deploy Key derivation changed, so old and new keys differ Version the derivation; treat a change as a migration
Table grew to millions of rows No expiry Scheduled delete on created_at
Works locally, duplicates in production Single worker locally, several in production Test concurrency, not just repetition

11. Definition of done

  • A unique constraint on the key exists in the schema, not only in code.
  • Two concurrent claims of the same key produce exactly one winner — covered by a test.
  • A second delivery writes nothing and returns the byte-identical response and status code.
  • The same key with a different request body is rejected, not replayed.
  • The claim and the domain write commit in the same transaction.
  • No third-party call happens inside that transaction.
  • Every outbound provider call carries an idempotency key.
  • Expiry runs on a schedule, and the window is longer than every upstream retry window.
  • The domain layer contains no reference to idempotency.
