ChromaDB Embedded Vector Store

ChromaDB as an embedded vector store: persistence, metadata filtering and collection design for prototypes, CLI tools and local retrieval.

low1 dayVerified 2026-08-19
Vector search
Read it on GitHub ↗ Back to the catalogue

A vector store with no infrastructure: embedded in the process, persisted to a directory, useful the same afternoon — set up so that the day it stops being the right choice, moving off it is an export rather than an archaeology project.

Complexity: low · Typical build: 1 day · Verified: 2026-08-19 (re-check after ~90 days)

Examples in: Python. The architecture is language-agnostic: sections 5, 10 and 11 hold wherever you build this. Section 4 is illustrative — if your project is in another language, your agent translates the idioms rather than importing them, and nothing is lost. The portability discipline in §3 is the durable part and applies to any embedded store you might reach for instead.

Use when: you need retrieval working today and infrastructure is the thing in the way — a prototype, a demo, a desktop or CLI tool, a test suite that needs a real vector store, or embedded search inside another product.

Not for: a service with several processes writing at once. An embedded store is a library holding a directory, and two writers is not a configuration it has. Also not for a corpus you already know will be large or multi-tenant with hard isolation — starting here then is a migration you have scheduled in advance for no reason.

⚙️ INSTRUCTIONS FOR THE AI — READ BEFORE WRITING ANY CODE

Do not start coding.

Step 1 — Refresh. Verify the installed major and what changed in it — this library has had substantial rewrites, including a change of implementation language, and configuration and authentication have moved between versions. Confirm the current client constructors for the in-memory, persistent and client-server modes, and whether persistence is automatic or still requires an explicit call, because older examples are full of a call that no longer exists. Confirm whether any maintenance command is needed after upgrading. Report what you verified and what turned out wrong.

Step 2 — Read the project, then audit what already exists. Find whether more than one process will ever open the store — a web worker plus a background job counts, and it is the constraint that decides everything else. Find the embedding function currently in use, and whether it is the library's default: the default is convenient and it is a different model from whatever you will use in production, so a corpus built with it has to be re-embedded rather than moved. Establish whether the data can be regenerated from a source, since that decides how much this store's durability matters. Then audit §11 item by item, each marked already true, partly true or absent, with the file that decides it, reported before anything is proposed.

Assume the project is right until it demonstrably is not; code satisfying an item stays even where its shape differs from §4; replacing something that works needs a one-line reason; never delete a working path to make room for the blueprint's version. The same holds for language — §4 is illustrative, its idioms get translated into the project's language, and §11 is what has to become true rather than the syntax.

Step 3 — Write a plan for the gap only, and get it approved, including a ## Proposed stack section and the two conditions that will mean it is time to leave — written down now, while nobody is under pressure. Do not ask open framework questions — propose, and ask for confirmation once. Say what you are adding, what you are leaving alone, and what you propose to change, and touch nothing else.

Step 4 — Build in the order in §7. Step 5 — §11 is the definition of done.

1. The cost of the easiest possible start

Zero infrastructure is a real advantage and it is worth taking. The problem is that the same properties that make it easy to start make it easy to build things that cannot leave.

Using it as the tutorial shows Using it deliberately
The default embedding function, chosen by not choosing The model named explicitly, because the corpus is only portable if you know what produced it
Vectors are in the store and nowhere else The source text and its metadata are kept; the store is derived and rebuildable
Ids assigned as it goes Ids derived from the source, so re-ingesting replaces rather than duplicates
"We will move when we need to" Two written conditions that mean it is time, agreed before anyone is under pressure

The first row is the one that turns a move into a rewrite. The library will happily embed for you with a bundled default model, and that default is not what you will run in production. Vectors from two models cannot be compared, so "exporting to another store" is not a copy — it is re-embedding the entire corpus, at whatever the provider charges, on a deadline. Naming the model from the first line costs nothing and keeps the option open.

The second row matters because the failure mode of an embedded store is not corruption but creep. It works, so more gets built on it, and the constraint — one process writes — is discovered when a background worker is added, months later, by a colleague who did not know that was a constraint. That is not a defect of the library; it is what "embedded" means. Write down what it cannot do while it is still doing everything you need.

3. Project structure

app/retrieval/
├── store.py       the client, and the only module importing the library
├── embed.py       the embedding function, named and configured here
├── ingest.py      source documents to the store, rerunnable
└── export.py      everything out, in a form another store can read
data/
└── chroma/        the persistence directory — git-ignored, and reproducible

One rule: export.py exists from the first week and is tested. Not when a migration is planned — then. It is fifty lines, it makes the exit real rather than theoretical, and writing it early forces the two decisions that make an exit possible at all: knowing which model produced the vectors, and having ids that mean something outside this store.

4. Reference implementation

# app/retrieval/embed.py
from chromadb.utils import embedding_functions

# Named explicitly, never the library's default. The bundled default is convenient
# and it is a different model from anything you will run in production — and
# vectors from two models cannot be compared. Choosing by not choosing turns a
# future export into a full re-embed of the corpus, on someone else's deadline.
EMBEDDING_MODEL = "text-embedding-3-small"

embedding_function = embedding_functions.OpenAIEmbeddingFunction(
    api_key=settings.openai_api_key.get_secret_value(),
    model_name=EMBEDDING_MODEL,
)

# app/retrieval/store.py
import chromadb

# Persistent, not in-memory. The in-memory client is right for tests and loses
# everything on exit; using it in development produces a corpus that quietly
# disappears and a bug report about "search stopped working".
client = chromadb.PersistentClient(path=str(settings.chroma_dir))

collection = client.get_or_create_collection(
    name="documents",
    embedding_function=embedding_function,
    # The metric is fixed at creation and cannot be changed afterwards. Cosine for
    # normalised embeddings; the wrong choice ranks badly rather than failing, so
    # it is worth confirming against the model's documentation now.
    metadata={"hnsw:space": "cosine", "embedding_model": EMBEDDING_MODEL},
)

# app/retrieval/ingest.py
import hashlib


def chunk_id(document_id: str, index: int) -> str:
    # Derived, never generated. Rerunning ingestion for a changed document then
    # replaces its chunks; with random ids it inserts a second copy of everything
    # and retrieval degrades as duplicates crowd the results — with no error.
    return hashlib.sha256(f"{document_id}:{index}".encode()).hexdigest()[:32]


def ingest(document_id: str, chunks: list[str], meta: dict) -> None:
    collection.upsert(
        ids=[chunk_id(document_id, i) for i in range(len(chunks))],
        documents=chunks,
        metadatas=[{**meta, "document_id": document_id, "chunk_index": i,
                    # Recorded per record. When the model changes, this is what
                    # lets you find and re-embed the old rows instead of guessing.
                    "embedding_model": EMBEDDING_MODEL}
                   for i in range(len(chunks))],
    )

# app/retrieval/export.py
def export_all(path: Path) -> None:
    """Everything out, in a form another store can read.

    Written in the first week and tested, not when a migration is planned. It is
    what makes leaving a decision rather than a project — and writing it early is
    what forces ids and the model to be portable in the first place.
    """
    batch, offset = 1000, 0
    with path.open("w") as out:
        while True:
            page = collection.get(limit=batch, offset=offset,
                                  include=["documents", "metadatas", "embeddings"])
            if not page["ids"]:
                break
            for i, cid in enumerate(page["ids"]):
                out.write(json.dumps({
                    "id": cid,
                    "text": page["documents"][i],
                    "metadata": page["metadatas"][i],
                    # Only reusable if the target store uses the same model. If it
                    # does not, the text and metadata above are what matters and
                    # the vectors are recomputed.
                    "embedding": page["embeddings"][i],
                }) + "\n")
            offset += batch

5. Golden-standard rules

Rule Why
Forbidden: the library's default embedding function It is a different model from production, and vectors from two models cannot be compared — so an export becomes a full re-embed.
Forbidden: more than one process writing to the same directory An embedded store is a library holding files. Two writers is not a supported configuration and the damage is not always immediate.
Forbidden: generated ids Re-ingesting then duplicates the corpus, and duplicates crowd results without raising anything.
Forbidden: treating the store as the only copy of anything It holds derived data. Keep the source text and metadata; the store must be rebuildable.
Forbidden: the in-memory client outside tests It loses everything on exit and the symptom is "search stopped working" rather than an error.
The embedding model is recorded in the collection and on every record It is what makes a model change a scoped backfill rather than a full re-embed.
An export exists and is tested from the first week It makes leaving a decision instead of a project, and writing it early forces the choices that allow leaving.
The distance metric is chosen deliberately at creation It cannot be changed afterwards, and the wrong one ranks badly rather than failing.
The two conditions that mean it is time to leave are written down Decided while nobody is under pressure, they get acted on; left implicit, they are argued about during an incident.
The persistence directory is reproducible, not backed up Backing up derived data is effort spent protecting something you can regenerate.
Tests use an ephemeral client Otherwise a test writes into the development corpus and the failure appears somewhere else entirely.
The library major is pinned It has had substantial rewrites, and an unpinned upgrade is a rewrite you did not schedule.

6. Data contracts

id        derived from (document_id, chunk_index) — stable across re-ingestion
document  the chunk text, stored so an export needs no second source
metadata  {"document_id", "chunk_index", "embedding_model", ...}

The export format is the real contract, and it is deliberately dull: one JSON object per line with the text, the metadata, the id and the vector. Every store worth moving to can read that. The vector is only reusable if the target uses the same model; the text and metadata are what make the move possible when it does not, which is the common case.

The two conditions to write down now. Something like: more than one process needs to write, or the corpus passes a size at which search latency stops being acceptable. Both are checkable, neither is a matter of opinion at three in the morning, and having them written is what stops "we should probably move" from being a conversation held quarterly for two years.

7. Build order

  1. Persistent client, a named embedding model, one document, one search. The model is chosen here and everything portable follows from it.
  2. Derived ids and ingestion that is rerunnable, with a test asserting the record count is unchanged after a second run.
  3. The export, and a test that round-trips it — write it now, while it is fifty lines and nobody is waiting.
  4. Metadata filters, and a test that a filtered search never returns records outside the filter.
  5. The ephemeral test fixture, so no test can touch the real directory.
  6. The two exit conditions, written into the repository beside the store.
  7. A rebuild from source, executed once to prove the store is genuinely derived rather than authoritative.

Step 3 that early on purpose. An export written under pressure is written against whatever the ids and the model happen to be by then, and by then they are usually the two things that make the move expensive.

10. Failure modes

Symptom Cause Fix
Moving to another store turns out to require re-embedding everything The library's default embedding model was used and never recorded Name the model from the first line; record it per record
The corpus doubles and search quality drops Ids were generated, so re-ingestion inserted copies Derive ids from the document and chunk position
Search stops working after a restart, with no error The in-memory client was used outside tests Use the persistent client; keep the ephemeral one for tests
The store behaves strangely after adding a background worker Two processes are writing to one directory Move to a client-server deployment or a different store; this is the constraint that decides it
A test corrupted the development corpus Tests share the real directory An ephemeral client per test
An upgrade broke the application in ways the changelog did not obviously predict The major was unpinned and the library has been rewritten more than once Pin the major; read the migration notes before moving
Ranking is poor and nothing is wrong The distance metric does not match the embedding model Set it at creation; it cannot be changed later
Nobody can say whether it is time to move The exit conditions were never written down Two checkable conditions, agreed early
Restoring the store from a backup produced a stale corpus Derived data was backed up instead of regenerated Keep ingestion rerunnable; rebuild rather than restore
A filtered search returned records outside the filter The metadata filter was built incorrectly and nothing tested it Test the filter path, as with any query
Disk use grows well past the corpus size Old versions accumulate without maintenance Run whatever compaction the installed version provides; check the release notes

11. Definition of done

  • The embedding model is named explicitly in code and recorded on every record; a test asserts no record lacks it
  • Re-running ingestion for an unchanged document leaves the record count unchanged, covered by a test
  • An export produces every record with text, metadata and vector, and a round-trip test restores an identical corpus
  • The store is rebuildable from source by rerunning ingestion, demonstrated once end to end with the duration recorded
  • Tests use an ephemeral client; a test asserts the development directory is untouched by the suite
  • Only one process writes to the store, stated in the code and verified against the deployment
  • The distance metric is set at collection creation with the embedding model named beside it
  • The two conditions that mean it is time to move are written in the repository, both checkable
  • The library major is pinned, and the pinned version is recorded with the date it was verified
  • A metadata-filtered search never returns records outside the filter, covered by a test
  • The persistence directory is git-ignored and absent from backups, with a comment saying why
