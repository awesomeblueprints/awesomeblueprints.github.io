Pydantic Settings: Typed Configuration

Pydantic Settings for typed configuration: environment variables validated at startup, so a missing key is a failed deploy, not a 3am surprise.

low1 dayVerified 2026-08-19
Python
Read it on GitHub ↗ Back to the catalogue

Configuration read once, validated once, at startup — so a missing or malformed value stops the process before it serves a request, instead of surfacing two hours later as a 500 on whichever endpoint happens to touch it first.

Complexity: low · Typical build: 1 day · Verified: 2026-08-19 (re-check after ~90 days)

Examples in: Python, with pydantic-settings and FastAPI. The architecture is language-agnostic: sections 5, 10 and 11 hold wherever you build this. Section 4 is illustrative — if your project is in another language, your agent translates the idioms rather than importing them, and nothing is lost. The equivalents are Zod's .parse(process.env) in TypeScript, envconfig in Go, Ecto.Changeset over System.get_env in Elixir, and config + a validation callback in Rails.

Use when: anything about how the app behaves comes from outside the code — a database URL, an API key, a feature flag, a timeout, a bucket name — and you want it wrong-or-missing to be a failed deploy rather than a runtime surprise.

Not for: values that change while the process is running — feature flags flipped from a dashboard, per-tenant overrides, anything polled or pushed. Those are a runtime store with its own cache and invalidation, and freezing them into a settings object at startup is how a flag stops responding. Also not for validating user input; that arrives per request and belongs at the request boundary.

1. Why reading the environment where you need it fails

The obvious version is os.getenv("DATABASE_URL") at the point of use. It works on the first day and fails in four specific ways afterwards.

Reading the environment at the point of use Parsing it once at startup
A missing variable is discovered when the first request reaches that line — possibly hours after deploy, possibly only on the payment path A missing variable stops the process before it binds a port; the deploy fails and the old version keeps serving
Every value is a string; "0", "false" and "" are all truthy Every value is the declared type, and a value that cannot be coerced is a startup error naming the field
Nobody can list what the app needs — the answer is spread across forty files One class is the exhaustive list, and it is the thing you hand a new deployer
getenv("TIMEOUT", 30) in three files with three different defaults One default, in one place, with a type

The fourth row is the one that costs the most and gets noticed the least. Two modules disagreeing about a default is not an error anywhere; it is a system that behaves differently depending on which code path you entered through.

The property that makes this work is not the types. It is that the whole configuration is resolved before anything else runs. A settings object built lazily on first use has moved the failure later, which is the entire problem.

The rule the diagram encodes: there is exactly one arrow out of validation into the application, and one out of it into a dead process. Nothing downstream of instance can observe a half-valid configuration, because no such state is reachable.

3. Project structure

app/
├── config.py          the Settings class and the provider — the only file that reads the environment
├── main.py            imports settings at module level; startup fails here or not at all
├── deps.py            the provider wired as a framework dependency
└── ...
.env.example           every key, with a safe placeholder value — committed
.env                   local only — git-ignored

One rule: os.environ and os.getenv appear in exactly one file. Enforce it with a lint rule or a grep in CI, not with discipline. The moment a second file reads the environment directly, the Settings class stops being the exhaustive list of what the app needs, and the .env.example you hand a new deployer is quietly wrong.

4. Reference implementation

# app/config.py
from functools import lru_cache
from typing import Literal
from pydantic import Field, PostgresDsn, SecretStr, field_validator, model_validator
from pydantic_settings import BaseSettings, SettingsConfigDict


class Settings(BaseSettings):
    model_config = SettingsConfigDict(
        env_file=".env",              # development convenience; absent in production
        env_file_encoding="utf-8",
        env_nested_delimiter="__",    # NOT "_": a single underscore mis-assigns any
                                      # field whose own name contains one, and collides
                                      # with ordinary variables like USER
        env_ignore_empty=True,        # FOO= means "unset", not "empty string" — without
                                      # this, one blank line in a compose file overrides
                                      # the default with ""
        case_sensitive=False,
        extra="forbid",               # an unknown ORDERS_* key is a typo, and a typo in a
                                      # config key is silently the default value forever
        frozen=True,                  # nothing mutates settings at runtime; if something
                                      # needs to, it is not configuration (see Not for)
    )

    # No default: this is what makes a missing value a failed startup rather than a
    # connection to nowhere. Give a default only where the default is genuinely correct
    # in production, not merely convenient in development.
    database_url: PostgresDsn
    payment_api_key: SecretStr        # __repr__ prints '**********', so an accidental
                                      # log of the settings object cannot leak it
    environment: str = "development"
    request_timeout_seconds: float = Field(default=5.0, gt=0, le=60)
    allowed_origins: list[str] = Field(default_factory=list)

    @field_validator("environment")
    @classmethod
    def known_environment(cls, v: str) -> str:
        if v not in {"development", "staging", "production"}:
            raise ValueError(f"unknown environment {v!r}")
        return v

    @model_validator(mode="after")
    def production_is_locked_down(self) -> "Settings":
        # Cross-field rules are the ones a per-field type cannot express, and they are
        # where the expensive mistakes live. This one turns "we shipped the dev CORS
        # config to production" from an incident into a failed deploy.
        if self.environment == "production" and "*" in self.allowed_origins:
            raise ValueError("allowed_origins cannot contain '*' in production")
        return self


@lru_cache
def get_settings() -> Settings:
    # Cached because constructing it re-reads .env from disk. The cache is also what
    # lets tests swap the whole object: clear it, or override the dependency.
    return Settings()

# app/main.py
from fastapi import FastAPI
from app.config import get_settings

# Module level, deliberately. Import fails -> the process never binds a port -> the
# orchestrator sees a crash-looping container and keeps the previous version serving.
# Deferring this into a startup hook means the port is already open when it fails.
settings = get_settings()

app = FastAPI()

# tests/conftest.py
import pytest
from app.config import get_settings
from app.main import app


@pytest.fixture
def override_settings():
    def _override(**kwargs):
        # lru_cache is a global; a test that constructs Settings without clearing it
        # gets whichever object the first test happened to build. Clear, then override.
        get_settings.cache_clear()
        app.dependency_overrides[get_settings] = lambda: Settings(**kwargs)
    yield _override
    app.dependency_overrides.clear()
    get_settings.cache_clear()

5. Golden-standard rules

Rule Why
Exactly one module reads the environment It is the only way the Settings class stays the exhaustive list of what the app needs. Enforce in CI, not by review.
Forbidden: a default on any value that has no safe production value A default on DATABASE_URL or an API key converts a failed deploy into a running app pointed at the wrong thing, or at nothing. That is strictly worse than crashing.
Forbidden: reading .env in production Precedence between file and environment has had real bugs, and a file that exists on one host and not another produces environment-specific behaviour nobody can reproduce. Ship real environment variables or mounted secret files.
Forbidden: a single underscore as the nested delimiter It mis-assigns any field whose own name contains an underscore, and tries to JSON-parse ordinary variables like USER. Use __.
Empty means unset FOO= is one blank line in a compose file or a CI variable never filled in. Treated as a value it overrides your default with "", and "" is truthy in every string check you will write.
Unknown keys are an error extra="forbid". A misspelled key is not a missing feature, it is a value silently stuck at its default, and nothing will ever tell you.
Secrets are a secret type, not str Repr masking is what stops a settings object reaching a log aggregator intact. It is not encryption and does not pretend to be.
Settings are frozen A mutable settings object invites request-scoped mutation, which makes behaviour depend on request order. If a value must change at runtime it is not configuration.
Cross-field rules go in a model validator "Production may not use * origins" cannot be expressed as a field type, and rules of that shape are where the costly misconfigurations are.
Every key appears in a committed .env.example It is the only artefact that tells a new deployer what to supply. Generate it from the Settings class in CI so it cannot drift.
Fail before binding the port Validating in a startup hook means the health check may pass, the load balancer may route, and only then does it fail. Import-time is earlier than every one of those.

6. Data contracts

class Settings(BaseSettings):
    database_url: PostgresDsn                  # not str — a malformed URL fails here,
                                               # not on first connection
    payment_api_key: SecretStr                 # not str — repr is masked
    request_timeout_seconds: float = Field(gt=0, le=60)
                                               # not float — float() happily accepts
                                               # "0" and "-1", and a zero timeout
                                               # means every request fails at once
    environment: Literal["development", "staging", "production"]
                                               # not str — the set is closed and known

The constraint belongs in the type, not in a comment and not in a check at the call site. A float with gt=0 cannot reach the HTTP client as zero; a float documented as "must be positive" reaches it as zero the first time someone sets REQUEST_TIMEOUT_SECONDS=0 to "disable the timeout for debugging" — and every outbound call then fails instantly, which reads as the third party being down.

7. Build order

  1. One Settings class with the two or three values that have no safe default. Import it in main.py at module level. Run with the variables unset and confirm the process exits non-zero and names every missing field at once.
  2. Add .env for development and .env.example committed. Confirm a real environment variable beats the file.
  3. Tighten the types — DSN, SecretStr, Literal, bounded numbers — and confirm each rejects a bad value at startup rather than at use.
  4. Add the cross-field validators. Set ENVIRONMENT=production with a development-shaped config and confirm it refuses to start.
  5. Wire the provider as a framework dependency and the test override. Prove a test can run against different settings without touching the environment.
  6. Add the CI check that os.environ appears in one file only, and that .env.example lists every field.

Step 1 before step 3 on purpose: the failure this blueprint exists to prevent is "it started without the value", and that has to be demonstrated failing and then passing before any effort goes into type refinement.

10. Failure modes

Symptom Cause Fix
App runs for two hours, then one endpoint 500s with a connection error to None A default of None or "" on a value with no safe default; the app started happily and failed on first use Remove the default. A required field with no default is the whole mechanism.
A config value is mysteriously "" in one environment and correct elsewhere The variable is declared but empty — a blank compose line, or a CI secret that was never filled in. Empty is a value, not an absence env_ignore_empty=True, and assert non-empty in the type where blank is never valid
A nested setting silently keeps its default no matter what you export Single-underscore nested delimiter, and the field name contains an underscore — the variable is being assigned to a different field Use __ as the delimiter
Startup crashes with a JSON parse error naming a variable you never set, like USER Single-underscore delimiter made pydantic treat an ordinary shell variable as a nested submodel and try to parse it as JSON Use __, and set env_prefix so only your own variables are considered
A value from .env wins over the real environment variable in production An .env file present on the host, combined with Field(validation_alias=...) where the documented precedence has been reported to invert Do not ship .env to production at all — that removes the whole class. Verify the alias behaviour in your installed version if you must use aliases.
An API key appears in an error-tracking payload The settings object was logged, or included in an exception context, as a plain str SecretStr, and never log the settings object even so
Tests pass alone and fail together, or the second test sees the first test's config lru_cache on the provider is process-global and was never cleared between tests cache_clear() in the fixture teardown, and override the dependency rather than mutating the environment
A misspelled variable name has no effect and no error Extra keys ignored by default; the field kept its default value extra="forbid"

11. Definition of done

  • Starting the process with a required variable unset exits non-zero, before any port is bound, and the error names the field
  • Starting with several required variables unset reports all of them in one error, not the first
  • A malformed value of a typed field — a non-URL DSN, a negative timeout, an unknown environment name — fails at startup with the field named
  • A cross-field rule is enforced: a production-marked config with a development-shaped value refuses to start, covered by a test
  • grep -rn "os.environ\|os.getenv" over the application source returns hits in exactly one file, and CI fails if that changes
  • An unknown or misspelled configuration key causes a startup error rather than being ignored
  • Every secret-typed field renders masked in repr(), verified by a test that asserts the raw value is absent from the formatted settings object
  • .env.example contains every field in the Settings class, verified by a test or a CI step rather than by review
  • .env is git-ignored, and no .env is present in the production image or host
  • A test can run the application against different settings without setting process environment variables
  • Running the full test suite in a random order produces the same results as running it in file order
