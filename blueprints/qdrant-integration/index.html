Qdrant Vector Search with Filters

Qdrant vector search with filters: collection design, payload indexing, filterable HNSW and quantisation for large filtered workloads.

medium2–4 daysVerified 2026-08-19
Vector search
Read it on GitHub ↗ Back to the catalogue

A dedicated vector store: one collection with tenants separated by an indexed payload key rather than by collection, batch upload that does not outrun the server, filtered search that stays accurate, and snapshots you have restored at least once.

Complexity: medium · Typical build: 2–4 days · Verified: 2026-08-19 (re-check after ~90 days)

Examples in: Python. The architecture is language-agnostic: sections 5, 10 and 11 hold wherever you build this. Section 4 is illustrative — if your project is in another language, your agent translates the idioms rather than importing them, and nothing is lost. The collection design, tenancy and upload-rate concerns transfer to any dedicated vector store; the filtering behaviour described here is specific to this one and is the reason to choose it.

Use when: the corpus is large, search is filtered by attributes on almost every query, and you want a store built for that rather than a general database extended to do it.

Not for: a corpus that comfortably fits in the database you already run. A second stateful service means a second backup story, a second upgrade path and a second thing to be woken up for, and below a few million vectors that cost usually buys nothing. Also not a source of truth: it holds derived data, and treating it as the only copy of anything is how a re-index becomes a data-loss incident.

1. The two decisions that are expensive to reverse

Most of this is straightforward. Two choices are made on day one and cost a full re-index to change.

The obvious setup This one
A collection per tenant, because it feels like isolation One collection, tenants separated by an indexed payload key
Payload fields filtered without being indexed Every filtered field indexed, declared with the schema
Upload as fast as the loop can go Batched, with the server's own signal used as the brake
Snapshots configured and never restored A restore performed once, deliberately, and timed

The first row is the one that looks safest and is not. A collection carries real per-collection overhead, and hosted deployments cap how many you may have — a limit measured in the low thousands, which is a lot until the day it is not. Worse, the migration away is not a configuration change: it is re-uploading everything. One collection with a tenant key in the payload is the design that scales, and the isolation it gives is a filter, which is exactly as strong as your discipline about applying it.

The second row is what separates this store from bolting vectors onto a general database, and it is the strongest reason to be here at all. Approximate search with a filter can be done two ways. The common way runs the search first and discards non-matching results afterwards — which means a selective filter throws away most of what the index found, and the matches you wanted may never have been candidates. This store instead builds the graph so that filtered subsets stay traversable, keeping matching neighbours reachable during the search rather than removing them after it. That property is the reason to pay for a second service — and it only applies to fields you actually indexed.

The rule the diagram encodes: the arrow to another tenant is blocked by a filter, not by a wall. One collection means isolation is something the query does, every time. A query that forgets the filter is not rejected by anything — which is why §4 puts the filter below the application code rather than beside it.

3. Project structure

app/vectors/
├── schema.py      the collection definition and every payload index
├── client.py      the client, its timeouts and its retry policy
├── upload.py      batching, with the server's backpressure honoured
└── search.py      search, where the tenant filter is applied — the only entry point
ops/
└── restore.md     the restore procedure, with the date it was last practised

One rule: nothing calls the client's search directly. Every query goes through one function that takes a tenant and applies the filter itself. With tenancy implemented as a filter, a forgotten filter is a data-disclosure bug that looks like ordinary code, and the only reliable defence is that there is no way to write the query without it.

4. Reference implementation

# app/vectors/schema.py
from qdrant_client import models

COLLECTION = "documents"


async def ensure_collection(client) -> None:
    await client.create_collection(
        collection_name=COLLECTION,
        vectors_config=models.VectorParams(
            size=1536,
            # Must match what the embedding model was trained for. Cosine for
            # normalised embeddings, dot product where magnitude carries meaning.
            # The wrong choice does not error — it ranks badly, which is much
            # harder to notice than a failure.
            distance=models.Distance.COSINE,
        ),
        # Quantization trades a little accuracy for a large drop in memory. Worth
        # it above a few million vectors; premature below that, where it costs
        # recall for memory you were not short of.
        quantization_config=models.ScalarQuantization(
            scalar=models.ScalarQuantizationConfig(type=models.ScalarType.INT8,
                                                   always_ram=True)),
    )

    # The tenant key. This flag is not decoration: it tells the server to keep one
    # tenant's vectors together on disk, so a filtered search reads sequentially
    # instead of seeking across the whole file. On a large collection that is the
    # difference between a fast filtered query and a slow one.
    await client.create_payload_index(
        COLLECTION, field_name="tenant_id",
        field_schema=models.KeywordIndexParams(type="keyword", is_tenant=True))

    # Every other field that will ever appear in a filter. Filtering on an
    # unindexed field still works, which is the trap — it is simply slow, and
    # adding the index later means the collection is re-optimised.
    for field, schema in (("document_type", "keyword"), ("created_at", "datetime")):
        await client.create_payload_index(COLLECTION, field_name=field,
                                          field_schema=schema)

# app/vectors/upload.py
async def upload(client, points: list[models.PointStruct]) -> None:
    for batch in chunked(points, BATCH_SIZE):
        # wait=False returns as soon as the write is accepted rather than after it
        # is indexed. It is much faster and it means "uploaded" does not yet mean
        # "searchable" — so a test that uploads and immediately searches will be
        # flaky, and it will be blamed on the search.
        await client.upsert(COLLECTION, points=batch, wait=False)
        await _respect_backpressure(client)


async def _respect_backpressure(client) -> None:
    # Uploading as fast as the loop allows outruns indexing: the queue grows, the
    # server slows, and eventually it rejects writes. The server's own optimiser
    # status is the signal to pause on — a fixed sleep is either too slow all the
    # time or too fast exactly when it matters.
    while (await client.get_collection(COLLECTION)).status != models.CollectionStatus.GREEN:
        await asyncio.sleep(1)

# app/vectors/search.py
async def search(client, query_vector, tenant_id: str, k: int = 10,
                 document_type: str | None = None) -> list[Hit]:
    """The only way to query this collection.

    The tenant filter is built here, not passed in. With one collection, tenancy
    is a filter rather than a boundary — so a caller that could omit it is a
    disclosure bug waiting for a distracted afternoon.
    """
    must = [models.FieldCondition(key="tenant_id",
                                 match=models.MatchValue(value=tenant_id))]
    if document_type:
        must.append(models.FieldCondition(key="document_type",
                                          match=models.MatchValue(value=document_type)))

    return await client.query_points(
        COLLECTION, query=query_vector, limit=k,
        query_filter=models.Filter(must=must),
        # The filter is resolved through the payload index and the graph traversal
        # stays inside the matching subset, so a selective filter does not cost the
        # matches. That behaviour is the reason this store is worth a second
        # service — and it only applies to fields that were indexed.
        with_payload=True,
        search_params=models.SearchParams(hnsw_ef=max(64, k * 8)),
    )

# tests/test_tenancy.py
async def test_a_tenant_cannot_reach_another_tenants_points(client):
    # The one test that must exist. Everything else here is performance; this is
    # the difference between a filter and a promise.
    await upload(client, [point(tenant="a", text="secret"), point(tenant="b", text="other")])
    hits = await search(client, embed("secret"), tenant_id="b", k=10)
    assert all(h.payload["tenant_id"] == "b" for h in hits)

5. Golden-standard rules

Rule Why
Forbidden: a collection per tenant Each carries real overhead and hosted deployments cap the count. Migrating away is a full re-upload, not a setting.
Forbidden: a search path that does not take a tenant With one collection, isolation is a filter applied every time. The defence is that the query cannot be written without it.
Forbidden: filtering on a field with no payload index It works, which is the trap — it is simply slow, and adding the index later re-optimises the collection.
Forbidden: treating this store as a source of truth It holds derived data. Without a rebuild path, a re-index is a data-loss incident.
Forbidden: snapshots that have never been restored An untested restore is a plan. The first execution should not be during an outage.
The distance metric matches what the model was trained for The wrong one does not error; it ranks badly, which is far harder to notice.
Uploads are batched and paced by the server's own signal Uploading faster than indexing grows a queue until writes are rejected. A fixed sleep is wrong in both directions.
Accepted is not the same as searchable Fast uploads return before indexing finishes, so a test that uploads then searches is flaky and the search gets blamed.
Quantization is enabled when memory demands it, not by default It trades recall for memory, and below a few million vectors it costs the first without needing the second.
Point ids are derived from the source, not generated Otherwise re-ingesting the same document duplicates it, and nothing reports the duplicate.
The candidate list size is set per request, from k The default is tuned for nothing in particular, and it is the main quality dial at query time.
Recall is measured, not inferred from the absence of complaints Approximate search always returns k results quickly; whether they are the right ones is a separate question.

6. Data contracts

PointStruct(
    id=stable_id(document_id, chunk_index),   # derived, so re-ingest replaces
    vector=[...],
    payload={
        "tenant_id": "acme",        # indexed, and required on every search
        "document_id": 42,
        "chunk_index": 3,
        "document_type": "policy",  # indexed, because it is filtered
        "text": "...",              # returned with the hit, so no second lookup
        "embedding_model": "...",   # which model produced this vector
    },
)

The identifier is the contract that makes ingestion repeatable. Derived from the document and the chunk position, re-ingesting a changed document overwrites its points; generated randomly, it inserts a second copy of everything and retrieval degrades quietly as duplicates crowd the results.

Storing the text in the payload is a deliberate denormalisation. The alternative is a second lookup in the source database for every hit, on the latency-sensitive path, and the storage cost is small against that.

7. Build order

  1. Collection, one point, one search. Confirm the distance metric and the dimensionality against the model before anything is loaded.
  2. The payload indexes, including the tenant key, declared with the schema so they are never a later addition.
  3. The tenancy test, written before any real data exists. It is the one that must never fail, and it is cheapest to write now.
  4. Batched upload with backpressure, and a load of realistic size — the point where naive uploading first shows itself.
  5. Filtered search with recall measured, both filtered and unfiltered.
  6. Snapshot and a practised restore, timed and written down.
  7. Quantization and on-disk settings, only if the measurements from step 5 call for them.

Step 3 before real data because the tenancy test is the only one here whose failure is a disclosure rather than a slowdown, and writing it against an empty collection takes minutes.

10. Failure modes

Symptom Cause Fix
One tenant sees another's documents A search path without the tenant filter One entry point that builds the filter itself; the test from §7 step 3
Filtered searches are slow while unfiltered ones are fast The filtered field has no payload index Index every field that appears in a filter
Creating a new tenant fails A collection per tenant hit the deployment's collection cap One collection with a tenant key; migrating means re-uploading
Results are plausible and ranking is poor The distance metric does not match what the model was trained for Match it; this does not error, so it must be checked
A test uploads and immediately searches, and fails intermittently The write was accepted but not yet indexed Wait for indexing in tests, or use the synchronous write path there
Writes start being rejected during a bulk load Upload outran indexing and the queue grew until the server pushed back Batch, and pace on the server's status rather than on a fixed sleep
Retrieval quality degrades after a re-ingest Point ids were generated, so the corpus now holds two copies of everything Derive ids from the document and chunk position
Memory grows until the process is killed Full-precision vectors held in memory past what the host has Enable quantization or on-disk storage, then re-measure recall
Recall dropped after enabling quantization and nobody noticed It trades accuracy for memory and nothing reports the trade Measure recall before and after, on the same question set
The store was lost and rebuilding took days No rebuild path from the source of truth Keep ingestion rerunnable; this store holds derived data only
The restore did not work when it was needed Snapshots were configured and never tested Practise a restore; record the date and the duration
A client upgrade broke with a serialisation error Client and server versions are independent and drifted Pin both; check compatibility before upgrading either

11. Definition of done

  • A test asserts that a search for one tenant never returns another tenant's points
  • No code path calls the client's search directly; every query goes through the tenant-aware function, checked by grep in CI
  • Every field used in a filter has a payload index, verified against the live collection schema rather than the code
  • The tenant field is indexed with the tenant-oriented option, verified against the live schema
  • The distance metric matches the embedding model's, with the model named in a comment beside it
  • Recall at 10 is measured against exact search, filtered and unfiltered, and both numbers are recorded
  • Re-ingesting an unchanged document leaves the point count unchanged, covered by a test
  • A bulk load of realistic size completes with no rejected writes, and the pacing uses the server's status
  • A snapshot has been restored to an empty instance, the duration recorded, and the date noted in the runbook
  • The store can be rebuilt from the source of truth by rerunning ingestion, demonstrated once end to end
  • Client and server versions are pinned, and their compatibility is recorded
  • If quantization is enabled, recall was measured before and after and both numbers are recorded
