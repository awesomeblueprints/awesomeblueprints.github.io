Integration Tests with Real Dependencies

Integration tests with real dependencies: throwaway databases, containers, fixtures, isolation between tests and a suite that stays fast.

medium2–4 daysVerified 2026-08-19
Testing
Read it on GitHub ↗ Back to the catalogue

Tests against a real database and real infrastructure instead of mocks, isolated by a transaction that is rolled back rather than by cleanup code, fast enough to run on every change, and honest about the one thing mocks can never tell you.

Complexity: medium · Typical build: 2–4 days · Verified: 2026-08-19 (re-check after ~90 days)

Examples in: Python, with pytest, SQLAlchemy and PostgreSQL. The architecture is language-agnostic: sections 5, 10 and 11 hold wherever you build this. Section 4 is illustrative — if your project is in another language, your agent translates the idioms rather than importing them, and nothing is lost. The rollback-isolation pattern exists as use DatabaseTransactions in Laravel, Ecto.Sandbox in Elixir, and transactional fixtures in Rails — the mechanism differs, the guarantee does not.

Use when: the interesting failures are in the seams — a query that is wrong, a constraint that fires, a migration that does not apply, a serialisation that differs from what the client expects — and a mocked dependency would have agreed with the code either way.

Not for: logic that has no dependency. Running pure functions against a database container makes a ten-millisecond test a two-second one and proves nothing extra. Also not a replacement for production monitoring: these tests cover the inputs you thought of.

1. What a mock cannot tell you

A mocked repository returns what you told it to return. That makes it useful for testing the caller and useless for testing the assumption.

Mocked dependencies Real dependencies
The query is never executed, so a wrong join or a missing index is invisible The query runs, against the real planner, on the real schema
Constraints do not exist, so a unique violation your code cannot handle never fires The constraint fires, and the code either handles it or fails the test
Migrations are not applied, so a model and its table can disagree indefinitely The schema comes from migrations, so drift fails a test rather than a deploy
Types are whatever Python made up The driver's real round-trip — timestamps with time zones, decimals, JSON, nulls

The third row is the one that catches teams with good test coverage. Tests built on create_all from the models never execute the migrations, so a migration that does not apply cleanly is discovered on deploy. Create the test schema by running the migrations, and that entire class of failure moves from production to CI.

The isolation problem is the other half. The obvious approach is to delete rows afterwards, and it fails in three ways: it is slow, it is incomplete the moment someone adds a table, and a failing test skips its own cleanup and poisons every test after it. Wrapping each test in a transaction and rolling it back is faster, complete by construction, and unaffected by a test that raises.

The rule the diagram encodes: the application under test uses the test's own transaction. If the app opens its own connection, nothing the test does is visible to it and nothing it writes is rolled back — which is why the session must be injected rather than imported.

3. Project structure

tests/
├── integration/
│   ├── conftest.py     containers, migrations, the transactional session, the client
│   ├── test_orders_api.py
│   └── cassettes/      recorded third-party responses, committed
└── unit/               fast, no dependencies

One rule: containers start once per session, transactions per test. Starting a database per test is correct and unusably slow; sharing a database without transactional isolation is fast and wrong. The split is what makes the suite both.

4. Reference implementation

# tests/integration/conftest.py
import pytest
from alembic import command
from alembic.config import Config
from httpx import ASGITransport, AsyncClient
from sqlalchemy.ext.asyncio import AsyncSession, async_sessionmaker, create_async_engine
from testcontainers.postgres import PostgresContainer
from app.main import app
from app.db.session import get_session


@pytest.fixture(scope="session")
def postgres():
    # Once for the whole run. Per-test containers are correct and take about a
    # second each, which turns a 200-test suite into four minutes nobody runs.
    with PostgresContainer("postgres:17-alpine") as pg:
        yield pg


@pytest.fixture(scope="session")
async def engine(postgres):
    url = postgres.get_connection_url().replace("psycopg2", "asyncpg")
    eng = create_async_engine(url)

    # Migrations, not create_all. create_all builds the schema the models describe;
    # migrations build the schema production will actually have. When those differ,
    # create_all hides it until deploy — which is exactly the failure worth catching.
    cfg = Config("alembic.ini")
    cfg.set_main_option("sqlalchemy.url", url)
    async with eng.begin() as conn:
        await conn.run_sync(lambda c: command.upgrade(cfg, "head"))

    yield eng
    await eng.dispose()


@pytest.fixture
async def db_session(engine):
    """One transaction per test, rolled back at the end.

    Rollback rather than cleanup: it is faster, it is complete by construction —
    a new table needs no new teardown — and it survives a failing test, which
    skips its own cleanup and would otherwise poison every test after it.
    """
    async with engine.connect() as connection:
        outer = await connection.begin()
        # The session joins the already-open transaction instead of starting its
        # own. A commit inside the application code then only releases a savepoint,
        # so the code under test behaves exactly as in production while the outer
        # transaction still holds everything.
        session = async_sessionmaker(bind=connection, expire_on_commit=False)()
        nested = await connection.begin_nested()

        @event.listens_for(session.sync_session, "after_transaction_end")
        def restart_savepoint(sess, trans):
            # The application commits; that ends the savepoint. Reopen it so the
            # next statement is still inside the outer transaction.
            nonlocal nested
            if not nested.is_active:
                nested = connection.sync_connection.begin_nested()

        yield session
        await session.close()
        await outer.rollback()          # nothing the test did survives


@pytest.fixture
async def client(db_session):
    # The application must use the test's session, or its writes escape the
    # transaction and its reads cannot see the test's fixtures.
    app.dependency_overrides[get_session] = lambda: db_session
    transport = ASGITransport(app=app)   # in-process: no port, no listener, no flakiness
    async with AsyncClient(transport=transport, base_url="http://test") as c:
        yield c
    app.dependency_overrides.clear()


@pytest.fixture
async def authed_client(client, db_session):
    user = await create_user(db_session, email="t@example.com", scopes=["orders:write"])
    client.headers["Authorization"] = f"Bearer {create_access_token(str(user.id), user.scopes)}"
    return client

# tests/integration/test_orders_api.py
import pytest


async def test_duplicate_order_reference_is_rejected_by_the_database(authed_client, db_session):
    # The point of an integration test: this asserts the unique constraint exists
    # and that the code handles its violation. A mocked repository would agree with
    # whatever the code believed, including that the constraint was there.
    await authed_client.post("/api/v1/orders", json={"reference": "R-1", "quantity": 1})
    second = await authed_client.post("/api/v1/orders", json={"reference": "R-1", "quantity": 1})
    assert second.status_code == 409


async def test_totals_survive_the_database_round_trip(authed_client):
    # Decimals, timestamps and JSON are where the driver's real behaviour differs
    # from what a mock returns. This is cheap to assert and catches a whole class.
    created = await authed_client.post("/api/v1/orders", json={"quantity": 3})
    fetched = await authed_client.get(f"/api/v1/orders/{created.json()['id']}")
    assert fetched.json()["total"] == created.json()["total"]


@pytest.mark.slow
async def test_payment_capture_uses_the_recorded_provider_response(authed_client, vcr_cassette):
    # Recorded once against the real provider, replayed thereafter. The suite stays
    # deterministic and offline; the recording is refreshed deliberately, and that
    # refresh is when a provider's contract change is discovered.
    response = await authed_client.post("/api/v1/orders/1/capture")
    assert response.status_code == 200

5. Golden-standard rules

Rule Why
Forbidden: creating the test schema from the models instead of the migrations It hides every migration that does not apply cleanly until the deploy that runs it.
Forbidden: cleaning up by deleting rows Slow, incomplete the moment a table is added, and skipped entirely by a failing test — which then poisons everything after it.
Forbidden: the application opening its own connection during a test Its writes escape the test's transaction and its reads cannot see the test's data. Inject the session.
Forbidden: a live third-party call in the suite It makes the suite fail when someone else's service is down, and rate-limits you for having tests. Record and replay.
Forbidden: tests sharing a database without transactional isolation They pass alone, fail together, and the failure depends on order and timing.
Containers start once per session; transactions are per test Per-test containers are correct and turn a two-minute suite into a twenty-minute one.
Every test creates the data it needs Shared seed data becomes an implicit precondition, and changing it breaks tests that never mentioned it.
Integration tests are marked and separable Contributors need a fast default run; CI runs everything. If both are the same command, one of the two constituencies loses.
The API is exercised in process, not over a port A real listener adds a bind, a race and a flake, and proves nothing extra about the code.
Authenticated requests use the real token path A test client that bypasses authentication cannot tell you the route was protected.
Recordings of external services are committed and refreshed deliberately The refresh is when a provider's contract change is discovered — on your schedule rather than during an incident.
The suite has a stated time budget, enforced in CI Without a number, it grows until it is skipped, and a skipped suite is worse than none because it looks like coverage.

6. Data contracts

What an integration test may assume:

schema      built by running the migrations, identical to production's path
isolation   an open transaction; everything the test writes is rolled back
visibility  the app and the test share one transaction, so each sees the other
external    no live third-party calls; recorded responses only
order       arbitrary — tests must pass in any order and in parallel

The visibility guarantee is what separates this from "a test with a database nearby". If the application cannot see rows the test inserted, every test starts with an HTTP call to create its own fixtures, and the suite becomes slow for a reason that looks like thoroughness.

7. Build order

  1. One container, migrations applied, one test that queries the database. No isolation yet — prove the schema comes up from migrations first.
  2. The transactional fixture, then a test that writes a row and a second that asserts the row is gone. This is the guarantee everything else rests on.
  3. The in-process client with the session override, and a test asserting the application sees a row the test inserted.
  4. The authenticated client, using the real token path.
  5. Tests for the seams — constraint violations, migrations, round-trip types, the queries with joins.
  6. Record and replay for external services, with recordings committed.
  7. The marker split and the CI budget, then run the suite in parallel and fix what breaks.

Step 2 immediately after step 1 because every later test is only as trustworthy as that rollback. Two tests are enough to prove it and cheap to write now.

10. Failure modes

Symptom Cause Fix
A migration fails on deploy although the tests were green The test schema was built with create_all, so the migrations never ran Apply migrations to build the test database
Tests pass alone and fail together Shared state without transactional isolation, or a leftover from a failing test's skipped cleanup Wrap each test in a transaction and roll it back
The application cannot see rows the test inserted The app opened its own connection instead of using the test's session Override the session dependency with the test's
Data written by the app survives the test The app's commit ended the outer transaction rather than a savepoint Join the external transaction and restart the savepoint after each commit
The suite fails when a third-party service is down Tests call it live Record and replay
The suite takes twenty minutes A container is started per test, or every test creates its fixtures over HTTP Session-scoped containers; create fixtures directly against the session
A test occasionally fails on a port bind or a connection reset The app is served on a real port during tests Use an in-process transport
Tests pass in CI and the endpoint is unprotected in production The test client bypasses authentication Authenticate through the real token path
A provider changes its API and nobody notices for months Recordings are never refreshed Refresh them on a schedule and treat the diff as a review item
The suite is green but the slowest ten tests take most of the time Setup is repeated per test rather than shared Move invariant setup to session scope; keep only the transaction per test

11. Definition of done

  • The test schema is created by running the migrations, verified by a test that asserts the alembic version table is at head
  • A test writes a row and a following test asserts it is absent, proving rollback isolation
  • The application sees data the test inserted directly, covered by a test
  • Data written by the application during a test is absent after it, covered by a test
  • The suite passes with the order shuffled and with parallel workers
  • No test performs a live third-party HTTP call, enforced by blocking unrecorded requests
  • Authenticated requests go through the real token path, and a test asserts an unauthenticated request to a protected route is rejected
  • Integration tests are marked and excluded from the default local run
  • The suite runs in CI within its stated budget, and CI fails if it exceeds it
  • Containers start once per session, verified by the run log
  • At least one test asserts a database constraint fires and the application handles it
  • At least one test asserts a decimal and a timezone-aware timestamp survive the round trip unchanged
