LLM Tool Design

LLM tool design: naming, parameters, descriptions and results a model can actually use, and the failures caused by tools that read badly.

low2–4 daysVerified 2026-08-19
Agents
Read it on GitHub ↗ Back to the catalogue

The name, description, argument schema and return shape of each tool an agent can call. This is the interface the model programs against, and it is written for a reader with no memory, no debugger and one attempt per call.

Complexity: low · Typical build: 2–4 days · Verified: 2026-08-19 (re-check after ~90 days)

Examples in: Python with Pydantic. Only §4 and §6 are language-specific — the rules, failure modes and definition of done hold anywhere, and your agent translates the code.

Use when: an agent has more than one tool, and it picks the wrong one, sends malformed arguments, or misreads what came back. Also whenever tool schemas, descriptions or return shapes are being written or reworked.

Not for: a single-tool agent, or a call site where your code decides what runs and with which arguments. Nothing here applies when the model is not the one choosing.

⚙️ INSTRUCTIONS FOR THE AI — READ BEFORE WRITING ANY CODE

Do not start coding.

Step 1 — Refresh. Search the web and verify: the JSON Schema subset the provider in use actually enforces — several accept a schema and silently ignore parts of it, and additionalProperties, oneOf and nested $ref are the usual casualties; whether the provider supports strict schema adherence and what it costs; the current cap on tool count and total schema size. Report what you verified and where your assumptions were wrong.

Step 2 — Read the project, then audit what exists. Find every tool the agent already has, and read the descriptions rather than the handlers. Collect: names, what each description says about when not to use it, whether closed-set fields are enums, and what a typical result looks like in bytes.

Then audit what exists. Walk §11 item by item, marking each already true, partly true or absent with the file that decides it. Report that before proposing anything.

Assume the project is right until it demonstrably is not. Code that satisfies an item stays, whatever its shape — §4 is illustrative, and its idioms translate into this project's language. Replacing something that works needs a one-line reason. Never delete a working path to make room for the version written here. If nothing relevant exists, say so and use §3.

The same applies to language. §4 is illustrative: translate its idioms into this project's language and libraries rather than importing its shape. §11 is what has to become true — not the syntax it happens to be written in.

Step 3 — Write a plan for the gap only, and get it approved. List: which tools get a rewritten description, which arguments become enums, which responses get a size budget, and which tools should be merged or dropped. Order by how often each is chosen wrongly today, not by how easy it is to change.

In that plan, include a ## Proposed stack section. Do not ask an open question. Propose whether schemas are generated from typed models or written by hand — with a one-line reason, the versions verified in Step 1, and what would change the decision. Ask the user to confirm once.

Name what you are adding, leaving alone, and changing. Touch nothing else.

1. Why "the agent is dumb" is usually a bad interface

Most reports of a stupid agent are interface bugs. Two descriptions overlap, so the model picks whichever came first. A tool returns two hundred kilobytes of JSON, so the next turn has no room to think. A mutation returns {"ok": true}, so the model cannot tell whether anything changed and does it again.

In each case the model is reasoning correctly over a bad interface.

Endpoint-shaped tools Task-shaped tools
What a tool maps to One route in your service One thing a user wants
Calls per user request Four, chained by id One
Chances to fail Four One
Description written from The API reference The words users type
Result Whatever the endpoint returns What the model needs to decide next

This is the cheapest work in the whole subject: no runtime cost, no new dependency, and the improvement lands on every task at once. It is also the work that a stronger model does not do for you — a better reader still cannot tell two identical descriptions apart.

3. Project structure

tools/
├── registry.py        # name -> (schema, handler). One place a tool is declared.
├── schemas.py         # typed input models; schemas are generated, never hand-written twice
├── format.py          # result -> bounded text. One formatter per result shape.
├── errors.py          # exception class -> instruction for the model
└── impl/              # one file per tool. Plain functions, no agent imports.

The rule that keeps this maintainable: the schema the model sees is generated from the same type the handler takes. Hand-written schemas drift from handlers silently, and the symptom is an argument error the model cannot fix because the documentation it was given is a lie.

4. Reference implementation

The schema is the documentation. Every field says its format, its units and where the value comes from:

class SearchOrdersInput(BaseModel):
    """Search orders. Filters are ANDed."""
    model_config = {"extra": "forbid"}      # -> additionalProperties: false

    customer_email: str | None = Field(
        None, description="Exact match, lowercase. Get it from get_customer if unknown.")
    status: Literal["pending", "shipped", "delivered", "cancelled"] | None = Field(
        None, description="Order status. Omit for any status.")
    created_after: str | None = Field(
        None, description="ISO-8601 date, e.g. 2026-01-31. Inclusive, UTC.")
    limit: int = Field(20, ge=1, le=100, description="Max rows returned. Default 20.")

The description is a selection policy, not a summary. Four lines, in this order:

<One line: what it does.>
Use when <situation, in the words a user would use>. Returns <shape of result>.
Do not use for <the adjacent case> - use <other_tool> instead.
<Any precondition: "Requires a customer_id from get_customer.">

The same tool, wrong and right:

# WRONG - mirrors an endpoint, dumps whatever came back, says nothing on failure
def query_db(sql: str) -> str:
    """Run SQL."""
    return json.dumps(conn.execute(sql).fetchall())      # 200 KB of UUIDs and nulls

# RIGHT - task-shaped, bounded, and every exit tells the model what to do next
def search_orders(customer_email=None, status=None, created_after=None, limit=20) -> str:
    """Search orders by customer, status and date.

    Use when the user asks about order history, refunds or shipping status.
    Returns a compact table of up to `limit` rows plus a total count.
    Do not use to change an order - use update_order_status.
    """
    rows, total = repo.search(customer_email, status, created_after, limit)

    # "No results" is a dead end. Say how to get unstuck instead.
    if total == 0:
        return ("No orders matched. Check the email with get_customer, "
                "or widen the search by removing `status`.")

    header = "order_id | date | status | total_usd | items"
    lines = [f"{r.id} | {r.created_at:%Y-%m-%d} | {r.status:9} | "
             f"{r.total_usd:>8.2f} | {r.item_summary}" for r in rows]
    footer = f"\nShowing {len(rows)} of {total}."
    if total > len(rows):
        footer += " Narrow with created_after to see the rest."
    return header + "\n" + "\n".join(lines) + footer

Errors are instructions. Every one answers two questions: retry or not, and change what:

ERROR_HINTS = {
    "NotFound":    "No such {entity}. Use list_{entity}s to see valid ids.",
    "Forbidden":   "This account lacks permission. Ask the user; do not retry.",
    "RateLimited": "Rate limited. Wait before retrying, and batch your requests.",
    "Validation":  "{detail} Fix the argument and call again.",
}

Mutations return the resulting state, because a model that cannot observe its own effect cannot distinguish success from silence — and will repeat the call:

# not "ok"
return f"order_2026_00412: status pending -> shipped, tracking DHL-77Q4A2."

5. Golden-standard rules

Rule Why
One tool per user task, not per API endpoint Four chained calls are four chances to fail and four descriptions to confuse
Every description says when not to use it, and names the tool to use instead Positive-only descriptions produce confident wrong matches
Every closed set is an enum, never a free string Removes an entire class of argument error at zero cost
additionalProperties: false on every schema, required fields declared Otherwise invented arguments arrive silently and are ignored
Every field description states format, units and where to obtain the value The model guesses otherwise, and guesses consistently wrongly
The schema is generated from the type the handler takes Hand-written copies drift, and the model is blamed for following stale documentation
Every response is bounded, and says what was left out An unbounded result eats the context the next decision needs
A truncated or paginated response carries an explicit way to continue Silently dropped rows are read as "that was all of them"
Mutations return the resulting observable state A model that cannot see the effect repeats the call
Every error says whether to retry and what to change An error with neither is a dead end the model retries blindly
No stack traces, no bare HTTP codes They describe your internals and suggest nothing to do differently
Identifiers are human-readable and stable order_2026_00412 can be reasoned about; a raw UUID cannot
Tool names are unique across every connected server Two search tools make selection a coin flip
Above roughly fifteen tools, split the agent Selection accuracy falls off, and no wording of the descriptions recovers it
No execute or misc catch-all tool It absorbs every ambiguous call and hides the real gap in the toolset

6. Data contracts

class ToolSpec(BaseModel):
    name: str            # ^[a-z0-9_]{1,64}$, namespaced: crm_search_orders
    description: str     # what / use when / do not use for / preconditions
    input_schema: dict   # generated; additionalProperties: false
    mutating: bool       # true => must return observable state
    max_result_tokens: int = 2_000

class ToolOutcome(BaseModel):
    content: str         # always a string; you serialise structured data yourself
    is_error: bool = False
    elided: bool = False # true => content states what was left out and how to get it

Result-size budget, as a starting point: 2 000 tokens per call, 20 rows by default. Set the default limit to what a typical request needs, not to what the backend can return.

7. Build order

  1. Inventory. List every tool with its description and a real result, in bytes. The problems are usually visible before you measure anything.
  2. A labelled set of at least fifty requests, each tagged with the tool that should be chosen. Without it you cannot tell an improvement from a change.
  3. Descriptions. Rewrite to the four-line template. Add the "do not use for" clause to both tools in every confusable pair.
  4. Schemas. Enums for closed sets, additionalProperties: false, per-field format and units. Generate them from the handler's own types.
  5. Response formatting. One formatter per result shape, with a size budget and an explicit elision marker.
  6. Error mapping. Every exception class gets a sentence that says retry-or-not and change-what.
  7. Mutations start returning the resulting state.
  8. Re-run the labelled set. Record selection accuracy and argument error rate as the numbers you defend from now on.
  9. Merge or delete. Any tool never chosen correctly is either badly described or should not exist.

9. Metrics

Metric Target
Tool selection accuracy on the labelled set ≥ 95%; below 90% is an interface bug, not a model problem
Argument validation error rate < 2%; above 5% the schema demands something the model cannot know
Tokens per tool result, p95 < 2 000; above 5 000 one tool is eating the context
Calls per successfully completed task, p50 ≤ 4; above 8 the tools are endpoint-shaped
Repeated identical calls < 1%; above that, results are not observable enough
Tools never chosen in a week of traffic 0 — each one is dead weight paid for on every turn

10. Failure modes

Symptom Cause Fix
Right intent, wrong tool Two descriptions overlap Add "do not use for X, use Y" to both, and re-measure
Repeated argument validation errors The schema needs a value the model has no way to know Add a discovery tool, or accept a looser type and resolve it internally
Context blows up after one call Unbounded response Budget the result, paginate, return ids instead of blobs
The model repeats a mutation The response did not confirm the effect Return the resulting state, not "ok"
A good tool is never chosen The description uses internal jargon Rewrite it in the vocabulary users actually type
The agent thrashes between two tools Neither returns enough to decide Merge them into one task-shaped tool
Correct call, wrong interpretation Ambiguous units or timezone Put units in the field description and in the response
Invented arguments, silently ignored additionalProperties not set to false Set it, and let the validation error reach the model
Accuracy fell after adding one tool Count crossed the selection cliff Split into sub-agents with disjoint toolsets
Retry duplicated a side effect Handler is not idempotent Take an idempotency key, or make the write conditional

11. Definition of done

  • Every tool maps to a user task, not to an API endpoint.
  • Every description states what it does, when to use it, when not to, and any precondition.
  • Every confusable pair names the other tool explicitly, in both descriptions.
  • Every closed-set field is an enum; no free strings where the set is known.
  • Every schema sets additionalProperties: false and declares required fields.
  • Every field description gives format, units and where the value comes from.
  • Schemas are generated from the handler's own types, not maintained separately.
  • Every response has a size budget and states explicitly what was elided.
  • Every mutation returns the resulting observable state.
  • Every error tells the model whether to retry and what to change; no stack traces reach it.
  • Identifiers in results are human-readable and stable.
  • Tool names are unique across every connected server.
  • A labelled set of at least fifty requests measures selection accuracy, and runs in CI.
