LLM Tool Registry and Dispatcher

An LLM tool registry and dispatcher: declaring tools, validating arguments, result budgets, errors the model can act on and confirmation rules.

medium2–3 daysVerified 2026-08-19
Agents
Read it on GitHub ↗ Back to the catalogue

Managing twenty tools rather than writing one: a registry whose schemas cannot drift from the functions they describe, a dispatcher that validates what the model invented before calling anything, and a rule for which tools may run at the same time.

Complexity: medium · Typical build: 2–3 days · Verified: 2026-08-19 (re-check after ~90 days)

Examples in: Python. The architecture is language-agnostic: sections 5, 10 and 11 hold wherever you build this. Section 4 is illustrative — if your project is in another language, your agent translates the idioms rather than importing them, and nothing is lost. The equivalents are Zod schemas with a discriminated union dispatch in TypeScript, struct tags plus reflection in Go, and behaviour modules in Elixir.

Use when: an agent has more than a handful of tools, they are added by more than one person, and the failures are now operational rather than descriptive — a schema that no longer matches its function, an argument that reached the code unchecked, one slow tool holding up the turn.

Not for: designing an individual tool. What it should be called, how its description should read, what its arguments should be named and what shape its result should take are a different problem with a different answer, and doing it well matters more than anything here. Also not for a single-tool agent: a registry for one entry is indirection with no payoff.

⚙️ INSTRUCTIONS FOR THE AI — READ BEFORE WRITING ANY CODE

Do not start coding.

Step 1 — Refresh. Verify how the model provider represents tool calls in a response, and specifically whether it can return several in one turn — that decides whether the dispatcher needs concurrency at all, and providers differ. Verify the format for returning a tool result and a tool error, including how a result is correlated back to the call that produced it. Verify whether the SDK validates arguments against the declared schema before handing them to you, or whether that is entirely your responsibility — assume the latter until proven otherwise. Report what you verified and what turned out wrong.

Step 2 — Read the project, then audit what already exists. List every tool the agent currently exposes and, for each, record three things: where its schema comes from, whether it has a timeout, and whether running it twice is harmful. That last column is the one this blueprint needs and the one nobody has written down. Find whether any tool result is unbounded in size. Find whether tool schemas are hand-written next to the function or generated from it. Then audit §11 item by item, each marked already true, partly true or absent, with the file that decides it, reported before anything is proposed.

Assume the project is right until it demonstrably is not; code satisfying an item stays even where its shape differs from §4; replacing something that works needs a one-line reason; never delete a working path to make room for the blueprint's version. The same holds for language — §4 is illustrative, its idioms get translated into the project's language, and §11 is what has to become true rather than the syntax.

Step 3 — Write a plan for the gap only, and get it approved, including a ## Proposed stack section and the tool table from Step 2 with the parallel-safety column filled in. Do not ask open framework questions — propose, and ask for confirmation once. Say what you are adding, what you are leaving alone, and what you propose to change, and touch nothing else.

Step 4 — Build in the order in §7. Step 5 — §11 is the definition of done.

1. What breaks at the twentieth tool

One tool is a function with a description. Twenty is an operational system, and four things fail that did not exist at one.

Tools added one at a time A registry with a dispatcher
The schema is hand-written beside the function and drifts the first time a parameter is renamed The schema is derived from the signature, so drift is impossible rather than unlikely
Arguments the model invented go straight into the function Arguments are validated against the schema first, and a failure is returned as something the model can act on
One slow tool holds the whole turn Each tool has its own deadline
Every call site re-implements dispatch, and they diverge One dispatcher, one place where correlation, errors and limits are enforced

The first row is the quiet one. A hand-written schema is a second description of the same function, and the compiler checks neither against the other. Rename a parameter and the model keeps sending the old name — which arrives as an unknown keyword, or worse, is silently accepted by a permissive signature. Generate the schema from the function and this class of bug stops existing.

The second row is the one that costs money or data. A model producing an argument is producing text that resembles the type you asked for; it is not bound by it. An order_id may arrive as "42", as 42, as "ORD-42" or as a plausible-looking value for an order that does not exist. Validating at the boundary between the model and your code is the same discipline as validating a request body, for the same reason and with more urgency: the caller here is not merely untrusted, it is generative.

And there is a failure with no single-tool equivalent at all. When a provider returns several tool calls in one turn and the dispatcher runs them concurrently, tools that were correct in sequence can produce wrong answers together — one reading state another has not written yet, or two updating the same row. Nothing crashes; the agent proceeds confidently on a bad result. Sequential execution was hiding the coupling, not removing it.

The rule the diagram encodes: nothing reaches a handler without passing through validation and classification. They are two gates on one path, not helpers a call site may choose to use. A second entry point into the handlers is how a tool ends up being called with arguments nobody checked.

One rule: a tool exists only by being registered. No handler is importable and callable as a plain function from elsewhere in the agent path. If it is, someone will call it directly, and every guarantee in dispatch.py becomes optional.

4. Reference implementation

# app/tools/registry.py
import inspect
from dataclasses import dataclass
from pydantic import create_model


@dataclass(frozen=True)
class Tool:
    name: str
    description: str
    args_model: type          # derived, never hand-written
    fn: callable
    timeout: float
    max_result_chars: int
    # Three independent properties, and a tool needs all three to be safe to run
    # beside another. Collapsing them into one "safe" flag loses the reason, and
    # the reason is what someone needs when adding the twenty-first tool.
    atomic: bool              # one operation, no observable intermediate state
    idempotent: bool          # running it twice leaves the same world
    independent: bool         # touches no state another tool touches
    # Set this when the tool's effect cannot be undone by the agent itself within
    # the same run. That is the whole test, and it is decidable per tool without
    # knowing anything about how approval is presented: reading a record, running a
    # query, calling a read-only API - false. Sending a message, moving money,
    # deleting, writing to a system someone else observes, or anything a human would
    # have to unwind by hand - true. Reversibility is a property of the tool, so it
    # belongs beside the tool; how an approval is requested, held or expired is a
    # separate design and does not change which tools carry this flag.
    requires_confirmation: bool = False


_REGISTRY: dict[str, Tool] = {}


def tool(*, timeout=10.0, max_result_chars=8000,
         atomic=False, idempotent=False, independent=False,
         requires_confirmation=False):
    def decorator(fn):
        sig = inspect.signature(fn)
        # The schema is built from the signature and its annotations. A hand-written
        # copy is a second description of the same function that nothing checks
        # against the first — rename a parameter and the model keeps sending the old
        # name for as long as nobody notices.
        fields = {
            name: (p.annotation,
                   ... if p.default is inspect.Parameter.empty else p.default)
            for name, p in sig.parameters.items()
        }
        args_model = create_model(f"{fn.__name__}_args", **fields)

        if fn.__doc__ is None:
            # The description is what the model selects on. An undescribed tool is
            # one it will use wrongly, and failing here is cheaper than debugging that.
            raise ValueError(f"{fn.__name__}: a tool needs a docstring")

        _REGISTRY[fn.__name__] = Tool(
            name=fn.__name__, description=inspect.getdoc(fn), args_model=args_model,
            fn=fn, timeout=timeout, max_result_chars=max_result_chars,
            atomic=atomic, idempotent=idempotent, independent=independent,
            requires_confirmation=requires_confirmation)
        return fn
    return decorator


def declarations() -> list[dict]:
    """What the model is told exists. Generated, so it cannot disagree with the code."""
    return [{"name": t.name, "description": t.description,
             "input_schema": t.args_model.model_json_schema()}
            for t in _REGISTRY.values()]

# app/tools/dispatch.py
import asyncio
from pydantic import ValidationError


def parallel_safe(tool: Tool) -> bool:
    # All three, not any. A tool that is idempotent but shares state still races;
    # one that is independent but not atomic can be observed half-done. Sequential
    # execution was hiding this coupling — enabling concurrency reveals it, and it
    # reveals it as wrong answers rather than as crashes.
    return tool.atomic and tool.idempotent and tool.independent


async def dispatch(calls: list[ToolCall], context) -> list[ToolResult]:
    safe = [c for c in calls if _lookup(c) and parallel_safe(_lookup(c))]
    rest = [c for c in calls if c not in safe]

    results = list(await asyncio.gather(*(run_one(c, context) for c in safe)))
    for call in rest:                     # in the order the model asked for them
        results.append(await run_one(call, context))
    return results


async def run_one(call: ToolCall, context) -> ToolResult:
    tool = _REGISTRY.get(call.name)
    if tool is None:
        # A hallucinated tool name. Naming what does exist turns a dead end into a
        # correctable one — the model retries with a real tool instead of repeating.
        return ToolResult(call.id, is_error=True,
                          content=f"No tool named {call.name!r}. Available: "
                                  f"{', '.join(sorted(_REGISTRY))}")

    try:
        args = tool.args_model.model_validate(call.arguments)
    except ValidationError as exc:
        # Returned to the model, not raised. The model produced these arguments and
        # it is the only thing that can fix them; an exception here ends the turn
        # instead of correcting it. The message says which field and why.
        return ToolResult(call.id, is_error=True,
                          content=f"Invalid arguments: {_fields(exc)}")

    if tool.requires_confirmation and not context.confirmed(call.id):
        return ToolResult(call.id, is_error=True,
                          content="This action needs confirmation before it runs.")

    try:
        async with asyncio.timeout(tool.timeout):
            output = await tool.fn(**args.model_dump())
    except TimeoutError:
        # Also recoverable: the model may narrow the query and try again. Without a
        # per-tool deadline, one slow integration holds the whole turn, and with a
        # single global deadline a fast tool inherits a slow tool's budget.
        return ToolResult(call.id, is_error=True,
                          content=f"{tool.name} timed out after {tool.timeout}s. "
                                  f"Try a narrower request.")
    except Exception:
        # The internal error never goes to the model: it carries connection strings,
        # file paths and internal identifiers straight into the context — and the
        # context is often shown to the user.
        log.exception("tool failed", extra={"tool": tool.name})
        return ToolResult(call.id, is_error=True,
                          content=f"{tool.name} failed. The error has been logged.")

    text = serialise(output)
    if len(text) > tool.max_result_chars:
        # An unbounded result is a context-window failure with a delay on it: the
        # turn succeeds, and three turns later the conversation is truncated from
        # the front and the agent has forgotten its instructions.
        text = text[:tool.max_result_chars] + (
            f"\n\n[truncated at {tool.max_result_chars} characters; "
            f"narrow the request to see more]")
    return ToolResult(call.id, content=text)

5. Golden-standard rules

Rule Why
Forbidden: a hand-written schema beside the function it describes Two descriptions of one function that nothing checks against each other. The first rename breaks it silently.
Forbidden: calling a handler with unvalidated arguments The model generates text shaped like your types, not values bound by them. This boundary is the same as an HTTP one, with a more inventive caller.
Forbidden: raising out of the dispatcher for a recoverable failure Bad arguments, a missing tool and a timeout are all things the model can correct. Raising ends the turn instead.
Forbidden: an internal exception message reaching the model It carries connection strings, paths and identifiers into the context, and the context is often shown to the user.
Forbidden: running tools concurrently without the three-part check Atomic, idempotent and independent. Sequential order was hiding the coupling, and concurrency reveals it as confident wrong answers.
Forbidden: an unbounded tool result It is a context-window failure with a delay: the turn succeeds, and later the conversation is truncated from the front.
Forbidden: a handler reachable except through the dispatcher One direct call and every guarantee here becomes optional.
A tool needs confirmation when the agent cannot undo it in the same run It is a property of the tool, decidable where the tool is declared. Deferring the decision to whoever wires up approvals means it is made by someone who cannot see what the tool does.
Every tool has its own deadline A single global budget lets one slow integration spend a fast tool's time.
Every result is correlated by call id With several calls in one turn, position is not identity, and a mismatched result is a wrong answer the model cannot detect.
An unknown tool name is answered with the list of real ones It converts a dead end into a correctable one.
Parallel safety is three recorded properties, not one flag The reason is what the next person needs when adding a tool. A boolean loses it.
Every tool has a description, enforced at registration The description is what the model selects on; failing at start-up is cheaper than debugging a wrong choice.

6. Data contracts

ToolCall(id="toolu_01...", name="get_order", arguments={"order_id": "42"})
ToolResult(id="toolu_01...", content="...", is_error=False)

The id is the contract. A turn can contain several calls, results can be produced out of order, and the model matches them by identifier — so a dispatcher that returns results positionally is correct exactly until the first concurrent turn, and wrong silently after that.

is_error is the other half. An error returned as ordinary content is indistinguishable from a successful answer that happens to describe a failure, and the model treats it as data. Marked as an error, it is something to recover from.

7. Build order

  1. The registry with schemas derived from signatures, and a test that renaming a parameter changes the generated schema — proving drift is impossible.
  2. The dispatcher with validation, and a test feeding deliberately wrong arguments that asserts a correctable error is returned rather than raised.
  3. Per-tool timeouts, with a test on a deliberately slow tool.
  4. Correlation by id, with a test that returns results out of order.
  5. The three-part parallel classification, and a concurrency test that runs two tools sharing state and asserts they were not run together.
  6. Result size limits, with a test on a tool returning far too much.
  7. The confirmation flag, with a test that a marked tool does not execute without one.

Step 5 needs a test that deliberately races. Classified by reading rather than by testing, the parallel decision is an opinion, and it is wrong in exactly the cases that matter.

10. Failure modes

Symptom Cause Fix
The model keeps sending an argument name that no longer exists The schema is hand-written and was not updated with the signature Derive the schema from the function
A tool receives a value of the wrong type and fails deep inside Arguments were not validated at the boundary Validate against the derived schema before calling
A turn ends with a stack trace instead of the agent recovering The dispatcher raised for something the model could have fixed Return validation, timeout and unknown-tool failures as error results
A connection string appears in the conversation An internal exception message was returned as tool content Log the exception; return a fixed message
One integration being slow makes every turn slow One global deadline instead of per-tool ones A deadline per tool, recorded in the registry
The agent acts on the result of the wrong tool Results were matched positionally rather than by id Correlate by call id
With concurrency enabled, answers become subtly wrong Tools that were coupled ran together; sequential order had been hiding it Classify by atomic, idempotent and independent; run only tools passing all three together
Two tools update the same record and one update disappears Shared state mutated concurrently The same classification — independent is false for both
The agent forgets its instructions after a few tool calls An unbounded result filled the context and the history was truncated from the front Cap results and say they were capped
The model repeats a call to a tool that does not exist The error did not say what does exist List the available tools in the error
A destructive action ran without approval The handler was reachable outside the dispatcher Make registration the only path

11. Definition of done

  • Every tool schema is generated from its function signature; a test renames a parameter and asserts the generated schema changed
  • No handler is called anywhere except through the dispatcher, checked by grep in CI
  • Arguments of the wrong type or with unknown fields produce a returned error naming the field, covered by a test
  • An unknown tool name returns an error listing the real tools, covered by a test
  • Every tool has a deadline, and exceeding it returns a recoverable error rather than raising — covered by a test
  • No internal exception text reaches the model, covered by a test that fails a tool with a recognisable secret and asserts its absence
  • Results are correlated by call id, covered by a test that completes them out of order
  • Each tool records atomic, idempotent and independent, and a test asserts none is left at its default
  • Two tools sharing state are never executed concurrently, covered by a test that would detect the race
  • A result over its limit is truncated and says so, covered by a test
  • Every tool records whether the agent can undo it in the same run, and a test asserts none is left at its default
  • A tool marked as requiring confirmation does not execute without one, covered by a test
  • Registering a tool without a description fails at start-up, covered by a test
