LangChain LCEL: Composable Chains

LangChain LCEL chains: composing prompt, model and parser into one object that streams, batches and falls back, behind a replaceable boundary.

medium2–3 daysVerified 2026-08-19
LangChain
Read it on GitHub ↗ Back to the catalogue

Prompt, model and parser composed into one reusable object that streams, batches and falls back without any of it being written twice — and a boundary that keeps the framework out of the rest of the application.

Complexity: medium · Typical build: 2–3 days · Verified: 2026-08-19 (re-check after ~90 days)

Examples in: Python, with LangChain. The architecture is language-agnostic: sections 5, 10 and 11 hold wherever you build this. Section 4 is illustrative — if your project is in another language, your agent translates the idioms rather than importing them, and nothing is lost. The composition idea exists as the Vercel AI SDK's pipeline helpers in TypeScript and as plain function composition anywhere; what matters is the boundary in §3, which applies to any framework you adopt.

Use when: several places need the same prompt-to-parsed-output path, and you want streaming, batching and fallbacks once rather than per call site.

Not for: a single model call in a single place. Wrapping one call in a framework buys an abstraction with no second user and a dependency with its own release schedule. Also not for an agent that decides its own next step — that is a loop with tools, and a linear chain is the wrong shape for it however many branches you add.

⚙️ INSTRUCTIONS FOR THE AI — READ BEFORE WRITING ANY CODE

Do not start coding.

Step 1 — Refresh. Verify the installed LangChain major and what moved out of it. The 1.0 release kept the pipe composition and the runnable interface in the core package but relocated a large amount of older surface — including the legacy sequential chain helpers and the classic agent executor — into a separate compatibility package. Most examples you will find predate that split, so confirm before importing: an example that runs is not evidence it is current. Verify the current names for structured output, fallbacks and batching, and whether the agent-building entry point has changed. Report what you verified and what turned out wrong.

Step 2 — Read the project, then audit what already exists. Find every model call and record whether it streams, whether it retries, and where its prompt text lives. Find whether framework types already cross into business logic — a service function taking a message object, a repository returning a document type — because each one is a place the next major version will reach. Find how prompts are versioned today, if at all. Then audit §11 item by item, each marked already true, partly true or absent, with the file that decides it, reported before anything is proposed.

Assume the project is right until it demonstrably is not; code satisfying an item stays even where its shape differs from §4; replacing something that works needs a one-line reason; never delete a working path to make room for the blueprint's version. The same holds for language — §4 is illustrative, its idioms get translated into the project's language, and §11 is what has to become true rather than the syntax.

Step 3 — Write a plan for the gap only, and get it approved, including a ## Proposed stack section and the boundary: which module is allowed to import the framework. Do not ask open framework questions — propose, and ask for confirmation once. Say what you are adding, what you are leaving alone, and what you propose to change, and touch nothing else.

Step 4 — Build in the order in §7. Step 5 — §11 is the definition of done.

1. What composition buys, and what it costs

The hand-written version formats a prompt, calls the client, and parses the reply. It is obvious, and it is fine until the second caller.

A call written per site A composed chain
Streaming is added where someone needed it, and the other three sites do not have it Streaming, batching and async come from the composition itself
A retry is a try block someone remembered; the next site forgot Fallback is part of the object, so every caller has it
Four prompt strings drift apart and nobody can diff them One template, one place, versionable
Parsing is json.loads plus hope The parser is part of the chain and its failure is a typed failure

That is the case for it. Here is the cost, which the framework's own documentation will not press on you: a framework of this size moves. Its last major release kept the composition primitives but relocated a great deal of older surface into a compatibility package, and most public examples predate that split. That is not an argument against using it. It is an argument for exactly one boundary — the framework's types stop at one module — so that the next major version is a day's work in one directory instead of a search across the codebase.

The clearest way to think about the chain is that it is a declared pipeline rather than an executed one. You build the object once; calling it one way runs it whole, another way streams it, another runs a hundred inputs concurrently. Nothing in the pipeline knows which, which is precisely why it can be reused — and why putting business logic inside it is a mistake: that logic then only exists in a form the framework can run.

3. Project structure

app/llm/
├── chains/
│   ├── summarise.py     one chain per task, each independently testable
│   └── classify.py
├── prompts/
│   └── summarise.v3.md  prompt text as a file, versioned in the name
├── models.py            provider configuration and the fallback order
└── adapters.py          the boundary: framework types in, plain types out

One rule: langchain is imported only under app/llm/. Enforce it with a lint rule or a grep in CI. This is the single decision that makes a major upgrade survivable, and it is worth more than anything else in this document — it is also the one that erodes fastest, because importing a message type "just here" is always the smaller change in the moment.

4. Reference implementation

# app/llm/models.py
from langchain_anthropic import ChatAnthropic
from langchain_openai import ChatOpenAI

primary = ChatAnthropic(model=settings.primary_model, timeout=30, max_retries=0)
# max_retries=0 on purpose: the framework's own retry and the fallback below would
# otherwise compound, so a provider outage costs several minutes of retries before
# the fallback is ever reached.

# A different provider, not a smaller model from the same one. A provider outage
# takes all of its models with it, so a same-vendor fallback fails together with
# what it was meant to rescue.
model = primary.with_fallbacks([ChatOpenAI(model=settings.fallback_model, timeout=30)])

# app/llm/chains/summarise.py
from pathlib import Path
from langchain_core.prompts import ChatPromptTemplate
from langchain_core.output_parsers import PydanticOutputParser
from pydantic import BaseModel, Field


class Summary(BaseModel):
    headline: str = Field(max_length=120)
    points: list[str] = Field(min_length=1, max_length=5)
    # Constraints in the type, not in the prompt. "Give me at most five points" is
    # a request; a validator is a guarantee, and the difference shows up on the
    # inputs nobody tested.


# The prompt is a file, and its version is in the filename. Inline prompt strings
# cannot be diffed usefully, cannot be reviewed by someone who does not read
# Python, and cannot be rolled back without a deploy.
TEMPLATE = ChatPromptTemplate.from_messages([
    ("system", Path("app/llm/prompts/summarise.v3.md").read_text()),
    ("human", "{document}"),
])

parser = PydanticOutputParser(pydantic_object=Summary)

# The composition. This object is declared, not executed: the same chain runs
# whole, streams, or processes a hundred inputs concurrently depending only on how
# it is called. That is the reason to build one — and the reason not to put
# business logic inside it, because logic in here exists only in a form the
# framework can run.
summarise_chain = TEMPLATE | model | parser

# app/llm/adapters.py
from app.llm.chains.summarise import summarise_chain, Summary


async def summarise(document: str) -> Summary:
    """The boundary. Framework types go in; a plain model comes out.

    Every caller in the application goes through a function like this. When the
    framework's next major release renames something, the change stops at this
    file rather than appearing in forty call sites.
    """
    return await summarise_chain.ainvoke({"document": document})


async def summarise_many(documents: list[str]) -> list[Summary]:
    # Batching comes from the composition, not from a loop. Concurrency is bounded
    # here rather than by whatever the provider's rate limiter decides — an
    # unbounded batch is a 429 storm that looks like a provider problem.
    return await summarise_chain.abatch(
        [{"document": d} for d in documents],
        config={"max_concurrency": 5},
    )


async def summarise_streaming(document: str):
    # The same chain. Nothing was written twice to get this.
    async for chunk in summarise_chain.astream({"document": document}):
        yield chunk

# tests/test_summarise.py
from langchain_core.language_models.fake_chat_models import FakeListChatModel


def test_chain_parses_a_valid_response():
    # The chain is composable, so the model is replaceable. Testing the prompt and
    # the parser without a network call is the main practical payoff of building
    # it this way, and it is why chains stay small.
    chain = TEMPLATE | FakeListChatModel(responses=[VALID_JSON]) | parser
    result = chain.invoke({"document": "..."})
    assert len(result.points) <= 5

5. Golden-standard rules

Rule Why
Forbidden: importing the framework outside its own module It is the one decision that makes a major upgrade a day in one directory instead of a search across the codebase. It also erodes fastest, so enforce it in CI.
Forbidden: business logic inside a chain Logic there exists only in a form the framework can run, and it cannot be tested or reused without it.
Forbidden: a fallback to another model from the same provider An outage takes the provider's models with it, so the rescue fails alongside what it was rescuing.
Forbidden: provider retries and framework fallbacks both enabled They compound: an outage costs minutes of retries before the fallback is reached.
Forbidden: prompt text inline in code It cannot be diffed, reviewed by a non-programmer, or rolled back without a deploy.
Constraints live in the output type, not in the prompt A prompt asks; a validator guarantees. The difference appears on inputs nobody tested.
The version is in the prompt's filename It is what lets an evaluation name which prompt it scored.
Batching declares a concurrency limit Unbounded batches produce a rate-limit storm that reads as a provider fault.
One chain per task, small enough to test with a fake model The ability to test the prompt and the parser without a network call is the main practical payoff.
Every chain is traced Composition hides the call sites; without tracing, a failure inside a pipe is a stack trace with no inputs.
Examples are checked against the installed version, not trusted A large amount of surface moved packages in the last major release, and most public examples predate it.
Timeouts are set explicitly on the model A default that is generous or absent turns one slow call into a held worker.

6. Data contracts

in    plain application types — a string, a dataclass, a domain object
out   a validated model with its constraints in the type

The contract is that neither side of the adapter sees the other's types. Callers never receive a framework message object; the chain never receives a database row. It costs a few lines of mapping and it is what makes the framework replaceable — which, given how much of its surface moved in one release, is not a theoretical benefit.

A chain is also a declared pipeline: the same object invoked, streamed or batched. If a chain only works one of those ways, something inside it is doing work that belongs outside.

7. Build order

  1. One chain, one task, tested against a fake model. No network. This proves the prompt and the parser before any provider is involved.
  2. The adapter, and the CI check that the framework is imported nowhere else — added now, while there is one import to keep honest.
  3. The real model with an explicit timeout, and a cross-provider fallback with a test that forces the primary to fail.
  4. Structured output with constraints in the type, and a test with a response that violates one.
  5. Streaming and batching from the same chain, with a concurrency limit.
  6. Tracing, with the prompt version recorded on every run.
  7. The second chain, which is where you find out whether the boundary held.

Step 2 early because the import boundary is the thing that decays. Enforced when there is one import, it stays; introduced after twenty, it is a refactor nobody schedules.

Metric Target

10. Failure modes

Symptom Cause Fix
A framework upgrade breaks code in dozens of files Framework types crossed into business logic The adapter boundary, enforced in CI
An example from the documentation does not import It predates the package split of the last major release Verify against the installed version; check the compatibility package
A provider outage takes minutes to fail over Provider retries and framework fallbacks compound Disable the provider's own retries when a fallback is configured
The fallback fails alongside the primary Both are models from the same provider Fall back across providers
A batch job triggers rate limits and looks like a provider fault Batching with no concurrency limit Set one explicitly
Output occasionally violates a documented constraint The constraint was in the prompt rather than the type Move it into the output model as a validator
Nobody can say which prompt produced a bad answer The prompt is inline and unversioned Prompt files with the version in the name, recorded in traces
A failure inside a chain gives a stack trace with no inputs The chain is not traced Attach tracing at the composition
A chain cannot be streamed although the model supports it Something inside collects the whole output — usually logic that belongs outside Move it out; keep chains to prompt, model, parser
Latency is fine per call and terrible in aggregate Calls are sequential where the chain could batch Use the batching path with a bound
A slow provider holds workers until something else times out No explicit timeout on the model Set one

11. Definition of done

  • The framework is imported only under the LLM directory, checked by grep in CI
  • No function outside that directory accepts or returns a framework type, verified by inspecting the adapter signatures
  • Every chain has a test that runs it against a fake model with no network access
  • Forcing the primary provider to fail produces an answer from a different provider, covered by a test
  • Provider-level retries are disabled where a fallback is configured, verified by reading the model configuration
  • Every model has an explicit timeout
  • Output constraints are expressed in the output type, and a response violating one is rejected — covered by a test
  • Prompt text lives in versioned files; no prompt string appears inline, checked by grep in CI
  • The prompt version appears in every trace, verified on a real run
  • The same chain object serves the invoke, stream and batch paths, covered by one test per path
  • Batch calls declare a concurrency limit
  • Composition adds under 10 ms compared with a direct provider call, measured once and recorded
