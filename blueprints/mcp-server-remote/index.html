MCP Server over HTTP

An MCP server over HTTP: authorization, multi-tenancy, rate limits, transport and deployment for agents outside your own organisation.

high1–2 weeksVerified 2026-08-19
MCPAgents
Read it on GitHub ↗ Back to the catalogue

A public MCP server: one POST endpoint, authorization built for clients you have never met, tenant data that cannot leak through a tool, and an audit trail of everything an agent did on someone's behalf.

Complexity: high · Typical build: 1–2 weeks · Verified: 2026-08-19 (re-check after ~90 days)

Examples in: Python. The architecture is language-agnostic: sections 5, 10 and 11 hold wherever you build this. Section 4 is illustrative — if your project is in another language, your agent translates the idioms rather than importing them, and nothing is lost. The protocol details below are from the specification revision named on the Verified line, and that revision changed the transport substantially — treat any example older than it as wrong until checked.

Use when: people outside your organisation should be able to point their agent at your service — a product with an API, an internal platform used by several teams, anything where the caller is not the person who deployed the server.

Not for: a server for your own machine. That runs on the standard streams as a subprocess with your own permissions, needs no authorization and no deployment, and takes an afternoon. Building this instead means paying for tenancy, tokens and operations to solve a problem you do not have.

⚙️ INSTRUCTIONS FOR THE AI — READ BEFORE WRITING ANY CODE

Do not start coding.

Step 1 — Refresh. Verify the protocol revision and read its transport section directly, because the current one removed a great deal that older examples still show. There are no protocol-level sessions and no session header, no initialize handshake — each request carries its protocol version and client capabilities in _meta — no GET stream endpoint, and no resumable streams. server/discover is now required. Server-initiated requests are gone: where the server needs input it returns a result asking for it and the client retries the original request. On authorization, verify the current client registration mechanism: Dynamic Client Registration is deprecated in favour of client identifiers that are HTTPS URLs resolving to a metadata document. Report what you verified and what turned out wrong.

Step 2 — Read the project, then audit what already exists. Establish the tenancy model first, because it constrains everything: what identifies a tenant, where that identity comes from in a token, and whether any existing query can return rows without it. List every tool you intend to expose and, for each, what it can read and what it can write — a public MCP server is an API whose caller is a language model, and a tool that writes is reachable by whatever that model was persuaded to do. Find whether an authorization server already exists or whether one is part of this work. Then audit §11 item by item, each marked already true, partly true or absent, with the file that decides it, reported before anything is proposed.

Assume the project is right until it demonstrably is not; code satisfying an item stays even where its shape differs from §4; replacing something that works needs a one-line reason; never delete a working path to make room for the blueprint's version. The same holds for language — §4 is illustrative, its idioms get translated into the project's language, and §11 is what has to become true rather than the syntax.

Step 3 — Write a plan for the gap only, and get it approved, including a ## Proposed stack section, the tenancy design, the scope per tool, and what happens when a tool is called with a token that is valid but not entitled. Do not ask open framework questions — propose, and ask for confirmation once. Say what you are adding, what you are leaving alone, and what you propose to change, and touch nothing else.

Step 4 — Build in the order in §7. Step 5 — §11 is the definition of done.

1. Two things this is, that a local server is not

The protocol is the same. Everything around it is different, and two differences account for most of the work.

A local server A public one
Runs as the user; permissions are inherited Runs as itself; every request must prove who it is for
One user, no isolation to get wrong Every query is scoped to a tenant, and a missed scope is a disclosure
A client you configured Clients you have never met, registering without you
Nothing to audit — the user watched An agent acted on someone's behalf, and someone will ask what it did

The third row is the one with a recent answer. A public server cannot pre-register every client, and the old solution — clients registering themselves dynamically — is deprecated in the current revision. The replacement is that a client's identifier is an HTTPS URL, and that URL serves a small JSON document describing the client. Your authorization server fetches it, checks that the document's own identifier matches the URL it came from, and validates the redirect against the list inside. The practical consequences are worth stating: there is no registration endpoint to protect, the client identity is portable across authorization servers because it is self-hosted, and the trust decision becomes one about the domain hosting that document.

The second row is where the real damage lives. A tool is a function called by a language model on behalf of a caller, and the model can be persuaded — by a document it read, a page it fetched, a ticket it summarised. Tenancy therefore cannot be a parameter the model supplies. It comes from the token, it is applied below the tool, and no tool signature accepts it. Anything else is one convincing sentence away from being another customer's data.

The rule the diagram encodes: the tenant arrow comes from the token and enters below the tools. There is no path from the request body to tenancy. A tool that could receive a tenant as an argument is a tool a persuaded model can point anywhere.

3. Project structure

app/mcp/
├── endpoint.py     the single POST route: origin, headers, token, dispatch
├── auth.py         token validation, scopes, and the tenant claim
├── tenancy.py      the scoped session — the only way tools reach data
├── tools/
│   └── orders.py   handlers; none takes a tenant argument
├── limits.py       per-tenant quotas
└── audit.py        one record per call, written before the result is returned

One rule: tools receive a scoped data accessor, never a raw one. The scoping happens once, from the token, above every handler. A handler that can construct its own query is a handler that can construct an unscoped one, and that mistake is invisible in review because the code looks ordinary.

4. Reference implementation

# app/mcp/endpoint.py
PROTOCOL_VERSION = "2026-07-28"


@router.post("/mcp")
async def mcp_endpoint(request: Request):
    # One endpoint, POST only. The current revision removed the GET stream and
    # protocol-level sessions; an older client sending GET or DELETE gets 405,
    # and a session header is ignored rather than echoed.
    if (origin := request.headers.get("origin")) and not allowed_origin(origin):
        # Required by the spec, and it is what stops a page in someone's browser
        # from driving this server through their session.
        return JSONResponse({"jsonrpc": "2.0", "error": {"code": -32600,
                             "message": "Origin not allowed"}}, status_code=403)

    body = await request.json()
    meta = body.get("params", {}).get("_meta", {})

    # Headers mirror body fields so gateways can route without parsing JSON. If
    # they disagree, reject: otherwise a load balancer routes on one value while
    # this server executes on another, and the two decisions diverge.
    if request.headers.get("MCP-Protocol-Version") != meta.get(
            "io.modelcontextprotocol/protocolVersion"):
        return _error(body, -32020, "Header mismatch: protocol version", 400)
    if request.headers.get("Mcp-Method") != body.get("method"):
        return _error(body, -32020, "Header mismatch: method", 400)

    if meta.get("io.modelcontextprotocol/protocolVersion") != PROTOCOL_VERSION:
        # Name what is supported. A client that guesses wrong can correct itself;
        # one told only "no" cannot.
        return _error(body, -32022, f"Supported versions: {PROTOCOL_VERSION}", 400)

    principal = await authenticate(request)          # 401 with WWW-Authenticate if absent
    return await dispatch(body, principal)

# app/mcp/auth.py
async def authenticate(request: Request) -> Principal:
    token = _bearer(request)
    claims = jwt.decode(
        token, key=jwks_for(settings.issuer),
        # The allowlist, not the token's own header. Without it the token chooses
        # how it is verified, which is the whole family of algorithm-confusion
        # attacks in one missing argument.
        algorithms=["RS256"],
        audience=settings.resource_identifier,       # this server, specifically
        issuer=settings.issuer,
    )
    return Principal(
        subject=claims["sub"],
        # The tenant comes from here and from nowhere else. Not from an argument,
        # not from a header the client controls. A model that has read an
        # attacker's document must not be able to reach another tenant by asking.
        tenant_id=claims["tenant_id"],
        scopes=set(claims.get("scope", "").split()),
    )


def require_scope(scope: str, principal: Principal) -> None:
    if scope not in principal.scopes:
        # 403, not 401: the token is valid and refreshing it changes nothing.
        # Collapsing the two makes well-behaved clients refresh in a loop.
        raise Forbidden(f"This action requires the {scope} scope.")

# app/mcp/tenancy.py
@asynccontextmanager
async def scoped(principal: Principal):
    """The only way a tool reaches data.

    Scoping is applied once, above every handler, so no handler can be written
    without it. Passing a raw session down and trusting each tool to filter is
    the arrangement where one missed filter is a disclosure — and it looks like
    ordinary code in review.
    """
    async with session_factory() as session:
        await session.execute(text("SET LOCAL app.tenant_id = :t"),
                              {"t": principal.tenant_id})
        yield TenantScopedSession(session, principal.tenant_id)

# app/mcp/tools/orders.py
@tool(scope="orders:read", max_result_chars=8000)
async def search_orders(db: TenantScopedSession, query: str, limit: int = 20) -> str:
    """Search this account's orders by reference, customer name or product.

    Returns the reference, status, total and date. Use get_order for the full
    contents of one order.
    """
    # No tenant parameter, and none possible: `db` is already scoped. The
    # signature is the guarantee — a reviewer can see that this tool cannot be
    # pointed somewhere else, without reading the body.
    rows = await db.search_orders(query=query, limit=min(limit, 50))
    return render(rows)

# app/mcp/audit.py
async def record(principal: Principal, method: str, name: str,
                 arguments: dict, outcome: str) -> None:
    """One record per call, written whatever the outcome.

    An agent acted on someone's behalf and somebody will eventually ask what it
    did — after an incident, during an audit, or because a customer wants to
    know. Recording only successes leaves out exactly the calls that get asked
    about. Arguments are redacted by field, not by hoping they are harmless.
    """
    await audit_store.write(AuditRecord(
        at=utcnow(), tenant_id=principal.tenant_id, subject=principal.subject,
        client_id=principal.client_id, method=method, tool=name,
        arguments=redact(arguments), outcome=outcome))

5. Golden-standard rules

Rule Why
Forbidden: a tenant identifier that can arrive in a tool's arguments A model can be persuaded by anything it reads. Tenancy comes from the token and enters below the tools.
Forbidden: a tool holding an unscoped data accessor One missed filter is a disclosure, and it looks like ordinary code. Scope once, above the handlers.
Forbidden: verifying a token without an explicit algorithm allowlist Otherwise the token chooses how it is verified — the whole family of algorithm-confusion attacks in one missing argument.
Forbidden: skipping the origin check It is required, and it is what stops a page in a victim's browser from driving this server through their session.
Forbidden: accepting a request whose headers disagree with its body A gateway may route on the header while the server executes on the body, and the two decisions then diverge.
Forbidden: building on protocol-level sessions or a GET stream Both were removed. An older client sending them gets 405, and a session header is ignored rather than echoed.
Client registration uses the current mechanism, not the deprecated one Self-registration is deprecated; identifiers that resolve to a hosted metadata document replace it, and the trust decision moves to the domain.
Scopes are per tool, and 403 is distinct from 401 401 says get a new token; 403 says this one will never do. Collapsing them makes clients refresh forever.
Every call is audited, including failures Recording only successes omits exactly the calls that get asked about later.
Limits are per tenant, not per address One customer's agent in a loop must not consume another's capacity, and both may share an address.
Every result is bounded by the server It is the caller's context, but the size is your decision, and an unbounded result is a denial of service you shipped.
Tool schemas are versioned, and removal is announced Clients are configured by people you cannot contact; a silent removal breaks agents you will never hear about.

6. Data contracts

POST /mcp
Accept: application/json, text/event-stream
Authorization: Bearer <token>
MCP-Protocol-Version: 2026-07-28
Mcp-Method: tools/call
Mcp-Name: search_orders

One endpoint, POST only, headers mirroring the body and validated against it. The server answers with either a single JSON object or an SSE stream, chosen per request — clients must accept both, which is why the Accept header lists both.

Three protocol properties change how the server is written:

no sessions      each request stands alone; nothing is remembered between them,
                 so cross-call state is an explicit handle you mint and they pass
no resumption    a broken stream cancels its request; there is nothing to resume
no server calls  where the server needs input it returns a result asking for it,
                 and the client retries the original request carrying the answer

Closing a stream is the cancellation signal. There is no message to wait for, so a handler that ignores disconnection keeps working — and keeps billing — for a request nobody will read.

7. Build order

  1. The endpoint answering server/discover and tools/list, unauthenticated, with the header validation in place. Prove the transport against a real client before adding anything.
  2. Token validation with the algorithm allowlist and audience check, and the attack tests: a token with the algorithm switched, and one minted for a different audience. Both must fail before anything depends on this.
  3. Tenancy, with the scoped accessor and a test that two tenants' data never crosses. Written before the second tool exists.
  4. One tool, with a scope, and tests for 401, 403 and success.
  5. Result budgets and per-tenant limits.
  6. The audit log, covering success, failure and rejection.
  7. Client registration and a real third-party client, which is where the assumptions from step 2 are tested by someone else's implementation.

Step 3 before the second tool because tenancy is structural. Retrofitting it means auditing every handler written in the meantime, and the failure it prevents is the one that ends up in a disclosure notice.

10. Failure modes

Symptom Cause Fix
One customer's data appears in another's agent A tenant identifier was accepted as an argument, or a query ran unscoped Tenancy from the token, below the tools; a scoped accessor with no raw alternative
A forged token is accepted Verification used the token's own algorithm header Pass an explicit algorithm allowlist
A token issued for another service works here The audience was not validated Validate audience and issuer explicitly
A user's browser session was used to drive the server No origin check Validate the origin; reject with 403
A gateway routed one way and the server acted another Headers and body disagreed and were not compared Reject mismatches with the header-mismatch error
A well-behaved client refreshes tokens in a loop An authorization failure returned 401 instead of 403 Distinguish them
An older client cannot connect at all It expects sessions, a GET stream or the handshake, all removed Answer 405 to GET and DELETE, ignore session headers, and state the supported version in the error
A client waits forever after a dropped stream It expected to resume; resumability was removed Streams are not resumable; the request is cancelled
A handler keeps running and billing after the caller left Stream closure is the cancellation signal and was ignored Treat disconnection as cancellation and stop
Nobody can answer what an agent did during an incident Only successes were audited Audit every call and its outcome
One customer's runaway agent degrades everyone Limits are per address rather than per tenant Quota per tenant
Clients broke overnight after a tool was renamed The change was silent and the clients are configured by people you cannot reach Version schemas; announce removals; keep the old name working through a window

11. Definition of done

  • No tool signature accepts a tenant identifier, checked by inspecting every handler in a test
  • Tools cannot obtain an unscoped data accessor, checked by grep in CI
  • A test asserts one tenant's token never returns another tenant's rows, for every tool
  • A token with a switched algorithm and a token with the wrong audience are both rejected, each covered by a test
  • A request with an invalid origin is rejected with 403, covered by a test
  • A request whose headers disagree with its body is rejected with the header-mismatch error, covered by a test
  • Missing authentication returns 401 with the challenge header; a valid token lacking the scope returns 403 — both covered
  • GET and DELETE to the endpoint return 405, and a session header is ignored rather than echoed, covered by tests
  • Closing the response stream stops the work, covered by a test asserting the handler was cancelled
  • Every call produces an audit record with tenant, subject, client, tool and outcome — including rejected calls, covered by a test per path
  • Every tool result is bounded by the server, covered by a test with an oversized result
  • Rate limits are enforced per tenant, covered by a test with two tenants
  • A request for an unsupported protocol version is answered with the supported ones named, covered by a test
