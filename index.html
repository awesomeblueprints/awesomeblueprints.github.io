02 / What you can build

The things agents are asked for constantly. Each one has a blueprint.

AI agents

How to build an AI agent that stops, reports and can be resumed — rather than a loop with no iteration cap and no idea what it already did. Agent loops with step budgets, LangGraph state graphs with typed state and reducers, tool registries, and a pause where a person approves anything irreversible.

RAG and vector search

How to build a RAG pipeline that answers the second question as well as the first. Chunking and embeddings, pgvector in PostgreSQL, Qdrant with filters, ChromaDB for prototypes, and hybrid search with reciprocal rank fusion for the queries embeddings are blind to — identifiers, error codes, exact phrases.

MCP servers and clients

How to build an MCP server — over stdio for a developer's own machine, or over HTTP for agents outside your organisation, where authorization, tenancy and rate limits are the whole job. Plus the client side: connecting an agent to Model Context Protocol servers without one slow server stalling every run.

LLM plumbing

The parts that decide whether a feature survives contact with users: streaming model output over SSE and rendering it in the browser, structured output with JSON Schema, prompt-injection detection, LLM-as-a-judge evaluation, and tracing that can tell you which run produced the bad answer.

The backend underneath

An agent feature still runs on ordinary infrastructure, and this is where agents improvise most. FastAPI routers and versioning, Pydantic schemas and settings, PostgreSQL pooling, async SQLAlchemy, Alembic migrations, Redis caching and rate limits, WebSockets, Docker, GitHub Actions, JWT authentication and session revocation.

Skills

A skill is a different shape from a blueprint: instructions your agent loads when a task matches, rather than a document you hand it. The catalogue carries these alongside the blueprints and marks which is which.

## Architecture blueprints

This project carries architecture blueprints in `blueprints/`.

Before implementing any substantial feature, read
`blueprints/README.md`. It lists every blueprint available
here, with the situation each one is for and the situations
it must not be used for.

Never follow a blueprint silently — say which one you are
using, and why.
  1. 01Read it yourself first. Ten minutes tells you which architectural decisions the agent is about to make on your behalf.
  2. 02Give the file to your agent. Claude Code — drop it in the repo and reference it. Cursor / Windsurf — add to chat context or .cursor/rules/. ChatGPT, Gemini — paste as the first message.
  3. 03Let it do the steps. Verify current versions online, read project conventions, audit existing code against the checklist, propose a plan for approval. The audit is what stops it replacing code that already works.
  4. 04Build in the given order. §7 sequences by risk — whatever is most likely to be wrong is built and tested first.
  5. 05Check against §11. Every item is observable: run it, query it, or grep for it. If you cannot demonstrate an item, the feature is not done.
04 / Why

Ask an agent to “add RAGAS to my AI agent” and the result looks finished.

The metrics are wired up, the run is green, faithfulness reads 0.87. What that number is, though, is another model’s opinion — graded with no human label anywhere in the loop. Judges of this kind prefer longer answers, and published figures put roughly a quarter of pairwise verdicts flipping when the same two answers swap places. So the dashboard is confident, the score moves when you change a prompt, and nobody can say whether it moved because the answers got better. The framework is not the problem; an uncalibrated judge is. A blueprint is the missing half of that prompt: it tells the agent what correct looks like before it writes a line — here, that a judge is a measurement, and a measurement ships with its error: a hundred human-labelled cases, an agreement figure, and that figure printed beside every score.

05 / Questions

The things people ask before they try one.

How do I build an AI agent that doesn't invent its own architecture?

Give the agent the architecture before it starts, not corrections afterwards. A blueprint is one file stating what to build, in what order, and what it may not do: the components and how they talk, the rules that must not be broken, a build order sequenced by risk, and a checklist where every item is something you can run, query or grep for. The agent reads it, checks the current versions of whatever it is about to use, audits what your project already has, and proposes a plan before writing anything.

How do I build an MCP server?

It depends on who calls it, and the two answers share almost no code. A server on a developer's own machine runs as a subprocess over stdio with that developer's permissions — no authorization, no deployment, an afternoon of work. A server other people point their agents at needs authorization, tenant isolation, rate limits and somewhere to run. The catalogue has a blueprint for each, plus one for the client side.

How do I build a RAG pipeline that works in production?

Most of the answer is decided before retrieval runs. Chunk size, overlap and metadata set the ceiling on quality; re-ingestion has to update rather than duplicate; and embeddings alone are close to blind for identifiers, SKUs and error codes, which is what hybrid search fixes. Then choose a store: pgvector if the data is already in PostgreSQL, Qdrant if filtering dominates, ChromaDB if you need it working today.

Will an agent overwrite the code I already have?

No — every blueprint makes the agent audit the project first. It goes through the checklist item by item, marks each one already true, partly true or absent, names the file that decides it, and reports that before proposing anything. The rule it is given is explicit: never delete a working path to make room for the blueprint's version, and replacing something that works needs a reason from you. Blueprints are written for projects that already exist, not only for empty ones.

Does this work with Claude Code, Cursor and Copilot?

Yes, and with anything else that reads files. For Claude Code, put the folder in the repository and point CLAUDE.md at it. For Cursor or Windsurf, add the file to chat context or drop it in .cursor/rules/. For ChatGPT or Gemini, paste it as the first message. There is nothing to install and no runtime — a blueprint is a Markdown file.

Are the blueprints tied to Python?

The reference implementations are mostly Python, and the architecture is not. The rules, the failure modes and the definition of done hold in any language; the agent translates the idioms rather than importing them. Each blueprint says so at the top and names the equivalents where they exist.

What does it cost?

The published catalogue is free and MIT-licensed — clone it, copy one file, keep it in your repository. Nothing is time-limited and there is no account.

A blueprint is not a tutorial and not a framework. It is the half of the prompt you never write: what to build, in what order, and what the agent may not do. Written down once — so the same request builds the same system every time.
